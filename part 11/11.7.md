# فصل 88 - Authorization

## Authorization چیست؟

در فصل قبل با **Authentication** آشنا شدیم.

Authentication فقط پاسخ این سؤال را می‌دهد:

> آیا این کاربر واقعاً همان کسی است که ادعا می‌کند؟

اما سؤال مهم دیگری باقی می‌ماند.

فرض کنید دو کاربر وارد سیستم شده‌اند.

کاربر اول:

```text
Ali
Role: User
```

کاربر دوم:

```text
Sara
Role: Admin
```

هر دو Login کرده‌اند.

آیا هر دو باید بتوانند کاربران دیگر را حذف کنند؟

قطعاً خیر.

اینجاست که مفهوم **Authorization** مطرح می‌شود.

---

# Authorization چیست؟

Authorization به معنای:

> **تعیین سطح دسترسی کاربران**

است.

در این مرحله سیستم بررسی می‌کند:

> آیا این کاربر اجازه انجام این عملیات را دارد؟

---

# تفاوت Authentication و Authorization

Authentication:

```text
Who are you?
```

تو چه کسی هستی؟

---

Authorization:

```text
What are you allowed to do?
```

اجازه انجام چه کارهایی را داری؟

---

```text

↓

↓

↓

```

# نقش (Role)

Role مجموعه‌ای از Permissionها است.

مثلاً:

```text
Admin
```

می‌تواند:

* ایجاد کاربر
* حذف کاربر
* ویرایش کاربر
* مشاهده کاربران

را انجام دهد.

---

کاربر معمولی:

```text

```

تنها می‌تواند:

* مشاهده اطلاعات خود
* ویرایش پروفایل خود

را انجام دهد.

# کد وضعیت 403

اگر کاربر وارد شده باشد اما اجازه دسترسی نداشته باشد:

```text
403 Forbidden
```

ارسال می‌شود.

---

اگر کاربر اصلاً Login نکرده باشد:

```text
401 Unauthorized
```

برگردانده می‌شود.

```text

↓

```

---

# Authorization با Middleware

بهترین محل بررسی مجوزها:

```text

↓

↓

```

---

نمونه:

```javascript
function authorize(req, res, next) {

    if (req.user.role !== "admin") {

        return res.status(403).send("Forbidden");

    }

    next();

}
```

---

# Middleware عمومی

می‌توان Middleware را قابل استفاده مجدد نوشت.

```javascript
function authorize(role) {

    return (req, res, next) => {

        if (req.user.role !== role) {

            return res.status(403).send("Forbidden");

        }

        next();

    };

}
```

استفاده:

```javascript
app.delete(

    "/users",

    authorize("admin"),

    deleteUser

);
```

---

# چند Role

گاهی چند Role مجاز هستند.

```javascript
function authorize(...roles) {

    return (req, res, next) => {

        if (!roles.includes(req.user.role)) {

            return res.status(403).send("Forbidden");

        }

        next();

    };

}
```

استفاده:

```javascript
app.post(

    "/posts",

    authorize(

        "admin",

        "editor"

    ),

    createPost

);
```

---

# Permission-Based Authorization

در پروژه‌های بزرگ‌تر به‌جای Role از Permission استفاده می‌شود.

مثال:

```text
create:product

update:product

delete:product

read:product
```

---

بررسی:

```javascript
if (

    !user.permissions.includes(

        "delete:product"

    )

) {

    return res.status(403).send("Forbidden");

}
```

# مالکیت اطلاعات (Ownership)

گاهی کاربر فقط می‌تواند اطلاعات خودش را ویرایش کند.

مثلاً:

```text

```

اگر شناسه کاربر:

```text

```

باشد:

```javascript
if (

    req.user.id !== Number(req.params.id)

) {

    return res.status(403).send("Forbidden");

}
```

# اشتباهات رایج

### ۱- یکی دانستن Authentication و Authorization

ابتدا باید هویت کاربر تأیید شود و سپس سطح دسترسی او بررسی گردد.

---

### ۲- بررسی نکردن مجوزها

اشتباه:

```javascript
app.delete(

    "/users/:id",

    deleteUser

);
```

در این حالت هر کاربری می‌تواند عملیات حذف را انجام دهد.

---

### ۳- اعتماد به Role ارسال‌شده توسط کاربر

هرگز Role را از Body یا Query دریافت نکنید.

Role باید از اطلاعات معتبر مانند JWT یا پایگاه داده استخراج شود.

---

### ۴- استفاده از Roleهای نامشخص

بهتر است Roleها محدود و از قبل تعریف‌شده باشند.

مثلاً:

```text
admin

user

editor
```

---

### ۵- استفاده از 401 به جای 403

اگر کاربر وارد سیستم شده اما مجوز ندارد:

```text
403 Forbidden
```

باید ارسال شود.

---

### ۶- نادیده گرفتن Ownership

گاهی لازم است علاوه بر Role، مالک بودن منبع نیز بررسی شود.

---

# نکات حرفه‌ای

* همیشه Authentication را قبل از Authorization انجام دهید.
* مجوزها را در Middleware بررسی کنید.
* از Roleهای استاندارد استفاده کنید.
* برای پروژه‌های بزرگ از Permission-Based Access Control استفاده کنید.
* اصل حداقل دسترسی را رعایت کنید.
* Role و Permission را داخل پایگاه داده مدیریت کنید.
* اطلاعات حساس را فقط برای کاربران مجاز ارسال کنید.
* عملیات حساس مانند حذف اطلاعات را ثبت (Audit Log) کنید.

# پاسخ تشریحی

## پاسخ تمرین ۱

Authentication هویت کاربر را تأیید می‌کند، اما Authorization مشخص می‌کند کاربر پس از احراز هویت به چه عملیات یا منابعی دسترسی دارد.

---

## پاسخ تمرین ۲

```javascript
function authorize(req, res, next) {

    if (req.user.role !== "admin") {

        return res.status(403).send("Forbidden");

    }

    next();

}
```

---

## پاسخ تمرین ۳

```javascript
function authorize(...roles) {

    return (req, res, next) => {

        if (!roles.includes(req.user.role)) {

            return res.status(403).send("Forbidden");

        }

        next();

    };

}
```

---

## پاسخ تمرین ۴

```javascript
if (

    req.user.id !== Number(req.params.id)

) {

    return res.status(403).send("Forbidden");

}
```

---

## پاسخ تمرین ۵

* `401 Unauthorized` زمانی استفاده می‌شود که کاربر احراز هویت نشده یا Token معتبر ندارد.
* `403 Forbidden` زمانی استفاده می‌شود که کاربر احراز هویت شده، اما مجوز انجام عملیات موردنظر را ندارد.

# مینی‌پروژه

## سیستم مدیریت دسترسی کاربران (Authorization System)

### هدف

پیاده‌سازی یک سیستم Authorization برای REST API که با استفاده از Role و Permission، دسترسی کاربران را به منابع مختلف کنترل کند.

### امکانات

* تعریف Roleهای `admin`، `editor` و `user`
* Middleware بررسی Authentication
* Middleware بررسی Authorization
* محافظت از Routeهای مدیریتی
* بررسی مالکیت اطلاعات (Ownership)
* ارسال پاسخ‌های استاندارد `401` و `403`
* مدیریت مجوزهای مبتنی بر Role
* ثبت عملیات حساس در لاگ سیستم

### قابلیت‌های تکمیلی

* پیاده‌سازی Permission-Based Access Control (PBAC)
* مدیریت Roleها و Permissionها از طریق پنل مدیریت
* پشتیبانی از چندین Role برای هر کاربر
* ثبت Audit Log برای تمام عملیات مهم
* کش (Cache) کردن Permissionها برای افزایش کارایی
* آماده‌سازی پروژه برای پیاده‌سازی قابلیت‌های پیشرفته‌تر مانند **OAuth 2.0** و **OpenID Connect** در فصل‌های آینده
