# فصل 120 - Cache

## مقدمه

در فصل قبل درباره Performance Optimization صحبت کردیم و یاد گرفتیم که یکی از مهم‌ترین راه‌های بهبود Performance، پیدا کردن Bottleneck و کاهش هزینه عملیات سنگین است.

یکی از ابزارهای بسیار مهم برای این کار **Cache** است.

فرض کنید یک API داریم که اطلاعات محصولات را از Database دریافت می‌کند.

هر بار که کاربر درخواست زیر را ارسال می‌کند:

```text
GET /products
```

برنامه ممکن است:

```text
Request
   ↓
Node.js
   ↓
Database
   ↓
Query
   ↓
Result
   ↓
Response
```

را اجرا کند.

اگر هزار کاربر در مدت کوتاهی همین درخواست را ارسال کنند، ممکن است Database مجبور شود یک Query مشابه را هزار بار اجرا کند.

در حالی که شاید نتیجه این Query برای چند ثانیه یا چند دقیقه تغییر نکرده باشد.

در این شرایط می‌توان نتیجه را در Cache ذخیره کرد:

```text
Request
   ↓
Cache
   ├── Hit → Return Data
   │
   └── Miss
        ↓
     Database
        ↓
     Save to Cache
        ↓
     Return Data
```

در نتیجه درخواست‌های بعدی می‌توانند بدون مراجعه مجدد به Database پاسخ داده شوند.

Cache یکی از مهم‌ترین تکنیک‌ها برای افزایش Performance، کاهش فشار روی Database و کاهش Latency در سیستم‌های Backend است.

---

# 120.1 - Cache چیست؟

Cache یک محل نگهداری موقت داده‌هایی است که احتمال دارد دوباره مورد استفاده قرار بگیرند.

ایده اصلی بسیار ساده است:

> اگر یک داده را قبلاً محاسبه یا دریافت کرده‌ایم و احتمال دارد دوباره به آن نیاز داشته باشیم، می‌توانیم آن را برای مدتی ذخیره کنیم.

مثلاً:

```text
Database Query
       ↓
   Result
       ↓
     Cache
```

در درخواست بعدی:

```text
Request
   ↓
 Cache
   ↓
 Result
```

و دیگر لازم نیست Query دوباره اجرا شود.

---

# 120.2 - چرا از Cache استفاده می‌کنیم؟

مهم‌ترین دلایل استفاده از Cache:

* کاهش Response Time
* کاهش فشار روی Database
* کاهش تعداد درخواست به سرویس‌های خارجی
* کاهش هزینه پردازش
* افزایش Throughput
* افزایش Scalability
* کاهش Latency

فرض کنید یک Query:

```text
200ms
```

زمان ببرد.

اگر نتیجه از Cache در:

```text
5ms
```

قابل دریافت باشد، تفاوت بسیار زیادی ایجاد خواهد شد.

---

# 120.3 - Cache Hit چیست؟

وقتی داده مورد نیاز در Cache وجود داشته باشد، به آن:

```text
Cache Hit
```

می‌گوییم.

مثلاً:

```text
Request
   ↓
Cache
   ↓
Data Found
   ↓
Cache Hit
   ↓
Response
```

در این حالت نیازی به مراجعه به منبع اصلی داده نیست.

---

# 120.4 - Cache Miss چیست؟

اگر داده مورد نیاز در Cache وجود نداشته باشد:

```text
Cache Miss
```

رخ داده است.

مثلاً:

```text
Request
   ↓
Cache
   ↓
Data Not Found
   ↓
Cache Miss
   ↓
Database
```

بعد از دریافت نتیجه می‌توانیم آن را در Cache ذخیره کنیم:

```text
Database
   ↓
Result
   ↓
Cache
```

---

# 120.5 - Cache Hit Rate

یکی از Metricهای مهم:

```text
Cache Hit Rate
```

است.

فرمول ساده:

```text
Cache Hit Rate =
Cache Hits / Total Requests
```

مثلاً اگر:

```text
1000 Requests
900 Hits
100 Misses
```

داشته باشیم:

```text
Hit Rate = 90%
```

هرچه Hit Rate مناسب‌تر باشد، Cache احتمالاً تأثیر بیشتری روی Workload مورد نظر دارد.

اما Hit Rate بالا به‌تنهایی به معنی طراحی خوب Cache نیست.

---

# 120.6 - Cache در مقابل Database

Database معمولاً منبع اصلی و دائمی داده است.

Cache معمولاً:

* سریع‌تر است.
* موقتی است.
* ممکن است داده قدیمی داشته باشد.
* ظرفیت و عمر محدودتری دارد.

بنابراین نباید بدون طراحی مناسب Cache را جایگزین Database در نظر بگیریم.

ساختار معمول:

```text
Application
    ↓
  Cache
    ↓
Database
```

---

# 120.7 - انواع Cache

Cache را می‌توان از جنبه‌های مختلف دسته‌بندی کرد.

برخی انواع مهم:

* In-Memory Cache
* Distributed Cache
* Application Cache
* Database Cache
* HTTP Cache
* Browser Cache
* CDN Cache

در Backendهای Node.js، In-Memory Cache و Distributed Cache اهمیت زیادی دارند.

---

# 120.8 - In-Memory Cache چیست؟

در In-Memory Cache داده‌ها در Memory نگهداری می‌شوند.

مثلاً در ساده‌ترین حالت می‌توانیم از `Map` استفاده کنیم:

```js
const cache = new Map();

cache.set("user:1", {
  id: 1,
  name: "Ali",
});
```

دریافت:

```js
const user = cache.get("user:1");

console.log(user);
```

---

# 120.9 - ساده‌ترین Cache با Map

یک Cache بسیار ساده:

```js
const cache = new Map();

function setCache(key, value) {
  cache.set(key, value);
}

function getCache(key) {
  return cache.get(key);
}

setCache("name", "Ali");

console.log(getCache("name"));
```

خروجی:

```text
Ali
```

---

# 120.10 - مزیت In-Memory Cache

مزیت اصلی این نوع Cache سرعت بسیار بالا است.

داده در Memory قرار دارد و دسترسی به آن معمولاً بسیار سریع است.

مثلاً:

```text
Application Memory
      ↓
     Data
```

اما این روش محدودیت‌های مهمی نیز دارد.

---

# 120.11 - مشکل In-Memory Cache

فرض کنید برنامه Node.js را اجرا کرده‌ایم و Cache در:

```js
const cache = new Map();
```

قرار دارد.

اگر Server Restart شود:

```text
Application
    ↓
Restart
    ↓
Memory Cleared
    ↓
Cache Lost
```

بنابراین این نوع Cache دائمی نیست.

---

# 120.12 - مشکل Multiple Instances

فرض کنید برنامه ما فقط یک Instance داشته باشد:

```text
       Node.js
         ↓
       Cache
```

اما بعداً سیستم را Scale کنیم:

```text
             Load Balancer
             /           \
        Node.js A      Node.js B
           ↓              ↓
       Cache A          Cache B
```

حالا هر Instance Cache خودش را دارد.

ممکن است:

```text
Cache A ≠ Cache B
```

باشد.

این یکی از محدودیت‌های مهم Local In-Memory Cache است.

---

# 120.13 - Distributed Cache

برای سیستم‌هایی که چند Instance دارند، می‌توان از Distributed Cache استفاده کرد.

معماری:

```text
             Load Balancer
             /           \
        Node.js A      Node.js B
             \           /
              \         /
              Cache
```

هر Instance به Cache مشترک دسترسی دارد.

یکی از ابزارهای بسیار رایج برای این کار:

**Redis**

است که در فصل بعدی به‌صورت مستقل بررسی خواهد شد.

---

# 120.14 - Cache Key

هر داده‌ای که در Cache ذخیره می‌شود معمولاً یک:

```text
Key
```

دارد.

مثلاً:

```js
cache.set("user:1", user);
```

در اینجا:

```text
Key   = user:1
Value = user
```

است.

طراحی Key یکی از بخش‌های مهم سیستم Cache است.

---

# 120.15 - طراحی مناسب Cache Key

Key باید:

* واضح باشد.
* Unique باشد.
* قابل پیش‌بینی باشد.
* اطلاعات لازم برای تشخیص داده را داشته باشد.

مثلاً:

```text
user:1
user:2
product:100
product:200
```

برای Queryهای مختلف:

```text
products:page:1
products:page:2
```

---

# 120.16 - Cache Key برای Query

فرض کنید API زیر را داریم:

```text
GET /products?page=1&limit=20
```

Key مناسب:

```text
products:page:1:limit:20
```

است.

اگر:

```text
GET /products?page=2&limit=20
```

باشد:

```text
products:page:2:limit:20
```

است.

در نتیجه نتیجه هر Query با Query دیگر اشتباه نمی‌شود.

---

# 120.17 - TTL چیست؟

TTL مخفف:

```text
Time To Live
```

است.

یعنی داده Cache تا چه مدت معتبر باشد.

مثلاً:

```text
TTL = 60 seconds
```

یعنی بعد از 60 ثانیه داده منقضی شود.

---

# 120.18 - چرا TTL مهم است؟

اگر Cache هیچ Expiration نداشته باشد، ممکن است داده قدیمی برای مدت طولانی باقی بماند.

مثلاً:

```text
Database:
price = 100
```

Cache:

```text
price = 100
```

بعد قیمت Database تغییر کند:

```text
price = 120
```

اگر Cache حذف یا منقضی نشود، ممکن است کاربران همچنان:

```text
100
```

دریافت کنند.

---

# 120.19 - Cache Expiration

در یک Cache واقعی معمولاً باید مشخص کنیم:

```text
این داده چه زمانی منقضی شود؟
```

مثلاً:

```text
User Profile → 5 minutes
Product List → 1 minute
Configuration → 10 minutes
```

TTL باید بر اساس ماهیت داده انتخاب شود.

---

# 120.20 - Cache Invalidation

یکی از معروف‌ترین مشکلات سیستم‌های Cache:

```text
Cache Invalidation
```

است.

یعنی چه زمانی داده Cache را حذف یا به‌روزرسانی کنیم؟

فرض کنید:

```text
Database:
name = Ali
```

و:

```text
Cache:
name = Ali
```

کاربر نام خود را به:

```text
Reza
```

تغییر می‌دهد.

حالا:

```text
Database = Reza
Cache    = Ali
```

داریم.

اگر Cache را مدیریت نکنیم، داده اشتباه برگردانده می‌شود.

---

# 120.21 - Cache Invalidation هنگام Update

یک روش ساده:

```text
Update Database
      ↓
Delete Cache
```

مثلاً:

```js
await updateUser(userId, data);

cache.delete(`user:${userId}`);
```

در درخواست بعدی:

```text
Cache Miss
   ↓
Database
   ↓
New Data
   ↓
Cache
```

---

# 120.22 - Write-Through Cache

در Write-Through Cache، هنگام نوشتن داده، Cache نیز به‌روزرسانی می‌شود.

مثلاً:

```text
Application
   ↓
Cache
   ↓
Database
```

پس داده جدید هم در Cache و هم در Database نوشته می‌شود.

مزیت:

* Cache معمولاً داده جدیدتری دارد.

عیب:

* Write ممکن است پیچیده‌تر شود.
* عملیات بیشتری انجام می‌شود.

---

# 120.23 - Write-Back Cache

در Write-Back Cache ابتدا داده در Cache نوشته می‌شود و بعداً به منبع اصلی منتقل می‌شود.

مثلاً:

```text
Application
   ↓
Cache
   ↓
Later
   ↓
Database
```

مزیت:

* Write می‌تواند سریع‌تر باشد.

عیب:

* اگر Cache از بین برود، ممکن است داده هنوز به Database منتقل نشده باشد.
* پیاده‌سازی و مدیریت آن پیچیده‌تر است.

---

# 120.24 - Cache-Aside

یکی از الگوهای رایج:

```text
Cache-Aside
```

است.

جریان:

```text
Request
   ↓
Check Cache
   ↓
Hit? ─── Yes ──→ Return
   │
   No
   ↓
Database
   ↓
Store in Cache
   ↓
Return
```

مثال:

```js
let user = cache.get(`user:${id}`);

if (!user) {
  user = await getUserFromDatabase(id);

  cache.set(`user:${id}`, user);
}

return user;
```

این الگو در بسیاری از Backendها کاربرد دارد.

---

# 120.25 - Stale Data

گاهی Cache داده قدیمی دارد.

به چنین داده‌ای:

```text
Stale Data
```

گفته می‌شود.

مثلاً:

```text
Database = 120
Cache = 100
```

اگر Cache هنوز معتبر در نظر گرفته شود، ممکن است مقدار 100 برگردانده شود.

بنابراین باید بین:

```text
Performance
```

و:

```text
Freshness
```

تعادل برقرار کنیم.

---

# 120.26 - Cache Consistency

وقتی یک داده در چند محل نگهداری شود:

```text
Database
Cache
```

باید مشخص کنیم چگونه Consistency را مدیریت می‌کنیم.

سؤال مهم:

> اگر Database تغییر کرد، Cache چه زمانی تغییر کند؟

پاسخ بستگی به نیاز سیستم دارد.

---

# 120.27 - چه داده‌هایی برای Cache مناسب هستند؟

داده‌هایی که:

* زیاد خوانده می‌شوند.
* تغییرات کمی دارند.
* محاسبه یا دریافت آن‌ها پرهزینه است.
* نتیجه آن‌ها قابل Cache کردن است.

مثلاً:

```text
Product Categories
Popular Products
Public Configuration
User Profile
Expensive API Results
```

---

# 120.28 - چه داده‌هایی برای Cache مناسب نیستند؟

هر داده‌ای ارزش Cache کردن ندارد.

مثلاً داده‌ای که:

* دائماً تغییر می‌کند.
* بسیار کم استفاده می‌شود.
* Cache کردن آن پیچیدگی زیادی ایجاد می‌کند.
* نیاز به Consistency بسیار دقیق دارد.

ممکن است Candidate مناسبی برای Cache نباشد.

---

# 120.29 - Cache Stampede

یکی از مشکلات مهم:

```text
Cache Stampede
```

است.

فرض کنید یک داده Cache شده و تعداد زیادی کاربر به آن نیاز دارند.

TTL تمام می‌شود:

```text
Cache Expired
```

حالا 1000 Request هم‌زمان می‌رسند.

اگر همه ببینند Cache خالی است:

```text
1000 Requests
      ↓
1000 Database Queries
```

ممکن است Database ناگهان تحت فشار قرار بگیرد.

---

# 120.30 - جلوگیری از Cache Stampede

راهکارهای مختلفی وجود دارد، از جمله:

* Locking
* Request Coalescing
* Refresh Ahead
* Randomized TTL
* Background Refresh

ایده اصلی این است که همه Requestها هم‌زمان برای تولید مجدد یک داده به منبع اصلی هجوم نبرند.

---

# 120.31 - Cache Penetration

Cache Penetration زمانی رخ می‌دهد که درخواست‌هایی برای داده‌های ناموجود دائماً به Database برسند.

مثلاً:

```text
GET /users/999999999
```

اگر User وجود نداشته باشد:

```text
Cache Miss
   ↓
Database
   ↓
Not Found
```

اگر همین درخواست هزار بار تکرار شود، ممکن است Database دائماً Query شود.

---

# 120.32 - راهکار Cache Penetration

یکی از روش‌ها Cache کردن نتیجه منفی برای مدت کوتاه است.

مثلاً:

```text
user:999999999 → NOT_FOUND
```

با TTL کوتاه.

در نتیجه درخواست‌های تکراری لازم نیست هر بار به Database برسند.

---

# 120.33 - Cache Key Collision

اگر دو نوع داده از Key مشابه استفاده کنند:

```text
1
```

ممکن است داده‌ها با یکدیگر تداخل پیدا کنند.

بهتر است Namespace داشته باشیم:

```text
user:1
product:1
order:1
```

در نتیجه:

```text
user:1
```

با:

```text
product:1
```

اشتباه نمی‌شود.

---

# 120.34 - Cache Size

Cache محدودیت Memory دارد.

اگر بدون محدودیت داده ذخیره کنیم:

```js
cache.set(key, value);
```

ممکن است Memory به‌تدریج افزایش پیدا کند.

بنابراین باید مواردی مانند:

* TTL
* Maximum Size
* Eviction Policy

را در نظر بگیریم.

---

# 120.35 - Eviction Policy

وقتی Cache پر شود، باید تصمیم بگیریم کدام داده حذف شود.

یکی از سیاست‌های شناخته‌شده:

```text
LRU
```

است.

LRU مخفف:

```text
Least Recently Used
```

است.

یعنی داده‌ای که مدت بیشتری استفاده نشده، کاندید حذف شود.

---

# 120.36 - LFU

LFU مخفف:

```text
Least Frequently Used
```

است.

در این روش داده‌ای که کمتر استفاده شده است، کاندید حذف شدن خواهد بود.

انتخاب Policy مناسب به Workload سیستم بستگی دارد.

---

# 120.37 - Cache Locality

گاهی یک Application به Cache محلی خودش دسترسی دارد:

```text
Node.js
   ↓
Local Memory
```

این روش بسیار سریع است.

اما در محیط Distributed ممکن است نیاز به Cache مشترک داشته باشیم:

```text
Node.js A ─┐
Node.js B ─┼──→ Distributed Cache
Node.js C ─┘
```

---

# 120.38 - Cache Layer

در یک سیستم واقعی ممکن است چند لایه Cache داشته باشیم:

```text
Browser Cache
      ↓
CDN Cache
      ↓
Application Cache
      ↓
Distributed Cache
      ↓
Database
```

هر لایه هدف خاصی دارد.

---

# 120.39 - HTTP Cache

HTTP نیز مکانیزم‌های Cache دارد.

برای مثال Headerهایی مانند:

```text
Cache-Control
ETag
Last-Modified
```

می‌توانند برای کنترل Cache سمت Client و Proxyها استفاده شوند.

مثلاً:

```http
Cache-Control: max-age=60
```

یعنی Resource می‌تواند برای مدت مشخصی Cache شود.

---

# 120.40 - ETag

ETag یک Identifier برای نسخه‌ای از Resource است.

مثلاً Server:

```http
ETag: "abc123"
```

ارسال می‌کند.

Client در درخواست بعدی می‌تواند بگوید:

```http
If-None-Match: "abc123"
```

اگر Resource تغییر نکرده باشد، Server می‌تواند:

```text
304 Not Modified
```

برگرداند.

این کار می‌تواند حجم انتقال داده را کاهش دهد.

---

# 120.41 - Cache و API

برای APIهای Read-heavy، Cache می‌تواند بسیار مفید باشد.

مثلاً:

```text
GET /products
GET /categories
GET /popular-products
```

اما برای Endpointهای حساس به Consistency باید با دقت بیشتری Cache طراحی شود.

---

# 120.42 - Cache کردن User

مثلاً:


# 120.43 - Cache کردن با TTL ساده

می‌توان یک Cache ساده با TTL ساخت:

```js
const cache = new Map();

    expiresAt,
  });

}
```

## پاسخ تمرین 8

برای پیاده‌سازی کامل LRU می‌توان از ترکیب `Map` و ترتیب ورود/دسترسی استفاده کرد.

یک نسخه ساده:

```js
class LRUCache {
  constructor(limit) {
    this.limit = limit;
    this.cache = new Map();
  }

  get(key) {
    if (!this.cache.has(key)) {
      return undefined;
    }

    const value = this.cache.get(key);

    this.cache.delete(key);
    this.cache.set(key, value);

    return value;
  }

  set(key, value) {
    if (this.cache.has(key)) {
      this.cache.delete(key);
    }

    this.cache.set(key, value);

    if (this.cache.size > this.limit) {
      const firstKey = this.cache.keys().next().value;
      this.cache.delete(firstKey);
    }
  }
}
```

در این پیاده‌سازی، آخرین داده‌های استفاده‌شده در انتهای `Map` قرار می‌گیرند و قدیمی‌ترین مورد در صورت نیاز حذف می‌شود.

## پاسخ تمرین 9

```text

     ↓

Request 4 ─┤
Request 5 ─┘
```

یک راهکار استفاده از Lock یا Promise مشترک است.

مثلاً:

```js
const pending = new Map();

async function getData(key) {
  const cached = cache.get(key);

  if (cached) {
    return cached;
  }

  if (pending.has(key)) {
    return pending.get(key);
  }

  const promise = database.getData(key)
    .then((data) => {
      cache.set(key, data);
      return data;
    })
    .finally(() => {
      pending.delete(key);
    });

  pending.set(key, promise);

  return promise;
}
```

در این روش چند Request هم‌زمان می‌توانند منتظر یک Promise مشترک بمانند و فقط یک Query به Database ارسال شود.
