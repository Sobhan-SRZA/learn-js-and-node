# فصل 124 - Load Balancing

## مقدمه

در فصل‌های قبلی بخش Performance با مفاهیمی مانند **Performance Optimization، Cache، Redis، Compression و Cluster** آشنا شدیم. در ادامه این مسیر، یکی از مهم‌ترین مفاهیم برای ساخت برنامه‌های Node.js مقیاس‌پذیر، **Load Balancing** است.

در یک برنامه ساده ممکن است فقط یک Node.js Server داشته باشیم:

```text
Client
   │
   ▼
Node.js
   │
   ▼
Database
```

اما وقتی تعداد کاربران و درخواست‌ها افزایش پیدا می‌کند، یک Server ممکن است دیگر برای پاسخ‌گویی به تمام درخواست‌ها کافی نباشد.

در این شرایط می‌توانیم چند Instance از برنامه خود اجرا کنیم:

```text
              ┌── Node.js Instance 1
Client ──────►├── Node.js Instance 2
              └── Node.js Instance 3
```

اما سؤال مهم این است:

> چه چیزی تصمیم می‌گیرد هر Request به کدام Instance ارسال شود؟

پاسخ، **Load Balancer** است.

Load Balancing یعنی توزیع درخواست‌ها و بار کاری بین چند Server یا Instance، با هدف استفاده بهتر از منابع، افزایش ظرفیت سیستم و افزایش دسترس‌پذیری.

فصل Load Balancing در ساختار مستند در بخش **Performance** و بعد از فصل‌های Cache، Redis، Compression و Cluster قرار گرفته است. 

---

# 124.1 - Load Balancing چیست؟

**Load Balancing** به فرآیند تقسیم و توزیع Traffic بین چند Server گفته می‌شود.

فرض کنید سه Server داریم:

```text
Server 1
Server 2
Server 3
```

بدون Load Balancer ممکن است تمام درخواست‌ها به یک Server برسند:

```text
1000 Requests
      │
      ▼
  Server 1
```

اما با Load Balancer:

```text
                 Load Balancer
                /      |      \
               ▼       ▼       ▼
          Server 1 Server 2 Server 3
```

درخواست‌ها بین Serverها توزیع می‌شوند.

---

# 124.2 - چرا به Load Balancing نیاز داریم؟

فرض کنید API ما روی یک Server اجرا می‌شود:

```text
Client
  │
  ▼
Node.js
```

با افزایش کاربران، فشار روی Server بیشتر می‌شود:

```text
CPU     ██████████ 100%
Memory  █████████░ 90%
```

راه‌حل می‌تواند اضافه کردن Instanceهای بیشتر باشد:

```text
             Load Balancer
             /     |     \
            ▼      ▼      ▼
         Node.js Node.js Node.js
```

در این حالت می‌توانیم ظرفیت پردازش درخواست‌ها را افزایش دهیم.

مهم‌ترین اهداف Load Balancing:

* توزیع Traffic
* افزایش ظرفیت سیستم
* استفاده بهتر از منابع
* کاهش فشار روی یک Server
* افزایش Availability
* Failover
* کمک به Horizontal Scaling
* امکان اجرای چند Instance از Application

---

# 124.3 - Load Balancer چیست؟

**Load Balancer** سرویسی است که بین Client و Backend قرار می‌گیرد و درباره مقصد درخواست تصمیم‌گیری می‌کند.

معماری ساده:

```text
Client
  │
  ▼
Load Balancer
  │
  ├── Server 1
  ├── Server 2
  └── Server 3
```

Client معمولاً مستقیماً با Serverهای Backend ارتباط ندارد.

---

# 124.4 - Load Balancing در Node.js

Node.js برای اجرای Applicationهای Backend بسیار مناسب است، اما یک Process Node.js نیز منابع محدودی دارد.

در معماری بزرگ‌تر می‌توانیم چند Instance اجرا کنیم:

```text
Node.js Instance 1
Node.js Instance 2
Node.js Instance 3
Node.js Instance 4
```

و Load Balancer درخواست‌ها را بین آن‌ها توزیع کند.

```text
                  Client
                    │
                    ▼
              Load Balancer
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
   Node.js 1    Node.js 2    Node.js 3
```

---

# 124.5 - Load Balancing و Cluster

در فصل قبل با **Cluster** آشنا شدیم.

Cluster می‌تواند چند Worker از Node.js را اجرا کند:

```text
Server
  │
  ▼
Cluster
 ├── Worker 1
 ├── Worker 2
 └── Worker 3
```

Load Balancer می‌تواند یک لایه بالاتر قرار بگیرد:

```text
                    Load Balancer
                   /      |      \
                  ▼       ▼       ▼
               Server   Server   Server
                  │       │       │
               Cluster Cluster Cluster
```

در نتیجه:

* Load Balancer می‌تواند بین Serverها یا Instanceهای مختلف Traffic را توزیع کند.
* Cluster می‌تواند منابع یک Server را به چند Worker تقسیم کند.

---

# 124.6 - Load Balancing و Horizontal Scaling

یکی از کاربردهای مهم Load Balancing، **Horizontal Scaling** است.

فرض کنید ابتدا فقط یک Instance داریم:

```text
Node.js × 1
```

بعد:

```text
Node.js × 2
```

و در صورت افزایش Traffic:

```text
Node.js × 4
```

و:

```text
Node.js × 8
```

Load Balancer کمک می‌کند Traffic بین این Instanceها توزیع شود.

```text
                 Load Balancer
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
    Instance 1     Instance 2     Instance 3
```

---

# 124.7 - Load Balancing و Vertical Scaling

در **Vertical Scaling** به جای اضافه کردن Server، منابع Server را افزایش می‌دهیم.

مثلاً:

```text
2 CPU
4 GB RAM
```

به:

```text
8 CPU
16 GB RAM
```

تبدیل می‌شود.

اما Vertical Scaling محدودیت دارد.

در معماری‌های بزرگ معمولاً Horizontal Scaling اهمیت بیشتری پیدا می‌کند:

```text
Server
   ↓
Server + Server + Server
```

Load Balancer یکی از اجزای اصلی چنین معماری‌ای است.

---

# 124.8 - الگوریتم‌های Load Balancing

Load Balancer باید تصمیم بگیرد Request جدید به کدام Backend ارسال شود.

برای این کار الگوریتم‌های مختلفی وجود دارند.

مهم‌ترین آن‌ها:

* Round Robin
* Weighted Round Robin
* Least Connections
* IP Hash
* Random
* Least Response Time

---

# 124.9 - Round Robin

Round Robin یکی از ساده‌ترین روش‌ها است.

فرض کنید سه Server داریم:

```text
Server 1
Server 2
Server 3
```

درخواست‌ها:

```text
Request 1 → Server 1
Request 2 → Server 2
Request 3 → Server 3
Request 4 → Server 1
Request 5 → Server 2
Request 6 → Server 3
```

یعنی Serverها به صورت چرخشی انتخاب می‌شوند.

---

# 124.10 - Weighted Round Robin

فرض کنید Serverها قدرت یکسانی ندارند.

```text
Server 1 → قدرتمند
Server 2 → متوسط
Server 3 → ضعیف
```

می‌توان Weight تعیین کرد:

```text
Server 1 → 3
Server 2 → 2
Server 3 → 1
```

در نتیجه Server 1 درخواست بیشتری دریافت می‌کند.

---

# 124.11 - Least Connections

در روش **Least Connections**، درخواست جدید به Serverی ارسال می‌شود که Connection فعال کمتری دارد.

مثلاً:

```text
Server 1 → 50 Connections
Server 2 → 15 Connections
Server 3 → 30 Connections
```

Request جدید می‌تواند به:

```text
Server 2
```

ارسال شود.

این روش زمانی مفید است که Requestها مدت زمان یکسانی برای پردازش نداشته باشند.

---

# 124.12 - IP Hash

در IP Hash، اطلاعات مربوط به IP Client در انتخاب Backend نقش دارد.

مثلاً:

```text
Client A → Server 1
Client B → Server 2
Client C → Server 3
```

یکی از کاربردهای احتمالی آن حفظ Session Affinity است.

اما استفاده از IP Hash همیشه مناسب نیست.

اگر کاربران زیادی از یک Public IP مشترک استفاده کنند، ممکن است Traffic نامتعادل شود.

---

# 124.13 - Layer 4 Load Balancing

در Layer 4، Load Balancing در سطح Transport انجام می‌شود.

مفاهیمی مانند:

```text
IP
TCP
UDP
Port
```

در این سطح اهمیت دارند.

Load Balancer لزوماً محتوای HTTP Request را بررسی نمی‌کند.

---

# 124.14 - Layer 7 Load Balancing

Layer 7 در سطح Application انجام می‌شود.

در HTTP می‌توان اطلاعاتی مانند:

```text
HTTP Method
URL
Host
Headers
Cookies
```

را بررسی کرد.

مثلاً:

```text
/api/users
```

به Backend مربوط به API ارسال شود و:

```text
/images
```

به Backend مربوط به فایل‌های Static.

---

# 124.15 - Reverse Proxy

Load Balancerها اغلب در کنار مفهوم **Reverse Proxy** استفاده می‌شوند.

معماری:

```text
Client
  │
  ▼
Reverse Proxy
  │
  ├── Node.js 1
  ├── Node.js 2
  └── Node.js 3
```

Reverse Proxy درخواست Client را دریافت کرده و آن را به Backend مناسب ارسال می‌کند.

---

# 124.16 - Nginx به عنوان Load Balancer

در معماری‌های Node.js می‌توان از Nginx به عنوان Reverse Proxy و Load Balancer استفاده کرد.

مثال:

```nginx
upstream node_backend {
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
    server 127.0.0.1:3003;
}

server {
    listen 80;

    location / {
        proxy_pass http://node_backend;
    }
}
```

در این معماری:

```text
Client
  │
  ▼
Nginx
  │
  ├── Node.js :3001
  ├── Node.js :3002
  └── Node.js :3003
```

---

# 124.17 - Health Check

Load Balancer باید بتواند تشخیص دهد Backend سالم است یا خیر.

برای این کار معمولاً Health Check تعریف می‌شود.

مثلاً:

```http
GET /health
```

و Node.js پاسخ می‌دهد:

```json
{
  "status": "ok"
}
```

اگر Server پاسخ مناسب ندهد:

```text
Server 2 → Unhealthy
```

Load Balancer می‌تواند آن را موقتاً از Pool خارج کند.

---

# 124.18 - Health Check در Express

مثال ساده:

```js
app.get("/health", (req, res) => {
  res.status(200).json({
    status: "ok",
  });
});
```

این Endpoint باید سریع باشد و برای بررسی سلامت سرویس طراحی شود.

---

# 124.19 - Readiness Check

گاهی Application زنده است، اما آماده دریافت Traffic نیست.

مثلاً:

```text
Node.js → Running
Database → Down
```

در این شرایط Process زنده است، اما Application ممکن است نتواند Requestهای واقعی را پردازش کند.

برای این حالت می‌توان Endpoint جداگانه‌ای مانند:

```http
GET /ready
```

داشت.

---

# 124.20 - Liveness و Readiness

دو مفهوم مهم:

### Liveness

آیا Application هنوز زنده است؟

### Readiness

آیا Application آماده دریافت Traffic است؟

مثلاً:

```text
Liveness  → OK
Readiness → NOT READY
```

ممکن است زمانی اتفاق بیفتد که Process فعال باشد اما Dependencyهای ضروری در دسترس نباشند.

---

# 124.21 - Failover

فرض کنید:

```text
Server 1 → Healthy
Server 2 → Healthy
Server 3 → Healthy
```

و Server 2 از کار بیفتد:

```text
Server 1 → Healthy
Server 2 → Down
Server 3 → Healthy
```

Load Balancer باید بتواند Traffic را به Serverهای سالم ارسال کند.

```text
             Load Balancer
              /         \
             ▼           ▼
        Server 1      Server 3
```

این قابلیت به **Failover** کمک می‌کند.

---

# 124.22 - High Availability

Load Balancing می‌تواند بخشی از معماری High Availability باشد.

```text
                 Load Balancer
                /      |      \
               ▼       ▼       ▼
           Server 1 Server 2 Server 3
```

اگر یکی از Serverها خراب شود، Serverهای دیگر می‌توانند سرویس را ادامه دهند.

البته خود Load Balancer نیز باید در معماری‌های حساس به شکل High Availability طراحی شود.

---

# 124.23 - Single Point of Failure

این معماری:

```text
Clients
   │
   ▼
Load Balancer
   │
 ┌─┼─────────┐
 ▼ ▼         ▼
S1 S2        S3
```

اگر فقط یک Load Balancer داشته باشد، خود Load Balancer می‌تواند Single Point of Failure باشد.

بنابراین در سیستم‌های حساس باید معماری HA برای این بخش نیز در نظر گرفته شود.

---

# 124.24 - Stateless Application

Load Balancing زمانی ساده‌تر می‌شود که Application **Stateless** باشد.

یعنی اطلاعات مهم یک User فقط در Memory یک Instance نگهداری نشود.

معماری بهتر:

```text
Node.js 1 ──┐
Node.js 2 ──┼──► Redis
Node.js 3 ──┘
```

در این حالت Instanceهای مختلف می‌توانند به State مشترک دسترسی داشته باشند.

---

# 124.25 - مشکل Session در Load Balancing

فرض کنید User ابتدا به Server 1 وصل شود:

```text
Request 1 → Server 1
Session → Server 1 Memory
```

Request بعدی ممکن است به Server 2 برسد:

```text
Request 2 → Server 2
```

اما Server 2 Session مربوط به Server 1 را ندارد.

در نتیجه ممکن است User از Session خود خارج‌شده به نظر برسد.

---

# 124.26 - Sticky Session

یک راه‌حل، Sticky Session است.

در این حالت Client تا حد امکان به همان Backend قبلی هدایت می‌شود:

```text
Client A
   ↓
Server 1

Client A
   ↓
Server 1

Client A
   ↓
Server 1
```

اما Sticky Session همیشه بهترین راه‌حل نیست.

معماری Stateless معمولاً انعطاف‌پذیری بیشتری برای Scaling و Failover ایجاد می‌کند.

---

# 124.27 - Redis در معماری Load Balanced

با توجه به اینکه فصل Redis قبل از Load Balancing قرار گرفته است، Redis می‌تواند در معماری چند Instance نقش مهمی داشته باشد. 

مثلاً:

```text
                 Load Balancer
                /      |      \
               ▼       ▼       ▼
           Node.js  Node.js  Node.js
                \      |      /
                 \     |     /
                    Redis
```

Redis می‌تواند برای مواردی مانند:

* Session
* Cache
* Shared State
* Rate Limiting
* Pub/Sub

استفاده شود.

---

# 124.28 - Load Balancing و Database

Load Balancer لزوماً Database را Load Balance نمی‌کند.

ممکن است معماری ما این‌گونه باشد:

```text
             Load Balancer
            /      |      \
           ▼       ▼       ▼
        Node.js Node.js Node.js
            \      |      /
             \     |     /
               Database
```

در این حالت سه Application Instance داریم، اما Database همچنان یک نقطه مشترک است.

بنابراین Database می‌تواند تبدیل به Bottleneck شود.

---

# 124.29 - Connection Pool

هر Node.js Instance ممکن است Connection Pool جداگانه‌ای داشته باشد.

مثلاً:

```text
3 Instances
×
10 Connections
=
30 Database Connections
```

اگر تعداد Instanceها افزایش پیدا کند:

```text
10 Instances
×
10 Connections
=
100 Connections
```

بنابراین هنگام Scaling باید ظرفیت Database و Connection Pool را نیز در نظر گرفت.

---

# 124.30 - Load Balancing و WebSocket

WebSocket با HTTP Requestهای مستقل متفاوت است.

در HTTP:

```text
Request
   ↓
Response
```

اما WebSocket یک Connection طولانی‌مدت ایجاد می‌کند:

```text
Client
   │
   │ Persistent Connection
   │
   ▼
Server
```

در معماری چند Instance باید مواردی مانند:

* Connection Ownership
* Sticky Session در صورت نیاز
* Shared State
* Pub/Sub
* Redis

را در نظر گرفت.

---

# 124.31 - Forwarded Headers

وقتی Node.js پشت Load Balancer قرار دارد:

```text
Client
  ↓
Load Balancer
  ↓
Node.js
```

ممکن است Node.js مستقیماً IP واقعی Client را نبیند.

Proxyها می‌توانند اطلاعاتی مانند IP و Protocol اصلی را از طریق Headerهای Forwarded منتقل کنند.

از Headerهایی مانند:

```text
X-Forwarded-For
X-Forwarded-Proto
X-Forwarded-Host
```

استفاده می‌شود.

---

# 124.32 - `trust proxy` در Express

وقتی Express پشت Proxy قرار دارد، تنظیمات Proxy اهمیت پیدا می‌کند.

مثلاً در معماری مناسب:

```js
app.set("trust proxy", true);
```

اما نباید این تنظیم را بدون شناخت Proxyهای مورد اعتماد فعال کرد.

این تنظیم می‌تواند روی مواردی مانند:

```text
req.ip
req.protocol
Secure Cookies
```

تأثیر داشته باشد.

---

# 124.33 - Load Balancing و Cache

Cache می‌تواند فشار روی Backend را کاهش دهد.

یک معماری می‌تواند چنین باشد:

```text
Client
  ↓
Load Balancer
  ↓
Node.js
  ↓
Redis Cache
  ↓
Database
```

اگر داده در Cache وجود داشته باشد، لازم نیست هر Request به Database برسد.

---

# 124.34 - Load Balancing و CDN

برای فایل‌های Static مانند:

```text
Images
CSS
JavaScript
Fonts
Videos
```

می‌توان از CDN استفاده کرد.

مثلاً:

```text
                Client
               /      \
              ▼        ▼
            CDN    Load Balancer
                       │
                    Node.js
```

در نتیجه Traffic فایل‌های Static الزاماً به Application Server نمی‌رسد.

---

# 124.35 - Load Balancing و Compression

Compression می‌تواند در Application یا Proxy انجام شود.

مثلاً:

```text
Client
  ↓
Load Balancer
  ↓
Node.js
```

یا:

```text
Client
  ↓
Proxy + Compression
  ↓
Node.js
```

محل مناسب Compression باید با توجه به معماری و Performance واقعی مشخص شود.

---

# 124.36 - Load Balancing در Docker

در محیط‌های Containerized می‌توان چند Container از Node.js اجرا کرد:

```text
Load Balancer
      │
      ├── Container 1
      ├── Container 2
      └── Container 3
```

هر Container می‌تواند یک Instance از Application باشد.

---

# 124.37 - Load Balancing در Kubernetes

در Kubernetes می‌توان چند Pod از Application داشت:

```text
Service
   │
   ├── Pod 1
   ├── Pod 2
   └── Pod 3
```

Service می‌تواند Traffic را بین Podها توزیع کند.

---

# 124.38 - Load Balancing و Monitoring

صرفاً اجرای Load Balancer کافی نیست.

باید مواردی مانند:

```text
Request Count
Latency
Error Rate
5xx
Backend Health
Connections
CPU
Memory
```

را بررسی کنیم.

این اطلاعات به ما کمک می‌کنند بفهمیم آیا Traffic به شکل مناسبی توزیع شده است یا خیر.

---

# 124.39 - Load Balancing و Graceful Shutdown

وقتی می‌خواهیم یک Instance را خاموش یا Deploy کنیم، بهتر است ابتدا Traffic جدید را دریافت نکند.

فرآیند مناسب:

```text
Remove from Traffic
        ↓
Finish Active Requests
        ↓
Close Connections
        ↓
Shutdown
```

این کار باعث کاهش خطا هنگام Deployment و Scaling می‌شود.

## 1. تصور اینکه Load Balancer همه مشکلات Performance را حل می‌کند

اگر Database کند باشد:

```text
Load Balancer
      ↓
Node.js
      ↓
Slow Database
```

Load Balancer مشکل اصلی را حل نمی‌کند.

---

## 2. نداشتن Health Check

بدون Health Check ممکن است Requestها به Server خراب ارسال شوند.

---

## 3. نگه داشتن Session در Memory

در معماری چند Instance باعث ناسازگاری Session می‌شود.

---

## 4. استفاده بی‌دلیل از Sticky Session

Sticky Session می‌تواند Failover و Scaling را پیچیده‌تر کند.

---

## 5. نادیده گرفتن Database

اضافه کردن Node.js Instance بدون توجه به Database می‌تواند Database را به Bottleneck تبدیل کند.

---

## 6. نادیده گرفتن Connection Pool

افزایش Instanceها می‌تواند تعداد Database Connectionها را به شدت افزایش دهد.

---

## 7. اعتماد اشتباه به `X-Forwarded-For`

Headerهای Proxy باید از مسیرهای مورد اعتماد دریافت شوند.

---

## 8. تنظیم نادرست `trust proxy`

تنظیم نادرست می‌تواند روی IP، Protocol و Cookieها تأثیر بگذارد.

---

## 9. استفاده از Round Robin در همه شرایط

اگر Serverها یا Workloadها متفاوت باشند، الگوریتم‌های دیگر ممکن است مناسب‌تر باشند.

---

## 10. فراموش کردن WebSocket

WebSocket به دلیل داشتن Connectionهای طولانی‌مدت نیازمند طراحی دقیق‌تری است.

---

## 11. داشتن تنها یک Load Balancer در معماری حساس

خود Load Balancer می‌تواند Single Point of Failure باشد.

---

## 12. نداشتن Graceful Shutdown

خاموش کردن ناگهانی Instance ممکن است باعث قطع Requestهای فعال شود.

---

# نکات حرفه‌ای

## 1. Application را تا حد امکان Stateless طراحی کنید

این کار Scaling و Failover را ساده‌تر می‌کند.

---

## 2. Health و Readiness را جدا کنید

زنده بودن Process الزاماً به معنی آماده بودن Application نیست.

---

## 3. Health Check باید سبک باشد

Health Check نباید خودش باعث فشار زیاد روی Database یا سرویس‌های دیگر شود.

---

## 4. الگوریتم مناسب انتخاب کنید

برای Serverهای یکسان:

```text
Round Robin
```

می‌تواند کافی باشد.

برای Serverهای متفاوت:

```text
Weighted Round Robin
```

می‌تواند مناسب‌تر باشد.

---

## 5. Session را Shared کنید

در صورت نیاز از Redis یا Storage مشترک استفاده کنید.

---

## 6. Database را در محاسبات Scaling وارد کنید

تعداد Instanceهای Application را بدون توجه به ظرفیت Database افزایش ندهید.

---

## 7. Request ID داشته باشید

در معماری چند Instance، Request ID برای Trace کردن Request بسیار مفید است.

```text
Request
  ↓
Load Balancer
  ↓
Node.js 2
```

با داشتن Request ID می‌توان مسیر Request را بهتر دنبال کرد.

---

## 8. Instance ID را در Log ثبت کنید

مثلاً:

```json
{
  "requestId": "abc123",
  "instance": "node-2",
  "status": 200
}
```

این کار Debug کردن مشکلات توزیع‌شده را ساده‌تر می‌کند.

---

## 9. P95 و P99 را بررسی کنید

Average Latency همیشه تصویر کاملی از Performance نمی‌دهد.

Latencyهای Tail نیز اهمیت زیادی دارند.

---

## 10. Load Balancing را با Benchmark واقعی بررسی کنید

قبل و بعد از Scaling موارد زیر را مقایسه کنید:

```text
Throughput
Latency
P95
P99
CPU
Memory
Error Rate
```

---

## 11. Failover را عمداً تست کنید

یک Backend را عمداً از مدار خارج کنید و بررسی کنید سیستم چگونه واکنش نشان می‌دهد.

---

## 12. Deployment را با Load Balancer هماهنگ کنید

Instance را ابتدا از Traffic خارج کنید، سپس Deployment را انجام دهید و بعد دوباره وارد Pool کنید.

---

# پاسخ تشریحی

## پاسخ تمرین 1

Load Balancing یعنی توزیع Traffic بین چند Backend.

مثلاً:

```text
              Load Balancer
              /     |     \
             ▼      ▼      ▼
          Node 1  Node 2  Node 3
```

با این کار می‌توان ظرفیت سیستم را افزایش داد و در صورت خرابی یک Backend، Traffic را به Backendهای سالم ارسال کرد.

---

## پاسخ تمرین 2

توزیع Round Robin:

```text
Request 1 → Server 1
Request 2 → Server 2
Request 3 → Server 3
Request 4 → Server 1
Request 5 → Server 2
Request 6 → Server 3
Request 7 → Server 1
Request 8 → Server 2
Request 9 → Server 3
```

---

## پاسخ تمرین 3

چون قدرت CPUها متفاوت است، می‌توان Weightها را تقریباً متناسب با ظرفیت در نظر گرفت:

```text
Server 1 → 4
Server 2 → 2
Server 3 → 1
```

بنابراین Server اول Traffic بیشتری دریافت می‌کند.

---

## پاسخ تمرین 4

```js
app.get("/health", (req, res) => {
  res.status(200).json({
    status: "ok",
  });
});
```

---

## پاسخ تمرین 5

Liveness بررسی می‌کند Process زنده است.

Readiness بررسی می‌کند Application آماده دریافت Traffic است.

مثلاً:

```text
Node.js → Running
Database → Down
```

در این حالت:

```text
Liveness → OK
Readiness → NOT READY
```

ممکن است نتیجه منطقی باشد.

---

## پاسخ تمرین 6

Configuration نمونه:

```nginx
upstream node_backend {
    server 127.0.0.1:3001;
    server 127.0.0.1:3002;
    server 127.0.0.1:3003;
}

server {
    listen 80;

    location / {
        proxy_pass http://node_backend;
    }
}
```

ساختار:

```text
Client
  ↓
Nginx
  ├── :3001
  ├── :3002
  └── :3003
```

---

## پاسخ تمرین 7

فرض کنید Session در Server 1 باشد:

```text
Request 1 → Server 1
Session → Server 1 Memory
```

اگر Request دوم به Server 2 برسد:

```text
Request 2 → Server 2
```

Server 2 Session را ندارد.

به همین دلیل Session مشترک یا معماری Stateless اهمیت دارد.

---

## پاسخ تمرین 8

می‌توان Session را در Redis ذخیره کرد:

```text
Node 1 ──┐
Node 2 ──┼──→ Redis
Node 3 ──┘
```

در این حالت تمام Instanceها به یک State مشترک دسترسی دارند.

---

## پاسخ تمرین 9

```text
4 × 15 = 60
```

بنابراین حداکثر 60 Connection در این فرض داریم.

---

## پاسخ تمرین 10

چون ممکن است Bottleneck در بخش دیگری باشد:

```text
Node.js
   ↓
Database
```

اگر Database نتواند بار بیشتری تحمل کند، اضافه کردن Node.js Instance تأثیر محدودی خواهد داشت.

---

## پاسخ تمرین 11

`X-Forwarded-For` معمولاً برای انتقال IP اصلی Client از طریق Proxy یا Load Balancer استفاده می‌شود.

ساختار:

```text
Client
  ↓
Load Balancer
  ↓
Node.js
```

Node.js ممکن است مستقیم Client را نبیند، بنابراین Proxy اطلاعات IP را منتقل می‌کند.

---

## پاسخ تمرین 12

چون Proxy می‌تواند روی اطلاعاتی مانند:

```text
IP
Protocol
Secure Cookie
```

تأثیر داشته باشد.

اگر Proxyهای غیرقابل اعتماد در مسیر باشند، اعتماد بیش از حد به Forwarded Headers می‌تواند مشکل امنیتی ایجاد کند.

---

## پاسخ تمرین 13

Backend خراب باید از Pool خارج شود:

```text
Server 1 → Healthy
Server 2 → Down
Server 3 → Healthy
```

و Traffic جدید به Server 1 و Server 3 ارسال شود.

---

## پاسخ تمرین 14

Layer 4 بیشتر در سطح:

```text
IP
TCP
UDP
Port
```

کار می‌کند.

Layer 7 می‌تواند اطلاعات Application مانند:

```text
HTTP
URL
Headers
Cookies
```

را بررسی کند.

---

## پاسخ تمرین 15

HTTP Requestها معمولاً مستقل هستند:

```text
Request → Response
```

اما WebSocket یک Connection طولانی‌مدت ایجاد می‌کند.

بنابراین Connection باید به شکل صحیح مدیریت شود و در معماری چند Instance ممکن است به Shared State، Pub/Sub یا Session Affinity نیاز داشته باشیم.

---

## پاسخ تمرین 16

معماری:

```text
Client
  │
  ▼
Load Balancer
  │
  ├── Node.js 1
  ├── Node.js 2
  └── Node.js 3
        │
        ▼
      Redis
        │
        ▼
    Database
```

وظایف:

### Load Balancer

توزیع Traffic و مدیریت Backendها.

### Node.js

اجرای Business Logic و API.

### Redis

Cache و State مشترک و در صورت نیاز Session یا Rate Limit.

### Database

ذخیره‌سازی دائمی داده‌ها.

# مینی‌پروژه - Load Balanced Node.js API

در این مینی‌پروژه یک API ساده می‌سازیم که سه Instance از Node.js دارد و توسط Nginx در مقابل آن‌ها Load Balancing انجام می‌شود.

این پروژه با مباحث قبلی بخش Performance، مخصوصاً **Cache، Redis، Compression و Cluster** ارتباط مستقیم دارد. 

---

## هدف پروژه

معماری نهایی:

```text
                         Client
                           │
                           ▼
                    ┌─────────────┐
                    │    Nginx    │
                    │Load Balancer│
                    └──────┬──────┘
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
          Node.js       Node.js       Node.js
          :3001         :3002         :3003
             │             │             │
             └─────────────┼─────────────┘
                           │
                           ▼
                         Redis
                           │
                           ▼
                       Database
```

# مرحله 1 - ساخت پروژه

```bash
mkdir load-balanced-api
cd load-balanced-api

npm init -y

npm install express redis dotenv
```

# مرحله 2 - ساخت Server

```js
import express from "express";

const app = express();

app.use(express.json());

app.get("/", (req, res) => {
  res.json({
    message: "Load Balanced API",
    pid: process.pid,
    port: process.env.PORT,
  });
});

app.get("/health", (req, res) => {
  res.status(200).json({
    status: "ok",
    pid: process.pid,
  });
});

const port = process.env.PORT || 3000;

const server = app.listen(port, () => {
  console.log(`Server running on port ${port}`);
});
```

# مرحله 9 - Graceful Shutdown

برای Shutdown مناسب:

```js
process.on("SIGTERM", () => {
  server.close(() => {
    console.log("Server closed");
    process.exit(0);
  });
});
```

هدف:

```text
Stop receiving Traffic
        ↓
Finish Requests
        ↓
Close Connections
        ↓
Shutdown
```
