# فصل 123 - Cluster

## مقدمه

در فصل‌های قبل با مفاهیم مختلف Performance Optimization آشنا شدیم و یاد گرفتیم که برای ساخت یک Backend سریع و مقیاس‌پذیر باید به مواردی مانند Cache، Redis و Compression توجه کنیم.

اما یک سؤال مهم باقی می‌ماند:

> اگر یک برنامه Node.js روی یک CPU Core اجرا شود و این Core به حداکثر ظرفیت خود برسد، چگونه می‌توانیم از Coreهای دیگر سیستم نیز استفاده کنیم؟

یکی از راهکارهای Node.js برای این مسئله، استفاده از **Cluster** است.

به‌صورت ساده، Cluster به ما اجازه می‌دهد چند Process از برنامه Node.js را روی یک سیستم اجرا کنیم تا بتوانیم از چند CPU Core استفاده کنیم.

ساختار ساده:

```text
                Node.js Application
                       │
                    Primary
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
       Worker 1     Worker 2     Worker 3
          │            │            │
        CPU 1        CPU 2        CPU 3
```

هر Worker یک Process مستقل Node.js است.

---

# 123.1 - Cluster چیست؟

Cluster یک قابلیت داخلی Node.js است که امکان ایجاد چند Process از یک برنامه Node.js را فراهم می‌کند.

به جای اینکه فقط یک Process داشته باشیم:

```text
Server
  │
  └── Node.js Process
```

می‌توانیم چند Worker داشته باشیم:

```text
Server
  │
  ├── Worker 1
  ├── Worker 2
  ├── Worker 3
  └── Worker 4
```

این Workerها می‌توانند روی Coreهای مختلف CPU اجرا شوند.

---

# 123.2 - چرا Cluster؟

Node.js برای اجرای JavaScript از Event Loop استفاده می‌کند و یک Process معمولی Node.js معمولاً یک Event Loop اصلی برای اجرای JavaScript دارد.

اگر یک Server دارای:

```text
8 CPU Cores
```

باشد، اجرای فقط یک Process به این معنی نیست که تمام ظرفیت CPU برای اجرای JavaScript یک برنامه به‌صورت مستقیم مورد استفاده قرار می‌گیرد.

Cluster می‌تواند چند Process ایجاد کند:

```text
8 CPU Cores
     ↓
8 Worker Processes
```

البته تعداد Workerها باید بر اساس Workload واقعی انتخاب شود، نه صرفاً تعداد Coreها.

---

# 123.3 - Process چیست؟

قبل از یادگیری Cluster باید مفهوم Process را بدانیم.

Process یک نمونه در حال اجرای یک برنامه است.

مثلاً وقتی برنامه Node.js را اجرا می‌کنیم:

```bash
node server.js
```

یک Process ایجاد می‌شود.

به شکل ساده:

```text
Operating System
      │
      └── Node.js Process
              │
              ├── Event Loop
              ├── Memory
              └── JavaScript Execution
```

---

# 123.4 - Worker چیست؟

در Cluster، Worker به Processهایی گفته می‌شود که توسط Process اصلی ایجاد می‌شوند.

مثلاً:

```text
Primary
   │
   ├── Worker 1
   ├── Worker 2
   ├── Worker 3
   └── Worker 4
```

هر Worker Process مستقل خودش را دارد.

---

# 123.5 - Primary Process

در Cluster معمولاً یک Process اصلی داریم که مسئول مدیریت Workerها است.

در نسخه‌های جدید Node.js نام این Process معمولاً:

```text
Primary
```

است.

وظایفی مانند:

* ایجاد Worker
* مدیریت Workerها
* دریافت Eventهای Worker
* Restart کردن Workerهای از دست رفته
* Shutdown کردن Workerها

می‌توانند در این Process انجام شوند.

---

# 123.6 - Worker Process

Worker همان Processی است که Application واقعی را اجرا می‌کند.

مثلاً:

```js
app.listen(3000);
```

می‌تواند در Worker اجرا شود.

ساختار:

```text
Primary
   │
   ├── Worker
   │     └── Express
   │
   ├── Worker
   │     └── Express
   │
   └── Worker
         └── Express
```

# 123.7 - ماژول cluster

Node.js یک ماژول داخلی برای Cluster دارد:

```js
import cluster from "node:cluster";
```

همچنین برای تشخیص تعداد CPUها می‌توانیم از:

```js
import os from "node:os";
```

استفاده کنیم.

---

# 123.8 - تشخیص Primary و Worker

یکی از مفاهیم مهم:

```js
cluster.isPrimary
```

است.

مثلاً:

```js
import cluster from "node:cluster";

if (cluster.isPrimary) {
  console.log("Primary Process");
} else {
  console.log("Worker Process");
}
```

اگر Process اصلی باشد:

```text
cluster.isPrimary === true
```

و اگر Worker باشد:

```text
cluster.isPrimary === false
```

---

# 123.9 - ساخت اولین Cluster

یک مثال ساده:

```js
import cluster from "node:cluster";
import http from "node:http";

if (cluster.isPrimary) {
  cluster.fork();
  cluster.fork();
} else {
  const server = http.createServer(
    (req, res) => {
      res.end(
        `Worker: ${process.pid}`
      );
    }
  );

  server.listen(3000);
}
```

در این مثال:

```text
Primary
   │
   ├── Worker 1
   └── Worker 2
```

ایجاد می‌شود.

# 123.10 - process.pid

هر Process یک شناسه دارد که با:

```js
process.pid
```

قابل دسترسی است.

مثلاً:

```js
console.log(process.pid);
```

ممکن است خروجی:

```text

```

باشد.

برای Debug کردن Cluster، نمایش PID بسیار مفید است.

# 123.11 - تشخیص Worker

می‌توانیم PID Worker را در Response قرار دهیم:

```js
import http from "node:http";

const server = http.createServer(
  (req, res) => {
    res.end(
      `Worker PID: ${process.pid}`
    );
  }
);

server.listen(3000);
```

اگر چند درخواست ارسال کنیم، می‌توانیم ببینیم درخواست‌ها توسط Workerهای مختلف پردازش می‌شوند.

---

# 123.12 - cluster.fork()

برای ایجاد Worker از:

```js
cluster.fork();
```

استفاده می‌کنیم.

مثلاً:

```js
if (cluster.isPrimary) {
  cluster.fork();
  cluster.fork();
  cluster.fork();
} else {
  startServer();
}
```

در نتیجه Primary سه Worker ایجاد می‌کند.

---

# 123.13 - ایجاد Worker به تعداد CPU

یکی از روش‌های رایج:

```js
import os from "node:os";

const cpuCount =
  os.availableParallelism();
```

سپس:

```js
if (cluster.isPrimary) {
  for (
    let i = 0;
    i < cpuCount;
    i++
  ) {
    cluster.fork();
  }
} else {
  startServer();
}
```

این کار برنامه را قادر می‌کند چند Worker ایجاد کند.

اما:

> تعداد CPUها الزاماً تعداد بهینه Workerها نیست.

باید با Benchmark واقعی تصمیم بگیریم.

---

# 123.14 - os.availableParallelism()

در نسخه‌های جدید Node.js بهتر است برای تخمین میزان Parallelism قابل استفاده از:

```js
os.availableParallelism()
```

استفاده کنیم.

مثلاً:

```js
import os from "node:os";

console.log(
  os.availableParallelism()
);
```

این روش برای تعیین تعداد Workerها از روش‌های قدیمی‌تر مناسب‌تر است.

# 123.15 - Cluster و HTTP Server

یکی از کاربردهای رایج Cluster اجرای چند HTTP Server است.

مثلاً:

```text
                 Port 3000
                    │
          ┌─────────┼─────────┐
          ↓         ↓         ↓
       Worker 1  Worker 2  Worker 3
```

هر Worker می‌تواند Server خودش را داشته باشد.

# 123.16 - آیا همه Workerها یک Port دارند؟

بله، در سناریوی معمول Cluster می‌توان Workerها را روی یک Port اجرا کرد.

مثلاً:

```js
if (cluster.isPrimary) {
  cluster.fork();
  cluster.fork();
} else {
  app.listen(3000);
}
```

همه Workerها از:

```text
3000
```

استفاده می‌کنند.

Node.js و سیستم‌عامل مسئول هماهنگی لازم برای دریافت Connectionها هستند.

---

# 123.17 - Load Balancing در Cluster

وقتی چند Worker داریم، Connectionها باید بین آن‌ها توزیع شوند.

به‌صورت مفهومی:

```text
Client
   │
   ↓
Node.js Cluster
   │
   ├── Worker 1
   ├── Worker 2
   ├── Worker 3
   └── Worker 4
```

هدف این است که Workload بین Workerها توزیع شود.

# 123.18 - Cluster و Express

Cluster را می‌توان با Express ترکیب کرد.

مثلاً:

```bash
npm install express
```

سپس:

```js
import cluster from "node:cluster";
import os from "node:os";
import express from "express";

function startServer() {
  const app = express();

  app.get("/", (req, res) => {
    res.json({
      message: "Hello",
      pid: process.pid,
    });
  });

  app.listen(3000);
}

if (cluster.isPrimary) {
  const workers =
    os.availableParallelism();

  for (
    let i = 0;
    i < workers;
    i++
  ) {
    cluster.fork();
  }
} else {
  startServer();
}
```

# 123.20 - Memory در Cluster

یکی از نکات بسیار مهم:

> Workerها Memory مشترک ندارند.

مثلاً اگر Worker 1 داشته باشد:

```js
const users = [];
```

این Array در Memory همان Worker قرار دارد.

Worker 2 به همان Array دسترسی مستقیم ندارد.

ساختار:

```text
Worker 1
   │
   └── Memory A

Worker 2
   │
   └── Memory B
```

---

# 123.21 - مشکل In-Memory Cache

فرض کنید:

```js
const cache = new Map();
```

داریم.

اگر:

```text
Worker 1 → cache.set(...)
```

انجام دهد، Worker 2 لزوماً آن داده را در Cache خودش ندارد.

بنابراین:

```text
Worker 1
   └── Cache A

Worker 2
   └── Cache B
```

داریم.

---

# 123.22 - استفاده از Redis در Cluster

برای داشتن Cache مشترک بهتر است از یک Storage خارجی مانند Redis استفاده کنیم.

```text
Worker 1 ──┐
Worker 2 ──┤
Worker 3 ──┼──→ Redis
Worker 4 ──┘
```

در این حالت همه Workerها به یک Cache مشترک دسترسی دارند.

این یکی از دلایل اهمیت Redis در معماری‌های چند Process است.

---

# 123.23 - Session در Cluster

فرض کنید Session را داخل Memory نگه داریم:

```js
const sessions = new Map();
```

ممکن است:

```text
Request 1 → Worker 1
Request 2 → Worker 2
```

باشد.

Worker 2 Session ساخته‌شده در Worker 1 را نمی‌بیند.

این موضوع می‌تواند باعث مشکلات Session شود.

راهکارهای رایج:

```text
Redis
Database
Shared Session Store
```

هستند.

---

# 123.24 - Sticky Sessions

یکی از راهکارهای ممکن:

```text
Client
  ↓
Worker 1
  ↓
Worker 1
  ↓
Worker 1
```

است.

یعنی Requestهای یک Client تا حد امکان به یک Worker خاص هدایت شوند.

به این مفهوم:

```text
Sticky Session
```

گفته می‌شود.

اما Sticky Session همیشه بهترین راه‌حل نیست و طراحی Stateless همراه با Storage مشترک در بسیاری از سیستم‌ها انعطاف‌پذیری بیشتری دارد.

---

# 123.25 - Cluster و WebSocket

WebSocket در معماری Cluster نیازمند توجه بیشتری است.

فرض کنید:

```text
Client A
   ↓
Worker 1
```

و:

```text
Client B
   ↓
Worker 2
```

اگر Workerها بخواهند Eventها را با یکدیگر Share کنند، باید مکانیزم ارتباطی مناسبی داشته باشند.

Redis Pub/Sub یا معماری‌های مشابه می‌توانند در چنین سناریوهایی استفاده شوند.

# 123.26 - Worker Crash

یکی از مزایای مهم داشتن Primary این است که می‌توانیم خروج Workerها را تشخیص دهیم.

مثلاً:

```js
cluster.on(
  "exit",
  (worker) => {
    console.log(
      `Worker ${worker.process.pid} exited`
    );
  }
);
```

---

# 123.27 - Restart کردن Worker

می‌توان Worker جدید ایجاد کرد:

```js
cluster.on(
  "exit",
  (worker) => {
    console.log(
      `Worker ${worker.process.pid} died`
    );

    cluster.fork();
  }
);
```

در این حالت اگر Worker از بین برود، Primary Worker جدیدی ایجاد می‌کند.

---

# 123.28 - مراقب Restart Loop باشید

کد زیر می‌تواند خطرناک باشد:

```js
cluster.on("exit", () => {
  cluster.fork();
});
```

اگر Worker بلافاصله بعد از Startup Crash کند:

```text
Worker Crash
   ↓
Restart
   ↓
Crash
   ↓
Restart
   ↓
Crash
```

ممکن است وارد Restart Loop شویم.

در Production باید:

* تعداد Crashها
* فاصله زمانی Restart
* علت Crash
* Health Status

را کنترل کنیم.

---

# 123.29 - Worker Lifecycle

چرخه Worker را می‌توان این‌گونه دید:

```text
fork()
  ↓
online
  ↓
listening
  ↓
running
  ↓
disconnect / exit
```

Eventهای مختلف Cluster می‌توانند برای Monitoring استفاده شوند.

---

# 123.30 - Event مربوط به Online

مثلاً:

```js
cluster.on(
  "online",
  (worker) => {
    console.log(

  }
);
```

این Event زمانی مفید است که بخواهیم Startup Workerها را مشاهده کنیم.

# 123.31 - Event مربوط به Listening

می‌توان وضعیت Listening را نیز بررسی کرد:

```js
cluster.on(
  "listening",

      `Worker ${worker.process.pid} listening on ${address.port}`

  }

```

# 123.32 - Worker.disconnect()

می‌توان Worker را از Cluster خارج کرد.

مثلاً:

```js
worker.disconnect();
```

این موضوع در Shutdown کنترل‌شده اهمیت دارد.

# 123.33 - Graceful Shutdown

در Production نباید هنگام Deploy یا Shutdown ناگهانی Connectionهای فعال را قطع کنیم.

بهتر است:

```text
Stop accepting new work
        ↓
Finish active requests
        ↓
Close connections
        ↓
Exit
```

را دنبال کنیم.

---

# 123.34 - Cluster و Graceful Restart

در Deployment می‌توان Workerهای قدیمی را به شکل تدریجی خارج کرد و Workerهای جدید را وارد کرد.

مثلاً:

```text
Old Worker 1
Old Worker 2
     ↓
New Worker 1
New Worker 2
```

هدف این است که سرویس تا حد ممکن بدون Downtime باقی بماند.

---

# 123.35 - Cluster و Zero Downtime

Cluster به‌تنهایی تضمین نمی‌کند که Deployment شما Zero Downtime باشد.

اما می‌تواند بخشی از معماری برای:

```text
Rolling Restart
Graceful Shutdown
Worker Replacement
```

باشد.

در Production معمولاً ابزارهای دیگری مانند:

```text
Load Balancer
Reverse Proxy
Container Orchestrator
Process Manager
```

نیز در کنار آن قرار می‌گیرند.

# 123.36 - Cluster در برابر Worker Threads

Cluster و Worker Threads یکی نیستند.

### Cluster

```text
Multiple Processes
```

هر Worker:

```text
Process مستقل
Memory مستقل
Event Loop مستقل
```

دارد.

### Worker Threads

```text
Multiple Threads
داخل یک Process
```

هستند.

# 123.37 - چه زمانی Cluster؟

Cluster بیشتر برای اجرای چند Process از Server استفاده می‌شود.

مثلاً:

```text
HTTP Server
API Server
Web Server
```

در چند Process.

# 123.38 - چه زمانی Worker Threads؟

Worker Threads برای اجرای کارهای CPU-intensive داخل Threadهای جداگانه مناسب‌تر هستند.

مثلاً:

```text
Image Processing
Complex Calculation
CPU-heavy Algorithm
```

البته انتخاب نهایی به معماری برنامه بستگی دارد.

Child Process کاربرد عمومی‌تری دارد و می‌تواند برای اجرای Processهای مختلف استفاده شود.

مثلاً:

```text
Node.js
   ├── Cluster Workers
   │
   └── Other Child Processes
```

* Database
* Redis
* External Services

را نیز بررسی کند.

---

# 123.46 - Cluster و Scaling

Cluster بیشتر برای:

```text
Vertical Scaling
```

در یک Server مناسب است.

مثلاً:

```text
1 Server
   ↓
Multiple Node.js Workers
```

اما برای:

```text
Horizontal Scaling
```

می‌توان چند Server یا Container داشت:

```text
Load Balancer
   │
   ├── Server 1
   │     ├── Worker
   │     └── Worker
   │
   ├── Server 2
   │     ├── Worker
   │     └── Worker
   │
   └── Server 3
         ├── Worker
         └── Worker
```

---

# 123.47 - آیا همیشه به Cluster نیاز داریم؟

خیر.

اگر برنامه:

* Traffic کمی دارد
* CPU محدودیت ندارد
* روی Container اجرا می‌شود
* توسط Orchestrator مدیریت می‌شود

ممکن است Cluster انتخاب مناسبی نباشد.

گاهی بهتر است یک Process Node.js داشته باشیم و Scaling را در سطح Container یا Server انجام دهیم.

---

# 123.48 - Cluster و Docker

در محیط‌های Containerized باید با دقت تصمیم بگیریم.

مثلاً:

```text
Docker Container
   ↓
Node.js Cluster
   ↓
Multiple Workers
```

یا:

```text
Docker Container 1 → Node.js
Docker Container 2 → Node.js
Docker Container 3 → Node.js
```

هر دو معماری ممکن هستند.

در محیط‌هایی مانند Kubernetes، گاهی ترجیح داده می‌شود هر Container یک Process اصلی داشته باشد و Scaling توسط Orchestrator انجام شود.

---

# 123.49 - Cluster و Kubernetes

در معماری Kubernetes معمولاً:

```text
Kubernetes
   ↓
Multiple Pods
   ↓
Node.js Process
```

داریم.

در چنین محیطی ممکن است استفاده از Cluster داخل هر Pod ضروری نباشد.

باید بین:

```text
Process Scaling
Container Scaling
Pod Scaling
```

تصمیم درستی گرفته شود.

---

# 123.50 - Cluster و Performance

هدف Cluster این نیست که هر برنامه‌ای را چند برابر سریع‌تر کند.

Cluster بیشتر می‌تواند:

```text
CPU Utilization
Throughput
Concurrency
Availability
```

را در شرایط مناسب بهبود دهد.

اما نتیجه واقعی به Workload بستگی دارد.

---

# 123.51 - CPU-bound در برابر I/O-bound

اگر برنامه بیشتر:

```text
I/O-bound
```

باشد، Node.js می‌تواند با Event Loop عملکرد خوبی داشته باشد و Cluster همیشه اولین راهکار نیست.

اگر برنامه CPU زیادی مصرف کند:

```text
CPU-bound
```

استفاده از چند Process می‌تواند کمک‌کننده باشد.

اما برای محاسبات سنگین داخل JavaScript، Worker Threads نیز باید بررسی شوند.

# اشتباهات رایج

## 1. فرض کردن اینکه Cluster همیشه Performance را افزایش می‌دهد

Cluster یک ابزار است، نه یک دکمه جادویی برای افزایش Performance.

---

## 2. ایجاد Worker بیشتر از نیاز

اگر Server فقط 2 Core قابل استفاده داشته باشد، ایجاد Workerهای بسیار زیاد می‌تواند باعث:

```text

CPU Overhead
Memory Usage
```

شود.

---

## 3. نگه داشتن State داخل Memory

مثلاً:

```js
const users = new Map();
```

در یک Worker با Workerهای دیگر Shared نیست.

---

## 4. استفاده از In-Memory Session

Session داخل Memory یک Worker ممکن است در Request بعدی در Worker دیگری وجود نداشته باشد.

---

## 5. نادیده گرفتن Database Connections

افزایش Workerها ممکن است تعداد Connectionهای Database را نیز افزایش دهد.

---

## 6. Restart کردن Worker بدون محدودیت

اگر Worker دائماً Crash کند، Restart بدون کنترل می‌تواند سیستم را وارد Loop کند.

---

## 7. تصور اینکه Cluster جای Load Balancer است

Cluster جایگزین کامل Load Balancer در معماری‌های بزرگ نیست.

---

## 8. استفاده از Cluster بدون Monitoring

اگر Workerها Crash شوند و شما متوجه نشوید، مشکل Production ممکن است پنهان بماند.

---

## 9. استفاده از Cluster برای CPU-heavy Task بدون بررسی Worker Threads

برای بعضی محاسبات CPU-intensive، Worker Threads ممکن است گزینه مناسب‌تری باشند.

---

## 10. فرض کردن Shared Memory

Workerها Memory مشترک ندارند.

---

> **Cluster با ایجاد چند Process مستقل به Node.js اجازه می‌دهد از ظرفیت چند CPU Core استفاده کند، اما این کار باعث Shared شدن Memory نمی‌شود. بنابراین در یک معماری Cluster باید State، Cache، Session و سایر داده‌های مشترک را با دقت طراحی کنیم.**

همچنین باید به یاد داشته باشیم که **Cluster تنها یکی از روش‌های Scaling در Node.js است**. در پروژه‌های مدرن، بسته به معماری ممکن است استفاده از چند Container، Load Balancer و ابزارهایی مانند Kubernetes انتخاب مناسب‌تری نسبت به اجرای تعداد زیادی Worker داخل یک Process باشد.
