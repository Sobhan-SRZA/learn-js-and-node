# فصل 122 - Compression

## مقدمه

در فصل‌های قبل با مفاهیم **Performance Optimization**، **Cache** و **Redis** آشنا شدیم و دیدیم که یکی از اهداف مهم در Backend کاهش زمان پاسخ‌گویی و مصرف منابع است.

یکی دیگر از روش‌های مهم برای بهبود Performance، **Compression** یا فشرده‌سازی داده‌هاست.

وقتی Node.js یک Response را به Client ارسال می‌کند، ممکن است حجم زیادی داده منتقل شود:

```text
Node.js
   ↓
JSON Response
   ↓
Network
   ↓
Browser
```

فرض کنید API ما چنین داده‌ای برگرداند:

```json
{
  "id": 1,
  "name": "Ali",
  "description": "This is a very long description..."
}
```

اگر Response حجم زیادی داشته باشد، ارسال آن از طریق Network می‌تواند زمان بیشتری مصرف کند.

با Compression می‌توان داده را قبل از ارسال فشرده کرد:

```text
Node.js
   ↓
Response
   ↓
Compression
   ↓
Compressed Response
   ↓
Network
   ↓
Browser
   ↓
Decompression
```

در نتیجه حجم داده‌ای که از Server به Client منتقل می‌شود کاهش پیدا می‌کند.

---

# 122.1 - Compression چیست؟

Compression یعنی کاهش حجم داده بدون از بین بردن اطلاعات اصلی.

مثلاً ممکن است داده‌ای:

```text
100 KB
```

حجم داشته باشد و بعد از Compression به:

```text
25 KB
```

برسد.

در این حالت اطلاعات اصلی تغییر نکرده‌اند، اما حجم انتقال‌یافته کمتر شده است.

---

# 122.2 - چرا Compression مهم است؟

در Backend، یکی از هزینه‌های مهم:

```text
Network Transfer
```

است.

اگر Response بزرگ باشد:

```text
Response Size ↑
      ↓
Network Transfer ↑
      ↓
Response Time ↑
```

Compression می‌تواند حجم Response را کاهش دهد:

```text
Response Size ↓
      ↓
Network Transfer ↓
      ↓
Bandwidth Usage ↓
```

بنابراین مخصوصاً برای Responseهای متنی و بزرگ می‌تواند مفید باشد.

---

# 122.3 - Compression در Node.js

در Node.js می‌توان Responseها را با الگوریتم‌های مختلف فشرده کرد.

الگوریتم‌های مهم:

```text
Gzip
Brotli
Deflate
```

در پروژه‌های Web، معمولاً:

```text
gzip
br
```

بیشتر مورد توجه هستند.

---

# 122.4 - Compression در HTTP

Client می‌تواند به Server اعلام کند که چه نوع Compressionهایی را پشتیبانی می‌کند.

مثلاً Browser ممکن است Header زیر را ارسال کند:

```http
Accept-Encoding: gzip, deflate, br
```

یعنی Client می‌گوید:

> من می‌توانم Responseهای فشرده‌شده با این Encodingها را دریافت کنم.

Server سپس می‌تواند یکی از Encodingهای مناسب را انتخاب کند.

---

# 122.5 - Content-Encoding

وقتی Response فشرده می‌شود، Server باید مشخص کند داده با چه الگوریتمی فشرده شده است.

مثلاً:

```http
Content-Encoding: gzip
```

یا:

```http
Content-Encoding: br
```

Browser با مشاهده این Header متوجه می‌شود که Response باید Decode شود.

---

# 122.6 - Accept-Encoding

Header:

```http
Accept-Encoding
```

توسط Client برای اعلام Encodingهای قابل پشتیبانی استفاده می‌شود.

مثلاً:

```http
Accept-Encoding: gzip, deflate, br
```

این Header به Server کمک می‌کند مناسب‌ترین روش Compression را انتخاب کند.

---

# 122.7 - Content-Encoding در مقابل Content-Type

این دو Header را نباید با یکدیگر اشتباه بگیریم.

مثلاً:

```http
Content-Type: application/json
Content-Encoding: gzip
```

یعنی:

```text
نوع داده = JSON
روش فشرده‌سازی = gzip
```

پس Compression نوع داده را تغییر نمی‌دهد.

---

# 122.8 - Gzip چیست؟

Gzip یکی از الگوریتم‌های بسیار رایج برای فشرده‌سازی داده‌های Web است.

برای داده‌های متنی مانند:

* HTML
* CSS
* JavaScript
* JSON
* XML
* SVG

معمولاً می‌تواند حجم را به مقدار قابل توجهی کاهش دهد.

---

# 122.9 - Brotli چیست؟

**Brotli** الگوریتم Compression دیگری است که برای Web طراحی شده و توسط مرورگرهای مدرن پشتیبانی می‌شود.

در بسیاری از موارد Brotli می‌تواند نسبت Compression خوبی ارائه دهد.

مثلاً:

```text
JSON
 ↓
Brotli
 ↓
Compressed JSON
```

در Web مدرن، Brotli یکی از گزینه‌های مهم برای Response Compression است.

---

# 122.10 - Deflate چیست؟

Deflate نیز یکی از روش‌های قدیمی‌تر Compression در HTTP است.

در پروژه‌های جدید معمولاً Gzip و Brotli انتخاب‌های رایج‌تری هستند، اما شناخت Deflate برای درک HTTP Compression مفید است.

---

# 122.11 - Compression و CPU

Compression رایگان نیست.

Server باید داده را فشرده کند و این عملیات CPU مصرف می‌کند.

بنابراین:

```text
Compression
   ↓
Network Usage ↓
CPU Usage ↑
```

ممکن است اتفاق بیفتد.

هدف این است که بین:

```text
CPU Cost
```

و:

```text
Network Cost
```

تعادل مناسبی برقرار کنیم.

---

# 122.12 - Compression و Bandwidth

فرض کنید Response بدون Compression:

```text
1 MB
```

باشد.

اگر Compression حجم آن را به:

```text
250 KB
```

برساند، مقدار داده منتقل‌شده بسیار کمتر خواهد شد.

برای APIهایی که Responseهای بزرگی دارند، این موضوع می‌تواند اهمیت زیادی داشته باشد.

---

# 122.13 - Compression برای چه داده‌هایی مناسب است؟

Compression معمولاً برای داده‌های متنی بسیار مفید است.

مثلاً:

```text
JSON
HTML
CSS
JavaScript
XML
SVG
```

اما برای داده‌هایی که از قبل فشرده شده‌اند، سود Compression معمولاً بسیار کمتر است.

مثلاً:

```text
JPEG
PNG
WebP
MP4
ZIP
PDF
```

بسته به محتوا ممکن است Compression مجدد سود کمی داشته باشد یا حتی باعث افزایش حجم و مصرف CPU شود.

---

# 122.14 - Compression در Express

در Express می‌توان از Middleware مربوط به Compression استفاده کرد.

ابتدا:

```bash
npm install compression
```

سپس:

```js
import compression from "compression";

app.use(compression());
```

اکنون Middleware می‌تواند Responseهای مناسب را فشرده کند.

---

# 122.15 - یک مثال ساده

```js
import express from "express";
import compression from "compression";

const app = express();

app.use(compression());

app.get("/data", (req, res) => {
  res.json({
    message: "Hello Node.js",
  });
});

app.listen(3000);
```

اگر Client از Compression پشتیبانی کند، Middleware می‌تواند Response را فشرده کند.

---

# 122.16 - Compression Middleware چگونه کار می‌کند؟

به شکل ساده:

```text
Client
   │
   │ Accept-Encoding
   ▼
Express
   │
   ▼
compression middleware
   │
   ▼
Response
   │
   ▼
Compressed Response
```

Middleware قبل از ارسال Response بررسی می‌کند که آیا امکان Compression وجود دارد یا خیر.

---

# 122.17 - بررسی Headerها

در یک Response فشرده ممکن است چیزی شبیه این ببینیم:

```http
Content-Type: application/json
Content-Encoding: gzip
```

این یعنی Response:

```text
JSON
```

بوده و سپس با:

```text
gzip
```

فشرده شده است.

---

# 122.18 - Threshold

لازم نیست Responseهای بسیار کوچک را فشرده کنیم.

برای مثال، فشرده کردن:

```text
100 bytes
```

ممکن است ارزش CPU مصرف‌شده را نداشته باشد.

به همین دلیل می‌توان یک Threshold مشخص کرد.

مثلاً:

```js
app.use(
  compression({
    threshold: "1kb",
  })
);
```

در این حالت Responseهای کوچک‌تر از Threshold معمولاً Compression نمی‌شوند.

---

# 122.19 - چرا Response کوچک را Compress نکنیم؟

Compression خودش Overhead دارد.

برای داده بسیار کوچک:

```text
Compression Cost
>
Network Saving
```

ممکن است باشد.

بنابراین Threshold می‌تواند از Compression غیرضروری جلوگیری کند.

---

# 122.20 - Compression و JSON

یکی از بهترین موارد استفاده Compression در APIها:

```text
JSON
```

است.

مثلاً API:

```http
GET /users
```

ممکن است هزاران User برگرداند.

بدون Compression:

```text
Large JSON
   ↓
Network
```

با Compression:

```text
Large JSON
   ↓
gzip / Brotli
   ↓
Small Response
   ↓
Network
```

---

# 122.21 - Compression و REST API

در APIهای REST، Responseها معمولاً JSON هستند.

مثلاً:

```json
{
  "products": [
    {
      "id": 1,
      "name": "Laptop"
    },
    {
      "id": 2,
      "name": "Phone"
    }
  ]
}
```

اگر تعداد رکوردها زیاد باشد، Compression می‌تواند حجم Response را به شکل قابل توجهی کاهش دهد.

---

# 122.22 - Compression و Static Files

Compression فقط برای API نیست.

فایل‌هایی مانند:

```text
JavaScript
CSS
HTML
SVG
```

نیز می‌توانند فشرده شوند.

مثلاً:

```text
app.js
   ↓
Compression
   ↓
Browser
```

---

# 122.23 - Compression و Static Middleware

در Express ممکن است Static Fileها را با:

```js
app.use(express.static("public"));
```

ارائه کنیم.

Compression Middleware می‌تواند در مسیر مناسب روی Responseهای قابل فشرده‌سازی اثر بگذارد:

```js
app.use(compression());

app.use(express.static("public"));
```

البته در Production باید بررسی کنیم که آیا Reverse Proxy یا CDN از قبل Compression را انجام می‌دهد یا خیر.

---

# 122.24 - Compression در Reverse Proxy

در معماری Production ممکن است ساختار چنین باشد:

```text
Client
   ↓
Nginx / CDN
   ↓
Node.js
```

ممکن است Compression را به جای Node.js در Reverse Proxy انجام دهیم.

در این حالت:

```text
Node.js
   ↓
Uncompressed Response
   ↓
Nginx
   ↓
Compressed Response
   ↓
Client
```

مزیت این روش می‌تواند کاهش بار CPU روی Node.js باشد.

---

# 122.25 - Compression در CDN

CDNها نیز می‌توانند Responseها را در Edge Locationها فشرده کنند.

معماری:

```text
Client
   ↓
CDN
   ↓
Node.js
```

ممکن است CDN:

* Cache
* Compression
* TLS Termination
* Content Delivery

را مدیریت کند.

---

# 122.26 - Compression و Cache

Compression و Cache می‌توانند در کنار یکدیگر استفاده شوند.

مثلاً:

```text
Client
   ↓
CDN / Cache
   ↓
Compressed Response
```

اما باید به نحوه Cache کردن Representationهای مختلف توجه کرد.

مثلاً Client A:

```http
Accept-Encoding: gzip
```

و Client B:

```http
Accept-Encoding: br
```

ممکن است Representation متفاوتی دریافت کنند.

---

# 122.27 - Vary Header

وقتی Response بر اساس یک Request Header متفاوت تولید می‌شود، Header زیر اهمیت پیدا می‌کند:

```http
Vary: Accept-Encoding
```

این Header به Cacheها می‌گوید که Representation Response به مقدار `Accept-Encoding` وابسته است.

مثلاً:

```http
Vary: Accept-Encoding
Content-Encoding: br
```

---

# 122.28 - Compression و Streaming

Compression می‌تواند با Streamها نیز ترکیب شود.

به جای اینکه تمام داده را ابتدا در Memory قرار دهیم:

```text
Large Data
   ↓
Memory
   ↓
Compress
   ↓
Response
```

می‌توان در بعضی سناریوها:

```text
Data Stream
   ↓
Compression Stream
   ↓
Network
```

داشت.

این روش برای داده‌های بسیار بزرگ اهمیت بیشتری پیدا می‌کند.

---

# 122.29 - Node.js zlib

Node.js ماژول داخلی:

```text
zlib
```

را برای کار با Compression در اختیار ما قرار می‌دهد.

مثلاً:

```js
import { gzip } from "node:zlib";
```

و APIهای Promise:

```js
import { gzip } from "node:zlib/promises";
```

نیز قابل استفاده هستند.

---

# 122.30 - Gzip با zlib

مثلاً:

```js
import { gzip } from "node:zlib/promises";

const data = "Hello Node.js";

const compressed = await gzip(data);

console.log(compressed);
```

خروجی یک Buffer فشرده‌شده است.

---

# 122.31 - Unzip

برای باز کردن داده Gzip:

```js
import {
  gunzip,
} from "node:zlib/promises";

const original =
  await gunzip(compressed);

console.log(
  original.toString()
);
```

---

# 122.32 - Brotli با zlib

Node.js از Brotli نیز پشتیبانی می‌کند.

مثلاً:

```js
import {
  brotliCompress,
} from "node:zlib/promises";

const compressed =
  await brotliCompress(
    "Hello Node.js"
  );
```

برای Decompression نیز API متناظر وجود دارد.

---

# 122.33 - Compression در سطح Application یا Infrastructure؟

دو انتخاب رایج داریم:

```text
Application
Node.js
```

یا:

```text
Infrastructure
Nginx / CDN
```

هر دو می‌توانند مناسب باشند.

اگر Node.js مستقیماً به Client پاسخ می‌دهد، Compression Middleware می‌تواند انتخاب ساده‌ای باشد.

اگر Architecture دارای CDN یا Reverse Proxy است، بهتر است بررسی کنیم کدام لایه مسئول Compression باشد.

---

# 122.34 - Compression و HTTPS

Compression و Encryption دو موضوع متفاوت هستند.

معماری:

```text
Response
   ↓
Compression
   ↓
Encryption / TLS
   ↓
Network
```

به صورت مفهومی، داده ابتدا فشرده و سپس در لایه TLS محافظت می‌شود.

---

# 122.35 - خطر Compression در داده‌های حساس

Compression روی داده‌های حساس نیازمند دقت است.

ترکیب:

```text
Secret Data
+
Compression
+
Attacker-controlled Input
+
Encrypted Connection
```

در برخی سناریوهای خاص می‌تواند به حملات جانبی مانند:

```text
BREACH
```

مرتبط شود.

بنابراین نباید Compression را صرفاً یک گزینه بدون ملاحظات امنیتی در نظر گرفت، مخصوصاً برای Responseهایی که هم Secret دارند و هم داده قابل کنترل توسط مهاجم در همان Context قرار می‌گیرد.

---

# 122.36 - Compression Level

برخی الگوریتم‌ها امکان تعیین Compression Level دارند.

به شکل مفهومی:

```text
Compression Level
      ↓
CPU Usage ↑
      ↓
Compression Ratio ↑
```

اما رابطه دقیق به الگوریتم و داده بستگی دارد.

Compression بیشتر لزوماً همیشه بهترین انتخاب نیست.

---

# 122.37 - Trade-off

در Performance باید این سه عامل را همزمان در نظر بگیریم:

```text
CPU
Memory
Network
```

مثلاً:

```text
Compression زیاد
    ↓
CPU ↑
Network ↓
```

یا:

```text
Compression کم
    ↓
CPU ↓
Network ↑
```

هدف پیدا کردن نقطه مناسب برای Workload واقعی است.

---

# 122.38 - چه Responseهایی را Compress کنیم؟

معمولاً مواردی مانند:

```text
application/json
text/html
text/css
application/javascript
image/svg+xml
application/xml
```

کاندیدهای مناسبی هستند.

اما تصمیم نهایی باید بر اساس اندازه Response، نوع داده و معماری سیستم باشد.

---

# 122.39 - چه Responseهایی را Compress نکنیم؟

معمولاً فایل‌هایی که از قبل فشرده شده‌اند کاندید خوبی نیستند:

```text
JPEG
PNG
WebP
MP4
ZIP
GZIP
```

البته تصمیم نهایی باید با Benchmark واقعی گرفته شود.

---

# 122.40 - Compression و Performance

Compression می‌تواند:

```text
Bandwidth ↓
Response Size ↓
Network Transfer ↓
```

را به همراه داشته باشد.

اما:

```text
CPU ↑
```

نیز ممکن است رخ دهد.

بنابراین Compression بخشی از Performance Optimization است، نه اینکه همیشه و در هر شرایطی باعث سریع‌تر شدن برنامه شود.

---

# اشتباهات رایج

## 1. فشرده‌سازی همه چیز

اینکه برای همه Responseها Compression فعال کنیم لزوماً تصمیم خوبی نیست.

---

## 2. Compression فایل‌های از قبل فشرده‌شده

مثلاً:

```text
JPEG
PNG
ZIP
MP4
```

معمولاً سود زیادی از Compression مجدد نمی‌برند.

---

## 3. نادیده گرفتن CPU

Compression CPU مصرف می‌کند.

اگر Server CPU-bound باشد، Compression شدید می‌تواند Performance را بدتر کند.

---

## 4. استفاده از Compression روی Responseهای بسیار کوچک

برای Responseهای کوچک ممکن است Overhead Compression بیشتر از سود آن باشد.

---

## 5. Compression در چند لایه بدون بررسی

مثلاً:

```text
Node.js
   ↓
Nginx
   ↓
CDN
```

اگر همه لایه‌ها بدون هماهنگی Compression انجام دهند، ممکن است رفتار نامناسب یا پردازش غیرضروری ایجاد شود.

---

## 6. فراموش کردن Accept-Encoding

Server نباید فرض کند تمام Clientها تمام Compressionها را پشتیبانی می‌کنند.

---

## 7. نادیده گرفتن Vary

در سیستم‌هایی که Cache بین Encodingهای مختلف وجود دارد، `Vary: Accept-Encoding` می‌تواند مهم باشد.

---

## 8. Compression روی داده‌های حساس بدون بررسی امنیت

در سیستم‌های حساس باید Side Channelهای مرتبط با Compression را در نظر گرفت.

---

## 9. انتخاب Compression Level بالا بدون Benchmark

Compression Level بیشتر لزوماً بهترین انتخاب Production نیست.

---

## 10. Compress کردن Responseهای بزرگ بدون بررسی Streaming

برای داده‌های بسیار بزرگ باید Memory Usage و امکان Streaming را نیز بررسی کنیم.

---

# نکات حرفه‌ای

## 1. ابتدا اندازه‌گیری کنید

قبل از فعال کردن Compression:

```text
Response Size
```

# مرحله 5 - Cache

```js
import client from "./redis.js";

export async function getCache(key) {
  const data = await client.get(key);

  if (!data) {
    return null;
  }

  return JSON.parse(data);
}

export async function setCache(
  key,
  value
) {
  await client.set(
    key,
    JSON.stringify(value),
    {
      EX: 60,
    }
  );
}
```

# مرحله 6 - Service

```js
import {
  getProducts,
} from "./database.js";

import {
  getCache,
  setCache,
} from "./cache.js";

export async function findProducts(
  page,
  limit
) {
  const key =
    `products:${page}:${limit}`;

  const cached =
    await getCache(key);

  if (cached) {
    return cached;
  }

  const products =
    await getProducts(
      page,
      limit
    );

  await setCache(
    key,
    products
  );

  return products;
}
```

# مرحله 7 - Server

```js
import "dotenv/config";

import express from "express";
import compression from "compression";

import {
  findProducts,
} from "./product.service.js";

const app = express();

app.use(
  compression({
    threshold: "1kb",
  })
);

app.get(
  "/products",
  async (req, res) => {
    const page =
      Number(req.query.page) || 1;

    const limit =
      Number(req.query.limit) || 20;

    const products =
      await findProducts(
        page,
        limit
      );

    res.json({
      page,
      limit,
      products,
    });
  }
);

app.listen(
  process.env.PORT,
  () => {
    console.log(
      `Server running on ${process.env.PORT}`
    );
  }
);
```
