# فصل 125 - Profiling

## مقدمه

در فصل‌های قبلی بخش Performance یاد گرفتیم که چگونه با روش‌هایی مانند **Performance Optimization، Cache، Redis، Compression، Cluster و Load Balancing** عملکرد برنامه‌های Node.js را بهتر کنیم. این فصل به یکی از مهم‌ترین مهارت‌های یک برنامه‌نویس حرفه‌ای اختصاص دارد: **Profiling**.

فصل 125 در مستند اصلی نیز در بخش **Performance** و بعد از Load Balancing قرار گرفته است. 

اما قبل از اینکه چیزی را بهینه کنیم، باید بدانیم **دقیقاً چه چیزی کند است**.

یکی از اشتباهات رایج در Performance این است که برنامه‌نویس بر اساس حدس شروع به تغییر کد می‌کند:

```text
"احتمالاً این تابع کند است."

"احتمالاً Database مشکل دارد."

"باید Cache اضافه کنیم."

"شاید Node.js مشکل دارد."
```

این روش قابل اعتماد نیست.

روش حرفه‌ای این است:

```text
Measure
   ↓
Profile
   ↓
Find Bottleneck
   ↓
Analyze
   ↓
Optimize
   ↓
Measure Again
```

به این فرآیند **Profiling** می‌گوییم.

Profiling به ما کمک می‌کند بفهمیم برنامه در زمان اجرا چه مقدار CPU، Memory، I/O و سایر منابع را مصرف می‌کند و زمان اجرای برنامه بیشتر در کدام قسمت‌ها صرف می‌شود.

---

# 125.1 - Profiling چیست؟

**Profiling** فرآیند اندازه‌گیری و بررسی رفتار یک برنامه در زمان اجرا است.

با Profiling می‌توانیم سؤالاتی مانند این‌ها را پاسخ دهیم:

* کدام Function بیشتر CPU مصرف می‌کند؟
* کدام Function بیشتر اجرا می‌شود؟
* کدام قسمت برنامه بیشترین زمان را مصرف می‌کند؟
* آیا Memory Leak داریم؟
* Heap چقدر Memory مصرف می‌کند؟
* Garbage Collection چه مقدار فعالیت دارد؟
* Event Loop چقدر تحت فشار است؟
* آیا یک عملیات Synchronous باعث Block شدن Event Loop شده است؟
* آیا Bottleneck در Application است یا Database؟
* آیا یک Dependency باعث کندی شده است؟

---

# 125.2 - چرا Profiling مهم است؟

فرض کنید API ما کند شده است:

```text
GET /users
        ↓
      2.5s
```

ممکن است مشکل یکی از موارد زیر باشد:

```text
Application Code
Database
Network
External API
CPU
Memory
Garbage Collection
Serialization
File System
```

بدون Profiling فقط حدس می‌زنیم.

اما با Profiling می‌توانیم بفهمیم:

```text
Request: 2500ms

Database:       100ms
External API:   200ms
JavaScript:    2100ms
```

حالا مشخص است که مشکل اصلی کجاست.

---

# 125.3 - Profiling و Benchmark چه تفاوتی دارند؟

این دو مفهوم بسیار مهم هستند.

### Benchmark

می‌پرسد:

> این برنامه چقدر سریع است؟

مثلاً:

```text
Requests/sec = 5000
```

### Profiling

می‌پرسد:

> چرا این برنامه این‌قدر سریع یا کند است؟

مثلاً:

```text
Function A → 5%
Function B → 15%
Function C → 70%
```

پس:

```text
Benchmark → اندازه‌گیری Performance
Profiling  → پیدا کردن علت Performance
```

---

# 125.4 - Profiling و Monitoring

Monitoring و Profiling نیز یکسان نیستند.

### Monitoring

برای مشاهده وضعیت سیستم در طول زمان استفاده می‌شود:

```text
CPU
Memory
Latency
Error Rate
Requests
```

### Profiling

معمولاً برای بررسی عمیق‌تر رفتار برنامه و پیدا کردن Bottleneck استفاده می‌شود.

مثلاً Monitoring می‌گوید:

```text
CPU = 95%
```

اما Profiling می‌تواند نشان دهد:

```text
calculateReport()
→ 72% CPU
```

---

# 125.5 - Bottleneck چیست؟

**Bottleneck** بخشی از سیستم است که عملکرد کلی را محدود می‌کند.

مثلاً:

```text
Client
  ↓
Node.js
  ↓
Database
  ↓
External API
```

اگر Database بسیار کند باشد:

```text
Node.js → 20ms
Database → 2000ms
```

Database Bottleneck است.

یا اگر یک Function CPU زیادی مصرف کند:

```text
Database → 20ms
JavaScript → 2500ms
```

Application Code Bottleneck است.

---

# 125.6 - CPU Profiling

CPU Profiling یکی از مهم‌ترین انواع Profiling در Node.js است.

هدف:

> پیدا کردن Functionهایی که بیشترین زمان CPU را مصرف می‌کنند.

مثلاً:

```text
Function A → 5%
Function B → 10%
Function C → 80%
Function D → 5%
```

در این حالت ابتدا باید Function C را بررسی کنیم.

---

# 125.7 - CPU Profile

یک CPU Profile می‌تواند اطلاعاتی مانند این ارائه کند:

```text
Function
Self Time
Total Time
Call Count
Call Stack
```

دو مفهوم مهم:

### Self Time

زمانی که خود Function صرف اجرای عملیات کرده است.

### Total Time

زمان اجرای Function به همراه Functionهایی که از داخل آن فراخوانی شده‌اند.

---

# 125.8 - Call Stack در Profiling

در Profiling معمولاً Call Stack اهمیت زیادی دارد.

مثلاً:

```text
main()
  └── generateReport()
        └── calculate()
              └── heavyOperation()
```

اگر `heavyOperation()` زمان زیادی مصرف کند، باید مسیر اجرای آن را بررسی کنیم.

این موضوع به مفاهیمی مانند **Call Stack** که در بخش مفاهیم پیشرفته JavaScript یاد گرفتیم مرتبط است.

در فهرست دوره، Call Stack در فصل 32 قرار دارد.


# 125.16 - Profiling در زمان Load

برای Applicationهای Backend، Profiling باید در شرایط نزدیک به استفاده واقعی انجام شود.

مثلاً:

```text
100 Requests/sec
```

یا:

```text
500 Requests/sec
```

و سپس CPU Profile گرفته شود.

این کار کمک می‌کند Bottleneckهای واقعی را پیدا کنیم.

---

# 125.17 - Sampling Profiler

Profilerها می‌توانند با Sampling از وضعیت برنامه نمونه‌برداری کنند.

به جای بررسی تک‌تک دستورها، در بازه‌های زمانی مشخص وضعیت Call Stack بررسی می‌شود.

مثلاً:

```text
Sample 1 → Function A
Sample 2 → Function C
Sample 3 → Function C
Sample 4 → Function C
Sample 5 → Function B
```

اگر Function C در بخش بزرگی از Sampleها دیده شود، احتمالاً زمان زیادی از CPU در آن صرف می‌شود.

---

# 125.18 - Flame Graph

یکی از معروف‌ترین روش‌های نمایش نتایج Profiling، **Flame Graph** است.

یک Flame Graph می‌تواند چیزی شبیه این باشد:

```text
┌──────────────────────────────────────────────┐
│                    main                      │
├───────────────────────┬──────────────────────┤
│      API Handler      │    other             │
├──────────────┬────────┤                      │
│ calculate()  │ query  │                      │
├───────┬──────┤        │                      │
│ heavy │ loop │        │                      │
└───────┴──────┴────────┴──────────────────────┘
```

هرچه یک بخش از Profile سهم بیشتری داشته باشد، احتمالاً باید بیشتر بررسی شود.

---

# 125.19 - Flame Graph چگونه خوانده می‌شود؟

در حالت کلی:

* عرض Blockها اهمیت دارد.
* Blockهای عریض‌تر نشان‌دهنده سهم بیشتر در Sampleها هستند.
* Call Stack از پایین به بالا قابل دنبال کردن است.
* Functionهای Hot باید بررسی شوند.

نکته مهم:

> بزرگ بودن یک Function در Flame Graph لزوماً به معنی «بد بودن» آن Function نیست.

ممکن است Function ذاتاً کار زیادی انجام دهد.

---

# 125.20 - Hot Function چیست؟

Functionهایی که بخش قابل توجهی از زمان CPU را مصرف می‌کنند، معمولاً **Hot Function** نامیده می‌شوند.

مثلاً:

```text
processRequest() → 10%
parseData()      → 15%
calculate()      → 65%
```

در این حالت:

```text
calculate()
```

یک Hot Function است.

---

# 125.21 - CPU Intensive Code

کدهای CPU Intensive می‌توانند باعث افزایش مصرف CPU شوند.

مثلاً:

```js
function heavyCalculation() {
  let result = 0;

  for (let i = 0; i < 1_000_000_000; i++) {
    result += i;
  }

  return result;
}
```

اگر چنین تابعی در مسیر Request اجرا شود، می‌تواند Event Loop را تحت فشار قرار دهد.

---

# 125.22 - Profiling و Event Loop

Node.js بر معماری Event-Driven و Event Loop متکی است. این مفاهیم در فصل‌های 52 و 53 دوره قرار گرفته‌اند. 

اگر یک عملیات CPU-intensive روی Thread اصلی اجرا شود:

```text
Request
  ↓
Event Loop
  ↓
Heavy Function
  ↓
CPU Busy
```

ممکن است Requestهای دیگر نیز منتظر بمانند.

بنابراین Profiling می‌تواند به پیدا کردن این نوع مشکلات کمک کند.

---

# 125.23 - Synchronous Code و Profiling

کدهای Synchronous سنگین می‌توانند مشکل‌ساز باشند.

مثلاً:

```js
const fs = require("fs");

const data = fs.readFileSync("large-file.txt");
```

اگر فایل بسیار بزرگ باشد، این عملیات می‌تواند اجرای Thread اصلی را متوقف کند.

در چنین شرایطی Profiling می‌تواند کمک کند تا زمان صرف‌شده در این مسیر مشخص شود.

---

# 125.24 - Memory Profiling

CPU تنها چیزی نیست که باید Profile شود.

گاهی Application Memory زیادی مصرف می‌کند:

```text
Memory
███████████████████ 95%
```

در این شرایط باید Memory Profiling انجام دهیم.

هدف:

* بررسی Heap
* پیدا کردن Objectهای بزرگ
* بررسی رشد Memory
* پیدا کردن Memory Leak
* بررسی Garbage Collection

---

# 125.25 - Heap چیست؟

Heap بخشی از Memory است که JavaScript Objectها در آن مدیریت می‌شوند.

مثلاً:

```js
const users = [];

for (let i = 0; i < 1_000_000; i++) {
  users.push({
    id: i,
    name: `User ${i}`,
  });
}
```

در این حالت تعداد زیادی Object ایجاد می‌شود و Heap تحت فشار قرار می‌گیرد.

---

# 125.26 - Heap Snapshot

یکی از ابزارهای مهم برای Memory Profiling، **Heap Snapshot** است.

Heap Snapshot تصویری از وضعیت Heap در یک زمان مشخص ارائه می‌کند.

مثلاً:

```text
Snapshot 1
    ↓
Application runs
    ↓
Snapshot 2
```

سپس می‌توان تفاوت‌ها را بررسی کرد.

---

# 125.27 - مقایسه Heap Snapshotها

فرض کنید:

```text
Snapshot 1 → 50 MB
Snapshot 2 → 80 MB
Snapshot 3 → 120 MB
Snapshot 4 → 180 MB
```

اگر Memory بعد از انجام عملیات و Garbage Collection همچنان رشد کند، احتمال Memory Leak وجود دارد.

---

# 125.28 - Memory Leak

Memory Leak زمانی اتفاق می‌افتد که برنامه Memory را دیگر نیاز ندارد، اما Reference به آن همچنان حفظ شده است.

مثلاً:

```js
const cache = [];

setInterval(() => {
  cache.push(new Array(100_000));
}, 1000);
```

در این مثال آرایه `cache` دائماً رشد می‌کند.

---

# 125.29 - Global Variable و Memory Leak

استفاده نادرست از Stateهای Global می‌تواند باعث نگه داشتن داده‌ها برای مدت طولانی شود.

مثلاً:

```js
global.users = [];

function addUser(user) {
  global.users.push(user);
}
```

اگر این Array بدون محدودیت رشد کند، Memory مصرفی نیز افزایش پیدا می‌کند.

---

# 125.30 - Closure و Memory

Closure می‌تواند باعث شود Objectهایی که ظاهراً دیگر استفاده نمی‌شوند، همچنان در Memory باقی بمانند.

مثلاً:

```js
function createHandler() {
  const hugeData = new Array(1_000_000);

  return function () {
    console.log(hugeData.length);
  };
}
```

Function داخلی به `hugeData` دسترسی دارد، بنابراین این داده می‌تواند تا زمانی که Closure قابل دسترسی است، حفظ شود.

---

# 125.31 - Garbage Collection و Profiling

JavaScript دارای Garbage Collection است.

Garbage Collector Objectهایی را که دیگر قابل دسترسی نیستند، برای آزادسازی Memory شناسایی می‌کند.

اما Garbage Collection رایگان نیست.

اجرای GC می‌تواند CPU مصرف کند.

بنابراین اگر Application دائماً Objectهای زیادی ایجاد و حذف کند، ممکن است فشار بیشتری روی GC ایجاد شود.

---

# 125.32 - Garbage Collection Pressure

مثلاً:

```js
function process() {
  for (let i = 0; i < 1_000_000; i++) {
    const obj = {
      id: i,
      value: Math.random(),
    };
  }
}
```

اگر این الگو بسیار زیاد اجرا شود، Objectهای زیادی ساخته می‌شوند.

Profiler می‌تواند به بررسی این رفتار کمک کند.

---

# 125.33 - Allocation Profiling

گاهی مسئله اصلی CPU نیست؛ بلکه مقدار زیادی Object ایجاد می‌کنیم.

Allocation Profiling می‌تواند به بررسی Allocationهای Memory کمک کند.

سؤال‌هایی مانند:

```text
چه چیزی Object زیادی ایجاد می‌کند؟
کدام Function Allocation بیشتری دارد؟
کدام Objectها بیشتر ساخته می‌شوند؟
```

را می‌توان بررسی کرد.

---

# 125.34 - Profiling و Serialization

تبدیل Object به JSON نیز CPU مصرف می‌کند.

مثلاً:

```js
JSON.stringify(largeObject);
```

و:

```js
JSON.parse(largeString);
```

روی داده‌های بزرگ می‌تواند زمان‌بر باشد.

اگر API داده بزرگی ارسال کند، Profiling می‌تواند نشان دهد Serialization یا Parsing بخشی از Bottleneck است.

---

# 125.35 - Profiling و Regular Expression

Regular Expressionهای پیچیده نیز می‌توانند CPU زیادی مصرف کنند.

مثلاً Regexهای نامناسب می‌توانند باعث محاسبات سنگین شوند.

اگر Application با متن زیادی کار می‌کند، باید Regexها نیز در Performance Analysis بررسی شوند.

---

# 125.36 - Profiling و Database

Profiler معمولاً برای بررسی CPU و اجرای JavaScript بسیار مفید است، اما هر کندی الزاماً از JavaScript نیست.

مثلاً:

```text
Node.js
   ↓
Database Query
   ↓
2000ms
```

در این حالت CPU Profile ممکن است نشان دهد Node.js بیشتر زمان را منتظر I/O بوده است.

پس باید Application Profiling را با Database Monitoring و Query Analysis ترکیب کرد.

---

# 125.37 - Profiling و External API

فرض کنید:

```text
Node.js
   ↓
Payment API
   ↓
1800ms
```

ممکن است Node.js کند نباشد.

Dependency خارجی کند است.

بنابراین هنگام تحلیل Performance باید مرزهای سیستم را نیز در نظر بگیریم.

---

# 125.38 - `performance.now()`

برای اندازه‌گیری زمان اجرای بخشی از کد می‌توان از APIهای Performance استفاده کرد.

مثلاً:

```js
import { performance } from "node:perf_hooks";

const start = performance.now();

doSomething();

const end = performance.now();

console.log(`Time: ${end - start}ms`);
```

این روش برای اندازه‌گیری یک بخش مشخص از کد بسیار مفید است.

---

# 125.39 - `console.time()`

برای اندازه‌گیری ساده می‌توان از:

```js
console.time("operation");

doSomething();

console.timeEnd("operation");
```

استفاده کرد.

خروجی تقریباً:

```text
operation: 35.2ms
```

خواهد بود.

---

# 125.40 - Micro Benchmark

اگر بخواهیم دو روش را مقایسه کنیم:

```js
console.time("method-a");

methodA();

console.timeEnd("method-a");
```

و:

```js
console.time("method-b");

methodB();

console.timeEnd("method-b");
```

می‌توانیم یک مقایسه اولیه انجام دهیم.

اما این روش به تنهایی یک Benchmark حرفه‌ای محسوب نمی‌شود.

---

# 125.41 - چرا یک بار اندازه‌گیری کافی نیست؟

ممکن است اجرای یک Function:

```text
Run 1 → 10ms
Run 2 → 50ms
Run 3 → 12ms
Run 4 → 80ms
```

باشد.

دلایل مختلفی می‌توانند باعث تفاوت شوند:

* JIT
* Garbage Collection
* CPU Scheduling
* Cache
* سیستم‌عامل
* I/O

بنابراین باید اندازه‌گیری‌ها را در تعداد کافی تکرار کرد.

---

# 125.42 - Warm-up

V8 از تکنیک‌هایی مانند JIT Compilation برای بهینه‌سازی اجرای JavaScript استفاده می‌کند.

به همین دلیل اجرای اولیه یک Function ممکن است با اجرای بعدی متفاوت باشد.

بنابراین در Benchmark و Profiling باید مفهوم **Warm-up** را در نظر گرفت.

---

# 125.43 - Profiling و JIT

V8 می‌تواند کدهایی را که زیاد اجرا می‌شوند بهینه کند.

بنابراین ممکن است رفتار Function در ابتدا:

```text
Cold
```

و بعد از چند بار اجرا:

```text
Hot / Optimized
```

متفاوت باشد.

این یکی از دلایلی است که Benchmarkهای ساده ممکن است نتایج گمراه‌کننده ایجاد کنند.

---

# 125.44 - Deoptimization

گاهی V8 بهینه‌سازی انجام‌شده را کنار می‌گذارد.

این اتفاق می‌تواند به دلایل مختلفی رخ دهد.

در Performance Analysis پیشرفته، Deoptimization می‌تواند یک موضوع مهم باشد.

اما در ابتدای مسیر باید بدانیم:

> هر کدی که سریع به نظر می‌رسد، لزوماً همیشه با یک مسیر اجرای ثابت و یکسان اجرا نمی‌شود.

---

# 125.45 - Profiling با `node --prof`

Node.js قابلیت‌های داخلی برای Profiling نیز دارد.

یکی از گزینه‌های قدیمی‌تر:

```bash
node --prof app.js
```

است.

این روش برای تولید Profile مربوط به اجرای برنامه استفاده می‌شود.

پس از اجرا، فایل مربوط به Profiling تولید می‌شود که می‌توان آن را تحلیل کرد.

---

# 125.46 - Log کردن زمان اجرای عملیات

گاهی یک روش ساده برای پیدا کردن Bottleneck کافی است.

مثلاً:

```js
const start = performance.now();

const users = await getUsers();

console.log(
  `getUsers: ${performance.now() - start}ms`
);
```

این روش به ما می‌گوید این عملیات چقدر زمان برده است.

اما برای تحلیل عمیق‌تر باید از Profiling مناسب استفاده کرد.

# 125.48 - Profiling و Middleware

در یک Backend می‌توان Middlewareهایی برای اندازه‌گیری زمان Request ایجاد کرد.

مثلاً:

```js
app.use((req, res, next) => {
  const start = performance.now();

  res.on("finish", () => {
    const duration = performance.now() - start;

    console.log(
      `${req.method} ${req.url} - ${duration.toFixed(2)}ms`
    );
  });

  next();
});
```

این روش یک دید کلی از Latency Requestها می‌دهد.

---

# 125.49 - Profiling و P95

میانگین Latency همیشه کافی نیست.

مثلاً:

```text
Average = 100ms
```

اما:

```text
P95 = 500ms
P99 = 2000ms
```

ممکن است تعداد زیادی Request بسیار کند داشته باشیم.

بنابراین در سیستم‌های واقعی باید علاوه بر Average، معیارهایی مانند P95 و P99 را نیز بررسی کنیم.

# 125.50 - Profiling در Production

Profiling در Production باید با دقت انجام شود.

چون Profiling می‌تواند:

* CPU مصرف کند.
* Memory مصرف کند.
* حجم داده زیادی تولید کند.
* روی Performance تأثیر بگذارد.

به همین دلیل معمولاً باید:

* Profiling محدود باشد.
* Sampling مناسب باشد.
* روی Instance مشخص انجام شود.
* اطلاعات حساس جمع‌آوری نشود.
* در زمان مناسب انجام شود.

---

# 125.51 - Profiling در محیط Development

```text
      ↓

      ↓
```

```text
      ↓
9. مقایسه نتایج
```

# 125.56 - مثال کامل

فرض کنید:

```text
GET /report
```

زمان پاسخ:

```text
2500ms
```

با بررسی اولیه:

```text
Database → 100ms
JavaScript → 2200ms
```

CPU Profile می‌گیریم:

```text
generateReport() → 75%
formatData()    → 15%
other           → 10%
```

داخل `generateReport()`:

```text
formatData()
   ↓
heavyCalculation()
```

مشخص می‌شود:

```text
heavyCalculation() → 65%
```

اکنون به جای تغییر تصادفی بخش‌های مختلف، دقیقاً روی همین قسمت تمرکز می‌کنیم.

# 125.57 - بعد از Optimization

فرض کنیم Function را بهینه کردیم:

```text
Before:
heavyCalculation → 1600ms

After:
heavyCalculation → 200ms
```

زمان API:

```text
Before → 2500ms
After  → 900ms
```

حالا دوباره Profile می‌گیریم.

ممکن است Bottleneck جدید:

```text
Database → 600ms
```

باشد.

این نکته بسیار مهم است:

> بعد از رفع یک Bottleneck، ممکن است Bottleneck بعدی ظاهر شود.

# مینی‌پروژه - ساخت سیستم Profiling برای Node.js API

در این پروژه یک API می‌سازیم که بتوانیم Performance آن را اندازه‌گیری و Bottleneck آن را پیدا کنیم.

هدف پروژه این است که از:

* `performance.now()`
* `console.time()`
* CPU Profiling
* Memory Analysis
* Request Timing
* Benchmark

استفاده کنیم.

---

# مرحله 1 - ساخت پروژه

```bash
mkdir profiling-demo
cd profiling-demo

npm init -y

npm install express
```

---

# مرحله 2 - ساخت Server

```js
import express from "express";
import { performance } from "node:perf_hooks";

const app = express();

app.use(express.json());

app.use((req, res, next) => {
  const start = performance.now();

  res.on("finish", () => {
    const duration = performance.now() - start;

    console.log(
      `${req.method} ${req.originalUrl} - ${duration.toFixed(2)}ms`
    );
  });

  next();
});

app.get("/", (req, res) => {
  res.json({
    message: "Profiling Demo",
    pid: process.pid,
  });
});

app.listen(3000, () => {
  console.log("Server running on port 3000");
});
```

# مرحله 3 - ساخت عملیات CPU-intensive

```js
function heavyCalculation() {
  let result = 0;

  for (let i = 0; i < 50_000_000; i++) {
    result += i;
  }

  return result;
}
```

حالا Endpoint:

```js
app.get("/heavy", (req, res) => {
  const start = performance.now();

  const result = heavyCalculation();

  const duration = performance.now() - start;

  res.json({
    result,
    duration,
  });
});
```

# مرحله 9 - اضافه کردن Request ID

یک Request ID ساده ایجاد کنید:

```js
import crypto from "node:crypto";

app.use((req, res, next) => {
  const requestId = crypto.randomUUID();

  req.requestId = requestId;
  res.setHeader("X-Request-ID", requestId);

  next();
});
```

حالا Logها را به شکل زیر ثبت کنید:

```js
console.log({
  requestId: req.requestId,
  method: req.method,
  url: req.originalUrl,
  duration,
});
```

این کار در سیستم‌های واقعی برای Trace کردن Request بسیار مفید است.

# جمع‌بندی

Profiling یکی از مهم‌ترین مهارت‌ها برای Performance Engineering در Node.js است.

در این فصل یاد گرفتیم که نباید Performance را بر اساس حدس بهینه کنیم:

```text
❌ Guess
   ↓
❌ Random Optimization
```

بلکه باید:

```text
Measure
   ↓
Profile
   ↓
Find Bottleneck
   ↓
Optimize
   ↓
Measure Again
```

مهم‌ترین ابزارها و مفاهیمی که در این فصل یاد گرفتیم:

* Profiling
* Benchmark
* Monitoring
* Bottleneck
* CPU Profiling
* Memory Profiling
* Heap
* Heap Snapshot
* Memory Leak
* Garbage Collection
* Allocation
* Call Stack
* Sampling
* Flame Graph
* Hot Function
* CPU-intensive Code
* Event Loop و Performance
* `node --inspect`
* `node --inspect-brk`
* `node --prof`
* `performance.now()`
* `console.time()`
* JIT
* Warm-up
* Deoptimization
* P95
* P99
* Profiling در Production
* Baseline
* Performance Report

و مهم‌تر از همه:

> **هدف Profiling این نیست که صرفاً اطلاعات زیادی درباره برنامه جمع کنیم؛ هدف آن پیدا کردن Bottleneck واقعی و تصمیم‌گیری بر اساس داده است.**

این موضوع باعث می‌شود فصل 125 مکمل طبیعی فصل‌های قبلی Performance باشد: ابتدا Optimization، سپس Cache و Redis، Compression، Cluster و Load Balancing، و در نهایت Profiling برای اینکه بتوانیم **اندازه‌گیری کنیم، Bottleneck را پیدا کنیم و اثربخشی تمام این بهینه‌سازی‌ها را به‌صورت واقعی بسنجیم**. جایگاه این فصل در ساختار مستند نیز دقیقاً پس از Load Balancing تعریف شده است.
