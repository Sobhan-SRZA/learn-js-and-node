# فصل 119 - Performance Optimization

## مقدمه

وقتی یک برنامه Node.js را در ابتدای مسیر توسعه می‌دهیم، معمولاً مهم‌ترین هدف این است که برنامه درست کار کند.

اما در پروژه‌های واقعی، فقط درست کار کردن کافی نیست.

فرض کنید یک API داریم که در حالت عادی در کمتر از چند میلی‌ثانیه پاسخ می‌دهد. با افزایش تعداد کاربران، حجم داده‌ها و تعداد درخواست‌ها ممکن است همان API به‌تدریج کند شود.

ممکن است:

* CPU بیش از حد مصرف شود.
* Memory افزایش پیدا کند.
* Response Time زیاد شود.
* تعداد Requestهای قابل پردازش کاهش پیدا کند.
* Event Loop Block شود.
* Database به گلوگاه تبدیل شود.
* تعداد زیادی Object غیرضروری ایجاد شود.
* فایل‌های بزرگ به شکل نامناسب پردازش شوند.
* درخواست‌های تکراری بدون Cache پردازش شوند.

به مجموعه تکنیک‌ها و روش‌هایی که برای شناسایی و کاهش این مشکلات استفاده می‌کنیم، **Performance Optimization** یا بهینه‌سازی عملکرد گفته می‌شود.

در این فصل یاد می‌گیریم چگونه Performance یک برنامه Node.js را بررسی کنیم، Bottleneckها را پیدا کنیم و با روش‌های اصولی برنامه را سریع‌تر و کارآمدتر کنیم.

نکته بسیار مهم:

> Performance Optimization یعنی پیدا کردن گلوگاه واقعی و حل کردن آن؛ نه اینکه بدون اندازه‌گیری، کد را پیچیده‌تر کنیم.

---

# 119.1 - Performance چیست؟

Performance به رفتار برنامه از نظر منابع و سرعت اشاره دارد.

مهم‌ترین معیارها عبارت‌اند از:

* Response Time
* Throughput
* CPU Usage
* Memory Usage
* Event Loop Lag
* Latency
* Requests Per Second
* Error Rate

برای مثال اگر API ما:

```text
Request → 50ms → Response
```

داشته باشد، Latency آن حدود 50 میلی‌ثانیه است.

اگر همان API:

```text
Request → 2000ms → Response
```

طول بکشد، عملکرد آن بسیار ضعیف‌تر است.

---

# 119.2 - چرا Performance مهم است؟

Performance فقط به معنی «سریع بودن» نیست.

عملکرد مناسب باعث می‌شود:

* کاربران تجربه بهتری داشته باشند.
* Server بتواند Requestهای بیشتری پردازش کند.
* هزینه Infrastructure کاهش پیدا کند.
* منابع CPU و Memory بهتر استفاده شوند.
* سیستم در زمان افزایش کاربران پایدارتر باشد.
* احتمال Timeout کاهش پیدا کند.

---

# 119.3 - Performance و Scalability

دو مفهوم مهم:

```text
Performance
Scalability
```

را نباید با یکدیگر اشتباه بگیریم.

Performance بیشتر به عملکرد سیستم در یک شرایط مشخص مربوط است.

Scalability به توانایی سیستم برای مدیریت افزایش Load مربوط می‌شود.

مثلاً اگر API در هر ثانیه 100 Request را پردازش کند، با اضافه شدن کاربران ممکن است به 1000 Request در ثانیه نیاز داشته باشیم.

در این حالت باید علاوه بر Performance به Scalability نیز توجه کنیم.

---

# 119.4 - Bottleneck چیست؟

Bottleneck یا گلوگاه بخشی از سیستم است که عملکرد کل سیستم را محدود می‌کند.

مثلاً فرض کنید:

```text
API
 ↓
Validation
 ↓
Database
 ↓
Business Logic
 ↓
Response
```

اگر Database Query به‌جای 10 میلی‌ثانیه، 2 ثانیه طول بکشد، احتمالاً Database یکی از Bottleneckهای اصلی است.

در چنین شرایطی سریع‌تر کردن بخش‌های دیگر ممکن است تأثیر زیادی نداشته باشد.

---

# 119.5 - قانون مهم Performance

یکی از مهم‌ترین اصول:

> اول اندازه‌گیری، بعد بهینه‌سازی.

نباید صرفاً بر اساس حدس بگوییم:

```text
این قسمت احتمالاً کند است.
```

باید آن را اندازه‌گیری کنیم.

فرآیند مناسب:

```text
Measure
   ↓
Find Bottleneck
   ↓
Optimize
   ↓
Measure Again
```

---

# 119.6 - Benchmark چیست؟

Benchmark یعنی اجرای یک عملیات تحت شرایط مشخص و اندازه‌گیری عملکرد آن.

مثلاً می‌توانیم بررسی کنیم:

```text
Operation A → 10ms
Operation B → 100ms
Operation C → 500ms
```

در این حالت می‌توانیم بخش کندتر را شناسایی کنیم.

---

# 119.7 - اندازه‌گیری زمان اجرا

در Node.js می‌توان از:

```js
console.time();
console.timeEnd();
```

استفاده کرد.

مثلاً:

```js
console.time("operation");

for (let i = 0; i < 10_000_000; i++) {
  Math.sqrt(i);
}

console.timeEnd("operation");
```

خروجی ممکن است چیزی شبیه این باشد:

```text
operation: 45.123ms
```

این روش برای اندازه‌گیری‌های ساده مفید است.

---

# 119.8 - performance.now()

Node.js API مربوط به Performance را نیز در اختیار ما قرار می‌دهد.

مثلاً:

```js
import { performance } from "node:perf_hooks";

const start = performance.now();

for (let i = 0; i < 10_000_000; i++) {
  Math.sqrt(i);
}

const end = performance.now();

console.log(`Time: ${end - start}ms`);
```

این روش امکان اندازه‌گیری دقیق‌تر زمان عملیات را فراهم می‌کند.

---

# 119.9 - Benchmark واقعی

اگر می‌خواهیم دو روش را با یکدیگر مقایسه کنیم، بهتر است هر روش چندین بار اجرا شود.

مثلاً:

```js
function methodA() {
  // ...
}

function methodB() {
  // ...
}
```

سپس عملکرد آن‌ها را تحت شرایط مشابه بررسی می‌کنیم.

یک اجرای منفرد الزاماً نتیجه قابل اعتمادی به ما نمی‌دهد.

---

# 119.10 - CPU Usage

CPU یکی از منابع مهم سیستم است.

اگر یک عملیات CPU-intensive باشد، زمان زیادی از CPU مصرف می‌کند.

مثلاً:

```js
function heavyTask() {
  let result = 0;

  for (let i = 0; i < 1_000_000_000; i++) {
    result += i;
  }

  return result;
}
```

اجرای چنین کدی می‌تواند CPU را برای مدت زیادی درگیر کند.

---

# 119.11 - CPU-Bound چیست؟

یک عملیات CPU-Bound عملیاتی است که محدودیت اصلی آن قدرت پردازنده است.

مثلاً:

* محاسبات سنگین
* پردازش تصویر
* Compression سنگین
* Encryption سنگین
* تحلیل داده‌های بزرگ
* الگوریتم‌های پیچیده

در Node.js چنین عملیات‌هایی باید با دقت مدیریت شوند.

---

# 119.12 - I/O-Bound چیست؟

I/O-Bound عملیاتی است که بیشتر زمان آن صرف انتظار برای I/O می‌شود.

مثلاً:

* Database
* File System
* Network
* HTTP Request
* Redis
* سرویس خارجی

Node.js برای بسیاری از عملیات I/O بسیار مناسب است.

---

# 119.13 - تفاوت CPU-Bound و I/O-Bound

مثلاً:

```text
Database Query
```

ممکن است بیشتر I/O-Bound باشد.

اما:

```text
محاسبه یک الگوریتم سنگین
```

CPU-Bound است.

در Node.js این تفاوت بسیار مهم است، چون اجرای طولانی CPU-Bound روی Thread اصلی می‌تواند Event Loop را Block کند.

---

# 119.14 - Event Loop و Performance

Node.js از Event Loop استفاده می‌کند.

اگر کد ما مدت زیادی روی Thread اصلی اجرا شود:

```js
while (true) {
  // ...
}
```

Event Loop فرصت پردازش سایر کارها را نخواهد داشت.

در نتیجه Requestهای دیگر نیز تحت تأثیر قرار می‌گیرند.

---

# 119.15 - Event Loop Blocking

مثال:

```js
function blockEventLoop() {
  const start = Date.now();

  while (Date.now() - start < 5000) {
    // CPU work
  }
}
```

اگر این تابع در مسیر یک HTTP Request اجرا شود، ممکن است برای چند ثانیه پردازش سایر Requestها نیز مختل شود.

---

# 119.16 - چرا Loopهای سنگین خطرناک هستند؟

این کد:

```js
for (let i = 0; i < 1_000_000_000; i++) {
  // ...
}
```

ممکن است CPU را به‌شدت درگیر کند.

اگر در Main Thread اجرا شود، سایر کارهای Node.js نیز ممکن است منتظر بمانند.

بنابراین باید مشخص کنیم:

```text
آیا این کار CPU-Bound است؟
```

اگر جواب مثبت باشد، ممکن است نیاز به معماری متفاوتی داشته باشیم.

---

# 119.17 - Worker Threads

برای بعضی عملیات‌های CPU-intensive می‌توان از Worker Threads استفاده کرد.

برای مثال:

```js
import { Worker } from "node:worker_threads";

const worker = new Worker("./worker.js");

worker.on("message", (result) => {
  console.log(result);
});
```

Worker می‌تواند عملیات CPU-heavy را خارج از Thread اصلی اجرا کند.

این موضوع در فصل Worker Threads نیز بررسی شده است.

---

# 119.18 - Memory Usage

Performance فقط سرعت CPU نیست.

Memory نیز اهمیت زیادی دارد.

می‌توان Memory Usage را بررسی کرد:

```js
console.log(process.memoryUsage());
```

خروجی شامل اطلاعاتی مانند:

```text
rss
heapTotal
heapUsed
external
arrayBuffers
```

است.

---

# 119.19 - Memory Leak

Memory Leak زمانی رخ می‌دهد که برنامه حافظه‌ای را نگه می‌دارد که دیگر به آن نیاز ندارد.

مثلاً:

```js
const cache = [];

setInterval(() => {
  cache.push(new Array(100_000).fill("data"));
}, 1000);
```

در این مثال Array دائماً بزرگ‌تر می‌شود و حافظه بیشتری مصرف می‌کند.

---

# 119.20 - Objectهای غیرضروری

ایجاد Objectهای بسیار زیاد می‌تواند فشار بیشتری به Memory و Garbage Collector وارد کند.

مثلاً در یک حلقه بزرگ:

```js
for (let i = 0; i < 1_000_000; i++) {
  const user = {
    id: i,
    name: `User ${i}`,
  };
}
```

باید بررسی کنیم آیا واقعاً ایجاد این تعداد Object لازم است یا خیر.

---

# 119.21 - Garbage Collection

Node.js از JavaScript Engine مربوط به V8 استفاده می‌کند و V8 حافظه‌های بلااستفاده را مدیریت می‌کند.

اما Garbage Collection رایگان نیست.

ایجاد Objectهای بسیار زیاد می‌تواند باعث فشار بیشتر روی Garbage Collector شود.

بنابراین یکی از اصول Performance:

> Object و Data غیرضروری ایجاد نکنید.

---

# 119.22 - Database به‌عنوان Bottleneck

یکی از رایج‌ترین مشکلات Performance در Backendها Database است.

مثلاً:

```js
const users = await db.query("SELECT * FROM users");
```

اگر جدول میلیون‌ها رکورد داشته باشد، دریافت تمام ستون‌ها و تمام رکوردها می‌تواند بسیار پرهزینه باشد.

بهتر است فقط اطلاعات مورد نیاز را دریافت کنیم.

مثلاً:

```sql
SELECT id, name, email
FROM users
LIMIT 20;
```

---

# 119.23 - Pagination

به جای دریافت هزاران یا میلیون‌ها رکورد:

```text
GET /users
```

می‌توان از Pagination استفاده کرد:

```text
GET /users?page=1&limit=20
```

در نتیجه Server فقط بخش مورد نیاز را دریافت و ارسال می‌کند.

---

# 119.24 - N+1 Query Problem

فرض کنید ابتدا کاربران را دریافت می‌کنیم:

```text
1 Query
```

و سپس برای هر کاربر یک Query دیگر اجرا می‌کنیم:

```text
100 Users
+
100 Queries
```

در مجموع:

```text
101 Queries
```

این وضعیت می‌تواند Performance را به‌شدت کاهش دهد.

راه‌حل ممکن است شامل:

* JOIN
* Eager Loading
* Batch Query
* DataLoader
* Query Optimization

باشد.

---

# 119.25 - Index در Database

Index می‌تواند جستجو در Database را بسیار سریع‌تر کند.

مثلاً اگر مرتباً بر اساس:

```text
email
```

جستجو کنیم، ایجاد Index مناسب می‌تواند مفید باشد.

اما Index نیز هزینه دارد.

بنابراین باید بر اساس Queryهای واقعی تصمیم بگیریم.

---

# 119.26 - Select فقط داده مورد نیاز

این کد:

```sql
SELECT *
FROM users;
```

ممکن است اطلاعات بسیار بیشتری از نیاز برنامه برگرداند.

اگر فقط Email لازم داریم:

```sql
SELECT email
FROM users;
```

بهتر است.

هرچه Data کمتری جابه‌جا شود:

* Memory کمتر
* Network کمتر
* Serialization کمتر

مورد نیاز خواهد بود.

---

# 119.27 - Serialization

زمانی که Objectهای JavaScript را به JSON تبدیل می‌کنیم، Serialization انجام می‌شود.

مثلاً:

```js
const response = JSON.stringify(data);
```

اگر Data بسیار بزرگ باشد، Serialization نیز می‌تواند پرهزینه شود.

پس فقط داده مورد نیاز را ارسال کنید.

---

# 119.28 - Response Size

فرض کنید API به جای:

```json
{
  "id": 1,
  "name": "Ali"
}
```

اطلاعات بسیار زیادی ارسال کند.

حجم Response افزایش پیدا می‌کند.

این موضوع روی:

* CPU
* Memory
* Network
* Client
* Latency

تأثیر می‌گذارد.

---

# 119.29 - Compression

برای Responseهای بزرگ می‌توان از Compression استفاده کرد.

برای مثال در HTTP می‌توان Response را با روش‌هایی مانند:

```text
gzip
Brotli
```

فشرده کرد.

Compression باعث کاهش حجم داده منتقل‌شده می‌شود، اما خودش نیز CPU مصرف می‌کند.

پس باید بین CPU و Network Trade-off مناسب برقرار کنیم.

---

# 119.30 - Cache

اگر یک عملیات بارها با همان نتیجه اجرا شود، ممکن است بتوانیم نتیجه را Cache کنیم.

مثلاً:

```text
Request
 ↓
Cache
 ↓
Data
```

اگر Data در Cache موجود باشد، نیازی نیست هر بار Database Query اجرا شود.

Cache در فصل بعدی با جزئیات بیشتری بررسی خواهد شد.

---

# 119.31 - Connection Pooling

ایجاد Connection جدید برای هر Request می‌تواند هزینه‌بر باشد.

Database Clientها معمولاً از Connection Pool استفاده می‌کنند.

به جای:

```text
Request
 ↓
Create Connection
 ↓
Query
 ↓
Close Connection
```

می‌توان از Pool استفاده کرد:

```text
Connection Pool
 ↓
Reuse Connections
```

این کار برای سیستم‌های پرترافیک بسیار مهم است.

---

# 119.32 - Parallel Execution

اگر چند عملیات مستقل از یکدیگر باشند، ممکن است بتوانیم آن‌ها را به‌صورت موازی شروع کنیم.

روش نامناسب:

```js
const users = await getUsers();
const products = await getProducts();
const orders = await getOrders();
```

اگر این عملیات مستقل باشند، اجرای آن‌ها پشت سر هم زمان بیشتری می‌گیرد.

می‌توان از:

```js
const [users, products, orders] = await Promise.all([
  getUsers(),
  getProducts(),
  getOrders(),
]);
```

استفاده کرد.

---

# 119.33 - مراقبت از Promise.all

`Promise.all()` همیشه بهترین انتخاب نیست.

اگر تعداد زیادی Promise را هم‌زمان اجرا کنیم، ممکن است:

* Database تحت فشار قرار گیرد.
* API خارجی Rate Limit اعمال کند.
* Memory افزایش پیدا کند.
* Network تحت فشار قرار گیرد.

بنابراین Parallelism باید کنترل‌شده باشد.

---

# 119.34 - Sequential در مقابل Parallel

فرض کنید:

```js
await taskA();
await taskB();
await taskC();
```

زمان تقریبی:

```text
A + B + C
```

اما:

```js
await Promise.all([
  taskA(),
  taskB(),
  taskC(),
]);
```

زمان تقریبی:

```text
max(A, B, C)
```

البته زمانی که عملیات مستقل باشند.

---

# 119.35 - Async/Await و Performance

خود `async/await` به‌صورت ذاتی باعث کند شدن قابل توجه برنامه نمی‌شود.

مشکل معمولاً در نحوه استفاده از آن است.

مثلاً:

```js
for (const user of users) {
  await sendEmail(user.email);
}
```

اگر ارسال ایمیل‌ها مستقل باشند، اجرای کاملاً Sequential ممکن است کند باشد.

می‌توان با توجه به محدودیت سرویس از Parallelism یا Concurrency محدود استفاده کرد.

---

# 119.36 - Concurrency محدود

به جای اجرای 10,000 عملیات هم‌زمان، می‌توان مثلاً 10 یا 20 عملیات را هم‌زمان اجرا کرد.

این روش:

```text
Controlled Concurrency
```

نامیده می‌شود.

این کار باعث می‌شود فشار روی:

* Database
* Network
* APIهای خارجی
* Memory

کنترل شود.

---

# 119.37 - Stream به جای Buffer کامل

فرض کنید یک فایل 1GB داریم.

روش نامناسب:

```js
const data = await fs.promises.readFile("large-file.txt");
```

کل فایل وارد Memory می‌شود.

برای فایل‌های بزرگ بهتر است از Stream استفاده کنیم.

مثلاً:

```js
import fs from "node:fs";

const stream = fs.createReadStream("large-file.txt");

stream.on("data", (chunk) => {
  console.log(chunk.length);
});
```

Stream باعث می‌شود Data به‌صورت تدریجی پردازش شود.

---

# 119.38 - Lazy Processing

گاهی لازم نیست همه Data را از ابتدا پردازش کنیم.

می‌توانیم Data را فقط زمانی که لازم است پردازش کنیم.

این ایده:

```text
Lazy Processing
```

نام دارد.

# 119.39 - الگوریتم مناسب

یکی از مهم‌ترین عوامل Performance انتخاب Algorithm مناسب است.

مثلاً الگوریتمی با پیچیدگی:

```text

```

در مقابل:


بنابراین قبل از Micro-Optimization باید Algorithm را بررسی کنیم.

## پاسخ تمرین 9

یک نمونه `O(n²)`:

```js
function hasDuplicate(array) {
  for (let i = 0; i < array.length; i++) {
    for (let j = i + 1; j < array.length; j++) {
      if (array[i] === array[j]) {
        return true;
      }
    }
  }

  return false;
}
```

می‌توان با `Set` به راه‌حل تقریبی `O(n)` رسید:

```js
function hasDuplicate(array) {
  const seen = new Set();

  for (const value of array) {
    if (seen.has(value)) {
      return true;
    }

    seen.add(value);
  }

  return false;
}
```

در نسخه دوم هر مقدار را یک بار بررسی و در `Set` نگهداری می‌کنیم.

```js
import { performance } from "node:perf_hooks";

const start = performance.now();

await someOperation();

const end = performance.now();

console.log("Response time:", end - start);
console.log("Memory:", process.memoryUsage());
```

برای CPU نیز می‌توان از ابزارهای سیستم و Profiling استفاده کرد.

نکته مهم این تمرین پیدا کردن یک Bottleneck واقعی و سپس مقایسه قبل و بعد است.

## مرحله 2 - ساخت Analyzer

فایل:

```text
src/analyzer.js
```

```js
import { performance } from "node:perf_hooks";

export async function analyze(name, task) {
  const memoryBefore = process.memoryUsage();

  const start = performance.now();

  const result = await task();

  const end = performance.now();

  const memoryAfter = process.memoryUsage();

  return {
    name,
    result,
    duration: end - start,
    heapBefore: memoryBefore.heapUsed,
    heapAfter: memoryAfter.heapUsed,
  };
}
```

## مرحله 3 - اجرای Analyzer

```text
src/index.js
```

```js
import { analyze } from "./analyzer.js";
import {
  loopTask,
  arrayTask,
  objectTask,
} from "./tasks.js";

const tasks = [
  ["Loop Task", loopTask],
  ["Array Task", arrayTask],
  ["Object Task", objectTask],
];

for (const [name, task] of tasks) {
  const result = await analyze(name, task);

  console.log(result);
}
```

پس از اجرای نسخه اولیه، قابلیت‌های زیر را اضافه کنید.

## مرحله 1 - اجرای چندباره

هر Task را مثلاً 10 بار اجرا کنید و موارد زیر را محاسبه کنید:

```text
Minimum
Maximum
Average
```

---

## مرحله 2 - P95

نتایج اجراها را Sort کنید و مقدار تقریبی P95 را محاسبه کنید.

---

## مرحله 3 - گزارش جدول

خروجی را به شکل زیر نمایش دهید:

```text
Task          Average     Min      Max
---------------------------------------
Loop          12ms        10ms     20ms
Array         25ms        22ms     31ms
Object        40ms        35ms     51ms
```

---

## مرحله 4 - مقایسه قبل و بعد

یک Function کند بنویسید.

سپس آن را بهینه کنید.

مثلاً:

```text
Before: 500ms
After: 100ms
Improvement: 80%
```

---

## مرحله 5 - تحلیل Memory

Memory قبل و بعد از اجرای هر Task را ذخیره کنید.

سپس مشخص کنید کدام Task بیشترین Memory را مصرف کرده است.

# چالش نهایی

یک API کوچک Node.js بسازید که Endpoint زیر را داشته باشد:

```text
GET /performance
```

این Endpoint باید چند عملیات مختلف را اجرا و نتیجه زیر را برگرداند:

```json
{
  "results": [
    {
      "name": "task-1",
      "duration": 12
    },
    {
      "name": "task-2",
      "duration": 30
    }
  ]
}
```

سپس:

1. Response Time را اندازه‌گیری کنید.
2. Memory را بررسی کنید.
3. یک عملیات CPU-heavy اضافه کنید.
4. اثر آن روی Event Loop را بررسی کنید.
5. عملیات سنگین را به Worker Thread منتقل کنید.
6. Performance قبل و بعد را مقایسه کنید.
7. یک Benchmark ساده تهیه کنید.
8. نتیجه را مستند کنید.

# جمع‌بندی

Performance Optimization در Node.js به معنی تغییر کورکورانه کد برای سریع‌تر شدن نیست.

فرآیند صحیح این است:

```text
Measure
   ↓
Find Bottleneck
   ↓
Understand the Problem
   ↓
Optimize
   ↓
Benchmark Again
   ↓
Monitor
```

مهم‌ترین مواردی که در این فصل یاد گرفتیم:

* Performance
* Bottleneck
* Benchmark
* CPU-Bound
* I/O-Bound
* Event Loop Blocking
* Memory Usage
* Memory Leak
* Garbage Collection
* Database Optimization
* Pagination
* N+1 Query
* Index
* Serialization
* Response Size
* Compression
* Cache
* Connection Pooling
* Promise.all
* Concurrency
* Streams
* Algorithm Complexity
* Profiling
* Load Testing
* Stress Testing
* P95 و P99
* Performance Budget
* Premature Optimization

در نهایت مهم‌ترین اصل این فصل را به خاطر بسپارید:

> **اول اندازه‌گیری کن، بعد بهینه‌سازی کن.**

اگر ندانیم Bottleneck کجاست، ممکن است زمان زیادی صرف بهینه‌سازی بخشی کنیم که اصلاً مشکل اصلی سیستم نیست.
