# فصل 53 - Single Thread

## مقدمه

یکی از معروف‌ترین ویژگی‌های Node.js این جمله است:

> **Node.js یک محیط Single Thread است.**

اما این جمله معمولاً باعث سوءتفاهم می‌شود.

خیلی از افراد تصور می‌کنند:

* Node.js فقط می‌تواند یک کار انجام دهد.
* Node.js هم‌زمانی (Concurrency) ندارد.
* Node.js از Thread استفاده نمی‌کند.
* Node.js برای تعداد زیاد کاربران مناسب نیست.

همه این برداشت‌ها نادرست یا ناقص هستند.

در واقع:

* کد JavaScript در Node.js روی **یک Thread اصلی** اجرا می‌شود.
* اما عملیات ورودی/خروجی (I/O) به کمک **libuv**، **Event Loop** و در برخی موارد **Thread Pool** به‌صورت هم‌زمان مدیریت می‌شوند.

در این فصل به‌طور کامل بررسی می‌کنیم که Single Thread دقیقاً به چه معناست، چه مزایا و محدودیت‌هایی دارد و چگونه روی طراحی برنامه‌های Node.js تأثیر می‌گذارد.

---

# 53.1 - Thread چیست؟

**Thread** یا **رشته اجرایی**، کوچک‌ترین واحد اجرای یک برنامه است.

هر Thread می‌تواند مجموعه‌ای از دستورات را به‌ترتیب اجرا کند.

به‌صورت ساده:

```text id="a1v5nr"
Program

│

├── Thread 1

├── Thread 2

└── Thread 3
```

در برخی زبان‌ها مانند Java، C# یا C++ معمولاً چند Thread به‌صورت هم‌زمان اجرا می‌شوند.

---

# 53.2 - Single Thread یعنی چه؟

در Node.js، کد JavaScript به‌صورت پیش‌فرض روی **یک Thread اصلی** اجرا می‌شود.

یعنی:

```text id="o8b6wy"
JavaScript

↓

Main Thread
```

تمام کدهای JavaScript به‌ترتیب روی همین Thread اجرا می‌شوند.

مثال:

```js id="z2n8lh"
console.log("One");

console.log("Two");

console.log("Three");
```

خروجی:

```text id="b3t1jc"
One
Two
Three
```

کدها به‌ترتیب اجرا می‌شوند.

---

# 53.3 - آیا Node.js فقط یک Thread دارد؟

خیر.

این یکی از رایج‌ترین سوءتفاهم‌هاست.

آنچه Single Thread است:

* اجرای کد JavaScript

اما در پشت صحنه، Node.js از بخش‌های دیگری نیز استفاده می‌کند:

* Event Loop
* libuv
* Thread Pool
* سیستم‌عامل

بنابراین، Node.js فقط یک Thread در کل سیستم ندارد؛ بلکه **Thread اصلی برای اجرای JavaScript** دارد.

---

# 53.4 - چرا Single Thread؟

ممکن است این سؤال پیش بیاید:

چرا سازندگان Node.js از چند Thread برای اجرای JavaScript استفاده نکردند؟

دلایل اصلی:

* ساده‌تر شدن مدل برنامه‌نویسی
* حذف بسیاری از مشکلات هم‌زمانی
* جلوگیری از Race Conditionهای رایج
* کاهش نیاز به Lock و Mutex
* مصرف کمتر حافظه
* مدیریت آسان‌تر هزاران اتصال هم‌زمان

---

# 53.5 - اجرای ترتیبی کدها

فرض کنید:

```js id="k5y0tp"
console.log("Start");

for (let i = 0; i < 5; i++) {
    console.log(i);
}

console.log("End");
```

خروجی:

```text id="d0q3rm"
Start
0
1
2
3
4
End
```

هیچ بخش از کد قبل از پایان بخش قبلی اجرا نمی‌شود.

---

# 53.6 - عملیات Blocking

مشکل زمانی ایجاد می‌شود که Thread اصلی مشغول انجام یک کار طولانی شود.

```js id="u4n7bd"
const fs = require("fs");

const data = fs.readFileSync("large-file.txt");

console.log(data.length);
```

تا پایان خواندن فایل:

* هیچ درخواست دیگری پردازش نمی‌شود.
* Event Loop متوقف می‌شود.
* Thread اصلی آزاد نیست.

---

# 53.7 - عملیات Non-Blocking

راه‌حل استفاده از APIهای غیرهمگام است.

```js id="g1m9xz"
const fs = require("fs");

fs.readFile("large-file.txt", (err, data) => {
    console.log(data.length);
});

console.log("Program continues...");
```

خروجی تقریبی:

```text id="w8f2nk"
Program continues...
5242880
```

در این حالت Thread اصلی منتظر پایان عملیات نمی‌ماند.

---

# 53.8 - هم‌زمانی (Concurrency)

Node.js با استفاده از Event Loop می‌تواند هم‌زمان چند عملیات را مدیریت کند.

مثال:

```js id="m7r4qa"
setTimeout(() => {
    console.log("Task 1");
}, 1000);

setTimeout(() => {
    console.log("Task 2");
}, 500);

console.log("Start");
```

خروجی:

```text id="c5x1hv"
Start
Task 2
Task 1
```

هر دو Timer ثبت می‌شوند و Event Loop آن‌ها را در زمان مناسب اجرا می‌کند.

---

# 53.9 - Single Thread به معنی Sequential نیست

گاهی افراد تصور می‌کنند:

Single Thread یعنی هیچ کاری هم‌زمان انجام نمی‌شود.

اما در Node.js:

* اجرای JavaScript ترتیبی است.
* مدیریت عملیات I/O به‌صورت هم‌زمان انجام می‌شود.

این مفهوم را **Concurrency** می‌نامند.

---

# 53.10 - نقش libuv

وقتی برنامه می‌نویسد:

```js id="p9w6ld"
fs.readFile("data.txt", callback);
```

اتفاقات زیر رخ می‌دهد:

```text id="r4t8zo"
JavaScript

↓

Node Runtime

↓

libuv

↓

Operating System

↓

Callback Queue

↓

Event Loop

↓

Callback
```

Thread اصلی آزاد می‌ماند.

---

# 53.11 - Thread Pool

برخی عملیات مانند:

* File System
* Crypto
* Compression
* بعضی عملیات DNS

توسط Thread Pool انجام می‌شوند.

به‌صورت پیش‌فرض:

```text id="x6m0jq"
4 Worker Threads
```

تعداد آن با متغیر محیطی `UV_THREADPOOL_SIZE` قابل تغییر است، اما افزایش آن همیشه به معنی عملکرد بهتر نیست و باید بر اساس نیاز برنامه انجام شود.

---

# 53.12 - عملیات CPU-محور

فرض کنید:

```js id="n2h5ry"
function heavyTask() {
    let total = 0;

    for (let i = 0; i < 5_000_000_000; i++) {
        total += i;
    }

    return total;
}

heavyTask();

console.log("Done");
```

در این مدت:

* Event Loop متوقف می‌شود.
* هیچ درخواست جدیدی پاسخ داده نمی‌شود.
* سرور کند می‌شود.

---

# 53.13 - عملیات I/O محور

برنامه‌هایی مانند:

* API Server
* Chat Server
* REST API
* GraphQL
* WebSocket
* File Upload
* Streaming

اغلب I/O محور هستند.

Node.js برای این نوع برنامه‌ها بسیار مناسب است.

---

# 53.14 - چه زمانی از Worker Threads استفاده کنیم؟

اگر برنامه:

* پردازش تصویر انجام می‌دهد.
* رمزنگاری سنگین دارد.
* تحلیل داده انجام می‌دهد.
* محاسبات علمی انجام می‌دهد.
* هوش مصنوعی اجرا می‌کند.

بهتر است از Worker Threads یا سرویس‌های جداگانه استفاده شود تا Thread اصلی مسدود نشود.

---

# 53.15 - مقایسه Single Thread و Multi Thread

| ویژگی                | Single Thread     | Multi Thread   |
| -------------------- | ----------------- | -------------- |
| اجرای JavaScript     | یک Thread         | چند Thread     |
| پیچیدگی              | کمتر              | بیشتر          |
| مدیریت حافظه         | ساده‌تر            | پیچیده‌تر       |
| Race Condition       | کمتر              | بیشتر          |
| Lock و Mutex         | معمولاً نیاز ندارد | اغلب نیاز دارد |
| مناسب برای I/O       | بسیار مناسب       | مناسب          |
| مناسب برای CPU سنگین | ضعیف‌تر            | بهتر           |

---

# 53.16 - مزایای Single Thread

* سادگی طراحی
* مصرف حافظه کمتر
* حذف بسیاری از مشکلات هم‌زمانی
* مناسب برای برنامه‌های I/O محور
* مدیریت تعداد زیاد اتصال هم‌زمان
* توسعه و اشکال‌زدایی آسان‌تر

---

# 53.17 - محدودیت‌های Single Thread

* اجرای ضعیف‌تر برای محاسبات سنگین
* توقف کل برنامه در صورت مسدود شدن Thread اصلی
* حساسیت بیشتر به کدهای Blocking
* نیاز به استفاده از Worker Threads برای برخی سناریوها

---

# 53.18 - مثال واقعی در Node.js

```js id="e4t1vb"
const http = require("http");

const server = http.createServer((req, res) => {
    res.end("Hello Node.js");
});

server.listen(3000, () => {
    console.log("Server is running...");
});
```

این سرور می‌تواند تعداد زیادی اتصال هم‌زمان را مدیریت کند، زیرا بیشتر زمان خود را صرف انتظار برای عملیات I/O می‌کند و Thread اصلی معمولاً آزاد است.

---

# 53.19 - اشتباهات رایج

### 1) تصور اینکه Node.js فقط یک Thread در کل سیستم دارد

Node.js یک Thread اصلی برای اجرای JavaScript دارد، اما در پشت صحنه از Thread Pool و امکانات سیستم‌عامل نیز استفاده می‌کند.

---

### 2) استفاده از توابع Sync در سرور

توابعی مانند:

```js id="l8r2ks"
fs.readFileSync()
```

در برنامه‌های سروری می‌توانند باعث کاهش شدید کارایی شوند.

---

### 3) اجرای محاسبات سنگین روی Thread اصلی

این کار Event Loop را مسدود می‌کند و زمان پاسخ‌گویی به درخواست‌های دیگر را افزایش می‌دهد.

---

### 4) تصور اینکه Single Thread یعنی بدون هم‌زمانی

Node.js با استفاده از Event Loop و عملیات غیرهمگام، هم‌زمانی (Concurrency) را فراهم می‌کند.

---

### 5) استفاده بی‌دلیل از Worker Threads

هر پردازش جداگانه هزینه ایجاد و مدیریت دارد. از Worker Threads فقط زمانی استفاده کنید که واقعاً با پردازش‌های CPU-محور سنگین روبه‌رو هستید.

---

# 53.20 - نکات حرفه‌ای

* تا حد امکان از APIهای Async استفاده کن.
* Event Loop را با حلقه‌های طولانی یا پردازش‌های سنگین مسدود نکن.
* برای فایل‌های بزرگ از Stream استفاده کن.
* تفاوت Concurrency و Parallelism را به‌خوبی درک کن.
* قبل از استفاده از Worker Threads، عملکرد برنامه را اندازه‌گیری کن.
* عملیات CPU-محور را از مسیر پردازش درخواست‌های HTTP جدا نگه دار.
* ابزارهای Profiling و Monitoring را برای شناسایی نقاط مسدودکننده Event Loop به کار ببر.

# 53.22 - پاسخ تشریحی

## پاسخ تمرین 1

Node.js را Single Thread می‌نامند زیرا کد JavaScript روی یک Thread اصلی اجرا می‌شود. با این حال، برای برخی عملیات مانند کار با فایل یا رمزنگاری از Thread Pool و امکانات سیستم‌عامل استفاده می‌کند. بنابراین، تک‌رشته‌ای بودن به **اجرای JavaScript** اشاره دارد، نه کل معماری Node.js.

---

## پاسخ تمرین 2

در عملیات Blocking، Thread اصلی تا پایان کار منتظر می‌ماند؛ مانند `fs.readFileSync()`. در عملیات Non-Blocking، درخواست به libuv واگذار می‌شود و Thread اصلی به اجرای سایر کدها ادامه می‌دهد؛ مانند `fs.readFile()`.

---

* REST API

* سرویس‌های Streaming

## پاسخ تمرین 4

نمونه‌هایی از پردازش‌های مناسب برای Worker Threads:

* پردازش تصویر
* فشرده‌سازی فایل‌ها
* محاسبات ریاضی سنگین
* تحلیل داده

# 53.23 - مینی‌پروژه

## مقایسه رفتار Blocking و Non-Blocking

در این پروژه دو فایل را با روش همگام و ناهمگام می‌خوانیم تا تفاوت رفتار Thread اصلی را مشاهده کنیم.

```js id="v5n8qw"
const fs = require("fs");

console.log("Start");

// عملیات غیرهمگام
fs.readFile("file1.txt", "utf8", (err, data) => {
    if (err) {
        console.error(err);
        return;
    }

    console.log("Async File Read");
});

// عملیات همگام
const content = fs.readFileSync("file2.txt", "utf8");

console.log("Sync File Read");

console.log("End");
```

### خروجی تقریبی

```text id="y2c7lj"
Start
Sync File Read
End
Async File Read
```

در این مثال، مشاهده می‌کنیم که نسخه همگام اجرای Thread اصلی را متوقف می‌کند، اما نسخه غیرهمگام عملیات را به libuv واگذار کرده و برنامه بدون انتظار به اجرای دستورات بعدی ادامه می‌دهد.

---

## ایده‌هایی برای توسعه پروژه

* اندازه‌گیری زمان اجرای هر روش با `console.time()`
* خواندن هم‌زمان چند فایل و بررسی ترتیب اجرای Callbackها
* استفاده از نسخه Promise-based ماژول `fs`
* تبدیل پروژه به یک HTTP Server و مقایسه عملکرد در زمان ارسال درخواست‌های متعدد
* استفاده از Worker Threads برای انجام یک پردازش CPU-محور و مقایسه تأثیر آن بر پاسخ‌گویی سرور

---

# جمع‌بندی

Single Thread بودن Node.js به این معناست که کد JavaScript روی یک Thread اصلی اجرا می‌شود، اما این موضوع مانع مدیریت هم‌زمان هزاران عملیات ورودی/خروجی نیست. با کمک **Event Loop**، **libuv** و **Thread Pool**، Node.js می‌تواند عملکرد بسیار خوبی در برنامه‌های I/O محور مانند وب‌سرورها، APIها و برنامه‌های بلادرنگ داشته باشد. در مقابل، برای پردازش‌های CPU-محور سنگین باید از ابزارهایی مانند **Worker Threads** یا معماری‌های توزیع‌شده استفاده کرد تا Thread اصلی آزاد بماند و برنامه پاسخ‌گو باقی بماند.
