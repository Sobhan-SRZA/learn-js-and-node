# فصل 51 - معماری Node.js

## مقدمه

تا اینجای آموزش، با زبان JavaScript، مفاهیم شی‌گرایی، توابع، Async Programming و بسیاری از قابلیت‌های مهم Node.js آشنا شدیم.

اما هنوز یک سؤال مهم باقی مانده است:

> **Node.js در پشت صحنه چگونه کار می‌کند؟**

اگر بدانید معماری Node.js چگونه طراحی شده است، بسیاری از رفتارهای آن برایتان قابل درک خواهد شد.

مثلاً:

* چرا Node.js می‌تواند هزاران درخواست را هم‌زمان مدیریت کند؟
* Event Loop دقیقاً چیست؟
* چرا گفته می‌شود Node.js تک‌رشته‌ای (Single Thread) است؟
* پس عملیات هم‌زمان چگونه انجام می‌شوند؟
* نقش V8 چیست؟
* libuv چه کاری انجام می‌دهد؟
* Thread Pool چیست؟
* چه زمانی Node.js سریع است و چه زمانی نیست؟

در این فصل، با معماری داخلی Node.js آشنا می‌شویم؛ دانشی که هر توسعه‌دهنده Node.js باید داشته باشد.

---

# 51.1 - معماری Node.js چیست؟

معماری Node.js مجموعه‌ای از بخش‌های مختلف است که با همکاری یکدیگر امکان اجرای برنامه‌های JavaScript را خارج از مرورگر فراهم می‌کنند.

به‌صورت ساده، معماری Node.js از بخش‌های زیر تشکیل شده است:

```text
JavaScript Code
        │
        ▼
      V8 Engine
        │
        ▼
 Node.js Runtime
        │
        ▼
      libuv
        │
        ▼
Operating System
```

هر کدام از این بخش‌ها وظیفه خاصی دارند که در ادامه بررسی می‌کنیم.

---

# 51.2 - اجزای اصلی معماری Node.js

معماری Node.js از اجزای مهم زیر تشکیل شده است:

* V8 Engine
* Node.js Runtime
* Node APIs
* Event Loop
* Callback Queue
* Microtask Queue
* libuv
* Thread Pool
* Operating System

درک این اجزا، کلید فهم عملکرد Node.js است.

---

# 51.3 - V8 Engine

V8 موتور JavaScript است که توسط Google توسعه داده شده و در مرورگر Chrome و Node.js استفاده می‌شود.

وظایف V8:

* اجرای کد JavaScript
* تبدیل JavaScript به Machine Code
* مدیریت حافظه
* Garbage Collection
* بهینه‌سازی اجرای کد

مثال:

```js id="1xow4q"
const sum = 10 + 20;

console.log(sum);
```

این کد توسط V8 اجرا می‌شود.

---

# 51.4 - Node.js Runtime

Node.js فقط V8 نیست.

Node.js مجموعه‌ای از APIها و ابزارها را به V8 اضافه می‌کند.

برای مثال:

* File System
* Network
* HTTP
* Timers
* Process
* Streams
* Crypto
* Buffer

نمونه:

```js id="mjlwm0"
const fs = require("fs");

fs.readFile("test.txt", "utf8", (err, data) => {
    console.log(data);
});
```

خواندن فایل توسط V8 انجام نمی‌شود؛ این قابلیت را Node.js در اختیار ما قرار می‌دهد.

---

# 51.5 - Single Thread

یکی از معروف‌ترین ویژگی‌های Node.js این است که:

> Node.js به‌صورت پیش‌فرض روی یک Thread اصلی اجرا می‌شود.

یعنی:

```text
JavaScript Thread
```

فقط یک Thread مسئول اجرای کد JavaScript است.

اما این به معنی انجام تنها یک کار در کل سیستم نیست.

---

# 51.6 - پس هم‌زمانی چگونه انجام می‌شود؟

پاسخ:

**Event Loop + libuv**

وقتی یک عملیات زمان‌بر انجام می‌دهید:

```js id="j98q6v"
const fs = require("fs");

fs.readFile("test.txt", () => {
    console.log("Finished");
});
```

Thread اصلی منتظر پایان خواندن فایل نمی‌ماند.

بلکه عملیات را به libuv واگذار می‌کند و به اجرای سایر کدها ادامه می‌دهد.

---

# 51.7 - Event Loop

Event Loop قلب Node.js است.

وظیفه آن:

* بررسی صف‌ها
* اجرای Callbackها
* مدیریت عملیات Async

به زبان ساده:

```text
آیا کاری برای اجرا وجود دارد؟

↓

بله

↓

اجرا کن

↓

دوباره بررسی کن
```

این چرخه هزاران بار در ثانیه تکرار می‌شود.

---

# 51.8 - Callback Queue

وقتی یک عملیات Async تمام می‌شود، Callback آن وارد صف می‌شود.

مثال:

```js id="njlwmn"
setTimeout(() => {
    console.log("Hello");
}, 1000);
```

بعد از یک ثانیه:

Callback وارد Queue می‌شود.

سپس Event Loop آن را اجرا می‌کند.

---

# 51.9 - Microtask Queue

Microtaskها نسبت به Callback Queue اولویت بیشتری دارند.

مانند:

* Promise
* queueMicrotask()

مثال:

```js id="2gkrji"
console.log(1);

Promise.resolve().then(() => {
    console.log(2);
});

console.log(3);
```

خروجی:

```text
1
3
2
```

زیرا Promise در Microtask Queue قرار می‌گیرد و قبل از Taskهای بعدی اجرا می‌شود.

---

# 51.10 - libuv

libuv مهم‌ترین بخش Node.js بعد از V8 است.

وظایف:

* Event Loop
* File System
* DNS
* Network
* Thread Pool
* Async I/O

تقریباً تمام عملیات Async از طریق libuv انجام می‌شوند.

---

# 51.11 - Thread Pool

برخی عملیات توسط سیستم‌عامل قابل انجام نیستند.

در این حالت libuv از Thread Pool استفاده می‌کند.

به طور پیش‌فرض:

```text
4 Thread
```

عملیات‌هایی مانند:

* File System
* Crypto
* Compression
* DNS Lookup

معمولاً از Thread Pool استفاده می‌کنند.

---

# 51.12 - مسیر اجرای یک درخواست

فرض کنید فایل می‌خوانیم:

```js id="fy9plv"
fs.readFile("data.txt", () => {
    console.log("Done");
});
```

مراحل:

```text
JavaScript

↓

V8

↓

Node Runtime

↓

libuv

↓

Operating System

↓

پایان عملیات

↓

Callback Queue

↓

Event Loop

↓

اجرای Callback
```

---

# 51.13 - عملیات Blocking

نمونه:

```js id="5ob2cq"
const fs = require("fs");

const data = fs.readFileSync("test.txt");

console.log(data.toString());
```

در این حالت:

Thread اصلی متوقف می‌شود.

هیچ درخواست دیگری پردازش نمی‌شود.

---

# 51.14 - عملیات Non-Blocking

```js id="c9jlwm"
const fs = require("fs");

fs.readFile("test.txt", (err, data) => {
    console.log(data.toString());
});
```

Thread آزاد است.

برنامه به اجرای سایر بخش‌ها ادامه می‌دهد.

---

# 51.15 - معماری Event-Driven

Node.js بر پایه Event طراحی شده است.

نمونه:

```js id="w06gj8"
server.on("request", () => {
    console.log("Request");
});
```

وقتی Event رخ دهد، Callback اجرا می‌شود.

---

# 51.16 - چرا Node.js سریع است؟

دلایل:

* V8 بسیار سریع است.
* Non-Blocking I/O
* Event Loop
* مصرف کم حافظه
* عدم ساخت Thread برای هر درخواست
* مدیریت مناسب هزاران اتصال هم‌زمان

---

# 51.17 - چه زمانی Node.js انتخاب مناسبی نیست؟

برای کارهای سنگین CPU مانند:

* پردازش تصویر
* رندر ویدئو
* محاسبات ریاضی سنگین
* هوش مصنوعی
* شبیه‌سازی‌های بزرگ

اگر این کارها روی Thread اصلی انجام شوند، Event Loop مسدود می‌شود و عملکرد برنامه افت می‌کند.

برای این موارد می‌توان از **Worker Threads**، **Child Processes** یا سرویس‌های جداگانه استفاده کرد.

---

      ┌──────────┴──────────┐
      │                     │

                            │

                            ▼

# 51.19 - اشتباهات رایج

### 1) تصور اینکه Node.js چندرشته‌ای است

کد JavaScript روی یک Thread اصلی اجرا می‌شود، هرچند libuv از Thread Pool برای برخی عملیات استفاده می‌کند.

---

### 2) استفاده زیاد از توابع Sync

نمونه:

```js id="9cjlwm"
fs.readFileSync()
```

در سرورهای واقعی بهتر است از نسخه Async استفاده شود.

---

### 3) انجام محاسبات سنگین روی Thread اصلی

این کار Event Loop را متوقف می‌کند و باعث کند شدن کل برنامه می‌شود.

---

### 4) تصور اینکه Event Loop خودش عملیات را انجام می‌دهد

Event Loop فقط مدیریت و زمان‌بندی اجرای Callbackها را بر عهده دارد.

---

### 5) نادیده گرفتن تفاوت Microtask و Callback Queue

Promiseها همیشه قبل از Taskهای عادی بررسی می‌شوند.

---

# 51.20 - نکات حرفه‌ای

* تا حد امکان از APIهای Async استفاده کن.
* برای عملیات CPU-محور از Worker Threads استفاده کن.
* از Streamها برای فایل‌های بزرگ بهره ببر تا حافظه کمتری مصرف شود.
* Event Loop را با حلقه‌های بی‌نهایت یا محاسبات طولانی مسدود نکن.
* ساختار معماری Node.js را درک کن؛ حفظ کردن کافی نیست.
* هنگام طراحی APIها به Non-Blocking بودن توجه ویژه داشته باش.
* با ابزارهایی مانند `process.hrtime()` و `performance.now()` عملکرد برنامه را اندازه‌گیری کن.

# 51.22 - پاسخ تشریحی

## پاسخ تمرین 1

**V8** موتور اجرای JavaScript است و وظیفه تبدیل و اجرای کد JavaScript را بر عهده دارد. اما **Node.js Runtime** امکاناتی مانند کار با فایل، شبکه، HTTP، Stream، Buffer و سایر APIهای سمت سرور را به V8 اضافه می‌کند.

---

## پاسخ تمرین 2

در عملیات **Blocking**، Thread اصلی تا پایان عملیات منتظر می‌ماند و نمی‌تواند کار دیگری انجام دهد؛ مانند `fs.readFileSync()`. در عملیات **Non-Blocking**، درخواست به libuv واگذار می‌شود و Thread اصلی بلافاصله به اجرای سایر کدها ادامه می‌دهد؛ مانند `fs.readFile()`.

---

## پاسخ تمرین 3

مراحل اجرای `fs.readFile()` به صورت زیر است:

1. فراخوانی تابع از کد JavaScript
2. ارسال درخواست به Node.js Runtime
3. واگذاری عملیات به libuv
4. انجام عملیات توسط سیستم‌عامل یا Thread Pool
5. قرار گرفتن Callback در صف مناسب
6. اجرای Callback توسط Event Loop زمانی که Thread اصلی آزاد باشد.

---

## پاسخ تمرین 4

نمونه‌هایی از عملیاتی که معمولاً از Thread Pool استفاده می‌کنند:

* خواندن و نوشتن فایل‌ها
* عملیات رمزنگاری (`crypto`)
* فشرده‌سازی داده‌ها (`zlib`)
* برخی از عملیات DNS

---

## پاسخ تمرین 5

Node.js به دلیل استفاده از Event Loop و Non-Blocking I/O می‌تواند تعداد بسیار زیادی اتصال هم‌زمان را با مصرف منابع کم مدیریت کند. اما اگر محاسبات CPU-محور طولانی روی Thread اصلی انجام شود، Event Loop مسدود شده و پاسخ‌گویی به سایر درخواست‌ها کاهش می‌یابد.

---

# 51.23 - مینی‌پروژه

## مقایسه عملیات Blocking و Non-Blocking

در این پروژه، زمان اجرای نسخه همگام و ناهمگام خواندن فایل را مشاهده می‌کنیم.

```js id="x4clm7"
const fs = require("fs");

console.log("Application Started");

// Non-Blocking
fs.readFile("data.txt", "utf8", (err, data) => {
    if (err) {
        console.error(err);
        return;
    }

    console.log("Async File Read");
});

// Blocking
const content = fs.readFileSync("data.txt", "utf8");

console.log("Sync File Read");

console.log("Application Finished");
```

### خروجی تقریبی

```text
Application Started
Sync File Read
Application Finished
Async File Read
```

در این مثال مشاهده می‌کنیم که نسخه همگام (`readFileSync`) اجرای Thread اصلی را متوقف می‌کند، اما نسخه ناهمگام (`readFile`) عملیات را به libuv واگذار کرده و برنامه بدون انتظار به اجرای دستورات بعدی ادامه می‌دهد.

---

## ایده‌هایی برای توسعه پروژه

* مقایسه `readFile` و `readFileSync` روی فایل‌های بزرگ
* استفاده از `Promise` و `async/await` برای خواندن فایل
* نمایش زمان اجرای هر روش با `console.time()` و `console.timeEnd()`
* خواندن هم‌زمان چند فایل و بررسی ترتیب اجرای Callbackها
* استفاده از Stream برای فایل‌های حجیم و مقایسه مصرف حافظه

---

# جمع‌بندی

معماری Node.js بر پایه همکاری **V8**، **Node.js Runtime**، **libuv** و **Event Loop** طراحی شده است. JavaScript روی یک Thread اصلی اجرا می‌شود، اما عملیات ورودی/خروجی به‌صورت غیرهمگام مدیریت می‌شوند و همین موضوع باعث شده Node.js برای ساخت سرورهای وب، APIها، برنامه‌های بلادرنگ (Real-Time) و سرویس‌های شبکه‌ای عملکرد بسیار خوبی داشته باشد. درک این معماری، پایه‌ای محکم برای یادگیری مباحث پیشرفته‌تر مانند Event Loop، Worker Threads، Streams و بهینه‌سازی عملکرد برنامه‌ها فراهم می‌کند.
