# فصل 115 - CSRF

## مقدمه

در فصل‌های قبل با چند مورد از مهم‌ترین مباحث امنیتی Node.js آشنا شدیم؛ از Hash کردن Password و Encryption گرفته تا Helmet، Rate Limit، CORS و XSS. در فهرست اصلی این مستند، **CSRF** نیز به‌عنوان فصل 115 و یکی از مباحث بخش امنیت قرار گرفته است. 

CSRF مخفف عبارت:

```text
Cross-Site Request Forgery
```

است.

CSRF یکی از حملات مهم Web Applicationهاست که در آن مهاجم تلاش می‌کند کاربرِ احراز هویت‌شده را وادار کند درخواستی را به یک سایت ارسال کند، در حالی که کاربر قصد انجام آن عملیات را نداشته است.

برای درک CSRF باید چند مفهوم قبلی را کنار هم قرار دهیم:

```text
HTTP
Cookie
Session
Authentication
Browser
CORS
SameSite Cookie
```

به‌خصوص Cookie اهمیت زیادی دارد؛ زیرا Browser می‌تواند Cookieهای مربوط به یک سایت را به‌صورت خودکار همراه Request ارسال کند.

---

# 115.1 - CSRF چیست؟

فرض کنید کاربر وارد یک سایت بانکی شده است:

```text
https://bank.example
```

کاربر Login کرده و Browser یک Session Cookie دریافت کرده است:

```text
session=abc123
```

حالا کاربر به یک سایت مخرب می‌رود:

```text
https://evil.example
```

اگر شرایط لازم برای CSRF وجود داشته باشد، سایت مخرب می‌تواند تلاش کند Browser کاربر را وادار به ارسال Request به سایت بانک کند.

مثلاً:

```text
Attacker Website
       ↓
Browser User
       ↓
Bank Server
```

اگر Browser Cookie احراز هویت را همراه Request ارسال کند و Server نیز Request را بدون بررسی CSRF بپذیرد، ممکن است عملیات ناخواسته انجام شود.

---

# 115.2 - یک مثال ساده

فرض کنید API زیر وجود دارد:

```http
POST /api/transfer
```

و Server برای شناسایی کاربر از Session Cookie استفاده می‌کند:

```http
Cookie: session=abc123
```

Request واقعی کاربر:

```http
POST /api/transfer
Cookie: session=abc123
Content-Type: application/json
```

Body:

```json
{
  "amount": 100,
  "to": "user-2"
}
```

کاربر قصد انجام این انتقال را دارد.

اما در CSRF مهاجم تلاش می‌کند همان Browser را وادار به ارسال یک Request ناخواسته کند.

---

# 115.3 - چرا CSRF امکان‌پذیر است؟

یکی از قطعات مهم این مسئله:

```text
Browser Cookie Behavior
```

است.

وقتی Authentication بر اساس Cookie انجام می‌شود، Browser می‌تواند Cookie مربوط به Domain مقصد را همراه Request ارسال کند.

در نتیجه:

```text
User
↓
Login
↓
Session Cookie
↓
Browser
```

و سپس:

```text
Malicious Website
↓
Browser
↓
Target Website
↓
Session Cookie
```

ممکن است باعث ایجاد یک Request معتبر از دید Authentication شود.

---

# 115.4 - CSRF به Authentication وابسته است

CSRF معمولاً زمانی اهمیت زیادی پیدا می‌کند که Server از اطلاعاتی استفاده کند که Browser خودش به‌صورت خودکار ارسال می‌کند.

یکی از نمونه‌های رایج:

```text
Session Cookie
```

است.

یعنی Server ممکن است بگوید:

```text
این Request دارای Session Cookie معتبر است
پس کاربر احراز هویت شده است.
```

اما سؤال مهم این است:

```text
آیا خود کاربر واقعاً این Request را ارسال کرده است؟
```

CSRF دقیقاً روی همین مسئله تمرکز دارد.

---

# 115.5 - تفاوت Authentication و CSRF Protection

Authentication پاسخ این سؤال است:

```text
این کاربر چه کسی است؟
```

CSRF Protection به سؤال دیگری مربوط است:

```text
آیا این Request واقعاً از طرف همان کاربر و از مسیر مورد انتظار Application ایجاد شده است؟
```

بنابراین:

```text
Authentication
≠
CSRF Protection
```

---

# 115.6 - جریان یک حمله CSRF

یک جریان ساده:

```text
1. User Login
       ↓
2. Session Cookie
       ↓
3. User visits malicious website
       ↓
4. Malicious page triggers Request
       ↓
5. Browser sends Cookie when applicable
       ↓
6. Server receives Request
       ↓
7. Server must verify Request intent/origin
```

اگر Server فقط به Session Cookie اعتماد کند، ممکن است آسیب‌پذیر باشد.

---

# 115.7 - CSRF و Cookie

در Applicationهایی که Authentication بر پایه Cookie است، تنظیمات Cookie اهمیت زیادی دارند.

سه Attribute مهم:

```text
HttpOnly
Secure
SameSite
```

هستند.

در فصل XSS با `HttpOnly` و `Secure` آشنا شدیم. در این فصل `SameSite` اهمیت ویژه‌ای پیدا می‌کند.

---

# 115.8 - SameSite چیست؟

`SameSite` یکی از Attributeهای Cookie است که مشخص می‌کند Cookie در چه شرایطی در درخواست‌های Cross-Site ارسال شود.

مقادیر رایج:

```text
Strict
Lax
None
```

هستند.

---

# 115.9 - SameSite=Strict

مثلاً:

```js
res.cookie("session", sessionId, {
  httpOnly: true,
  secure: true,
  sameSite: "strict"
});
```

در حالت `Strict` محدودیت بیشتری برای ارسال Cookie در شرایط Cross-Site اعمال می‌شود.

این می‌تواند سطح محافظت در برابر CSRF را افزایش دهد، اما باید با نیازهای واقعی Application سازگار باشد.

---

# 115.10 - SameSite=Lax

یکی از تنظیمات رایج:

```js
res.cookie("session", sessionId, {
  httpOnly: true,
  secure: true,
  sameSite: "lax"
});
```

است.

`Lax` محدودیت‌هایی برای ارسال Cookie در Cross-Site Requestها اعمال می‌کند و برای بسیاری از Applicationها گزینه مناسبی است، اما رفتار دقیق آن باید با سناریوی Authentication و Navigation برنامه بررسی شود.

---

# 115.11 - SameSite=None

اگر Cookie باید در شرایط Cross-Site ارسال شود، ممکن است از:

```text
SameSite=None
```

استفاده شود.

در این حالت معمولاً Cookie باید:

```text
Secure
```

نیز باشد.

مثلاً:

```js
res.cookie("session", sessionId, {
  httpOnly: true,
  secure: true,
  sameSite: "none"
});
```

استفاده از `None` باید با دقت انجام شود، زیرا محدودیت‌های Cross-Site Cookie را کاهش می‌دهد.

---

# 115.12 - CSRF Token چیست؟

یکی از روش‌های معروف مقابله با CSRF استفاده از:

```text
CSRF Token
```

است.

Server یک مقدار تصادفی و غیرقابل حدس تولید می‌کند و آن را به Client می‌دهد.

سپس Client هنگام ارسال Requestهای حساس Token را نیز ارسال می‌کند.

جریان:

```text
Server
  ↓
Generate CSRF Token
  ↓
Client
  ↓
Request + CSRF Token
  ↓
Server
  ↓
Validate Token
```

اگر Token معتبر نباشد، Request رد می‌شود.

---

# 115.13 - چرا CSRF Token مفید است؟

فرض کنید مهاجم بتواند باعث ارسال یک Request شود.

اما مهاجم Token معتبر را در اختیار ندارد.

پس:

```text
Request
+
Invalid/Missing Token
        ↓
Reject
```

در نتیجه حمله خنثی می‌شود.

---

# 115.14 - Token باید قابل حدس نباشد

CSRF Token باید مقدار مناسبی داشته باشد و قابل حدس یا پیش‌بینی نباشد.

نباید چیزی مانند این باشد:

```text
123456
```

یا:

```text
userId + timestamp
```

Token باید با یک روش امن و مناسب تولید شود.

در Node.js می‌توان برای تولید داده تصادفی از APIهای `crypto` استفاده کرد.

---

# 115.15 - تولید Token با Node.js

Node.js دارای ماژول:

```js
crypto
```

است.

برای مثال:

```js
import crypto from "node:crypto";

const csrfToken = crypto.randomBytes(32).toString("hex");

console.log(csrfToken);
```

خروجی نمونه:

```text
f3a8c1...
```

مقدار واقعی در هر اجرای برنامه متفاوت خواهد بود.

---

# 115.16 - ارسال CSRF Token

فرض کنید Server Token را در اختیار Frontend قرار می‌دهد.

Frontend می‌تواند آن را همراه Request ارسال کند:

```http
POST /api/profile
X-CSRF-Token: TOKEN_VALUE
```

Server سپس Header را بررسی می‌کند.

---

# 115.17 - بررسی Token در Node.js

یک Middleware ساده:

```js
function csrfProtection(req, res, next) {
  const token = req.get("X-CSRF-Token");

  if (!token) {
    return res.status(403).json({
      message: "CSRF token is required"
    });
  }

  // Token validation
  next();
}
```

این مثال فقط ساختار کلی Middleware را نشان می‌دهد.

در Application واقعی باید Token با مقدار معتبر مربوط به Session یا کاربر مقایسه شود.

---

# 115.18 - چرا Header اختصاصی مفید است؟

یکی از روش‌های رایج ارسال CSRF Token استفاده از Header اختصاصی است:

```http
X-CSRF-Token: ...
```

این روش برای درخواست‌های API می‌تواند مناسب باشد؛ زیرا یک سایت مهاجم معمولاً نباید بتواند به‌سادگی Headerهای دلخواه Cross-Origin را ارسال کند.

البته این موضوع با CORS و نحوه پیکربندی آن ارتباط دارد.

---

# 115.19 - CSRF و CORS

CSRF و CORS دو مفهوم متفاوت هستند.

```text
CSRF
↓
آیا Request ناخواسته می‌تواند از طرف کاربر ایجاد شود؟

CORS
↓
آیا Browser اجازه می‌دهد JavaScript یک Origin به Response یک Origin دیگر دسترسی داشته باشد؟
```

بنابراین:

```text
CORS ≠ CSRF Protection
```

---

# 115.20 - آیا CORS جلوی CSRF را می‌گیرد؟

خیر، نباید CORS را به عنوان جایگزین CSRF Protection در نظر گرفت.

ممکن است Browser ارسال برخی Requestها را بدون اجازه خواندن Response امکان‌پذیر کند.

پس:

```text
Cannot Read Response
```

لزوماً به معنی:

```text
Cannot Send Request
```

نیست.

---

# 115.21 - Origin چیست؟

برای درک CSRF باید مفهوم:

```text
Origin
```

را بشناسیم.

Origin از سه بخش اصلی تشکیل می‌شود:

```text
Scheme
Host
Port
```

مثلاً:

```text
https://example.com:443
```

شامل:

```text
Scheme = https
Host   = example.com
Port   = 443
```

است.

---

# 115.22 - بررسی Origin

Server می‌تواند در برخی Applicationها Header مربوط به Origin را بررسی کند:

```http
Origin: https://example.com
```

و فقط Originهای مورد انتظار را قبول کند.

مثلاً:

```js
const allowedOrigin = "https://example.com";

if (req.get("Origin") !== allowedOrigin) {
  return res.status(403).json({
    message: "Invalid origin"
  });
}
```

این یک مثال ساده آموزشی است و سیاست واقعی باید متناسب با معماری Application طراحی شود.

---

# 115.23 - Referer چیست؟

Header دیگری که ممکن است برای بررسی درخواست مورد استفاده قرار بگیرد:

```http
Referer
```

است.

این Header می‌تواند نشان دهد Request از چه URLای آمده است.

اما نباید بدون بررسی شرایط و محدودیت‌های Privacy و Browser، تنها به آن به‌عنوان تنها لایه دفاعی متکی شد.

---

# 115.24 - Origin و Referer

به‌صورت خلاصه:

```text
Origin
↓
Origin درخواست را مشخص می‌کند.

Referer
↓
URL یا صفحه مبدأ Request را مشخص می‌کند.
```

در بسیاری از سناریوها بررسی `Origin` گزینه مناسبی برای تشخیص Cross-Site Request است.

---

# 115.25 - روش‌های اصلی مقابله با CSRF

چند لایه دفاعی مهم:

```text
1. SameSite Cookie
2. CSRF Token
3. Origin Validation
4. Referer Validation در سناریوهای مناسب
5. طراحی صحیح Authentication
```

بهترین انتخاب به نوع Application بستگی دارد.

---

# 115.26 - SameSite و CSRF Token

در بسیاری از Applicationهای حساس می‌توان از دفاع چندلایه استفاده کرد:

```text
SameSite Cookie
        +
CSRF Token
        +
Origin Validation
```

این روش به جای وابستگی به یک مکانیزم، چند لایه دفاعی ایجاد می‌کند.

---

# 115.27 - چه Requestهایی بیشتر اهمیت دارند؟

CSRF معمولاً برای عملیات State-Changing اهمیت بیشتری دارد.

مثلاً:

```text
POST
PUT
PATCH
DELETE
```

مانند:

```text
تغییر Email
تغییر Password
انتقال پول
حذف حساب
ایجاد سفارش
ویرایش اطلاعات
```

در مقابل، عملیات Read-only مانند `GET` نباید برای تغییر State استفاده شوند.

---

# 115.28 - GET نباید State را تغییر دهد

طراحی خطرناک:

```http
GET /delete-account
```

طراحی بهتر:

```http
DELETE /account
```

یا یک عملیات State-Changing مناسب دیگر.

اصل مهم:

> GET را برای عملیات بدون Side Effect طراحی کنید.

این کار علاوه بر CSRF، طراحی API را نیز بهتر می‌کند.

---

# 115.29 - چرا استفاده از GET برای Delete خطرناک است؟

اگر حذف حساب با GET انجام شود، ممکن است یک صفحه یا Resource خارجی باعث ارسال آن Request شود.

مثلاً:

```text
GET /delete-account
```

نباید عملیات مخربی مانند Delete را انجام دهد.

---

# 115.30 - CSRF در Session Authentication

فرض کنید:

```text
Login
 ↓
Session
 ↓
Cookie
 ↓
Authenticated Request
```

در این معماری CSRF باید به‌صورت جدی بررسی شود.

چون Browser می‌تواند Session Cookie را به شکل خودکار مدیریت کند.

---

# 115.31 - CSRF و JWT

JWT به خودی خود تضمین نمی‌کند که Application در برابر CSRF امن باشد.

باید ببینیم Token کجا نگهداری می‌شود و چگونه ارسال می‌شود.

اگر Token در Cookie قرار داشته باشد:

```text
JWT
↓
Cookie
↓
Browser
↓
Automatic Cookie Sending
```

موضوع CSRF همچنان اهمیت دارد.

---

# 115.32 - JWT در Authorization Header

در معماری‌هایی که Client Token را به صورت:

```http
Authorization: Bearer TOKEN
```

ارسال می‌کند، شرایط CSRF با Cookie-based Authentication متفاوت است؛ زیرا Browser معمولاً این Header را به‌صورت خودکار برای یک سایت دیگر اضافه نمی‌کند.

اما این به معنی امن بودن کامل سیستم نیست و مسائل دیگری مانند XSS و Token Storage همچنان باید بررسی شوند.

---

# 115.33 - CSRF و SPA

در SPAها مانند Applicationهای React، Vue یا Angular، معماری Authentication اهمیت زیادی دارد.

اگر Authentication با Cookie انجام شود:

```text
SPA
↓
Cookie-based Session
↓
CSRF Protection
```

باید CSRF را در طراحی در نظر گرفت.

اگر Token در Authorization Header قرار گیرد، مدل تهدید متفاوت خواهد بود.

---

# 115.34 - CSRF در API

وجود API به معنی حذف خودکار CSRF نیست.

باید بررسی کنیم:

```text
Authentication Method
Cookie
Authorization Header
Browser
CORS
SameSite
Token
```

چگونه با یکدیگر کار می‌کنند.

---

# 115.35 - Double Submit Cookie

یک تکنیک دیگر:

```text
Double Submit Cookie
```

است.

در این روش یک Token به Cookie داده می‌شود و Client همان Token را در Request نیز ارسال می‌کند.

مثلاً:

```text
Cookie:
csrfToken=ABC123
```

و:

```http
X-CSRF-Token: ABC123
```

Server دو مقدار را مقایسه می‌کند.

---

# 115.36 - ایده Double Submit Cookie

جریان:

```text
Server
   ↓
CSRF Token
   ↓
Cookie

Client
   ↓
Token
   ↓
Header

Server
   ↓
Compare
   ↓
Accept / Reject
```

این روش در بعضی معماری‌ها کاربرد دارد، اما پیاده‌سازی دقیق آن باید با مدل امنیتی Application هماهنگ باشد.

---

# 115.37 - CSRF Token در Session

یک روش دیگر این است که Token را در Session نگهداری کنیم.

مثلاً:

```text
Session
 ├── userId
 └── csrfToken
```

سپس Request باید Token مناسب Session را ارائه دهد.

Server:

```text
Request Token
      ↓
Compare
      ↓
Session Token
```

اگر برابر نباشند:

```http
403 Forbidden
```

برگردانده می‌شود.

---

# 115.38 - کد مفهومی CSRF Middleware

```js
function csrfProtection(req, res, next) {
  const token = req.get("X-CSRF-Token");
  const sessionToken = req.session.csrfToken;

  if (!token || token !== sessionToken) {
    return res.status(403).json({
      message: "Invalid CSRF token"
    });
  }

  next();
}
```

این کد برای آموزش مفهوم است.

در پروژه واقعی باید مواردی مانند:

```text
Token Generation
Token Lifecycle
Session Management
Timing-safe Comparison
Error Handling
```

نیز بررسی شوند.

---

# 115.39 - استفاده از Timing-Safe Comparison

برای مقایسه Secretها بهتر است به تفاوت‌های Timing نیز توجه شود.

Node.js دارای:

```js
crypto.timingSafeEqual()
```

است.

مثلاً:

```js
import crypto from "node:crypto";

const a = Buffer.from(token);
const b = Buffer.from(sessionToken);

if (
  a.length !== b.length ||
  !crypto.timingSafeEqual(a, b)
) {
  return res.status(403).json({
    message: "Invalid CSRF token"
  });
}
```

این موضوع برای طراحی دقیق‌تر مقایسه Secretها اهمیت دارد.

---

# 115.40 - CSRF و Password Change

Endpointهایی مانند:

```http
POST /change-password
```

باید به‌شدت محافظت شوند.

زیرا تغییر Password یک عملیات حساس است.

مثلاً:

```text
Authentication
+
CSRF Protection
+
Input Validation
+
Password Policy
+
Rate Limit
```

می‌تواند بخشی از طراحی امنیتی آن باشد.

---

# 115.41 - CSRF و انتقال پول

Endpoint:

```http
POST /transfer
```

یکی از نمونه‌های حساس است.

اگر چنین Endpointی وجود داشته باشد:

```json
{
  "amount": 1000,
  "account": "123"
}
```

نباید صرفاً با دیدن Session Cookie درخواست را معتبر بدانیم.

باید سیاست‌های امنیتی مناسب برای عملیات حساس طراحی شود.

---

# 115.42 - CSRF و Authorization

CSRF و Authorization نیز متفاوت هستند.

Authorization می‌گوید:

```text
آیا این کاربر اجازه انجام این عملیات را دارد؟
```

CSRF می‌پرسد:

```text
آیا این Request واقعاً از مسیر مورد انتظار و با قصد کاربر ارسال شده است؟
```

بنابراین هر دو باید در Application بررسی شوند.

---

# 115.43 - پاسخ مناسب به CSRF

وقتی Token نامعتبر است، معمولاً Response مناسب:

```http
403 Forbidden
```

است.

مثلاً:

```js
return res.status(403).json({
  message: "CSRF validation failed"
});
```

# 115.44 - CSRF فقط با یک Middleware حل نمی‌شود

ممکن است Middleware داشته باشیم:

```js
app.use(csrfProtection);
```

اما اگر برخی Endpointها از آن عبور کنند یا Authentication به شکل دیگری پیاده‌سازی شده باشد، همچنان ممکن است مشکل باقی بماند.

باید کل Application بررسی شود.

# اشتباهات رایج

## 1. تصور اینکه CORS جلوی CSRF را می‌گیرد

```text
CORS ≠ CSRF Protection
```

CORS و CSRF دو مسئله متفاوت هستند.

---

## 2. تصور اینکه JWT همیشه جلوی CSRF را می‌گیرد

نحوه نگهداری و ارسال JWT اهمیت دارد.

JWT داخل Cookie شرایط متفاوتی نسبت به JWT در Authorization Header دارد.

---

## 3. اعتماد کامل به SameSite

SameSite بسیار مفید است، اما طراحی امنیتی Application نباید بدون بررسی معماری فقط به یک مکانیزم وابسته باشد.

---

## 4. استفاده از GET برای عملیات حساس

اشتباه:

```http
GET /delete-user
```

عملیات تغییر وضعیت باید از Method مناسب استفاده کند.

---

## 5. استفاده از Token قابل پیش‌بینی

مثلاً:

```text
userId
timestamp
123456
```

برای CSRF Token مناسب نیستند.

---

## 6. بررسی نکردن CSRF روی Endpointهای حساس

مانند:

```text
/change-password
/transfer
/delete-account
/update-email
```

---

## 7. یکی دانستن Authentication و CSRF Protection

وجود Session معتبر به‌تنهایی ثابت نمی‌کند Request توسط کاربر موردنظر ایجاد شده است.

---

## 8. ارسال CSRF Token ثابت برای تمام کاربران

Token باید به شکل مناسب با Session یا Client مرتبط باشد.

---

## 9. قرار دادن Token در URL

مثلاً:

```text
/api/delete?csrfToken=...
```

قرار دادن Secret یا Token در URL می‌تواند باعث قرار گرفتن آن در History، Log یا مکان‌های دیگر شود.

# پاسخ تشریحی

## پاسخ تمرین 1

CSRF حمله‌ای است که در آن مهاجم تلاش می‌کند Browser یک کاربر احراز هویت‌شده را وادار به ارسال Request ناخواسته به یک Application کند.

---

## پاسخ تمرین 2

```text
Cross-Site Request Forgery
```

---

## پاسخ تمرین 3

زیرا Browser می‌تواند Cookie مربوط به سایت مقصد را در شرایط مشخص به‌صورت خودکار همراه Request ارسال کند.

در نتیجه Server ممکن است Request مهاجم را دارای Authentication معتبر تشخیص دهد.

---

## پاسخ تمرین 4

Authentication مشخص می‌کند کاربر چه کسی است.

CSRF Protection کمک می‌کند Server مطمئن شود Request حساس در شرایط مورد انتظار Application ایجاد شده و صرفاً به دلیل وجود Credential خودکار Browser پذیرفته نشده است.

---

## پاسخ تمرین 5

`SameSite` یک Attribute مربوط به Cookie است که نحوه ارسال Cookie در شرایط Cross-Site را کنترل می‌کند.

---

## پاسخ تمرین 6

```text
Strict
Lax
None
```

## پاسخ تمرین 7

`Strict` محدودیت بیشتری برای ارسال Cookie در شرایط Cross-Site اعمال می‌کند.

`Lax` محدودیت کمتری دارد و در بسیاری از سناریوهای معمول Web قابل استفاده است.

## پاسخ تمرین 8

CSRF Token مقداری است که Server تولید می‌کند و Client باید آن را همراه Request حساس ارسال کند.

Server Token را بررسی می‌کند و در صورت نامعتبر بودن Request را رد می‌کند.

بنابراین CORS جایگزین CSRF Protection نیست.

# مرحله 3 - Session ساده

برای مثال آموزشی یک Session بسیار ساده در Memory ایجاد می‌کنیم:

```js
const sessions = new Map();

function createSession(userId) {
  const sessionId = crypto.randomBytes(32).toString("hex");

  const csrfToken = crypto.randomBytes(32).toString("hex");

  sessions.set(sessionId, {
    userId,
    csrfToken
  });

  return {
    sessionId,
    csrfToken
  };
}
```

# مرحله 5 - Session Middleware

```js
function authentication(req, res, next) {
  const sessionId = req.cookies.session;

  if (!sessionId) {
    return res.status(401).json({
      message: "Unauthorized"
    });
  }

  const session = sessions.get(sessionId);

  if (!session) {
    return res.status(401).json({
      message: "Invalid session"
    });
  }

  req.session = session;

  next();
}
```

# مرحله 6 - CSRF Middleware

```js
function csrfProtection(req, res, next) {
  const token = req.get("X-CSRF-Token");

  if (!token) {
    return res.status(403).json({
      message: "CSRF token required"
    });
  }

  if (token !== req.session.csrfToken) {
    return res.status(403).json({
      message: "Invalid CSRF token"
    });
  }

  next();
}
```

برای Production بهتر است مقایسه Secretها نیز با روش مناسب انجام شود.

مهم‌ترین نکات:

```text
CORS ≠ CSRF Protection

Authentication ≠ CSRF Protection

JWT ≠ CSRF Protection کامل

SameSite ≠ تنها لایه امنیتی

GET نباید برای تغییر State استفاده شود
```

یک طراحی مناسب می‌تواند از چند لایه تشکیل شود:

```text
                 Request
                    │
                    ▼
             Authentication
                    │
                    ▼
              Authorization
                    │
                    ▼
              Origin Check
                    │
                    ▼
              CSRF Validation
                    │
                    ▼
                Validation
                    │
                    ▼
              Business Logic
```

در نهایت، امنیت CSRF نباید به یک Header، یک Cookie یا یک Middleware خلاصه شود؛ باید روش Authentication، نحوه ارسال Cookie، معماری Frontend، CORS، Origin و تمام Endpointهای State-Changing را در کنار یکدیگر بررسی کرد.
