# فصل 108 - امنیت در Node.js

## مقدمه

امنیت یکی از مهم‌ترین بخش‌های توسعه Backend است.

وقتی با Node.js یک برنامه واقعی می‌سازیم، معمولاً با اطلاعات حساسی مانند اطلاعات کاربران، رمز عبور، توکن‌های احراز هویت، اطلاعات پرداخت، فایل‌ها و داده‌های پایگاه داده سروکار داریم.

یک برنامه ممکن است از نظر عملکرد کاملاً درست باشد، اما اگر از نظر امنیتی ضعیف باشد، مهاجم می‌تواند:

* اطلاعات کاربران را سرقت کند.
* به حساب کاربران دسترسی پیدا کند.
* رمزهای عبور را استخراج کند.
* اطلاعات پایگاه داده را تغییر دهد یا حذف کند.
* درخواست‌های مخرب به سرور ارسال کند.
* فایل‌های غیرمجاز روی سرور آپلود کند.
* منابع سرور را مصرف کند.
* سرویس را از دسترس خارج کند.
* از آسیب‌پذیری‌های موجود در Dependencies استفاده کند.

بنابراین امنیت چیزی نیست که در پایان پروژه به برنامه اضافه کنیم؛ بلکه باید از همان ابتدای طراحی و توسعه در نظر گرفته شود.

در این فصل با مفاهیم پایه و مهم امنیت در برنامه‌های Node.js آشنا می‌شویم و یاد می‌گیریم چگونه از یک Backend در برابر بسیاری از حملات رایج محافظت کنیم.

> **نکته:** امنیت یک موضوع بسیار گسترده است. فصل‌های بعدی این بخش هرکدام به‌صورت اختصاصی موضوعاتی مانند Hash کردن Password، Encryption، Helmet، Rate Limit، CORS، XSS، CSRF، SQL Injection، NoSQL Injection و Environment Variables را بررسی می‌کنند. در این فصل ابتدا یک دید کلی و معماری امنیتی نسبت به Node.js پیدا می‌کنیم.

---

# 108.1 - امنیت چیست؟

امنیت نرم‌افزار یعنی محافظت از برنامه، اطلاعات و منابع آن در برابر دسترسی، تغییر، افشا یا سوءاستفاده غیرمجاز.

در Backend معمولاً باید از چند چیز محافظت کنیم:

```text
User
  ↓
Internet
  ↓
Web Server
  ↓
Application
  ↓
Database
  ↓
Files / External Services
```

هرکدام از این بخش‌ها می‌توانند نقطه‌ای برای حمله باشند.

برای مثال:

```text
Attacker
   ↓
HTTP Request
   ↓
Node.js Server
   ↓
Vulnerable Code
   ↓
Database
```

اگر ورودی کاربر بدون بررسی وارد Query شود، ممکن است SQL Injection اتفاق بیفتد.

اگر رمز عبور به‌صورت Plain Text ذخیره شود، در صورت لو رفتن Database تمام رمزها در اختیار مهاجم قرار می‌گیرند.

اگر محدودیتی برای تعداد درخواست‌ها وجود نداشته باشد، مهاجم می‌تواند تعداد بسیار زیادی Request ارسال کند.

# 108.2 - سه اصل مهم امنیت

یکی از مفاهیم پایه در امنیت، سه اصل معروف **CIA Triad** است.

## Confidentiality

محرمانگی یعنی اطلاعات فقط در اختیار افراد مجاز قرار بگیرد.

مثلاً:

```text
Password
Access Token
Personal Information
Payment Information
```

نباید برای کاربران غیرمجاز قابل مشاهده باشند.

---

## Integrity

تمامیت یا صحت اطلاعات یعنی داده‌ها بدون اجازه تغییر نکنند.

برای مثال یک کاربر نباید بتواند:

```text
balance = 100
```

را به:

```text
balance = 1000000
```

تغییر دهد.

---

## Availability

دسترس‌پذیری یعنی سرویس در زمان مورد نیاز در دسترس باشد.

برای مثال مهاجم نباید بتواند با ارسال میلیون‌ها درخواست، سرور را از کار بیندازد.

# 108.4 - Trust Nothing

یکی از مهم‌ترین اصول امنیتی:

> هیچ ورودی خارجی را به‌صورت پیش‌فرض قابل اعتماد فرض نکنید.

ورودی خارجی می‌تواند از موارد مختلفی وارد برنامه شود:

```text
req.body
req.params
req.query
req.headers
cookies
uploaded files
environment
external APIs
WebSocket messages
```

مثلاً فرض کنید API زیر را داریم:

```http
POST /users
```

و کاربر این داده را ارسال می‌کند:

```json
{
  "name": "Sobhan",
  "age": 20
}
```

نباید فرض کنیم همیشه همین داده ارسال می‌شود.

ممکن است مهاجم ارسال کند:

```json
{
  "name": "<malicious-data>",
  "age": "hello"
}
```

یا حتی ساختار کاملاً متفاوتی ارسال کند.

پس باید ورودی را:

1. دریافت کنیم.
2. اعتبارسنجی کنیم.
3. پاک‌سازی یا Normalize کنیم.
4. سپس از آن استفاده کنیم.

# 108.5 - Input Validation

Validation یعنی بررسی کنیم داده‌ای که وارد برنامه می‌شود شرایط مورد انتظار ما را دارد یا خیر.

مثلاً اگر سن باید عدد باشد:

```js
const age = 20;
```

معتبر است.

اما:

```js
const age = "hello";
```

معتبر نیست.

مثلاً برای Email:

```text
sobhan@example.com
```

می‌تواند معتبر باشد.

اما:

```text
hello
```

ساختار Email ندارد.

---

## Validation در Backend ضروری است

حتی اگر Frontend Validation داشته باشیم، باز هم باید در Backend Validation انجام دهیم.

چرا؟

چون کاربر می‌تواند مستقیماً API را صدا بزند و Frontend را دور بزند.

```text
Frontend
   ↓
Validation
   ↓
Backend
   ↓
Database
```

نباید فقط به Validation سمت Frontend اعتماد کنیم.

بهتر است:

```text
Client Validation
+
Server Validation
```

داشته باشیم.

# 108.7 - Principle of Least Privilege

یکی از اصول مهم امنیتی:

> هر شخص، سرویس یا بخش برنامه فقط باید حداقل دسترسی مورد نیاز خود را داشته باشد.

مثلاً اگر یک API فقط باید اطلاعات کاربران را بخواند، نباید دسترسی حذف Database را داشته باشد.

به جای:

```text
Full Access
```

بهتر است:

```text
Read Only
```

باشد.

این اصل برای:

* کاربران
* Database
* API Keys
* Services
* Containers
* Files
* Processes

قابل استفاده است.

# 108.8 - Password Security

رمز عبور نباید به‌صورت Plain Text ذخیره شود.

اشتباه:

```js
{
  email: "user@example.com",
  password: "123456"
}
```

اگر Database لو برود، رمز کاربران مستقیماً در اختیار مهاجم قرار می‌گیرد.

به‌جای ذخیره مستقیم Password باید از Password Hashing استفاده کنیم.

ساختار بهتر:

```text
Password
   ↓
Hash Function
   ↓
Password Hash
   ↓
Database
```

مثلاً:

```text
Password:
MySecretPassword

Stored:
$2b$...
```

در فصل 109 به‌صورت کامل Hash Password را بررسی خواهیم کرد.

# 108.9 - Hash با Encryption متفاوت است

این دو مفهوم را نباید اشتباه بگیریم.

## Hash

Hash معمولاً یک‌طرفه است.

```text
Password
   ↓
Hash
   ↓
Hash Value
```

هدف آن این است که مقدار اصلی را مستقیماً نتوانیم از Hash به دست بیاوریم.

برای Password معمولاً از الگوریتم‌های مناسب Password Hashing مانند:

```text
bcrypt
scrypt
Argon2
```

استفاده می‌شود.

---

## Encryption

Encryption برای تبدیل داده به شکلی است که با یک Key بتوان آن را رمزگشایی کرد.

```text
Plain Data
    ↓
Encryption + Key
    ↓
Encrypted Data
    ↓
Decryption + Key
    ↓
Plain Data
```

Encryption در فصل 110 بررسی خواهد شد.

# 108.10 - مدیریت Secretها

اطلاعات حساس نباید مستقیماً داخل Source Code قرار بگیرند.

مثلاً این کار مناسب نیست:

```env
JWT_SECRET=...
API_KEY=...
```

و در Node.js:

```js
const secret = process.env.JWT_SECRET;
```

فصل 118 به Environment Variables اختصاص دارد.

```text
 HTTPS
```

# 108.14 - Cookie Security

اگر از Cookie برای Session یا Token استفاده می‌کنیم، باید تنظیمات امنیتی مناسب داشته باشیم.

برخی Attributeهای مهم Cookie عبارت‌اند از:

```text
HttpOnly
Secure
SameSite
```

### HttpOnly

باعث می‌شود JavaScript سمت Client نتواند مستقیماً Cookie را بخواند.

### Secure

Cookie فقط از طریق HTTPS ارسال می‌شود.

### SameSite

به کنترل ارسال Cookie در درخواست‌های Cross-Site کمک می‌کند.

# 108.15 - XSS

XSS مخفف:

```text
Cross-Site Scripting
```

است.

در این نوع حمله، مهاجم تلاش می‌کند محتوای مخرب را وارد صفحه یا سیستم کند تا در Context کاربر اجرا شود.

مثلاً اگر یک برنامه متن کاربر را بدون کنترل مناسب نمایش دهد، می‌تواند خطرناک باشد.

برای کاهش خطر XSS باید:

* ورودی‌ها را Validate کنیم.
* خروجی‌ها را به شکل مناسب Encode کنیم.
* HTML را بدون نیاز وارد صفحه نکنیم.
* از Security Headers استفاده کنیم.
* از ابزارهای مناسب Sanitization در موارد لازم استفاده کنیم.

فصل 114 به‌صورت کامل به XSS اختصاص دارد.

---

# 108.16 - SQL Injection

SQL Injection یکی از حملات معروف به برنامه‌هایی است که Queryهای SQL را به‌صورت ناامن می‌سازند.

مثلاً ساخت Query با Concatenation مستقیم ورودی کاربر:

```js
const query = `
  SELECT *
  FROM users
  WHERE email = '${email}'
`;
```

می‌تواند خطرناک باشد.

راهکار اصلی:

```text
Parameterized Query
```

یا استفاده صحیح از ORM/Query Builderها است.

مثلاً به‌صورت مفهومی:

```text
SQL Query
+
Parameters
```

به جای ساختن SQL با String Concatenation.

فصل 116 به SQL Injection اختصاص دارد.

---

# 108.17 - NoSQL Injection

استفاده از MongoDB یا Databaseهای NoSQL به معنی حذف کامل Injection نیست.

مثلاً اگر داده کاربر مستقیماً وارد Query شود:

```js
{
  username: userInput
}
```

باید نوع و ساختار ورودی کنترل شود.

نباید فرض کنیم چون SQL نداریم، Injection نیز وجود ندارد.

فصل 117 به NoSQL Injection اختصاص دارد.

# 108.18 - Rate Limiting

مهاجم می‌تواند درخواست‌های زیادی به Server ارسال کند.

مثلاً:

```text
POST /login
POST /login
POST /login
POST /login
...
```

اگر محدودیتی وجود نداشته باشد، ممکن است:

* Server تحت فشار قرار بگیرد.
* Brute Force انجام شود.
* منابع مصرف شوند.

Rate Limiting می‌تواند تعداد درخواست‌ها را محدود کند.

مثلاً:

```text
100 requests / minute
```

یا برای Login محدودیت شدیدتری قرار دهیم.

فصل 112 به Rate Limit اختصاص دارد.

# 108.19 - Brute Force

در حمله Brute Force، مهاجم تلاش می‌کند تعداد زیادی ترکیب مختلف را امتحان کند.

مثلاً:

```text
Password 1
Password 2
Password 3
...
```

برای مقابله با آن می‌توان از مواردی مانند:

* Rate Limiting
* Password Policy
* Account Lockout با طراحی مناسب
* MFA
* CAPTCHA در سناریوهای مناسب
* Monitoring

استفاده کرد.

# 108.20 - CORS

CORS مخفف:

```text
Cross-Origin Resource Sharing
```

است.

مثلاً تنظیم بیش از حد باز:

```text
Allow Any Origin
```

ممکن است برای بعضی معماری‌ها نامناسب باشد.

بهتر است Originهای مورد نیاز را مشخص کنیم.

فصل 113 به CORS اختصاص دارد.

# 108.21 - CSRF

CSRF مخفف:

```text
Cross-Site Request Forgery
```

است.

این حمله معمولاً زمانی اهمیت ویژه پیدا می‌کند که Authentication بر پایه Cookie باشد و Browser بتواند Cookie را به‌صورت خودکار ارسال کند.

راهکارهای دفاعی بسته به معماری می‌توانند شامل:

* SameSite Cookie
* CSRF Token
* بررسی Origin
* بررسی Referer در سناریوهای مناسب
* طراحی صحیح Authentication

باشند.

فصل 115 به CSRF اختصاص دارد.

# 108.22 - File Upload Security

آپلود فایل یکی از قسمت‌های حساس Backend است.

نباید صرفاً به نام فایل اعتماد کنیم.

مواردی که باید بررسی شوند:

```text
File Size
File Type
MIME Type
File Extension
File Content
File Name
Storage Location
Access Permission
```

مثلاً نباید اجازه دهیم کاربر هر فایلی را بدون محدودیت روی Server ذخیره کند.

همچنین بهتر است فایل‌های User در مسیرهایی قرار بگیرند که امکان اجرای ناخواسته آن‌ها وجود نداشته باشد.

# 108.23 - Path Traversal

یکی از خطرهای مرتبط با فایل‌ها Path Traversal است.

مثلاً ورودی مخرب ممکن است تلاش کند به مسیرهای خارج از محدوده مجاز دسترسی پیدا کند.

نمونه مفهومی:

```text
../../secret-file
```

بنابراین هنگام کار با مسیر فایل باید:

* ورودی را Validate کنیم.
* مسیر نهایی را بررسی کنیم.
* از Pathهای کنترل‌شده استفاده کنیم.
* دسترسی به فایل‌ها را محدود کنیم.

ماژول `path` در Node.js برای مدیریت صحیح مسیرها بسیار مهم است.

# 108.24 - Error Handling و امنیت

Error Message نباید اطلاعات حساس Server را در اختیار کاربر قرار دهد.

```text
Database Connection String
File System Path
Internal Stack Trace
API Keys
Environment Variables
SQL Query
Internal Architecture
```

در محیط Development می‌توان جزئیات بیشتری نمایش داد.

اما در Production معمولاً بهتر است پاسخ عمومی باشد:

```json
{
  "message": "Internal Server Error"
```

و جزئیات کامل خطا در Logging امن ثبت شود.

# 108.25 - Logging امن

Logging برای تشخیص مشکلات و حملات بسیار مهم است.

اما نباید اطلاعات حساس را Log کنیم.

مثلاً این کار خطرناک است:

```js
console.log({
  email,
  password,
  token
```

به‌خصوص:

# 108.27 - Supply Chain Security

## پاسخ تمرین 3

یک پیاده‌سازی ساده:

```js
function createUser(age) {
  if (typeof age !== "number") {
    throw new Error("Age must be a number");
  }

  if (!Number.isFinite(age)) {
    throw new Error("Age must be a finite number");
  }

  if (age < 0) {
    throw new Error("Age cannot be negative");
  }

  return {
    age
  };
}
```

در پروژه واقعی می‌توان Validation را با ابزارهای تخصصی نیز انجام داد.

## پاسخ تمرین 4

```js
const permissions = {
  user: ["read"],
  editor: ["read", "write"],
  admin: ["read", "write", "delete"]
};
```

سپس:

```js
function can(role, action) {
  return permissions[role]?.includes(action) ?? false;
}
```

مثلاً:

```js
can("user", "read");   // true
can("user", "delete"); // false

can("editor", "write"); // true

can("admin", "delete"); // true
```

# مینی‌پروژه - طراحی یک Secure User API

در این مینی‌پروژه قرار است یک Backend ساده برای مدیریت کاربران طراحی کنیم که اصول پایه امنیت را رعایت کند.

## هدف پروژه

API زیر را در نظر بگیرید:

```text

GET    /users/me
PATCH  /users/me
```

---

## مرحله 1 - Register

کاربر اطلاعات زیر را ارسال می‌کند:

```json
{
  "email": "user@example.com",
  "password": "MyPassword123"
}
```

Server باید:

1. ورودی را Validate کند.
2. Email را بررسی کند.
3. Password را بررسی کند.
4. Password را Hash کند.
5. User را در Database ذخیره کند.
6. Password خام را ذخیره نکند.
7. Password را Log نکند.

---

## مرحله 2 - Login

کاربر:

```text
Email
Password
```

را ارسال می‌کند.

Server باید:

```text
Validate
   ↓
Find User
   ↓
Compare Password
   ↓
Create Authentication Token
```

را انجام دهد.

---

## مرحله 3 - Protected Route

Endpoint:

```text
GET /users/me
```

باید فقط برای کاربر Authentication شده قابل دسترسی باشد.

جریان:

```text
Request
   ↓
Authentication Middleware
   ↓
Validate Token
   ↓
Identify User
   ↓
Controller
```

---

## مرحله 4 - Authorization

فرض کنید بعداً Roleهای زیر اضافه می‌شوند:

```text
user
admin
```

و Endpoint زیر فقط برای Admin است:

```text
DELETE /users/:id
```

باید علاوه بر Authentication، Authorization نیز انجام شود.

```text
Authentication
       ↓
Authorization
       ↓
Delete User
```

---

## مرحله 5 - Rate Limit

برای Endpoint زیر محدودیت قرار دهید:

```text

```

هدف:

```text
جلوگیری از Brute Force
```

---

## مرحله 6 - Error Handling

اطلاعات حساس نباید به Client برگردند.

برای خطای داخلی:

```json
{
  "message": "Internal Server Error"
}
```

اما جزئیات خطا باید برای Debugging در Logging مناسب ثبت شود.

# نتیجه‌گیری

امنیت در Node.js یک Feature مستقل نیست؛ بلکه مجموعه‌ای از اصول و تکنیک‌هایی است که باید در تمام قسمت‌های Backend رعایت شوند.

یک Backend امن فقط به این معنی نیست که Passwordها Hash شده‌اند.

ما باید کل مسیر را بررسی کنیم:

```text

   ↓

   ↓

   ↓

   ↓
Authorization
   ↓
Business Logic
   ↓
Database
   ↓
External Services
```

و در تمام این لایه‌ها به موارد امنیتی توجه کنیم.

در فصل‌های بعدی این بخش، هرکدام از مهم‌ترین موضوعات امنیت Node.js را عمیق‌تر بررسی خواهیم کرد:

```text
109 → Hash Password
110 → Encryption
111 → Helmet
112 → Rate Limit
113 → CORS
114 → XSS
```
