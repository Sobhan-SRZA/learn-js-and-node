# فصل 116 - SQL Injection

## مقدمه

در فصل‌های قبل با بخش‌های مختلف امنیت در Node.js آشنا شدیم. یکی از مهم‌ترین آسیب‌پذیری‌هایی که در برنامه‌های Backend و به‌خصوص برنامه‌هایی که با Databaseهای SQL کار می‌کنند باید بشناسیم، **SQL Injection** است.

SQL Injection زمانی اتفاق می‌افتد که داده‌ای که کاربر ارسال کرده است، بدون کنترل و به شکل ناامن وارد Query SQL شود و باعث شود ساختار Query تغییر کند.

به زبان ساده:

```text
User Input
    ↓
Node.js
    ↓
SQL Query
    ↓
Database
```

اگر ورودی کاربر به‌صورت ناامن مستقیماً وارد Query شود، ممکن است کاربر بتواند رفتار Query را تغییر دهد.

این آسیب‌پذیری می‌تواند پیامدهایی مانند:

```text
خواندن اطلاعات غیرمجاز
تغییر اطلاعات
حذف اطلاعات
دور زدن Login
افشای اطلاعات حساس
```

داشته باشد.

بنابراین SQL Injection یکی از مهم‌ترین موضوعات امنیتی هنگام ساخت API با Node.js و SQL Database است.

---

# 116.1 - SQL Injection چیست؟

فرض کنید یک API برای Login داریم.

کاربر ارسال می‌کند:

```json
{
  "username": "sobhan",
  "password": "123456"
}
```

برنامه ممکن است بخواهد Query زیر را ایجاد کند:

```sql
SELECT *
FROM users
WHERE username = 'sobhan'
AND password = '123456';
```

اگر برنامه مقدار ورودی کاربر را مستقیماً داخل String Query قرار دهد، کاربر می‌تواند ورودی خاصی ارسال کند که ساختار Query را تغییر دهد.

مشکل اصلی این است:

```text
User Input
+
SQL Code
```

نباید با یکدیگر ترکیب شوند.

---

# 116.2 - یک مثال آسیب‌پذیر

کد خطرناک:

```js
const username = req.body.username;
const password = req.body.password;

const query = `
  SELECT *
  FROM users
  WHERE username = '${username}'
  AND password = '${password}'
`;
```

اینجا مقدار `username` و `password` مستقیماً وارد SQL شده‌اند.

مثلاً اگر کاربر مقدار عادی ارسال کند:

```text
sobhan
```

Query طبیعی خواهد بود.

اما اگر ورودی شامل کاراکترهایی باشد که ساختار SQL را تغییر دهند، Query نهایی می‌تواند برخلاف انتظار برنامه عمل کند.

---

# 116.3 - مشکل اصلی String Concatenation

یکی از الگوهای خطرناک:

```js
const query =
  "SELECT * FROM users WHERE username = '" +
  username +
  "'";
```

یا:

```js
const query = `
  SELECT *
  FROM users
  WHERE username = '${username}'
`;
```

است.

مشکل:

```text
Code
+
Data
```

با یکدیگر ترکیب شده‌اند.

روش امن باید این دو را از یکدیگر جدا کند.

---

# 116.4 - SQL Injection چگونه اتفاق می‌افتد؟

جریان آسیب‌پذیر:

```text
User Input
    ↓
String Concatenation
    ↓
SQL Query
    ↓
Database
```

جریان امن:

```text
User Input
    ↓
Parameterized Query
    ↓
Database Driver
    ↓
SQL Query
```

در روش دوم Database Driver مقدار کاربر را به‌عنوان **Data** در نظر می‌گیرد، نه بخشی از SQL Code.

---

# 116.5 - Parameterized Query چیست؟

Parameterized Query یا Prepared Statement یکی از مهم‌ترین روش‌های جلوگیری از SQL Injection است.

به‌جای اینکه مقدار کاربر را مستقیماً وارد Query کنیم، از Placeholder استفاده می‌کنیم.

مثلاً:

```sql
SELECT *
FROM users
WHERE username = ?;
```

سپس مقدار را جداگانه به Driver می‌دهیم.

---

# 116.6 - Parameterized Query در Node.js

نحوه استفاده به Database و Driver مورد استفاده بستگی دارد.

برای مثال در PostgreSQL:

```js
const result = await pool.query(
  "SELECT * FROM users WHERE username = $1",
  [username]
);
```

در اینجا:

```text
$1
```

Placeholder است.

و:

```js
[username]
```

مقدار آن را مشخص می‌کند.

---

# 116.7 - چرا این روش امن‌تر است؟

در:

```js
pool.query(
  "SELECT * FROM users WHERE username = $1",
  [username]
);
```

SQL و Data جدا هستند.

یعنی:

```text
SQL:
SELECT * FROM users WHERE username = $1

Data:
username
```

Database Driver این دو را به شکلی مناسب مدیریت می‌کند.

---

# 116.8 - مثال با MySQL

در MySQL معمولاً می‌توان از `?` به‌عنوان Placeholder استفاده کرد.

مثلاً:

```js
const [rows] = await connection.execute(
  "SELECT * FROM users WHERE username = ?",
  [username]
);
```

در اینجا نیز مقدار کاربر به‌عنوان Parameter ارسال شده است.

---

# 116.9 - مثال با SQLite

در SQLite نیز می‌توان از Parameter استفاده کرد.

برای مثال:

```js
const user = db
  .prepare("SELECT * FROM users WHERE username = ?")
  .get(username);
```

اصل کلی همچنان یکی است:

```text
SQL Structure
≠
User Data
```

---

# 116.10 - SQL Injection در Login

یکی از سناریوهای معروف SQL Injection مربوط به Login است.

کد آسیب‌پذیر:

```js
const query = `
  SELECT *
  FROM users
  WHERE username = '${username}'
  AND password = '${password}'
`;
```

مشکل اینجاست که ورودی Login مستقیماً وارد Query شده است.

---

# 116.11 - روش امن Login

بهتر است Query پارامتری باشد:

```js
const result = await pool.query(
  `
  SELECT id, username, password_hash
  FROM users
  WHERE username = $1
  `,
  [username]
);
```

سپس Password باید با Hash ذخیره‌شده مقایسه شود.

مثلاً:

```text
User Password
      ↓
Hash Verification
      ↓
Stored Password Hash
```

نباید Password خام را در Database ذخیره کنیم.

---

# 116.12 - SQL Injection در Search

فرض کنید API زیر داریم:

```http
GET /users?search=sobhan
```

کد آسیب‌پذیر:

```js
const query = `
  SELECT *
  FROM users
  WHERE username LIKE '%${search}%'
`;
```

این روش مناسب نیست.

روش پارامتری:

```js
const result = await pool.query(
  `
  SELECT *
  FROM users
  WHERE username LIKE $1
  `,
  [`%${search}%`]
);
```

---

# 116.13 - SQL Injection در INSERT

کد خطرناک:

```js
const query = `
  INSERT INTO users (username, email)
  VALUES ('${username}', '${email}')
`;
```

روش بهتر:

```js
const result = await pool.query(
  `
  INSERT INTO users (username, email)
  VALUES ($1, $2)
  `,
  [username, email]
);
```

---

# 116.14 - SQL Injection در UPDATE

کد آسیب‌پذیر:

```js
const query = `
  UPDATE users
  SET email = '${email}'
  WHERE id = ${id}
`;
```

روش امن‌تر:

```js
await pool.query(
  `
  UPDATE users
  SET email = $1
  WHERE id = $2
  `,
  [email, id]
);
```

---

# 116.15 - SQL Injection در DELETE

کد خطرناک:

```js
const query = `
  DELETE FROM users
  WHERE id = ${id}
`;
```

روش پارامتری:

```js
await pool.query(
  `
  DELETE FROM users
  WHERE id = $1
  `,
  [id]
);
```

---

# 116.16 - فقط Stringها خطرناک نیستند

ممکن است تصور کنیم فقط Stringها باعث SQL Injection می‌شوند.

اما این کد نیز الگوی مناسبی نیست:

```js
const query = `
  SELECT *
  FROM users
  WHERE id = ${req.params.id}
`;
```

حتی اگر انتظار داشته باشیم `id` عدد باشد، نباید ورودی Request را بدون کنترل و به شکل مستقیم داخل Query قرار دهیم.

روش بهتر:

```js
const id = Number(req.params.id);

if (!Number.isInteger(id)) {
  return res.status(400).json({
    message: "Invalid id"
  });
}

const result = await pool.query(
  "SELECT * FROM users WHERE id = $1",
  [id]
);
```

---

# 116.17 - Validation و Parameterization

دو مفهوم مهم:

```text
Validation
Parameterization
```

هستند.

Validation مشخص می‌کند:

```text
آیا داده از نظر Business Rule معتبر است؟
```

Parameterization کمک می‌کند:

```text
داده کاربر به‌عنوان SQL Code تفسیر نشود.
```

پس:

```text
Validation
≠
SQL Injection Protection
```

هر دو اهمیت دارند.

---

# 116.18 - آیا فقط Validation کافی است؟

خیر.

مثلاً:

```js
const id = Number(req.params.id);
```

خوب است، اما نباید به این معنی باشد که:

```js
const query = `SELECT * FROM users WHERE id = ${id}`;
```

همیشه بهترین روش است.

بهتر است همچنان از Parameterized Query استفاده کنیم:

```js
pool.query(
  "SELECT * FROM users WHERE id = $1",
  [id]
);
```

---

# 116.19 - SQL Injection در ORDER BY

یکی از مواردی که باید دقت بیشتری داشته باشیم، قسمت‌هایی مانند:

```sql
ORDER BY
```

است.

فرض کنید:

```text
GET /users?sort=username
```

و کد:

```js
const query = `
  SELECT *
  FROM users
  ORDER BY ${sort}
`;
```

اینجا نمی‌توانیم صرفاً به شکل زیر عمل کنیم:

```js
"ORDER BY $1"
```

و انتظار داشته باشیم Placeholder مانند مقدار معمولی رفتار کند.

زیرا `sort` در اینجا بخشی از **SQL Structure** است، نه یک مقدار ساده.

---

# 116.20 - Allowlist برای Dynamic SQL

برای قسمت‌هایی مانند Column Name باید از Allowlist استفاده کنیم.

مثلاً:

```js
const allowedSortFields = {
  username: "username",
  email: "email",
  createdAt: "created_at"
};

const sortField = allowedSortFields[req.query.sort];

if (!sortField) {
  return res.status(400).json({
    message: "Invalid sort field"
  });
}
```

سپس:

```js
const query = `
  SELECT *
  FROM users
  ORDER BY ${sortField}
`;
```

در این حالت مقدار `sortField` از مجموعه‌ای مشخص و کنترل‌شده انتخاب شده است.

---

# 116.21 - Dynamic SQL

گاهی واقعاً نیاز داریم بخشی از SQL را به‌صورت Dynamic بسازیم.

مثلاً:

```text
ORDER BY
Column Name
Table Name
Direction
```

در این موارد باید تفاوت میان:

```text
Value
```

و:

```text
SQL Identifier / Structure
```

را بدانیم.

برای Value:

```text
Parameterized Query
```

برای Identifierهای محدود:

```text
Allowlist
```

---

# 116.22 - Dynamic Table Name

مثلاً:

```js
const table = req.query.table;

const query = `
  SELECT *
  FROM ${table}
`;
```

این طراحی خطرناک است.

Table Name را نباید مستقیماً از کاربر گرفت.

روش بهتر:

```js
const allowedTables = {
  users: "users",
  products: "products",
  orders: "orders"
};

const tableName = allowedTables[req.query.table];

if (!tableName) {
  return res.status(400).json({
    message: "Invalid table"
  });
}
```

---

# 116.23 - SQL Injection و ORM

استفاده از ORM می‌تواند بسیاری از Queryها را امن‌تر و ساده‌تر کند.

مثلاً ORMها معمولاً برای Queryهای معمولی Parameterization را مدیریت می‌کنند.

اما:

```text
ORM
≠
امنیت خودکار
```

اگر Query Raw بنویسیم، همچنان باید مراقب SQL Injection باشیم.

---

# 116.24 - Raw SQL

گاهی نیاز داریم SQL خام بنویسیم:

```js
const query = `
  SELECT *
  FROM users
  WHERE email = $1
`;
```

این کاملاً قابل استفاده است، به شرط اینکه ورودی‌ها به شکل Parameterized وارد شوند.

مشکل اصلی Raw SQL نیست.

مشکل این است:

```text
Unsafe Dynamic SQL
```

---

# 116.25 - Stored Procedure

در بعضی Databaseها می‌توان از Stored Procedure استفاده کرد.

اما استفاده از Stored Procedure به‌تنهایی تضمین نمی‌کند که SQL Injection وجود نداشته باشد.

اگر داخل Procedure نیز SQL Dynamic به‌صورت ناامن ساخته شود، همچنان امکان آسیب‌پذیری وجود دارد.

---

# 116.26 - Least Privilege

حتی اگر SQL Injection اتفاق بیفتد، سطح دسترسی Database User اهمیت زیادی دارد.

فرض کنید Application فقط نیاز دارد:

```text
SELECT
INSERT
UPDATE
```

انجام دهد.

اما Database User اجازه کامل داشته باشد:

```text
DROP DATABASE
CREATE DATABASE
ALTER SYSTEM
```

ریسک بسیار بیشتر می‌شود.

اصل مهم:

```text
Least Privilege
```

یعنی هر Account فقط حداقل دسترسی لازم را داشته باشد.

---

# 116.27 - Database User مخصوص Application

بهتر است Application با User مخصوص خودش به Database متصل شود:

```text
Application
    ↓
Application DB User
    ↓
Limited Permissions
```

نه اینکه از Account مدیریتی Database استفاده شود.

---

# 116.28 - SQL Injection و Error Handling

این کد مناسب نیست:

```js
try {
  await db.query(query);
} catch (error) {
  res.status(500).json({
    error: error.message
  });
}
```

زیرا ممکن است جزئیات Database را به Client نمایش دهد.

بهتر:

```js
try {
  await db.query(query);

  res.json({
    message: "Success"
  });
} catch (error) {
  console.error(error);

  res.status(500).json({
    message: "Internal server error"
  });
}
```

---

# 116.29 - اطلاعاتی که نباید به Client بدهیم

نباید Errorهایی مانند موارد زیر را بدون دلیل به Client نمایش دهیم:

```text
SQL Query
Database Host
Table Name
Column Name
Stack Trace
Database Credentials
Internal File Paths
```

Client معمولاً باید یک Error عمومی دریافت کند.

---

# 116.30 - Logging

از طرف دیگر، Error نباید کاملاً نادیده گرفته شود.

بهتر است اطلاعات مناسب در Server Log ثبت شود:

```js
console.error(error);
```

در Production بهتر است از سیستم Logging مناسب استفاده شود.

---

# 116.31 - SQL Injection و Transactions

Transaction مستقیماً جایگزین SQL Injection Protection نیست.

مثلاً:

```text
Transaction
≠
SQL Injection Protection
```

Transaction برای مدیریت Atomicity و سازگاری عملیات Database است.

در حالی که Parameterization برای جلوگیری از ترکیب ناامن Data و SQL اهمیت دارد.

---

# 116.32 - SQL Injection و Prepared Statement

Prepared Statement یکی از مفاهیم کلیدی برای مقابله با SQL Injection است.

ایده کلی:

```text
SQL Template
      +
Parameters
      ↓
Database Driver
```

به جای:

```text
User Input
      ↓
String Concatenation
      ↓
SQL
```

---

# 116.33 - یک الگوی امن در Node.js

مثلاً:

```js
async function findUserByEmail(email) {
  const result = await pool.query(
    `
    SELECT id, username, email
    FROM users
    WHERE email = $1
    `,
    [email]
  );

  return result.rows[0];
}
```

این الگو خوانا و قابل استفاده مجدد است.

---

# 116.34 - Repository Pattern

در پروژه‌های بزرگ می‌توان Database Access را جدا کرد:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
Database
```

مثلاً:

```js
async function findUserById(id) {
  const result = await pool.query(
    "SELECT * FROM users WHERE id = $1",
    [id]
  );

  return result.rows[0];
}
```

این کار باعث می‌شود Queryها متمرکزتر و قابل بررسی‌تر باشند.

---

# 116.35 - بررسی Queryهای پروژه

در Code Review باید دنبال الگوهای مشکوک بگردیم:

```js
`${userInput}`
```

در Queryهای SQL.

یا:

```js
"SELECT ... " + input
```

یا:

```js
"DELETE ... " + id
```

یا:

```js
`ORDER BY ${sort}`
```

هر Dynamic SQL باید بررسی شود.

# 116.36 - ابزارهای کمک‌کننده

برای کاهش خطا می‌توان از موارد زیر استفاده کرد:

```text
ORM
Query Builder
Prepared Statements
Static Analysis
Code Review
Security Testing
Integration Testing
```

اما هیچ‌کدام جای فهم اصول SQL Injection را نمی‌گیرند.

## 10. استفاده از SQL خام بدون بررسی

# مرحله 7 - Sort امن

فرض کنید کاربر بتواند انتخاب کند:

```text
username
email
createdAt
```

Allowlist:

```js
const allowedSortFields = {
  username: "username",
  email: "email",
  createdAt: "created_at"
};
```

استفاده:

```js
app.get("/users", async (req, res) => {
  const search = String(req.query.search ?? "");
  const sort = String(req.query.sort ?? "createdAt");

  const sortField = allowedSortFields[sort];

  if (!sortField) {
    return res.status(400).json({
      message: "Invalid sort field"
    });
  }

  const result = await pool.query(
    `
    SELECT id, username, email, created_at
    FROM users
    WHERE username ILIKE $1
    ORDER BY ${sortField}
    `,
    [`%${search}%`]
  );

  res.json(result.rows);
});
```

اینجا:

```text
search
```

یک Value است و با Parameterization کنترل شده است.

اما:

```text
sortField
```

یک SQL Identifier است و با Allowlist کنترل شده است.

# جمع‌بندی

SQL Injection نتیجه ترکیب ناامن:

```text
User Input
+
SQL Query
```

است.

یکی از مهم‌ترین اصول برای جلوگیری از آن:

```text
Parameterized Queries
```

است.

برای Valueها:

```js
pool.query(
  "SELECT * FROM users WHERE id = $1",
  [id]
);
```

و برای Dynamic Identifierهایی مانند Sort یا Column:

```text
Allowlist
```

استفاده می‌کنیم.

همچنین امنیت فقط با Parameterization تمام نمی‌شود:

```text
SQL Injection Protection
        +
Input Validation
        +
Least Privilege
        +
Authentication
        +
Authorization
        +
Secure Error Handling
        +
Logging
        +
Security Testing
```

در نتیجه یک Developer حرفه‌ای Node.js باید بتواند علاوه بر نوشتن Query، تشخیص دهد **کدام قسمت Query باید ثابت باشد، کدام قسمت باید Parameter شود و کدام قسمت باید با Allowlist کنترل شود.**
