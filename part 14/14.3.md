# فصل 110 - Encryption

## مقدمه

در فصل قبل یاد گرفتیم که برای ذخیره Password از **Hashing** استفاده می‌کنیم؛ زیرا معمولاً نمی‌خواهیم بتوانیم Password اصلی را از مقدار ذخیره‌شده بازیابی کنیم.

اما همیشه داده‌ها را نمی‌توانیم Hash کنیم.

گاهی لازم است داده‌ای را به شکلی ذخیره کنیم که بعداً بتوانیم مقدار اصلی آن را دوباره به دست بیاوریم.

برای مثال:

* اطلاعات حساس کاربران
* Tokenهای قابل بازیابی در برخی معماری‌ها
* اطلاعات محرمانه‌ای که برنامه باید بعداً استفاده کند
* داده‌های حساس ذخیره‌شده در Database
* اطلاعاتی که باید بین سرویس‌های مورد اعتماد منتقل شوند

در این موارد ممکن است از **Encryption** استفاده کنیم.

Encryption یعنی تبدیل داده قابل خواندن به داده‌ای رمزگذاری‌شده با استفاده از یک **Key**.

```text
Plaintext
    ↓
Encryption + Key
    ↓
Ciphertext
```

و برای برگرداندن داده:

```text
Ciphertext
    ↓
Decryption + Key
    ↓
Plaintext
```

در این فصل یاد می‌گیریم:

* Encryption چیست؟
* تفاوت Encryption و Hashing
* Plaintext و Ciphertext
* Key چیست؟
* Symmetric Encryption
* Asymmetric Encryption
* AES
* مفهوم IV
* مفهوم Authentication Tag
* استفاده از `node:crypto`
* AES-GCM در Node.js
* مدیریت Key
* Encryption در Database
* Encryption در انتقال اطلاعات
* Key Rotation
* تفاوت Encryption و Encoding
* اشتباهات رایج
* نکات حرفه‌ای
* تمرین
* پاسخ تشریحی
* مینی‌پروژه

---

# 110.1 - Encryption چیست؟

Encryption فرآیندی است که در آن یک داده قابل خواندن را به داده‌ای تبدیل می‌کنیم که بدون داشتن اطلاعات لازم برای Decryption قابل استفاده یا خواندن مستقیم نباشد.

داده اصلی را معمولاً:

```text
Plaintext
```

می‌نامیم.

داده رمزگذاری‌شده:

```text
Ciphertext
```

نام دارد.

ساختار کلی:

```text
Plaintext
    │
    │ Encryption
    │ + Key
    ▼
Ciphertext
```

و برعکس:

```text
Ciphertext
    │
    │ Decryption
    │ + Key
    ▼
Plaintext
```

---

# 110.2 - مثال ساده

فرض کنید اطلاعات زیر را داریم:

```text
National ID: 1234567890
```

اگر بخواهیم این اطلاعات را Encrypt کنیم:

```text
1234567890
     ↓
Encryption
     ↓
Encrypted Data
```

مقدار ذخیره‌شده دیگر نباید به‌سادگی قابل خواندن باشد.

بعداً برنامه می‌تواند با Key مناسب آن را Decrypt کند:

```text
Encrypted Data
      ↓
Decryption + Key
      ↓
1234567890
```

---

# 110.3 - چرا Encryption لازم است؟

فرض کنید اطلاعات حساس را در Database ذخیره می‌کنیم.

اگر Database به هر دلیلی افشا شود:

```text
Attacker
   ↓
Database
   ↓
Sensitive Data
```

اگر اطلاعات حساس بدون محافظت ذخیره شده باشند، مهاجم می‌تواند مستقیماً آن‌ها را مشاهده کند.

Encryption یک لایه محافظتی اضافه می‌کند:

```text
Attacker
   ↓
Database
   ↓
Encrypted Data
   ↓
Need Encryption Key
```

البته Encryption به‌تنهایی امنیت کامل ایجاد نمی‌کند.

اگر مهاجم هم Database و هم Encryption Key را به دست بیاورد، ممکن است بتواند داده‌ها را Decrypt کند.

بنابراین مدیریت Key بسیار مهم است.

---

# 110.4 - تفاوت Encryption و Hashing

این تفاوت را باید کاملاً یاد بگیریم.

## Hashing

```text
Plaintext
    ↓
Hash
```

هدف اصلی این است که مقدار اصلی را مستقیماً از Hash بازیابی نکنیم.

مثال:

```text
Password
    ↓
Password Hash
```

برای Password Storage مناسب است.

---

## Encryption

```text
Plaintext
    ↓
Encryption + Key
    ↓
Ciphertext
```

و بعد:

```text
Ciphertext
    ↓
Decryption + Key
    ↓
Plaintext
```

Encryption زمانی مناسب است که برنامه در آینده به داده اصلی نیاز داشته باشد.

---

# 110.5 - Encryption و Encoding

Encoding نیز با Encryption متفاوت است.

مثلاً Base64:

```js
const encoded = Buffer
  .from("Hello")
  .toString("base64");
```

خروجی ممکن است چیزی شبیه:

```text
SGVsbG8=
```

باشد.

اما Base64 رمزنگاری نیست.

هر شخصی می‌تواند آن را Decode کند:

```text
Base64
  ↓
Decode
  ↓
Hello
```

پس:

```text
Encoding ≠ Encryption
```

و:

```text
Base64 ≠ Security
```

---

# 110.6 - Key چیست؟

Key یک مقدار است که الگوریتم Encryption یا Decryption از آن استفاده می‌کند.

به‌صورت ساده:

```text
Plaintext
   +
Key
   ↓
Encryption
   ↓
Ciphertext
```

و:

```text
Ciphertext
   +
Key
   ↓
Decryption
   ↓
Plaintext
```

امنیت بسیاری از سیستم‌های Encryption به مدیریت صحیح Key وابسته است.

---

# 110.7 - Symmetric Encryption

در Symmetric Encryption معمولاً از یک Key برای Encryption و Decryption استفاده می‌شود.

```text
          Same Key
         /        \
        ↓          ↓
Encryption      Decryption
        ↓          ↑
     Ciphertext
```

به‌صورت ساده:

```text
Plaintext
   ↓
Encrypt + Key
   ↓
Ciphertext
   ↓
Decrypt + Key
   ↓
Plaintext
```

---

# 110.8 - مزایای Symmetric Encryption

Symmetric Encryption معمولاً:

* سریع است.
* برای حجم زیاد داده مناسب است.
* برای Encryption فایل‌ها مناسب است.
* برای Encryption داده‌های Database کاربرد دارد.

یکی از الگوریتم‌های معروف Symmetric Encryption:

```text
AES
```

است.

---

# 110.9 - Asymmetric Encryption

در Asymmetric Encryption از یک جفت Key استفاده می‌شود:

```text
Public Key
Private Key
```

به‌صورت مفهومی:

```text
Public Key
     ↓
Encryption
     ↓
Ciphertext
     ↓
Private Key
     ↓
Decryption
```

Public Key می‌تواند در اختیار دیگران قرار گیرد، اما Private Key باید محرمانه باقی بماند.

---

# 110.10 - Public Key و Private Key

Public Key:

```text
می‌تواند منتشر شود
```

Private Key:

```text
باید Secret باقی بماند
```

در سیستم‌های Asymmetric، این دو Key نقش‌های متفاوتی دارند.

از الگوریتم‌های شناخته‌شده در این حوزه می‌توان به:

```text
RSA
ECC
```

اشاره کرد.

---

# 110.11 - Symmetric یا Asymmetric؟

به‌صورت کلی:

| ویژگی      | Symmetric                   | Asymmetric                  |
| ---------- | --------------------------- | --------------------------- |
| تعداد Key  | یک Key اصلی                 | Public + Private            |
| سرعت       | معمولاً بالا                | معمولاً پایین‌تر            |
| داده حجیم  | مناسب                       | معمولاً مناسب نیست          |
| نمونه      | AES                         | RSA / ECC                   |
| مدیریت Key | نیازمند حفاظت از Secret Key | Private Key باید محافظت شود |

در سیستم‌های واقعی گاهی هر دو روش با هم استفاده می‌شوند.

---

# 110.12 - AES

AES مخفف:

```text
Advanced Encryption Standard
```

است.

AES یکی از الگوریتم‌های شناخته‌شده Symmetric Encryption است.

AES با Keyهای با اندازه‌های مشخص مانند:

```text
128-bit
192-bit
256-bit
```

کار می‌کند.

یکی از انتخاب‌های رایج در Applicationهای جدید:

```text
AES-256
```

است.

اما انتخاب الگوریتم و Mode باید با توجه به نیاز سیستم و کتابخانه‌های معتبر انجام شود.

---

# 110.13 - AES Mode

AES به‌تنهایی کافی نیست؛ باید Mode مناسب نیز انتخاب شود.

از Modeهای مختلفی وجود دارد، اما برای Applicationهای جدید باید به سمت **Authenticated Encryption** رفت.

یکی از گزینه‌های مهم:

```text
AES-GCM
```

است.

AES-GCM علاوه بر Confidentiality، امکان بررسی Integrity و Authenticity داده رمزگذاری‌شده را نیز فراهم می‌کند.

---

# 110.14 - چرا AES-GCM؟

فرض کنید فقط داده را Encrypt کنیم:

```text
Plaintext
   ↓
Encryption
   ↓
Ciphertext
```

ممکن است مسئله فقط مخفی کردن محتوا نباشد.

همچنین باید بتوانیم متوجه شویم که Ciphertext در مسیر یا هنگام ذخیره‌سازی دستکاری نشده است.

AES-GCM می‌تواند علاوه بر Ciphertext یک مقدار Authentication Tag نیز تولید کند:

```text
Plaintext
    ↓
AES-GCM
    ↓
Ciphertext + Authentication Tag
```

در هنگام Decryption، Tag بررسی می‌شود.

اگر داده دستکاری شده باشد، Decryption باید شکست بخورد.

---

# 110.15 - IV چیست؟

در بسیاری از الگوریتم‌های Symmetric Encryption از یک مقدار مانند:

```text
IV
```

یا Initialization Vector استفاده می‌شود.

در AES-GCM معمولاً از یک Nonce/IV با طول مناسب استفاده می‌شود.

نکته بسیار مهم:

> برای یک Key مشخص، نباید Nonce/IV را به‌صورت نادرست و تکراری استفاده کنیم.

در طراحی AES-GCM، مدیریت صحیح Nonce/IV حیاتی است.

---

# 110.16 - آیا IV باید Secret باشد؟

معمولاً IV/Nonce مانند Encryption Key Secret نیست.

می‌توان آن را همراه Ciphertext ذخیره یا منتقل کرد.

مثلاً:

```text
{
  iv,
  ciphertext,
  authTag
}
```

چیزی که باید Secret بماند:

```text
Encryption Key
```

است.

---

# 110.17 - Authentication Tag چیست؟

در AES-GCM، Authentication Tag برای بررسی صحت و اصالت Ciphertext استفاده می‌شود.

ساختار مفهومی:

```text
Plaintext
    ↓
AES-GCM
    ↓
┌───────────────┐
│ Ciphertext    │
│ Auth Tag      │
└───────────────┘
```

هنگام Decryption:

```text
Ciphertext
   +
Auth Tag
   +
Key
   ↓
AES-GCM
   ↓
Plaintext
```

اگر داده دستکاری شده باشد، بررسی Tag شکست می‌خورد.

---

# 110.18 - استفاده از `node:crypto`

Node.js ماژول داخلی:

```text
node:crypto
```

را برای عملیات Cryptographic در اختیار ما قرار می‌دهد.

مثلاً:

```js
import crypto from "node:crypto";
```

این ماژول قابلیت‌های مختلفی برای:

* Encryption
* Decryption
* Hashing
* Random Bytes
* Key Generation
* Digital Signature
* Cryptographic Operations

فراهم می‌کند.

---

# 110.19 - تولید Key تصادفی

برای ساخت Secret Key نباید از رشته‌های قابل حدس استفاده کنیم.

مثلاً:

```js
const key = "my-secret-key";
```

روش مناسبی برای تولید یک Key Cryptographic نیست.

می‌توان از قابلیت‌های Cryptographically Secure موجود در Node.js استفاده کرد.

مثلاً:

```js
import crypto from "node:crypto";

const key = crypto.randomBytes(32);
```

برای AES-256، 32 بایت برابر با 256 بیت است.

---

# 110.20 - AES-256-GCM در Node.js

یک نمونه آموزشی ساده:

```js
import crypto from "node:crypto";

const algorithm = "aes-256-gcm";
const key = crypto.randomBytes(32);
const iv = crypto.randomBytes(12);

const cipher = crypto.createCipheriv(
  algorithm,
  key,
  iv
);

const encrypted = Buffer.concat([
  cipher.update("Hello Node.js"),
  cipher.final()
]);

const authTag = cipher.getAuthTag();

console.log({
  iv: iv.toString("hex"),
  encrypted: encrypted.toString("hex"),
  authTag: authTag.toString("hex")
});
```

در این مثال:

```text
key
```

محرمانه است.

اما:

```text
iv
encrypted
authTag
```

می‌توانند برای انجام Decryption در کنار Ciphertext نگهداری شوند.

---

# 110.21 - Decryption با AES-GCM

برای Decrypt کردن:

```js
import crypto from "node:crypto";

const decipher = crypto.createDecipheriv(
  "aes-256-gcm",
  key,
  iv
);

decipher.setAuthTag(authTag);

const decrypted = Buffer.concat([
  decipher.update(encrypted),
  decipher.final()
]);

console.log(decrypted.toString("utf8"));
```

اگر اطلاعات دستکاری شده باشند، ممکن است عملیات Decryption در `final()` با خطا مواجه شود.

---

# 110.22 - ساختار داده Encryption

می‌توانیم اطلاعات مورد نیاز برای Decryption را به‌صورت ساختاری نگهداری کنیم:

```js
const encryptedData = {
  iv,
  authTag,
  ciphertext
};
```

در ذخیره‌سازی واقعی معمولاً این مقادیر به شکل مناسب Serialize می‌شوند.

مثلاً:

```json
{
  "iv": "...",
  "authTag": "...",
  "ciphertext": "..."
}
```

اما:

```text
key
```

نباید همراه این Object در Database عمومی ذخیره شود.

---

# 110.23 - Key را کجا ذخیره کنیم؟

این بخش بسیار مهم است.

اشتباه:

```js
const key = "123456789";
```

Key باید از Configuration امن یا Secret Management دریافت شود.

برای مثال در محیط ساده:

```env
ENCRYPTION_KEY=...
```

و:

```js
const key = Buffer.from(
  process.env.ENCRYPTION_KEY,
  "base64"
);
```

در سیستم‌های حساس‌تر می‌توان از Secret Managerهای تخصصی استفاده کرد.

اصل مهم:

```text
Database
     ↓
Encrypted Data

Secret Management
     ↓
Encryption Key
```

---

# 110.24 - چرا Key را کنار Ciphertext ذخیره نکنیم؟

اگر:

```text
Database
 ├── encryptedData
 └── encryptionKey
```

در یک محل قرار داشته باشند، در صورت افشای کامل Database، مهاجم ممکن است هر دو را در اختیار داشته باشد.

بهتر است Key در محل جدا و کنترل‌شده نگهداری شود:

```text
Database
   ↓
Ciphertext

Secret Manager
   ↓
Encryption Key
```

---

# 110.25 - Encryption در Database

گاهی لازم است بعضی Fieldها در Database به‌صورت Encryption شده ذخیره شوند.

مثلاً:

```text
User
├── id
├── email
├── phone
├── sensitiveData
└── ...
```

می‌توانیم:

```text
sensitiveData
      ↓
Encryption
      ↓
encryptedSensitiveData
```

را ذخیره کنیم.

اما باید بدانیم Encryption روی Query کردن داده نیز اثر می‌گذارد.

---

# 110.26 - مشکل Search روی داده Encryption شده

فرض کنید:

```text
phone = "09120000000"
```

را Encrypt کنیم.

Database دیگر مقدار واقعی را نمی‌بیند.

بنابراین Queryهایی مانند:

```sql
WHERE phone = '09120000000'
```

به شکل معمول قابل انجام نیستند.

این یکی از Trade-offهای Encryption است.

---

# 110.27 - Encryption و Performance

Encryption هزینه محاسباتی دارد.

اگر تمام داده‌های سیستم را بدون دلیل Encrypt کنیم:

```text
Performance
↓
Complexity
↑
Storage
↑
Key Management
↑
```

بنابراین باید مشخص کنیم کدام داده واقعاً نیاز به Encryption دارد.

---

# 110.28 - Encryption در Transit

یکی از مهم‌ترین کاربردهای Encryption، محافظت از اطلاعات هنگام انتقال است.

مثلاً:

```text
Client
   ↓
HTTPS / TLS
   ↓
Node.js Server
```

در اینجا TLS از داده در مسیر انتقال محافظت می‌کند.

به همین دلیل برای Production باید از HTTPS استفاده کنیم.

---

# 110.29 - Encryption at Rest

Encryption در زمان ذخیره‌سازی را می‌توان:

```text
Encryption at Rest
```

نامید.

مثلاً:

```text
Application
   ↓
Encrypted Data
   ↓
Database / Storage
```

این موضوع با Encryption در Transit متفاوت است.

---

# 110.30 - Encryption در Transit و At Rest

| نوع                   | هدف                     |
| --------------------- | ----------------------- |
| Encryption in Transit | محافظت هنگام انتقال     |
| Encryption at Rest    | محافظت هنگام ذخیره‌سازی |

مثلاً:

```text
Client
  │
  │ HTTPS
  ▼
Server
  │
  │ Encryption at Rest
  ▼
Database
```

یک سیستم امن ممکن است هر دو را به کار ببرد.

---

# 110.31 - آیا HTTPS جای Encryption در Database را می‌گیرد؟

خیر.

HTTPS از داده هنگام انتقال محافظت می‌کند.

اما وقتی داده به Database رسید:

```text
HTTPS
   ↓
Server
   ↓
Database
```

دیگر HTTPS به‌تنهایی از داده ذخیره‌شده محافظت نمی‌کند.

بنابراین بسته به Threat Model ممکن است به Encryption at Rest یا Field-Level Encryption نیز نیاز داشته باشیم.

---

# 110.32 - Key Rotation

ممکن است بخواهیم Encryption Key را در طول زمان تغییر دهیم.

این فرآیند:

```text
Key Rotation
```

نام دارد.

مثلاً:

```text
Old Key
   ↓
Data
```

و بعد:

```text
New Key
   ↓
Future Encryption
```

اما اگر داده‌های قبلی با Key قدیمی Encrypt شده باشند، باید برای Decryption آن‌ها Key قبلی نیز مدیریت شود.

یک معماری می‌تواند Keyها را با Version نگهداری کند:

```text
key-v1
key-v2
key-v3
```

و هر داده مشخص کند با کدام Key Version رمزگذاری شده است.

---

# 110.33 - Encryption و Key Versioning

مثلاً:

```json
{
  "version": 2,
  "iv": "...",
  "authTag": "...",
  "ciphertext": "..."
}
```

در این حالت برنامه می‌داند برای Decryption از کدام Key استفاده کند.

---

# 110.34 - Digital Signature با Encryption یکی نیست

Signature نیز با Encryption تفاوت دارد.

هدف Signature معمولاً:

```text
Integrity
+
Authenticity
```

است.

مثلاً:

```text
Data
  ↓
Signing
  ↓
Signature
```

گیرنده می‌تواند Signature را بررسی کند.

اما Signature الزاماً داده را مخفی نمی‌کند.

بنابراین:

```text
Encryption → Confidentiality
Signature → Integrity / Authenticity
```

این مفاهیم را نباید با هم اشتباه گرفت.

---

# 110.35 - آیا JWT رمزنگاری شده است؟

به‌صورت معمول JWTهایی که با الگوریتم‌های JWS استفاده می‌شوند، **Signed** هستند، نه اینکه Payload آن‌ها لزوماً Encrypt شده باشد.

بنابراین نباید اطلاعات بسیار محرمانه را فقط به این دلیل که داخل JWT قرار گرفته‌اند، مخفی فرض کنیم.

ساختار معمول JWT:

```text
Header
.
Payload
.
Signature
```

Payload معمولاً قابل Decode شدن است.

پس:

```text
Signed ≠ Encrypted
```

# 110.36 - چه زمانی از Encryption استفاده کنیم؟

مثلاً زمانی که:

```text
داده باید بعداً قابل بازیابی باشد
```

و در عین حال نمی‌خواهیم مقدار خام آن مستقیماً در Storage قرار گیرد.

نمونه‌های احتمالی:

```text
Sensitive Personal Data
API Credentials
Third-party Secrets
Private Configuration
Sensitive Business Data
```

اما برای هر داده حساس الزاماً Field-Level Encryption بهترین راهکار نیست؛ Threat Model و نیاز سیستم باید بررسی شود.

## پاسخ تمرین 6

نمونه:

```js
import crypto from "node:crypto";

const algorithm = "aes-256-gcm";
const key = crypto.randomBytes(32);
const iv = crypto.randomBytes(12);

const cipher = crypto.createCipheriv(
  algorithm,
  key,
  iv
);

const encrypted = Buffer.concat([
  cipher.update("Hello Node.js", "utf8"),
  cipher.final()
]);

const authTag = cipher.getAuthTag();

console.log({
  key: key.toString("base64"),
  iv: iv.toString("base64"),
  ciphertext: encrypted.toString("base64"),
  authTag: authTag.toString("base64")
});
```

در پروژه واقعی نباید Secret Key را در خروجی عمومی یا Log قرار دهیم؛ نمایش آن در این تمرین صرفاً برای فهم ساختار است.

```js
const decipher = crypto.createDecipheriv(

  key,
  iv

  decipher.update(encrypted),
  decipher.final()

console.log(decrypted.toString("utf8"));
```

# جمع‌بندی

Encryption یکی از ابزارهای مهم امنیت Backend است، اما باید دقیقاً بدانیم چه زمانی و چگونه از آن استفاده کنیم.

مهم‌ترین مفاهیم این فصل:

```text
Encryption
    ↓
Plaintext → Ciphertext
```

و:

```text
Decryption
    ↓
Ciphertext → Plaintext
```

همچنین:

```text
Hashing ≠ Encryption
Encoding ≠ Encryption
Signing ≠ Encryption
```

برای Password:

```text
Password
   ↓
Password Hashing
```

و برای داده‌ای که باید بعداً قابل بازیابی باشد، در صورت نیاز:

```text
Sensitive Data
   ↓
Encryption
   ↓
Ciphertext
```

در Node.js می‌توان از:

```js
import crypto from "node:crypto";
```

استفاده کرد و برای سناریوهای Symmetric Encryption، الگوریتم‌هایی مانند:

```text
AES-256-GCM
```

از گزینه‌های شناخته‌شده هستند.

در نهایت باید به خاطر داشته باشیم:

```text
Strong Algorithm
+
Secure Key
+
Correct IV/Nonce Handling
+
Authentication
+
Secure Key Storage
+
Key Rotation
+
Proper Authorization
```

همگی بخشی از یک سیستم Encryption قابل اتکا هستند.

**Encryption فقط به معنی Encrypt کردن داده نیست؛ مدیریت صحیح Key بخش بسیار مهم این مسئله است.**
