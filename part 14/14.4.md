# فصل 111 - Helmet

## مقدمه

در فصل‌های قبل با بخش‌های مختلف امنیت در Node.js آشنا شدیم؛ از Hash کردن Password و Encryption گرفته تا روش‌های محافظت از اطلاعات حساس.

اما امنیت یک برنامه فقط به Authentication، Password و Database محدود نمی‌شود.

وقتی یک برنامه Node.js به‌عنوان Web Server یا API اجرا می‌شود، مرورگر و Client از طریق HTTP با آن ارتباط برقرار می‌کنند. در این ارتباط، Headerهای HTTP نقش مهمی دارند و بعضی از آن‌ها می‌توانند به کاهش ریسک حملات رایج در سمت مرورگر کمک کنند.

یکی از ابزارهای معروف برای مدیریت برخی از این Security Headerها در برنامه‌های Express، پکیج **Helmet** است.

Helmet مجموعه‌ای از Middlewareهای کوچک برای Express است که با تنظیم Security Headerهای HTTP به افزایش امنیت Application کمک می‌کند.

به‌عنوان مثال، Helmet می‌تواند Headerهایی را برای کنترل مواردی مانند:

* جلوگیری از نمایش سایت در `iframe` در شرایط خاص
* کنترل نوع محتوای قابل تفسیر توسط Browser
* محدود کردن اطلاعات ارسال‌شده در `Referer`
* فعال کردن برخی سیاست‌های امنیتی مرورگر
* کنترل رفتار مربوط به Resourceها
* کاهش برخی حملات مبتنی بر Browser

تنظیم کند.

نکته مهم این است که Helmet یک **راه‌حل کامل امنیتی** نیست.

Helmet:

```text
Authentication
Authorization
Validation
Database Security
Password Hashing
Encryption
Rate Limiting
```

را جایگزین نمی‌کند.

بلکه یکی از لایه‌های امنیتی Application است:

```text
                Node.js Application
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
 Authentication   Validation     Helmet
        ↓              ↓              ↓
 Authorization    Database      Security Headers
        └──────────────┼──────────────┘
                       ↓
                    Security
```

---

# 111.1 - Helmet چیست؟

Helmet یک مجموعه Middleware برای Express است که Security Headerهای HTTP را تنظیم می‌کند.

در یک Application معمولی Express ممکن است Headerهای Response به شکل زیر باشند:

```http
HTTP/1.1 200 OK
Content-Type: text/html
```

Helmet می‌تواند Headerهای امنیتی بیشتری را به Response اضافه کند.

به‌صورت مفهومی:

```http
HTTP/1.1 200 OK
Content-Type: text/html
X-Content-Type-Options: nosniff
Content-Security-Policy: ...
Referrer-Policy: ...
...
```

هدف این Headerها این است که به Browser بگویند منابع و محتوای Response را با چه سیاست‌هایی مدیریت کند.

---

# 111.2 - چرا Security Headerها مهم هستند؟

Browser فقط HTML را دریافت نمی‌کند.

ممکن است یک صفحه شامل موارد مختلفی باشد:

```text
HTML
CSS
JavaScript
Image
Font
Iframe
API Request
External Resource
```

Browser باید تصمیم بگیرد با هرکدام چگونه رفتار کند.

Security Headerها می‌توانند در این تصمیم‌گیری نقش داشته باشند.

مثلاً:

```text
Server
   ↓
HTTP Response
   ↓
Security Headers
   ↓
Browser
```

در نتیجه بخشی از سیاست امنیتی Application از طریق HTTP Headerها به Browser منتقل می‌شود.

---

# 111.3 - نصب Helmet

اگر پروژه Express دارید، Helmet را نصب کنید:

```bash
npm install helmet
```

بعد:

```js
import express from "express";
import helmet from "helmet";

const app = express();

app.use(helmet());
```

با همین Middleware ساده، مجموعه‌ای از تنظیمات امنیتی Helmet فعال می‌شوند.

---

# 111.4 - استفاده پایه از Helmet

یک Server ساده:

```js
import express from "express";
import helmet from "helmet";

const app = express();

app.use(helmet());

app.get("/", (req, res) => {
  res.send("Hello Node.js");
});

app.listen(3000, () => {
  console.log("Server running on port 3000");
});
```

در اینجا:

```js
app.use(helmet());
```

باعث می‌شود Helmet روی Responseهای Application اعمال شود.

---

# 111.5 - Helmet چگونه کار می‌کند؟

Helmet خودش یک Server جداگانه نیست.

Helmet یک Middleware است.

بنابراین در زنجیره Middlewareهای Express قرار می‌گیرد:

```text
Request
   ↓
Helmet
   ↓
Other Middleware
   ↓
Route
   ↓
Response
```

به‌صورت ساده:

```js
app.use(helmet());
```

یعنی Helmet را در مسیر پردازش Requestهای Application قرار داده‌ایم.

---

# 111.6 - Middleware چیست؟

برای درک Helmet باید Middleware را بشناسیم.

Middleware تابعی است که در مسیر پردازش Request و Response اجرا می‌شود.

ساختار ساده:

```js
app.use((req, res, next) => {
  console.log("Middleware");

  next();
});
```

`next()` اجازه می‌دهد پردازش به Middleware یا Route بعدی منتقل شود.

Helmet نیز از همین مفهوم استفاده می‌کند.

---

# 111.7 - Security Header چیست؟

HTTP Headerها اطلاعاتی درباره Request یا Response هستند.

مثلاً:

```http
Content-Type: application/json
```

مشخص می‌کند نوع محتوا چیست.

Security Headerها برای اعمال برخی سیاست‌های امنیتی استفاده می‌شوند.

نمونه:

```http
X-Content-Type-Options: nosniff
```

یا:

```http
Referrer-Policy: no-referrer
```

یا:

```http
Content-Security-Policy: ...
```

---

# 111.8 - Header `X-Content-Type-Options`

یکی از Headerهای مهم:

```http
X-Content-Type-Options: nosniff
```

است.

هدف آن جلوگیری از برخی رفتارهای MIME Sniffing در Browser است.

به‌صورت ساده:

```text
Browser
   ↓
Content-Type
   ↓
nosniff
   ↓
Do not guess content type
```

Helmet می‌تواند این Header را تنظیم کند.

---

# 111.9 - MIME Sniffing چیست؟

Browserها گاهی برای تشخیص نوع محتوا رفتارهایی انجام می‌دهند که می‌تواند در بعضی شرایط خطرناک باشد.

مثلاً Server اعلام می‌کند:

```http
Content-Type: text/plain
```

اما محتوای Response ممکن است طوری باشد که Browser آن را به شکل دیگری تفسیر کند.

`nosniff` به Browser می‌گوید نوع اعلام‌شده توسط Server را به شکل مشخصی رعایت کند.

---

# 111.10 - Content-Security-Policy

یکی از مهم‌ترین مفاهیم مرتبط با Helmet:

```text
Content-Security-Policy
```

یا:

```text
CSP
```

است.

CSP به Browser می‌گوید منابع Application از چه Sourceهایی اجازه Load شدن دارند.

مثلاً:

```text
JavaScript
CSS
Image
Font
Frame
```

می‌توانند محدود شوند.

---

# 111.11 - هدف CSP

فرض کنید Application ما JavaScript را از منابع مختلف دریافت می‌کند:

```text
https://example.com
https://cdn.example.com
```

می‌توانیم سیاستی تعریف کنیم که فقط منابع مورد اعتماد اجازه اجرا داشته باشند.

به‌صورت مفهومی:

```text
Browser
   │
   ├── Trusted Source → Allow
   │
   └── Unknown Source → Block
```

این موضوع می‌تواند در کاهش ریسک برخی حملات مانند XSS مؤثر باشد.

---

# 111.12 - CSP و XSS

یکی از حملات مهم Web:

```text
Cross-Site Scripting
```

یا:

```text
XSS
```

است.

فرض کنید مهاجم بتواند Script مخرب را وارد صفحه کند.

در یک حالت ساده:

```html
<script>
  maliciousCode();
</script>
```

CSP می‌تواند یک لایه دفاعی اضافه کند و مشخص کند Browser اجازه اجرای Script را از چه منابعی دارد.

اما:

> CSP جایگزین Input Validation و Output Encoding نیست.

---

# 111.13 - فعال کردن CSP با Helmet

Helmet می‌تواند CSP را مدیریت کند:

```js
import helmet from "helmet";

app.use(
  helmet({
    contentSecurityPolicy: true
  })
);
```

در بسیاری از موارد:

```js
app.use(helmet());
```

خودش تنظیمات CSP پیش‌فرض را نیز در مجموعه Middlewareهایش در نظر می‌گیرد.

اما تنظیمات مناسب CSP به نوع Application وابسته است.

---

# 111.14 - چرا CSP ممکن است Application را خراب کند؟

فرض کنید Application شما از:

```text
Inline Script
External CDN
External Font
External Image
```

استفاده می‌کند.

اگر CSP را بیش از حد محدود کنیم، ممکن است Browser این منابع را Block کند.

مثلاً:

```text
Application
   ↓
CSP
   ↓
External Script
   ↓
BLOCK
```

در نتیجه ممکن است صفحه ظاهراً خراب شود.

بنابراین CSP باید با توجه به منابع واقعی Application تنظیم شود.

---

# 111.15 - `default-src`

یکی از Directiveهای CSP:

```text
default-src
```

است.

مثلاً:

```text
default-src 'self'
```

به‌صورت مفهومی یعنی منابع پیش‌فرض فقط از Origin خود Application مجاز باشند.

```text
Your Website
    ↓
'self'
    ↓
Own Origin
```

---

# 111.16 - `script-src`

برای محدود کردن JavaScript می‌توان از:

```text
script-src
```

استفاده کرد.

مثلاً:

```text
script-src 'self'
```

یعنی Scriptها از Origin خود Application مجاز باشند.

---

# 111.17 - `style-src`

برای CSS:

```text
style-src
```

استفاده می‌شود.

مثلاً:

```text
style-src 'self'
```

---

# 111.18 - `img-src`

برای Imageها:

```text
img-src
```

استفاده می‌شود.

مثلاً:

```text
img-src 'self' https://images.example.com
```

یعنی Imageها می‌توانند از Application و Domain مشخص‌شده دریافت شوند.

---

# 111.19 - تنظیم CSP در Helmet

مثال:

```js
import helmet from "helmet";

app.use(
  helmet({
    contentSecurityPolicy: {
      directives: {
        defaultSrc: ["'self'"],
        scriptSrc: ["'self'"],
        styleSrc: ["'self'"],
        imgSrc: ["'self'", "data:"]
      }
    }
  })
);
```

نکته مهم:

این مثال صرفاً آموزشی است.

CSP مناسب باید بر اساس منابع واقعی Application طراحی و تست شود.

---

# 111.20 - Referrer-Policy

Browserها ممکن است هنگام ارسال Request، اطلاعاتی درباره صفحه قبلی را از طریق:

```text
Referer
```

منتقل کنند.

Header زیر می‌تواند نحوه ارسال این اطلاعات را کنترل کند:

```http
Referrer-Policy
```

مثلاً:

```http
Referrer-Policy: no-referrer
```

یعنی Browser اطلاعات Referrer را ارسال نکند.

---

# 111.21 - چرا Referrer مهم است؟

فرض کنید URL شما شامل اطلاعات حساس باشد:

```text
https://example.com/reset?token=SECRET
```

اگر Referrer به شکل نامناسب منتقل شود، ممکن است اطلاعاتی که نباید منتقل شوند، در شرایط خاص به Resourceهای دیگر نشت کنند.

به همین دلیل کنترل Referrer می‌تواند بخشی از Security Policy باشد.

---

# 111.22 - X-Frame-Options

یکی دیگر از مفاهیم قدیمی‌تر ولی مهم:

```http
X-Frame-Options
```

است.

این Header می‌تواند مشخص کند صفحه در `iframe` چگونه نمایش داده شود.

مثلاً:

```http
X-Frame-Options: SAMEORIGIN
```

یعنی صفحه فقط در Frameهایی از همان Origin قابل نمایش باشد.

این موضوع در کاهش برخی سناریوهای:

```text
Clickjacking
```

مؤثر است.

---

# 111.23 - Clickjacking چیست؟

در Clickjacking، مهاجم ممکن است صفحه‌ای را در یک Frame قرار دهد و کاربر را فریب دهد تا روی چیزی کلیک کند که ظاهراً چیز دیگری به نظر می‌رسد.

به‌صورت مفهومی:

```text
Malicious Website
       ↓
     iframe
       ↓
Your Website
```

Security Policyهای مربوط به Frame می‌توانند یک لایه دفاعی در برابر چنین سناریوهایی باشند.

---

# 111.24 - HSTS

یکی دیگر از Headerهای مهم:

```text
Strict-Transport-Security
```

یا:

```text
HSTS
```

است.

HSTS به Browser می‌گوید Application باید از HTTPS استفاده کند.

مثلاً:

```http
Strict-Transport-Security: max-age=31536000
```

به Browser می‌گوید برای مدت مشخصی به HTTPS پایبند باشد.

---

# 111.25 - HSTS و HTTPS

HSTS را باید با دقت در Production فعال کرد.

ساختار:

```text
Browser
   ↓
HTTPS
   ↓
Node.js Application
```

اگر Application واقعاً از HTTPS پشتیبانی می‌کند، HSTS می‌تواند یک لایه امنیتی مهم باشد.

اما فعال کردن HSTS قبل از آماده بودن HTTPS می‌تواند باعث مشکل دسترسی شود.

---

# 111.26 - HTTPS Proxy و `trust proxy`

در بسیاری از Productionها Node.js مستقیماً به Internet متصل نیست.

ممکن است معماری به این شکل باشد:

```text
Browser
   ↓
HTTPS
   ↓
Reverse Proxy
   ↓
Node.js
```

مثلاً:

```text
Nginx
Load Balancer
Cloud Proxy
```

در این شرایط باید مفهوم `trust proxy` در Express را نیز درست مدیریت کنیم.

Helmet به‌تنهایی جایگزین تنظیم صحیح Reverse Proxy نمی‌شود.

---

# 111.27 - Helmet فقط برای Browser است؟

تمرکز اصلی Helmet روی HTTP Security Headerها و رفتار Browser است.

اگر API شما فقط برای:

```text
Mobile App
Other Backend
CLI
```

استفاده شود، برخی قابلیت‌های Browser-specific ممکن است اهمیت کمتری داشته باشند.

اما همچنان Security Headerها و سیاست‌های HTTP می‌توانند بخشی از Hardening API باشند.

---

# 111.28 - Helmet و REST API

برای یک REST API نیز می‌توان Helmet را فعال کرد:

```js
import express from "express";
import helmet from "helmet";

const app = express();

app.use(helmet());
app.use(express.json());

app.get("/api/users", (req, res) => {
  res.json({
    message: "Users"
  });
});

app.listen(3000);
```

Helmet به‌تنهایی API را امن نمی‌کند.

برای API واقعی به موارد دیگری مانند:

```text
Authentication
Authorization
Validation
Rate Limiting
CORS
Logging
Error Handling
Input Sanitization
```

نیز نیاز داریم.

---

# 111.29 - بررسی Headerهای Response

می‌توانیم Response Headerها را با ابزارهایی مانند Browser DevTools یا ابزارهای HTTP بررسی کنیم.

مثلاً:

```bash
curl -I http://localhost:3000
```

ممکن است Headerهایی مانند موارد زیر را ببینیم:

```text
Content-Security-Policy
Cross-Origin-Opener-Policy
Cross-Origin-Resource-Policy
Origin-Agent-Cluster
Referrer-Policy
Strict-Transport-Security
X-Content-Type-Options
X-DNS-Prefetch-Control
X-Download-Options
X-Frame-Options
X-Permitted-Cross-Domain-Policies
```

مجموع Headerهای دقیق به نسخه Helmet و تنظیمات Application بستگی دارد.

---

# 111.30 - Helmet و CORS

Helmet و CORS دو مفهوم متفاوت هستند.

Helmet:

```text
Security Headers
```

را مدیریت می‌کند.

CORS:

```text
Cross-Origin Resource Sharing
```

را مدیریت می‌کند.

مثلاً:

```text
Helmet
  ↓
Browser Security Policies

CORS
  ↓
Cross-Origin Requests
```

ممکن است Application به هر دو نیاز داشته باشد.

---

# 111.31 - Helmet و Rate Limiting

Helmet جلوی ارسال تعداد زیادی Request را نمی‌گیرد.

برای این کار به Rate Limiting نیاز داریم.

مثلاً:

```text
Helmet
   +
Rate Limiter
   +
Authentication
   +
Validation
```

هرکدام یک مشکل امنیتی متفاوت را هدف قرار می‌دهند.

---

# 111.32 - ترتیب Middlewareها

ترتیب Middlewareها در Express اهمیت دارد.

یک ساختار ساده:

```js
app.use(helmet());

app.use(express.json());

app.use("/api", routes);
```

اما ترتیب دقیق باید بر اساس نیاز Application تعیین شود.

مثلاً Middleware مربوط به Error Handling معمولاً در بخش مناسب و بعد از Routeها قرار می‌گیرد.

---

# 111.33 - غیرفعال کردن یک قابلیت

Helmet قابل تنظیم است.

مثلاً می‌توان Middleware خاصی را غیرفعال یا تنظیم کرد.

ساختار تنظیمات به نسخه Helmet و Middleware موردنظر بستگی دارد.

نکته مهم:

> چیزی را فقط برای رفع یک خطای Development غیرفعال نکنید، بدون اینکه بدانید چه Security Policyای را حذف می‌کنید.

---

# 111.34 - Development و Production

ممکن است تنظیمات امنیتی در Development و Production تفاوت‌هایی داشته باشند.

مثلاً در Development:

```text
localhost
Development CDN
Debug Tools
```

وجود داشته باشد.

اما در Production:

```text
HTTPS
Strict CSP
Production Domain
Secure Cookies
```

مورد استفاده قرار گیرند.

با این حال نباید Production را فقط با خاموش کردن Security Featureها ساده‌تر کنیم.

---

# 111.35 - Helmet در پروژه واقعی

یک ساختار مناسب می‌تواند چیزی شبیه این باشد:

```text
src/
├── app.js
├── config/
│   └── security.js
├── middleware/
│   ├── auth.js
│   ├── error.js
│   └── rate-limit.js
├── routes/
└── services/
```

تنظیمات Helmet را می‌توان در یک محل مشخص نگهداری کرد.

مثلاً:

```js
import helmet from "helmet";

export const securityMiddleware = helmet({
  // Security configuration
});
```

و در Application:

```js
app.use(securityMiddleware);
```

در Chrome یا مرورگرهای مشابه:

می‌توان Headerهای Response را بررسی کرد.

این روش یکی از ساده‌ترین راه‌ها برای اطمینان از اعمال شدن تنظیمات Helmet است.

# 111.37 - Helmet جایگزین Security Audit نیست

ممکن است Application این کد را داشته باشد:

```js
app.use(helmet());
```

اما همچنان آسیب‌پذیر باشد.

مثلاً:

```text
SQL Injection
Broken Authentication
IDOR
Weak Password Policy
Sensitive Data Exposure
Rate Limit Bypass
Authorization Bugs
```

# پاسخ تشریحی

## پاسخ تمرین 1

Helmet مجموعه‌ای از Middlewareهای Express برای تنظیم Security Headerهای HTTP است.

Helmet امنیت Application را کامل نمی‌کند؛ بلکه یکی از لایه‌های Security Hardening است.

---

## پاسخ تمرین 2

```js
import express from "express";
import helmet from "helmet";

const app = express();

app.use(helmet());

app.get("/", (req, res) => {
  res.send("Hello");
});

app.listen(3000, () => {
  console.log("Server running on port 3000");
});
```

---

## پاسخ تمرین 3

Helmet روی Security Headerها و برخی سیاست‌های امنیتی Browser تمرکز دارد.

CORS مشخص می‌کند Browser چه درخواست‌های Cross-Origin را اجازه دهد.

پس:

```text
Helmet ≠ CORS
```

---

## پاسخ تمرین 4

```http
X-Content-Type-Options: nosniff
```

به Browser می‌گوید از MIME Sniffing خودداری کند و نوع محتوای اعلام‌شده را به شکل مناسب رعایت کند.

---

## پاسخ تمرین 5

CSP مخفف:

```text
Content-Security-Policy
```

است.

CSP مشخص می‌کند منابع مختلف مانند Script، Style و Image از چه Sourceهایی مجاز هستند.

اگر مهاجم بتواند Scriptی وارد صفحه کند، CSP مناسب می‌تواند مانع اجرای آن در برخی سناریوها شود.

اما CSP جایگزین Validation و سایر روش‌های مقابله با XSS نیست.

---

## پاسخ تمرین 6

### `default-src`

Policy پیش‌فرض منابع را مشخص می‌کند.

### `script-src`

منابع مجاز JavaScript را مشخص می‌کند.

### `style-src`

منابع مجاز CSS را مشخص می‌کند.

### `img-src`

منابع مجاز Imageها را مشخص می‌کند.

---

## پاسخ تمرین 7

```http
Referrer-Policy: no-referrer
```

به Browser می‌گوید اطلاعات Referrer را ارسال نکند.

---

## پاسخ تمرین 8

Clickjacking حمله‌ای است که در آن مهاجم می‌تواند کاربر را با قرار دادن یک صفحه در Frame و طراحی رابط گمراه‌کننده، به انجام یک عمل ناخواسته ترغیب کند.

Security Policyهای مربوط به Frame مانند:

```text
X-Frame-Options
```

و سیاست‌های مدرن مرتبط با CSP می‌توانند در کاهش این ریسک مؤثر باشند.

---

## پاسخ تمرین 9

چون HSTS به Browser می‌گوید به HTTPS پایبند باشد.

اگر HTTPS به‌درستی آماده نباشد، ممکن است Browser دسترسی به Application را به مشکل بیندازد.

---

## پاسخ تمرین 10

می‌توان با:

```bash
curl -I http://localhost:3000
```

یا Browser DevTools Headerهای Response را بررسی کرد.

نمونه Headerهایی که ممکن است مشاهده شوند:

```text
Content-Security-Policy
Referrer-Policy
X-Content-Type-Options
X-Frame-Options
Strict-Transport-Security
```

مجموع Headerها به Configuration و Version بستگی دارد.

---

## پاسخ تمرین 11

یک Policy مفهومی می‌تواند این باشد:

```text
default-src 'self';
script-src 'self' https://cdn.example.com;
style-src 'self';
img-src 'self' https://images.example.com;
```

در Helmet:

```js
app.use(
  helmet({
    contentSecurityPolicy: {
      directives: {
        defaultSrc: ["'self'"],
        scriptSrc: [
          "'self'",
          "https://cdn.example.com"
        ],
        styleSrc: ["'self'"],
        imgSrc: [
          "'self'",
          "https://images.example.com"
        ]
      }
    }
  })
);
```

البته Policy واقعی باید با منابع واقعی Application تست شود.

---

## پاسخ تمرین 12

چون Helmet فقط بخشی از Security Application را پوشش می‌دهد.

برای مثال هنوز باید به موارد زیر توجه کنیم:

```text

Authorization
Input Validation
Rate Limiting
Database Security
HTTPS
Secure Cookies
CORS
Logging
Error Handling
Dependency Security
```

بنابراین:

```js
app.use(helmet());
```

یک لایه امنیتی است، نه کل سیستم امنیتی.

# جمع‌بندی

Helmet یکی از ساده‌ترین ابزارهایی است که می‌توان برای افزایش Security Hardening یک Application مبتنی بر Express استفاده کرد.

استفاده پایه:

```js
import helmet from "helmet";

app.use(helmet());
```

اما نکته اصلی این فصل فقط نصب Helmet نیست.

باید بدانیم Helmet با استفاده از Security Headerها به Browser می‌گوید چگونه با بخش‌هایی از Application رفتار کند.

مفاهیم مهم این فصل:

```text
Helmet
Security Headers
CSP
X-Content-Type-Options
Referrer-Policy
X-Frame-Options
HSTS
Clickjacking
MIME Sniffing
HTTPS
CORS
```

و مهم‌تر از همه:

```text
Helmet
    ≠
Complete Security
```

یک Application امن باید چندین لایه امنیتی داشته باشد:

```text
HTTPS
+
Helmet
+
Authentication
+
Authorization
+
Validation
+
Rate Limiting
+
Secure Database
+
Secure Cookies
+
Dependency Security
+
Logging & Monitoring
```

بنابراین Helmet را باید به‌عنوان **یکی از لایه‌های دفاعی Application** در نظر بگیریم، نه جایگزینی برای سایر اصول امنیتی.
