# فصل 114 - XSS

## مقدمه

در فصل‌های قبلی با مفاهیم مختلف امنیت در Node.js آشنا شدیم و موضوعاتی مانند Hash Password، Encryption، Helmet، Rate Limit و CORS را بررسی کردیم. این فصل نیز بخشی از **بخش ۱۴ - امنیت** مستند است؛ بخشی که پس از فصل‌های امنیت در Node.js، Hash Password، Encryption، Helmet، Rate Limit و CORS قرار گرفته و قبل از CSRF، SQL Injection، NoSQL Injection و Environment Variables ادامه پیدا می‌کند. 

یکی از آسیب‌پذیری‌های بسیار مهم در برنامه‌های Web، حمله‌ای با نام:

> Cross-Site Scripting

یا به اختصار:

> XSS

است.

XSS زمانی رخ می‌دهد که برنامه، داده‌ای که از یک منبع غیرقابل اعتماد دریافت کرده است را بدون پردازش و کنترل مناسب در محتوای قابل اجرای مرورگر قرار دهد.

به زبان ساده، اگر کاربر بتواند محتوایی را وارد کند و برنامه همان محتوا را به شکلی نمایش دهد که Browser آن را به عنوان کد اجراشدنی تفسیر کند، ممکن است برنامه در برابر XSS آسیب‌پذیر باشد.

---

# 114.1 - XSS چیست؟

XSS مخفف:

```text
Cross-Site Scripting
```

است.

هدف کلی XSS این است که مهاجم بتواند محتوای کنترل‌شده توسط خودش را وارد صفحه‌ای کند که توسط کاربران دیگر مشاهده می‌شود و Browser آن محتوا را به شکلی ناامن تفسیر کند.

مثلاً تصور کنید یک سایت امکان ثبت Comment دارد:

```text
User → Comment → Server → Database → Browser
```

اگر Comment بدون کنترل مناسب ذخیره و سپس در صفحه قرار بگیرد، ممکن است ورودی مخرب در Browser قربانی اجرا شود.

---

# 114.2 - چرا نام آن Cross-Site Scripting است؟

با وجود اینکه مخفف آن XSS است، نام اصلی آن:

```text
Cross-Site Scripting
```

است.

حرف اول `X` به این دلیل استفاده می‌شود که با `CSS` که مخفف رایج Cascading Style Sheets است اشتباه نشود.

---

# 114.3 - XSS در کدام بخش اتفاق می‌افتد؟

XSS در نهایت در محیط Client و Browser اتفاق می‌افتد، اما Backend می‌تواند نقش بسیار مهمی در ایجاد یا جلوگیری از آن داشته باشد.

مثلاً:

```text
Browser
   ↓
Request
   ↓
Node.js
   ↓
Database
   ↓
Node.js
   ↓
HTML Response
   ↓
Browser
```

اگر Backend داده غیرقابل اعتماد را بدون کنترل مناسب وارد Response کند، Frontend ممکن است آن را به شکل ناامن نمایش دهد.

---

# 114.4 - داده غیرقابل اعتماد چیست؟

هر داده‌ای که کاربر یا یک سیستم خارجی بتواند کنترل کند باید بالقوه غیرقابل اعتماد در نظر گرفته شود.

برای مثال:

```text
req.body
req.query
req.params
Cookie
Header
Database
External API
Uploaded File Metadata
```

ممکن است حاوی داده‌ای باشند که نباید مستقیماً در HTML یا Contextهای حساس قرار بگیرد.

---

# 114.5 - یک مثال ساده

فرض کنید API زیر را داریم:

```js
app.post("/comments", (req, res) => {
  const comment = req.body.comment;

  saveComment(comment);

  res.json({
    message: "Comment saved"
  });
});
```

ممکن است فکر کنیم:

```js
const comment = req.body.comment;
```

کاملاً بی‌خطر است.

اما مشکل اصلی ممکن است در زمان نمایش Comment اتفاق بیفتد.

مثلاً:

```text
Database
   ↓
Comment
   ↓
HTML
   ↓
Browser
```

بنابراین باید کل جریان داده را بررسی کنیم.

---

# 114.6 - Stored XSS

یکی از مهم‌ترین انواع XSS:

```text
Stored XSS
```

است.

در این نوع حمله، داده مخرب در Server یا Database ذخیره می‌شود.

مثلاً:

```text
Attacker
   ↓
Comment
   ↓
Node.js
   ↓
Database
   ↓
Victim
   ↓
Browser
```

این نوع XSS مخصوصاً برای سیستم‌هایی مانند:

```text
Blog
Forum
Comment System
Social Network
CMS
```

مهم است.

---

# 114.7 - Reflected XSS

در:

```text
Reflected XSS
```

محتوای مخرب معمولاً در Request وجود دارد و Server آن را در Response بازتاب می‌دهد، بدون اینکه لزوماً در Database ذخیره شود.

مثلاً:

```text
Browser
   ↓
Request
   ↓
Server
   ↓
Response
   ↓
Browser
```

اگر داده ورودی بدون Encoding مناسب در Response قرار بگیرد، ممکن است مشکل امنیتی ایجاد شود.

---

# 114.8 - DOM-based XSS

نوع دیگری از XSS:

```text
DOM-based XSS
```

است.

در این حالت، آسیب‌پذیری عمدتاً در JavaScript سمت Client ایجاد می‌شود.

مثلاً کدی که داده غیرقابل اعتماد را مستقیماً وارد HTML می‌کند:

```js
element.innerHTML = userInput;
```

این موضوع بیشتر مربوط به Frontend است، اما برای یک Node.js Developer نیز مهم است؛ زیرا Backend و Frontend معمولاً با یکدیگر کار می‌کنند.

---

# 114.9 - تفاوت انواع XSS

به‌صورت خلاصه:

| نوع           | محل اصلی جریان داده                               |
| ------------- | ------------------------------------------------- |
| Stored XSS    | داده در Server/Database ذخیره می‌شود               |
| Reflected XSS | داده در Request دریافت و در Response بازتاب می‌شود |
| DOM-based XSS | JavaScript سمت Client باعث ایجاد مشکل می‌شود       |

---

# 114.10 - XSS چگونه به وجود می‌آید؟

یک الگوی خطرناک این است:

```text
Untrusted Input
      ↓
No Validation
      ↓
No Sanitization / Encoding
      ↓
HTML
      ↓
Browser
```

در مقابل، جریان امن‌تر:

```text
Untrusted Input
      ↓
Validation
      ↓
Safe Handling
      ↓
Context-Aware Output Encoding
      ↓
Browser
```

---

# 114.11 - Input Validation

یکی از لایه‌های دفاعی:

```text
Input Validation
```

است.

Validation یعنی بررسی کنیم داده ورودی مطابق قوانین مورد انتظار ما هست یا خیر.

مثلاً اگر:

```text
username
```

باید فقط شامل حروف، عدد و `_` باشد، می‌توانیم این محدودیت را اعمال کنیم.

---

# 114.12 - Validation به تنهایی کافی نیست

یک اشتباه مهم این است که تصور کنیم:

```text
Validation = XSS Protection
```

این تصور درست نیست.

Validation یک لایه دفاعی است، اما باید محل استفاده از داده و Context آن را نیز در نظر بگیریم.

---

# 114.13 - Output Encoding

یکی از مهم‌ترین مفاهیم دفاع در برابر XSS:

```text
Output Encoding
```

است.

هدف این است که داده به شکلی نمایش داده شود که Browser آن را به عنوان داده در نظر بگیرد، نه کد.

مثلاً کاراکترهایی مانند:

```text
<
>
"
'
&
```

در Contextهای مناسب باید به شکل امن نمایش داده شوند.

---

# 114.14 - Context مهم است

Encoding یک مفهوم عمومی نیست که برای همه جا یک روش داشته باشد.

Context می‌تواند متفاوت باشد:

```text
HTML
HTML Attribute
JavaScript
CSS
URL
```

بنابراین روش دفاع نیز باید متناسب با Context باشد.

---

# 114.15 - چرا Context مهم است؟

فرض کنید داده کاربر قرار است در HTML Text قرار بگیرد:

```html
<div>USER_INPUT</div>
```

این Context با حالتی که داده داخل Attribute قرار گرفته متفاوت است:

```html
<div title="USER_INPUT"></div>
```

و این مورد نیز با JavaScript متفاوت است:

```html
<script>
  const value = "USER_INPUT";
</script>
```

بنابراین نباید یک روش Encoding را بدون توجه به Context در همه جا استفاده کرد.

---

# 114.16 - خطر `innerHTML`

در Frontend این کد می‌تواند خطرناک باشد:

```js
element.innerHTML = userInput;
```

زیرا `innerHTML` می‌تواند String را به HTML تبدیل کند.

برای نمایش متن ساده، معمولاً رویکردی مانند:

```js
element.textContent = userInput;
```

امن‌تر است؛ زیرا مقدار را به عنوان متن قرار می‌دهد.

---

# 114.17 - Node.js و XSS

Node.js خودش به‌صورت خودکار XSS را برطرف نمی‌کند.

Node.js یک Runtime است و شما باید در Application خود:

```text
Validation
Safe Data Handling
Output Encoding
Sanitization در موارد لازم
Secure Headers
```

را به شکل مناسب پیاده‌سازی کنید.

---

# 114.18 - Express و XSS

در Express ممکن است داده از Request دریافت شود:

```js
app.post("/comments", (req, res) => {
  const { comment } = req.body;

  // ...
});
```

این داده باید به عنوان:

```text
Untrusted Data
```

در نظر گرفته شود.

نباید صرفاً به این دلیل که داده از JSON آمده است، آن را امن فرض کنیم.

---

# 114.19 - JSON به معنی امن بودن نیست

این Request:

```json
{
  "comment": "user input"
}
```

از نظر XSS به خودی خود امن نیست.

JSON فقط یک Format برای انتقال داده است.

اگر مقدار آن بعداً به شکل ناامن در HTML قرار بگیرد، همچنان ممکن است مشکل ایجاد شود.

---

# 114.20 - XSS و Template Engine

اگر از Template Engine استفاده کنیم، باید بدانیم Template Engine چگونه داده را Render می‌کند.

بسیاری از Template Engineها برای نمایش معمولی، HTML Escape را انجام می‌دهند.

اما ممکن است Syntaxهایی برای:

```text
Raw HTML
Unescaped Output
```

نیز داشته باشند.

استفاده نادرست از این قابلیت‌ها می‌تواند خطرناک باشد.

---

# 114.21 - Raw HTML

فرض کنید یک Template Engine قابلیتی برای Render کردن HTML خام دارد.

مثلاً:

```text
{{{content}}}
```

یا Syntax مشابه.

اگر:

```text
content
```

از کاربر آمده باشد، قرار دادن مستقیم آن در Raw HTML می‌تواند خطرناک باشد.

---

# 114.22 - Sanitization چیست؟

گاهی Application عمداً اجازه می‌دهد کاربر بخشی از HTML را وارد کند.

مثلاً یک سیستم Blog ممکن است اجازه دهد کاربر بنویسد:

```html
<strong>Hello</strong>
```

در این شرایط حذف کامل HTML ممکن است مطلوب نباشد.

اینجا:

```text
HTML Sanitization
```

می‌تواند کاربرد داشته باشد.

Sanitizer باید عناصر و Attributeهای خطرناک را حذف یا محدود کند.

---

# 114.23 - Validation در برابر Sanitization

این دو مفهوم یکسان نیستند.

### Validation

می‌پرسد:

```text
آیا داده مطابق قوانین مورد انتظار است؟
```

### Sanitization

می‌پرسد:

```text
چگونه داده را به شکل امن‌تر تبدیل یا پاک‌سازی کنیم؟
```

هر دو می‌توانند بخشی از دفاع Application باشند.

---

# 114.24 - آیا همه HTMLها را حذف کنیم؟

نه لزوماً.

اگر Application قرار است فقط متن دریافت کند، بهتر است اصلاً HTML را به عنوان ورودی مورد نیاز قبول نکنیم.

اما اگر Application واقعاً به Rich Text نیاز دارد، باید از Sanitization مناسب استفاده شود.

اصل مهم:

> فقط به اندازه نیاز Application قابلیت دریافت HTML را باز بگذارید.

---

# 114.25 - CSP چیست؟

یکی از لایه‌های دفاعی مهم در برابر XSS:

```text
Content Security Policy
```

یا:

```text
CSP
```

است.

CSP به Browser می‌گوید منابع و Scriptها را از چه منابعی می‌تواند بارگذاری یا اجرا کند.

CSP می‌تواند اثر برخی حملات XSS را کاهش دهد.

---

# 114.26 - CSP جایگزین Encoding نیست

نباید تصور کنیم:

```text
CSP
```

به‌تنهایی تمام مشکلات XSS را حل می‌کند.

بهتر است دفاع چندلایه داشته باشیم:

```text
Validation
+
Safe Rendering
+
Output Encoding
+
Sanitization when needed
+
CSP
```

---

# 114.27 - Helmet و XSS

در فصل 111 با Helmet آشنا شدیم.

Helmet می‌تواند برخی Security Headerهای HTTP را تنظیم کند و برای امنیت کلی Web Application مفید باشد.

اما:

```text
Helmet ≠ XSS Protection کامل
```

باید همچنان داده‌های User را به شکل امن مدیریت کنیم.

---

# 114.28 - X-XSS-Protection

Header قدیمی:

```http
X-XSS-Protection
```

در گذشته برای برخی Browserها استفاده می‌شد.

اما نباید آن را به عنوان راهکار اصلی و مدرن دفاع در برابر XSS در نظر گرفت.

راهکارهای مهم‌تر شامل:

```text
Safe Output Handling
Context-Aware Encoding
Sanitization
CSP
```

هستند.

---

# 114.29 - Cookie و XSS

XSS می‌تواند برای سرقت یا سوءاستفاده از اطلاعات موجود در Browser خطرناک باشد.

یکی از دفاع‌های مهم برای Cookieهای حساس استفاده از:

```text
HttpOnly
```

است.

مثلاً:

```js
res.cookie("session", sessionId, {
  httpOnly: true,
  secure: true
});
```

با `HttpOnly`، JavaScript سمت Browser نمی‌تواند مستقیماً Cookie را از طریق `document.cookie` بخواند.

---

# 114.30 - HttpOnly جلوی XSS را نمی‌گیرد

این نکته بسیار مهم است.

`HttpOnly` باعث نمی‌شود XSS غیرممکن شود.

بلکه یکی از پیامدهای احتمالی XSS، یعنی دسترسی مستقیم JavaScript به Cookieهای HttpOnly، محدود می‌شود.

بنابراین:

```text
HttpOnly
```

یک لایه دفاعی است، نه درمان کامل XSS.

---

# 114.31 - Secure Cookie

برای Cookieهای حساس بهتر است در HTTPS از:

```text
Secure
```

نیز استفاده شود.

مثلاً:

```js
res.cookie("session", sessionId, {
  httpOnly: true,
  secure: true
});
```

---

# 114.32 - XSS و Session

اگر Session Cookie قابل دسترسی توسط JavaScript باشد، یک XSS موفق می‌تواند خطر بیشتری ایجاد کند.

به همین دلیل Session Cookie معمولاً باید با تنظیمات امنیتی مناسب مانند:

```text
HttpOnly
Secure
SameSite
```

پیکربندی شود.

---

# 114.33 - XSS و JWT

اگر JWT در Browser نگهداری شود، محل ذخیره‌سازی آن اهمیت زیادی دارد.

برای مثال نگهداری Token در یک محل قابل دسترسی مستقیم JavaScript می‌تواند در صورت وقوع XSS ریسک ایجاد کند.

بنابراین طراحی Authentication باید با در نظر گرفتن:

```text
XSS
CSRF
Cookie Security
Token Storage
```

انجام شود.

---

# 114.34 - XSS فقط مشکل Frontend نیست

ممکن است تصور کنیم:

```text
XSS → مشکل Frontend
```

اما در Applicationهای واقعی، Backend نیز در جریان داده نقش دارد.

مثلاً:

```text
POST /comments
       ↓
Node.js
       ↓
Database
       ↓
GET /comments
       ↓
Frontend
       ↓
Browser
```

اگر Backend داده نامطمئن را بدون طراحی امنیتی مناسب ذخیره و ارائه کند، احتمال ایجاد XSS افزایش پیدا می‌کند.

---

# 114.35 - دفاع چندلایه

بهترین رویکرد:

```text
                    User Input
                        │
                        ▼
                  Validation
                        │
                        ▼
                 Safe Processing
                        │
                        ▼
                 Secure Storage
                        │
                        ▼
                 Safe Rendering
                        │
                        ▼
                Output Encoding
                        │
                        ▼
                       CSP
                        │
                        ▼
                     Browser
```

هیچ‌کدام از این لایه‌ها به تنهایی جایگزین تمام لایه‌های دیگر نیستند.

# اشتباهات رایج

## 1. اعتماد کردن به Input کاربر

اشتباه:

```js
const comment = req.body.comment;
```

و فرض اینکه چون داده از User آمده مشکلی ندارد.

---

## 2. تصور اینکه JSON امن است

JSON فقط Format انتقال داده است و تضمین نمی‌کند مقدار داخل آن امن باشد.

---

## 3. استفاده از `innerHTML` برای داده User

```js
element.innerHTML = userInput;
```

برای داده غیرقابل اعتماد خطرناک است.

---

## 4. استفاده بی‌دلیل از Raw HTML

اگر HTML خام لازم نیست، آن را فعال نکنید.

---

## 5. اعتماد به Sanitization به تنهایی

Sanitization می‌تواند مفید باشد، اما نباید جایگزین طراحی صحیح Output Handling شود.

---

## 6. اعتماد به Validation به تنهایی

Validation یک لایه دفاعی است و به تنهایی تضمین نمی‌کند Application در برابر XSS امن باشد.

---

## 7. تصور اینکه Helmet همه چیز را حل می‌کند

Helmet ابزار مهمی است، اما XSS را به‌طور کامل حل نمی‌کند.

---

## 8. تصور اینکه HttpOnly جلوی XSS را می‌گیرد

HttpOnly فقط دسترسی JavaScript به Cookie را محدود می‌کند.

---

## 9. ذخیره HTML خام بدون نیاز

اگر Application فقط متن ساده نیاز دارد، بهتر است HTML خام ذخیره و Render نشود.

---

## 10. نادیده گرفتن DOM-based XSS

حتی اگر Backend کاملاً امن باشد، Frontend می‌تواند با DOM APIهای ناامن آسیب‌پذیر شود.

---

# نکات حرفه‌ای

## 1. داده User را همیشه Untrusted در نظر بگیرید

حتی اگر داده از:

```text
Database
Internal API
Admin Panel
```

آمده باشد، باید Context و منبع آن را بررسی کنید.

---

## 2. Context را قبل از Encoding مشخص کنید

ابتدا مشخص کنید داده قرار است کجا قرار بگیرد:

```text
HTML
Attribute
```

# پاسخ تشریحی

## پاسخ تمرین 1

XSS یا Cross-Site Scripting آسیب‌پذیری‌ای است که در آن داده کنترل‌شده توسط مهاجم می‌تواند در Context مرورگر به شکل ناامن تفسیر یا اجرا شود.

---

## پاسخ تمرین 2

سه نوع مهم:

```text
Stored XSS
Reflected XSS
DOM-based XSS
```

---

## پاسخ تمرین 3

در Stored XSS، داده مخرب معمولاً در Server یا Database ذخیره می‌شود و بعداً به کاربران دیگر ارائه می‌شود.

در Reflected XSS، داده معمولاً از Request وارد می‌شود و Server آن را در Response بازتاب می‌دهد.

---

## پاسخ تمرین 4

DOM-based XSS عمدتاً در سمت Client و در تعامل JavaScript با DOM اتفاق می‌افتد.

---

## پاسخ تمرین 5

JSON فقط یک قالب انتقال داده است.

مثلاً:

```json
{
  "name": "user input"
}
```

اگر مقدار `name` بعداً به شکل ناامن در HTML قرار گیرد، JSON جلوی آن را نمی‌گیرد.

---

## پاسخ تمرین 6

Validation بررسی می‌کند داده مطابق قوانین مورد انتظار است یا خیر.

Sanitization داده را پاک‌سازی یا به شکل امن‌تری تبدیل می‌کند.

---

## پاسخ تمرین 7

چون `innerHTML` می‌تواند String را به HTML تبدیل کند. اگر مقدار از منبع غیرقابل اعتماد آمده باشد، ممکن است محتوای ناامن وارد DOM شود.

---

## پاسخ تمرین 8

برای نمایش متن ساده:

```js
element.textContent = userInput;
```

انتخاب مناسب‌تری است؛ زیرا مقدار را به عنوان متن قرار می‌دهد، نه HTML.

---

## پاسخ تمرین 9

با:

```text
HttpOnly
```

JavaScript سمت Browser نمی‌تواند مستقیماً Cookie را از طریق APIهایی مانند `document.cookie` بخواند.

---

## پاسخ تمرین 10

خیر.

HttpOnly فقط یک لایه دفاعی برای Cookie است و جلوی خود XSS را نمی‌گیرد.

---

## پاسخ تمرین 11

CSP یا Content Security Policy به Browser می‌گوید منابع و Scriptها از چه منابعی می‌توانند بارگذاری یا اجرا شوند.

این Policy می‌تواند اثر برخی حملات XSS را کاهش دهد.

---

## پاسخ تمرین 12

یک طراحی مناسب می‌تواند شامل این مراحل باشد:

```text
Request
↓
Validation
↓
Safe Processing
↓
Secure Storage
↓
Safe Output Handling
↓
Context-Aware Encoding
↓
CSP
```

---

## پاسخ تمرین 13

چون:

```js
req.body.comment
```

داده‌ای است که توسط Client کنترل می‌شود و باید Untrusted در نظر گرفته شود.

مشکل اصلی فقط ذخیره‌کردن نیست؛ باید بررسی شود این داده بعداً در چه Contextی Render خواهد شد.

---

## پاسخ تمرین 14

چون ممکن است Application عمداً به Rich Text نیاز داشته باشد.

در این حالت بهتر است به جای حذف کامل HTML، فقط HTML و Attributeهای مجاز را Allow کنیم و بقیه را با Sanitization مناسب حذف کنیم.

---

## پاسخ تمرین 15

CORS یک مکانیزم Browser برای کنترل دسترسی Cross-Origin است.

XSS یک آسیب‌پذیری مرتبط با اجرای محتوای غیرقابل اعتماد در Context مرورگر است.

این دو مفهوم متفاوت هستند و یکی جایگزین دیگری نیست.

# مرحله 9 - اضافه کردن Validation

فرض کنید Comment ساده باید حداقل و حداکثر طول داشته باشد:

```js
function validateComment(comment) {
  if (typeof comment !== "string") {
    return false;
  }

  if (comment.length < 1) {
    return false;
  }

  if (comment.length > 1000) {
    return false;
  }

  return true;
}
```

و در Route:

```js
app.post("/api/comments", (req, res) => {
  const { comment } = req.body;

  if (!validateComment(comment)) {
    return res.status(400).json({
      message: "Invalid comment"
    });
  }

  comments.push({
    id: comments.length + 1,
    comment
  });

  res.status(201).json({
    message: "Comment created"
  });
});
```

# جمع‌بندی

XSS یکی از مهم‌ترین آسیب‌پذیری‌های Web Application است و برای یک Node.js Developer شناخت آن ضروری است.

مهم‌ترین مفاهیم این فصل:

```text
XSS
Cross-Site Scripting
Stored XSS
Reflected XSS
DOM-based XSS
Untrusted Input
Validation
Sanitization
Output Encoding
Context-Aware Encoding
innerHTML
textContent
CSP
HttpOnly
Secure Cookie
SameSite
Helmet
Safe Rendering
```

مهم‌ترین اصل:

> هر داده‌ای که تحت کنترل کاربر یا یک منبع غیرقابل اعتماد است، باید تا زمانی که خلافش ثابت نشده، Untrusted در نظر گرفته شود.

همچنین نباید یک ابزار را به عنوان راه‌حل کامل XSS در نظر گرفت:

```text
Validation
≠
Sanitization
≠
CSP
≠
Helmet
≠
HttpOnly
```

امنیت واقعی حاصل ترکیب چند لایه دفاعی است.

در یک Node.js Application امن باید جریان کامل داده را بررسی کنیم:

```text
Input
  ↓
Validation
  ↓
Processing
  ↓
Storage
  ↓
Output
  ↓
Encoding / Sanitization
  ↓
Browser
```

و فصل بعدی این بخش از مستند به موضوع **CSRF** می‌پردازد که در فهرست اصلی بلافاصله بعد از XSS قرار گرفته است.
