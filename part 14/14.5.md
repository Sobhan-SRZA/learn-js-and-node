# فصل 112 - Rate Limit

## مقدمه

در یک Application واقعی، همه Requestها از طرف کاربران عادی ارسال نمی‌شوند.

ممکن است یک کاربر به‌صورت عادی از API استفاده کند:

```text
GET /api/products
GET /api/products/10
POST /api/orders
```

اما یک مهاجم یا حتی یک Client دارای Bug ممکن است در مدت کوتاهی هزاران Request ارسال کند:

```text
Request 1
Request 2
Request 3
...
Request 10000
```

اگر Server برای تعداد Requestها محدودیتی نداشته باشد، این وضعیت می‌تواند باعث مصرف بیش از حد منابع Server شود و در بعضی سناریوها به حملات Brute Force، سوءاستفاده از Endpointها و برخی حملات Denial-of-Service کمک کند.

یکی از راهکارهای مهم برای کنترل این موضوع **Rate Limiting** است.

Rate Limit یعنی:

> برای یک Client مشخص، در یک بازه زمانی مشخص، تعداد Requestهای مجاز را محدود کنیم.

مثلاً:

```text
100 Request
در هر
15 دقیقه
```

اگر Client بیشتر از این مقدار Request ارسال کند، Server می‌تواند Response زیر را برگرداند:

```http
HTTP/1.1 429 Too Many Requests
```

Rate Limiting یکی از لایه‌های مهم Security در Node.js و مخصوصاً APIها است.

---

# 112.1 - Rate Limit چیست؟

Rate Limit یعنی محدود کردن تعداد درخواست‌هایی که یک Client می‌تواند در یک بازه زمانی مشخص ارسال کند.

مثلاً:

```text
100 Requests / 15 Minutes
```

یعنی یک Client در بازه ۱۵ دقیقه‌ای حداکثر ۱۰۰ Request مجاز دارد.

اگر Request شماره ۱۰۱ ارسال شود:

```text
Client
  │
  ├── Request 1   → Allow
  ├── Request 2   → Allow
  ├── ...
  ├── Request 100 → Allow
  └── Request 101 → Block
```

Server می‌تواند Request اضافی را رد کند.

---

# 112.2 - چرا Rate Limit لازم است؟

بدون Rate Limiting:

```text
Client
   │
   ├── Request
   ├── Request
   ├── Request
   ├── Request
   ├── Request
   └── ...
           ↓
        Server
```

یک Client می‌تواند تعداد بسیار زیادی Request ارسال کند.

این موضوع ممکن است باعث:

* مصرف CPU
* مصرف RAM
* مصرف Database Connection
* افزایش Network Traffic
* افزایش Load
* کند شدن Application
* فشار روی External APIها
* Brute Force
* سوءاستفاده از Endpointها

شود.

---

# 112.3 - Rate Limit و DDoS

Rate Limiting می‌تواند در برابر برخی الگوهای Abuse کمک کند، اما:

> Rate Limiting به‌تنهایی راه‌حل کامل DDoS نیست.

فرض کنید Application فقط یک Server داشته باشد:

```text
Internet
   ↓
Node.js
```

اگر حجم حمله بسیار بزرگ باشد، ممکن است ترافیک قبل از رسیدن به Rate Limiter منابع Infrastructure را مصرف کند.

برای مقابله با حملات بزرگ‌تر معمولاً به لایه‌های دیگری مانند:

```text
CDN
WAF
Load Balancer
Cloud Protection
Network Filtering
```

نیاز است.

---

# 112.4 - Rate Limit و Brute Force

یکی از مهم‌ترین کاربردهای Rate Limiting، محدود کردن تلاش‌های Login است.

فرض کنید Endpoint زیر وجود دارد:

```http
POST /api/auth/login
```

مهاجم می‌تواند Passwordهای مختلف را امتحان کند:

```text
admin / password1
admin / password2
admin / password3
admin / password4
...
```

بدون Rate Limiting:

```text
10000 Attempts
```

ممکن است در مدت کوتاهی انجام شود.

اما با Rate Limit:

```text
5 Attempts / Minute
```

سرعت حمله بسیار کاهش پیدا می‌کند.

---

# 112.5 - HTTP Status Code 429

برای اعلام اینکه Client بیش از حد مجاز Request ارسال کرده، از:

```http
429 Too Many Requests
```

استفاده می‌شود.

مثلاً:

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
```

و Response:

```json
{
  "message": "Too many requests"
}
```

---

# 112.6 - Retry-After

Server می‌تواند مشخص کند Client چه مدت باید صبر کند.

مثلاً:

```http
Retry-After: 60
```

یعنی Client بهتر است ۶۰ ثانیه صبر کند.

Response:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

و:

```json
{
  "message": "Too many requests"
}
```

---

# 112.7 - Rate Limit چه چیزی را محدود می‌کند؟

Rate Limit می‌تواند بر اساس معیارهای مختلف اعمال شود.

مثلاً:

```text
IP Address
User ID
API Key
Session
Access Token
Route
Global Application
```

مثلاً:

```text
IP A → 100 requests
IP B → 100 requests
IP C → 100 requests
```

یا:

```text
User 1 → 100 requests
User 2 → 100 requests
```

---

# 112.8 - Rate Limit بر اساس IP

یکی از ساده‌ترین روش‌ها، محدود کردن Request بر اساس IP است.

مثلاً:

```text
100 requests / 15 minutes / IP
```

یعنی هر IP حداکثر ۱۰۰ Request در ۱۵ دقیقه داشته باشد.

ساختار مفهومی:

```text
IP 192.168.1.10
      ↓
   Counter
      ↓
   87 / 100
```

---

# 112.9 - مشکل Rate Limit بر اساس IP

IP همیشه نشان‌دهنده یک User نیست.

مثلاً در یک شبکه دانشگاه یا شرکت:

```text
User A ─┐
User B ─┤
User C ─┼──→ Same Public IP
User D ─┤
User E ─┘
```

اگر Rate Limit فقط بر اساس IP باشد، ممکن است چند کاربر واقعی یک محدودیت مشترک داشته باشند.

---

# 112.10 - Rate Limit بر اساس User

اگر کاربر Login کرده باشد، می‌توان Rate Limit را بر اساس User ID اعمال کرد.

مثلاً:

```text
User 101 → 100 requests
User 102 → 100 requests
User 103 → 100 requests
```

این روش می‌تواند نسبت به IP دقیق‌تر باشد.

اما برای Requestهای قبل از Login همچنان نیاز به یک معیار دیگر داریم.

---

# 112.11 - ترکیب IP و User

در Applicationهای حساس می‌توان چند نوع محدودیت داشت.

مثلاً:

```text
IP Limit:
1000 requests / hour

User Limit:
500 requests / hour
```

و برای Login:

```text
IP:
20 attempts / 15 minutes

Account:
5 attempts / 15 minutes
```

این روش چند لایه دفاعی ایجاد می‌کند.

---

# 112.12 - Global Rate Limit

می‌توان یک Limit کلی برای Application تعریف کرد.

مثلاً:

```text
10000 requests / minute
```

یعنی مجموع Requestهای Application از مقدار مشخصی بیشتر نشود.

این روش برای کنترل Load کلی Application مفید است.

اما معمولاً به‌تنهایی کافی نیست.

---

# 112.13 - Route-Based Rate Limit

ممکن است هر Endpoint نیاز به Limit متفاوتی داشته باشد.

مثلاً:

```text
GET /api/products
1000 requests / minute
```

ولی:

```text
POST /api/auth/login
5 requests / minute
```

چون Login حساس‌تر است.

به همین دلیل بهتر است Rate Limit را بر اساس اهمیت Endpoint نیز طراحی کنیم.

---

# 112.14 - Endpointهای حساس

Endpointهای زیر معمولاً حساس‌تر هستند:

```text
/login
/register
/forgot-password
/reset-password
/verify-code
/send-otp
/change-password
/payment
```

برای این Endpointها معمولاً Rate Limit سخت‌گیرانه‌تری مناسب است.

---

# 112.15 - Rate Limit و OTP

فرض کنید Endpoint زیر داریم:

```http
POST /api/auth/send-otp
```

اگر محدودیتی وجود نداشته باشد:

```text
Attacker
   ↓
send OTP
send OTP
send OTP
send OTP
...
```

می‌تواند باعث:

* مصرف سرویس SMS
* افزایش هزینه
* آزار کاربر
* سوءاستفاده از سیستم

شود.

پس Rate Limiting در این Endpoint بسیار مهم است.

---

# 112.16 - Rate Limit و Password Reset

Endpoint:

```http
POST /api/auth/forgot-password
```

نیز باید محافظت شود.

مثلاً:

```text
3 requests / hour / account
```

یا محدودیت مناسب دیگری بر اساس معماری Application.

---

# 112.17 - الگوریتم‌های Rate Limiting

Rate Limiting روش‌های مختلفی دارد.

مهم‌ترین الگوریتم‌ها:

```text
Fixed Window
Sliding Window
Token Bucket
Leaky Bucket
```

درک این الگوریتم‌ها برای یک Node.js Developer مهم است.

---

# 112.18 - Fixed Window

در Fixed Window زمان به بازه‌های ثابت تقسیم می‌شود.

مثلاً:

```text
10:00 - 10:15
10:15 - 10:30
10:30 - 10:45
```

و برای هر Window یک Counter داریم.

مثلاً:

```text
10:00 - 10:15
Request Count = 100
```

وقتی Window تمام شود، Counter Reset می‌شود.

---

# 112.19 - مثال Fixed Window

فرض کنید:

```text
Limit = 5
Window = 1 minute
```

Client:

```text
10:00:05 → Request 1
10:00:10 → Request 2
10:00:20 → Request 3
10:00:30 → Request 4
10:00:40 → Request 5
10:00:50 → Block
```

در:

```text
10:01:00
```

Window جدید شروع می‌شود.

---

# 112.20 - مشکل Fixed Window

یک مشکل معروف وجود دارد.

فرض کنید:

```text
Limit = 100
Window = 1 minute
```

Client می‌تواند نزدیک انتهای Window اول:

```text
99 requests
```

و بلافاصله بعد از شروع Window دوم:

```text
100 requests
```

ارسال کند.

در مدت بسیار کوتاهی:

```text
199 requests
```

ارسال شده است.

به این مشکل Boundary Effect گفته می‌شود.

---

# 112.21 - Sliding Window

Sliding Window به جای استفاده از بازه‌های کاملاً ثابت، Requestهای اخیر را بررسی می‌کند.

مثلاً:

```text
Last 60 seconds
```

برای هر Request بررسی می‌کنیم در ۶۰ ثانیه گذشته چند Request ثبت شده است.

---

# 112.22 - مثال Sliding Window

فرض کنید:

```text
Limit = 5
Window = 60 seconds
```

Requestها:

```text
12:00:05
12:00:10
12:00:20
12:00:30
12:00:40
```

Request بعدی در:

```text
12:00:45
```

باید رد شود.

وقتی Request قدیمی‌تر از ۶۰ ثانیه شود، از Window خارج می‌شود.

---

# 112.23 - Token Bucket

در Token Bucket به‌جای Counter ساده، یک Bucket از Tokenها داریم.

مثلاً:

```text
Bucket Capacity = 10
```

هر Request:

```text
1 Token
```

مصرف می‌کند.

Tokenها نیز با یک نرخ مشخص دوباره تولید می‌شوند.

مثلاً:

```text
1 Token / Second
```

---

# 112.24 - مثال Token Bucket

```text
Bucket:
[● ● ● ● ● ● ● ● ● ●]
```

Client یک Request می‌فرستد:

```text
[● ● ● ● ● ● ● ● ●]
```

بعد از مدتی Token جدید اضافه می‌شود:

```text
[● ● ● ● ● ● ● ● ● ●]
```

این الگوریتم امکان Burst کنترل‌شده را فراهم می‌کند.

---

# 112.25 - Leaky Bucket

در Leaky Bucket درخواست‌ها با یک Rate مشخص پردازش می‌شوند.

مفهوم کلی:

```text
Requests
   ↓
┌───────────┐
│   Queue   │
└───────────┘
      ↓
  Fixed Rate
      ↓
   Server
```

این روش می‌تواند برای کنترل جریان Requestها مناسب باشد.

---

# 112.26 - انتخاب الگوریتم

هیچ الگوریتمی برای همه Applicationها بهترین نیست.

باید بر اساس نیاز انتخاب کرد:

| الگوریتم       | ویژگی                 |
| -------------- | --------------------- |
| Fixed Window   | ساده و کم‌هزینه       |
| Sliding Window | کنترل دقیق‌تر         |
| Token Bucket   | مناسب Burst کنترل‌شده |
| Leaky Bucket   | کنترل جریان خروجی     |

---

# 112.27 - پیاده‌سازی ساده با Express

برای پروژه‌های Express می‌توان از Packageهای آماده استفاده کرد.

یکی از Packageهای معروف:

```text
express-rate-limit
```

است.

نصب:

```bash
npm install express-rate-limit
```

---

# 112.28 - استفاده از `express-rate-limit`

مثال ساده:

```js
import express from "express";
import rateLimit from "express-rate-limit";

const app = express();

const limiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 100
});

app.use(limiter);

app.get("/", (req, res) => {
  res.json({
    message: "Hello"
  });
});

app.listen(3000);
```

در این مثال:

```text
15 minutes
↓
100 requests
```

برای هر Client در نظر گرفته می‌شود.

---

# 112.29 - `windowMs`

گزینه:

```js
windowMs
```

مدت Window را مشخص می‌کند.

مثلاً:

```js
windowMs: 60 * 1000
```

یعنی:

```text
60 seconds
```

یا:

```js
windowMs: 15 * 60 * 1000
```

یعنی:

```text
15 minutes
```

---

# 112.30 - `limit`

گزینه:

```js
limit
```

تعداد Requestهای مجاز را مشخص می‌کند.

مثلاً:

```js
limit: 100
```

یعنی در Window مشخص‌شده حداکثر ۱۰۰ Request مجاز باشد.

---

# 112.31 - پیام خطا

می‌توان Response مناسب تعریف کرد:

```js
const limiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 100,
  message: {
    error: "Too many requests"
  }
});
```

در صورت عبور از Limit، Client باید Response مناسبی دریافت کند.

---

# 112.32 - Status Code

برای Rate Limit معمولاً:

```http
429 Too Many Requests
```

استفاده می‌شود.

مثلاً:

```js
const limiter = rateLimit({
  windowMs: 60 * 1000,
  limit: 5,
  statusCode: 429
});
```

---

# 112.33 - Rate Limit فقط برای یک Route

لازم نیست Rate Limiter را روی کل Application اعمال کنیم.

می‌توانیم فقط روی Login قرار دهیم:

```js
const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 5
});

app.post("/api/login", loginLimiter, loginHandler);
```

این روش در Endpointهای حساس بسیار مفید است.

---

# 112.34 - Rate Limit برای Routeهای مختلف

مثلاً:

```js
const generalLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 200
});

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 5
});

app.use("/api", generalLimiter);

app.post("/api/login", loginLimiter, loginHandler);
```

در اینجا:

```text
API عمومی → 200
Login → 5
```

است.

---

# 112.35 - Rate Limit و Reverse Proxy

در Production ممکن است معماری این‌گونه باشد:

```text
Client
  ↓
CDN / Load Balancer
  ↓
Reverse Proxy
  ↓
Node.js
```

در این حالت IP واقعی Client ممکن است مستقیماً در `req.ip` قابل تشخیص نباشد، مگر اینکه Proxyها به‌درستی تنظیم شده باشند.

در Express مفهوم مهمی به نام:

```js
app.set("trust proxy", ...)
```

وجود دارد.

---

# 112.36 - خطر تنظیم اشتباه `trust proxy`

اگر:

```js
trust proxy
```

به‌صورت نادرست تنظیم شود، مهاجم ممکن است بتواند IP مورد استفاده برای Rate Limit را جعل کند یا رفتار غیرمنتظره ایجاد شود.

پس قبل از تنظیم آن باید معماری واقعی Network را بدانیم.

---

# 112.37 - Rate Limit در چند Server

فرض کنید Application ما روی سه Server اجرا شود:

```text
          Load Balancer
          /     |     \
         /      |      \
       Node    Node    Node
        A       B       C
```

اگر Rate Limit را فقط داخل RAM هر Node نگه داریم:

```text
Server A → 100
Server B → 100
Server C → 100
```

یک Client ممکن است در مجموع تعداد بسیار بیشتری Request ارسال کند.

---

# 112.38 - مشکل In-Memory Rate Limit

فرض کنید:

```text
Limit = 100
```

اما سه Instance داریم:

```text
Node A → 100
Node B → 100
Node C → 100
```

در بدترین حالت Client می‌تواند:

```text
300 requests
```

ارسال کند.

به همین دلیل در معماری Distributed معمولاً به Shared Store نیاز داریم.

---

# 112.39 - Redis برای Rate Limiting

یکی از گزینه‌های رایج برای Shared Rate Limit Store:

```text
Redis
```

است.

معماری:

```text
                Load Balancer
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       Node A      Node B      Node C
          │           │           │
          └───────────┼───────────┘
                      ↓
                    Redis
```

در این حالت Counterها می‌توانند در یک Store مشترک قرار بگیرند.

---

# 112.40 - چرا Redis مناسب است؟

Redis عملیات بسیار سریعی روی داده‌های ساده دارد.

برای Rate Limiting معمولاً به عملیات‌هایی مانند:

```text
INCR
EXPIRE
GET
SET
```

نیاز داریم.

مثلاً به‌صورت مفهومی:

```text
rate:user:123
→ 42
```

یعنی User شماره ۱۲۳ در Window فعلی ۴۲ Request داشته است.

---

# 112.41 - Rate Limit و Atomic Operation

در سیستم‌های Concurrent باید مراقب Race Condition باشیم.

مثلاً دو Request همزمان:

```text
Request A → Read = 99
Request B → Read = 99
```

هر دو ممکن است فکر کنند Request مجاز است.

به همین دلیل عملیات Counter باید به شکل مناسب و Atomic انجام شوند.

Redis برای چنین الگوهایی ابزارهای مناسبی دارد.

---

# 112.42 - Rate Limit و Database

بهتر است برای هر Request یک Query سنگین به Database نزنیم تا Counter را ذخیره کنیم.

این کار:

```text
Request
  ↓
Database
  ↓
Update Counter
```

می‌تواند خودش تبدیل به Bottleneck شود.

برای Rate Limiting پرتعداد، یک Store سریع‌تر مانند Redis معمولاً انتخاب مناسب‌تری است.

---

# 112.43 - Rate Limit برای Login

یک نمونه معماری:

```text
POST /login
       ↓
IP Rate Limit
       ↓
Account Rate Limit
       ↓
Validate Input
       ↓
Check User
       ↓
Verify Password
       ↓
Create Session/JWT
```

این لایه‌ها در کنار هم امنیت بیشتری ایجاد می‌کنند.

---

# 112.44 - آیا باید User را Lock کنیم؟

Rate Limiting با Account Lockout یکی نیست.

مثلاً:

```text
Rate Limit
```

می‌تواند سرعت تلاش‌ها را کاهش دهد.

اما:

```text
Account Lockout
```

ممکن است حساب کاربر را برای مدتی قفل کند.

Account Lockout باید با دقت طراحی شود؛ چون مهاجم می‌تواند با ارسال Password اشتباه برای حساب دیگران باعث قفل شدن حساب آن‌ها شود.

---

# 112.45 - Rate Limit و CAPTCHA

در برخی Applicationها می‌توان بعد از تعداد مشخصی تلاش ناموفق، CAPTCHA درخواست کرد.

مثلاً:

```text
Attempt 1 → Allow
Attempt 2 → Allow
Attempt 3 → Allow
Attempt 4 → CAPTCHA
Attempt 5 → CAPTCHA
```

CAPTCHA و Rate Limit می‌توانند مکمل یکدیگر باشند.

---

# 112.46 - Rate Limit و API Key

برای APIهای عمومی می‌توان Limit را بر اساس API Key تعیین کرد.

مثلاً:

```text
Free API Key
→ 1000 requests/day

Pro API Key
→ 100000 requests/day
```

در این حالت:

```text
API Key
   ↓
Rate Limit Policy
```

---

# 112.47 - Rate Limit و User Plan

در یک SaaS ممکن است محدودیت بر اساس Subscription باشد:

```text
Free
→ 100 requests/hour

Basic
→ 10,000 requests/hour

Pro
→ 100,000 requests/hour
```

این نوع Rate Limiting علاوه بر Security، بخشی از Business Logic نیز محسوب می‌شود.

---

# 112.48 - Rate Limit Headers

Client باید بتواند تا حد امکان بفهمد محدودیت فعلی چیست.

Headerهای مربوط به Rate Limit می‌توانند اطلاعاتی مانند:

```text
Limit
Remaining
Reset
```

را در اختیار Client قرار دهند.

مثلاً:

```http
RateLimit-Limit: 100
RateLimit-Remaining: 42
```

پیاده‌سازی دقیق این Headerها به ابزار و استاندارد مورد استفاده بستگی دارد.

---

# 112.49 - طراحی Response مناسب

Response مناسب:

```json
{
  "error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "Too many requests"
  }
}
```

می‌تواند برای Client قابل پردازش‌تر باشد.

در کنار آن:

```http
429 Too Many Requests
```

قرار می‌گیرد.

---

# 112.50 - Client باید چه کار کند؟

وقتی Client پاسخ `429` دریافت کرد، نباید بلافاصله دوباره Request ارسال کند.

بهتر است:

```text
429
 ↓
Wait
 ↓
Retry
```

و اگر `Retry-After` وجود دارد، آن را رعایت کند.

در سیستم‌های حرفه‌ای می‌توان از:

```text
Exponential Backoff
```

نیز استفاده کرد.

---

# 112.51 - Exponential Backoff

به جای Retry سریع:

```text
Retry
Retry
Retry
Retry
```

فاصله Retryها افزایش پیدا می‌کند:

```text
1s
2s
4s
8s
16s
```

این روش فشار روی Server را کاهش می‌دهد.

---

# 112.52 - Rate Limit و Logging

وقتی Rate Limit فعال می‌شود، بهتر است Eventهای مهم ثبت شوند.

مثلاً:

```json
{
  "event": "rate_limit_exceeded",
  "ip": "client-ip",
  "route": "/api/login",
  "timestamp": "..."
}
```

اما باید مراقب باشیم اطلاعات حساس مانند Password یا Token در Log ذخیره نشوند.

---

# 112.53 - Monitoring

در Production می‌توان Metricهایی مانند این‌ها را بررسی کرد:

```text
Rate Limit Hits
429 Responses
Requests / Second
Requests / Minute
Top IPs
Top Endpoints
Failed Login Attempts
```

اگر ناگهان تعداد `429` زیاد شود، ممکن است نشانه:

```text
Attack
Bug
Misconfigured Client
Traffic Spike
```

باشد.

---

# 112.54 - Rate Limit و Fairness

Rate Limiting فقط Security نیست.

می‌تواند باعث شود منابع Server بین Clientها منصفانه‌تر تقسیم شوند.

مثلاً:

```text
Client A → 1000 requests
Client B → 10 requests
```

با Rate Limit می‌توان جلوی مصرف بیش از حد Client A را گرفت.

---

# 112.55 - اشتباهات رایج

## 1. استفاده از یک Limit برای همه Endpointها

Login و دریافت Product معمولاً نیاز یکسانی ندارند.

---

## 2. Rate Limit بسیار سخت‌گیرانه

اگر:

```text
5 requests / hour
```

برای یک API عمومی قرار دهیم، ممکن است کاربران واقعی مرتباً `429` دریافت کنند.

---

## 3. Rate Limit بسیار باز

اگر:

```text
1,000,000 requests / second
```

قرار دهیم، عملاً Protection خاصی ایجاد نکرده‌ایم.

---

## 4. اعتماد کامل به IP

چند User ممکن است یک IP مشترک داشته باشند.

---

## 5. نادیده گرفتن Proxy

در Production ممکن است IP واقعی Client پشت Proxy قرار داشته باشد.

---

## 6. ذخیره Counter فقط در RAM در معماری چند سروره

در این حالت هر Instance Counter خودش را دارد.

---

## 7. ذخیره Counter در Database برای هر Request

این کار می‌تواند Database را تحت فشار قرار دهد.

---

## 8. تصور اینکه Rate Limit جلوی DDoS را به‌طور کامل می‌گیرد

Rate Limiting فقط یکی از لایه‌های دفاعی است.

---

## 9. Rate Limit نکردن Endpointهای حساس

خصوصاً:

```text
Login
OTP
Password Reset
```

---

## 10. عدم رعایت 429 در Client

Client نباید بعد از دریافت `429` به شکل سریع و بی‌نهایت Retry کند.

---

## 11. Log کردن اطلاعات حساس

هیچ‌وقت Password، Token یا Secret را فقط برای Debug در Log ثبت نکنید.

---

## 12. تست نکردن Rate Limit

Rate Limiting باید با Load و Integration Test آزمایش شود.

# نکات حرفه‌ای

## 1. برای هر Endpoint Policy مناسب داشته باشید

مثلاً:

```text
GET /products
→ 500/min

POST /login
→ 5/min

POST /send-otp
→ 3/10min
```

## 2. چند لایه Rate Limit استفاده کنید

مثلاً:

```text
Global
+
IP
+
User
+
Route
```

---

## 3. برای Production از Shared Store استفاده کنید

اگر چند Instance دارید، Rate Limit باید وضعیت مشترکی داشته باشد.

Redis یکی از انتخاب‌های رایج است.

---

## 4. `trust proxy` را آگاهانه تنظیم کنید

هرگز تنظیمات Proxy را بدون شناخت Infrastructure کپی نکنید.

---

## 5. Rate Limit را با Metrics همراه کنید

بدون Monitoring ممکن است متوجه نشوید که:

```text
429
```

ها به دلیل حمله ایجاد شده‌اند یا به دلیل Limit اشتباه.

---

## 6. Rate Limit را بر اساس Business طراحی کنید

ممکن است یک User Pro به Limit بسیار بالاتری نیاز داشته باشد.

---

## 7. برای Authentication سخت‌گیرتر باشید

Endpointهای Login، OTP و Password Reset معمولاً باید محدودیت‌های ویژه داشته باشند.

---

## 8. Backoff را در Client رعایت کنید

بعد از `429`:

```text
Wait
↓
Retry
```

بهتر از Retry فوری است.

---

## 9. Rate Limit را با WAF/CDN ترکیب کنید

برای Applicationهای بزرگ:

```text
CDN/WAF
   ↓
Rate Limit
   ↓
Node.js
```

می‌تواند معماری مناسب‌تری باشد.

---

## 10. Fail Open یا Fail Closed را مشخص کنید

اگر Rate Limit Store مانند Redis در دسترس نباشد، باید از قبل تصمیم گرفته باشید:

```text
Fail Open
```

یا:

```text
Fail Closed
```

هرکدام Trade-off امنیتی و Availability متفاوتی دارند.

برای Endpointهای حساس، تصمیم‌گیری باید آگاهانه باشد.

---

## 11. Rate Limit را با Authentication ترکیب کنید

بعد از Login:

```text
User ID
```

معیار بسیار خوبی برای Rate Limiting است.

قبل از Login:

```text
IP
Device/Session signals
```

و معیارهای دیگر می‌توانند استفاده شوند.

---

## 12. به IPv4 و IPv6 توجه کنید

در طراحی سیستم‌های مبتنی بر IP باید IPv4 و IPv6 را در نظر گرفت.

همه Serverها وضعیت مشترکی داشته باشند.

# خروجی نهایی پروژه

در پایان پروژه باید بتوانید سیستمی داشته باشید که:

```text
                Client
                   │
                   ▼
                 HTTPS
                   │
                   ▼
                Helmet
                   │
                   ▼
              Rate Limiter
                   │
          ┌────────┼────────┐
          ↓        ↓        ↓
       General   Login     OTP
        Limit     Limit    Limit
          │        │        │
          └────────┼────────┘
                   ↓
                 Route
                   ↓

                   ↓
                Database
```

و در معماری چند سروره:

```text
                 Client
                    ↓
              Load Balancer
                    ↓
        ┌───────────┼───────────┐
        ↓           ↓           ↓
      Node 1      Node 2      Node 3
        │           │           │
        └───────────┼───────────┘
                    ↓
                  Redis
```

به این ترتیب Rate Limiting از یک Middleware ساده به یک بخش واقعی از معماری Security و Scalability در Node.js تبدیل می‌شود.

# جمع‌بندی نهایی فصل

در این فصل یاد گرفتیم که Rate Limiting یکی از مهم‌ترین ابزارهای کنترل Abuse در Applicationهای Node.js است.

مهم‌ترین مفاهیم:

```text
Rate Limit
429 Too Many Requests
Retry-After
Fixed Window
Sliding Window
Token Bucket
Leaky Bucket
IP-Based Limiting
User-Based Limiting
Route-Based Limiting
Global Limiting
Redis
Distributed Rate Limiting
Brute Force Protection
API Abuse
```

در یک Application واقعی نباید فقط بگوییم:

```js
app.use(rateLimiter);
```

بلکه باید مشخص کنیم:

```text
چه چیزی؟
برای چه کسی؟
در چه Endpointی؟
در چه بازه‌ای؟
با چه الگوریتمی؟
با چه Storeای؟
در چند Instance؟
با چه Responseای؟
```

```text
HTTPS
   +
Helmet

Rate Limiting
   +
Authentication
   +
Authorization
   +
Validation
   +
Secure Database
   +
Logging
   +
Monitoring
   +
WAF / CDN
```
