# فصل 109 - Hash Password

## مقدمه

رمز عبور یکی از حساس‌ترین اطلاعات یک سیستم است.

وقتی کاربر در یک برنامه ثبت‌نام می‌کند، معمولاً چیزی شبیه این وارد می‌کند:

```text
Email: sobhan@example.com
Password: MySecretPassword123
```

یکی از بزرگ‌ترین اشتباهات امنیتی این است که Password را مستقیماً در Database ذخیره کنیم:

```text
users
────────────────────────────
id | email              | password
1  | user@example.com   | MySecretPassword123
```

اگر Database به هر دلیلی افشا شود، مهاجم می‌تواند رمز عبور کاربران را مستقیماً مشاهده کند.

راهکار استاندارد این است که Password را قبل از ذخیره‌سازی **Hash** کنیم:

```text
Password
   ↓
Password Hashing Algorithm
   ↓
Password Hash
   ↓
Database
```

در این فصل یاد می‌گیریم:

* Hash چیست؟
* چرا Password باید Hash شود؟
* تفاوت Hash و Encryption چیست؟
* چرا نباید از Hashهای عمومی مانند SHA-256 برای Password استفاده کنیم؟
* Salt چیست؟
* Hash کردن Password با Node.js
* استفاده از `bcrypt`
* مقایسه Password با Hash
* Register و Login امن
* مدیریت Cost Factor
* Timing Attack
* Password Policy
* Password Reset
* اشتباهات رایج
* نکات حرفه‌ای
* تمرین‌های عملی
* مینی‌پروژه

---

# 109.1 - Hash چیست؟

Hash Function تابعی است که یک ورودی را دریافت می‌کند و یک خروجی با اندازه مشخص تولید می‌کند.

به‌صورت ساده:

```text
Input
  ↓
Hash Function
  ↓
Hash
```

مثلاً:

```text
"hello"
   ↓
Hash Function
   ↓
"...."
```

ویژگی مهم Hash این است که معمولاً یک‌طرفه طراحی می‌شود.

یعنی:

```text
Password → Hash
```

را می‌توانیم انجام دهیم، اما هدف این نیست که:

```text
Hash → Password
```

را بتوانیم مستقیماً انجام دهیم.

---

# 109.2 - چرا Password را Hash می‌کنیم؟

فرض کنید Database ما شامل این اطلاعات باشد:

```text
email: user@example.com
password: 123456
```

اگر Database لو برود، مهاجم Password واقعی را می‌بیند.

اما اگر Hash ذخیره کنیم:

```text
email: user@example.com
password_hash: $2b$12$...
```

مقدار اصلی Password در Database وجود ندارد.

بنابراین:

```text
Password
   ↓
Hash
   ↓
Database
```

امنیت بسیار بهتری نسبت به ذخیره Plain Text دارد.

---

# 109.3 - Plain Text Password

Plain Text یعنی Password بدون رمزنگاری یا Hash ذخیره شود.

مثلاً:

```js
const user = {
  email: "user@example.com",
  password: "123456"
};
```

این کار نباید در یک سیستم واقعی انجام شود.

حتی اگر Database فقط توسط برنامه قابل دسترسی باشد، باز هم ذخیره Plain Text خطرناک است.

ممکن است:

* Database هک شود.
* Backup لو برود.
* Developer اشتباهی اطلاعات را منتشر کند.
* Logها شامل Password باشند.
* یک SQL Injection اطلاعات را افشا کند.
* فردی با دسترسی داخلی به Database دسترسی پیدا کند.

---

# 109.4 - Hash با Encryption چه تفاوتی دارد؟

Hash و Encryption یکی نیستند.

## Hash

هدف Hash این است که داده به یک مقدار مشتق‌شده تبدیل شود و معمولاً نتوان آن را مستقیماً به مقدار اولیه برگرداند.

```text
Password
   ↓
Hash
```

برای Password Storage از Password Hashing استفاده می‌کنیم.

---

## Encryption

Encryption معمولاً قابل برگشت است؛ یعنی با Key مناسب می‌توان داده را Decrypt کرد.

```text
Data
 ↓
Encryption + Key
 ↓
Encrypted Data
 ↓
Decryption + Key
 ↓
Data
```

برای Password معمولاً نمی‌خواهیم چیزی داشته باشیم که بتوانیم با یک Key آن را به Password اصلی تبدیل کنیم.

بنابراین:

```text
Password → Hash
```

مناسب‌تر از:

```text
Password → Encryption
```

برای ذخیره Password است.

---

# 109.5 - آیا SHA-256 برای Password مناسب است؟

SHA-256 یک Hash Function قدرتمند عمومی است، اما برای ذخیره Password انتخاب مناسبی نیست.

ممکن است این کد را ببینیم:

```js
import crypto from "node:crypto";

const hash = crypto
  .createHash("sha256")
  .update(password)
  .digest("hex");
```

از نظر فنی این کد یک Hash تولید می‌کند، اما برای Password Storage مناسب نیست.

دلیل اصلی این است که Hashهای عمومی مانند SHA-256 برای سرعت بالا طراحی شده‌اند.

اما برای Password Hashing ما برعکس می‌خواهیم:

```text
Password Hashing
      ↓
محاسبه نسبتاً پرهزینه
      ↓
مقاومت بیشتر در برابر Brute Force
```

---

# 109.6 - Password Hashing Algorithm

برای Password باید از الگوریتم‌هایی استفاده کنیم که مخصوص Password Hashing طراحی شده‌اند.

از گزینه‌های شناخته‌شده:

```text
Argon2
bcrypt
scrypt
```

هستند.

این الگوریتم‌ها قابلیت‌هایی مانند Cost یا Work Factor دارند که باعث می‌شوند محاسبه Hash نسبت به Hashهای عمومی پرهزینه‌تر باشد.

---

# 109.7 - Salt چیست؟

یکی از مفاهیم بسیار مهم در Password Hashing، **Salt** است.

Salt یک مقدار تصادفی است که همراه Password در فرآیند Hashing استفاده می‌شود.

به‌صورت ساده:

```text
Password
   +
Random Salt
   ↓
Password Hashing
   ↓
Hash
```

مثلاً فرض کنید دو کاربر یک Password یکسان داشته باشند:

```text
User A:
Password = 123456

User B:
Password = 123456
```

اگر بدون Salt Hash شوند، ممکن است Hash یکسانی داشته باشند.

اما با Salt متفاوت:

```text
User A
Password + Salt A
       ↓
Hash A

User B
Password + Salt B
       ↓
Hash B
```

در نتیجه Hashها متفاوت خواهند بود.

---

# 109.8 - Salt چه مشکلی را حل می‌کند؟

فرض کنید مهاجم یک Database با این اطلاعات داشته باشد:

```text
user1 → hashA
user2 → hashA
user3 → hashA
```

ممکن است متوجه شود چند User یک Password یکسان دارند.

Salt باعث می‌شود حتی Passwordهای یکسان نیز معمولاً Hashهای متفاوتی داشته باشند.

همچنین Salt به مقابله با حملاتی مانند استفاده از Rainbow Table کمک می‌کند.

---

# 109.9 - آیا Salt باید Secret باشد؟

خیر.

Salt معمولاً Secret نیست.

می‌توانیم Salt را همراه Hash ذخیره کنیم.

ساختار مفهومی:

```text
Database
────────────────────────────
password_hash
salt
```

یا الگوریتمی که استفاده می‌کنیم ممکن است Salt را داخل رشته Hash ذخیره کند.

چیزی که باید Secret بماند، مواردی مانند:

```text
Secret Key
Pepper
JWT Secret
Encryption Key
```

هستند.

---

# 109.10 - Pepper چیست؟

Pepper شبیه Salt است، اما تفاوت مهمی دارد.

Salt:

```text
برای هر Password
معمولاً Unique
و قابل ذخیره همراه Hash
```

است.

اما Pepper:

```text
یک Secret مشترک
که خارج از Database نگهداری می‌شود
```

است.

به‌صورت مفهومی:

```text
Password
   +
Salt
   +
Pepper
   ↓
Hash
```

Pepper باید در محل امنی مانند Secret Management یا Environment Configuration مناسب نگهداری شود.

در پروژه‌های معمولی، ابتدا باید Password Hashing صحیح با الگوریتم مناسب و Salt را به‌درستی پیاده‌سازی کنیم.

# 109.11 - Bcrypt

`bcrypt` یکی از الگوریتم‌های شناخته‌شده برای Password Hashing است و سال‌ها در پروژه‌های Backend استفاده شده است.

در Node.js می‌توان از Packageهای مناسب برای کار با bcrypt استفاده کرد.

نصب:

```bash
npm install bcrypt
```

---

# 109.12 - Hash کردن Password با bcrypt

مثال:

```js
import bcrypt from "bcrypt";

const password = "MySecretPassword123";

const hash = await bcrypt.hash(password, 12);

console.log(hash);
```

عدد:

```text
12
```

یک Cost Factor است.

مقدار مناسب باید بر اساس سخت‌افزار و نیاز پروژه انتخاب و با Benchmark مناسب ارزیابی شود.

---

# 109.13 - چرا Hash خروجی متفاوت دارد؟

اگر Password یکسان را چند بار Hash کنیم، نباید انتظار داشته باشیم رشته Hash همیشه یکسان باشد.

مثلاً:

```js
const hash1 = await bcrypt.hash("123456", 12);
const hash2 = await bcrypt.hash("123456", 12);
```

ممکن است:

```text
hash1 !== hash2
```

باشد.

دلیل آن استفاده از Salt تصادفی است.

این رفتار طبیعی و مطلوب است.

---

# 109.14 - آیا باید Salt را خودمان بسازیم؟

در استفاده معمول از bcrypt، بهتر است اجازه دهیم Library فرآیند تولید و مدیریت Salt مورد نیاز را انجام دهد.

یعنی به‌جای طراحی دستی فرآیند:

```text
Generate Salt
Store Salt
Combine Password
Hash
```

از API استاندارد Library استفاده کنیم:

```js
const hash = await bcrypt.hash(password, 12);
```

---

# 109.15 - بررسی Password هنگام Login

هنگام Login، ما Password خام کاربر را دوباره Hash نمی‌کنیم و صرفاً Hashها را با `===` مقایسه نمی‌کنیم.

جریان درست:

```text
Login Password
      ↓
bcrypt.compare()
      ↓
Stored Password Hash
      ↓
true / false
```

مثلاً:

```js
import bcrypt from "bcrypt";

const password = "MySecretPassword123";

const isValid = await bcrypt.compare(
  password,
  storedHash
);

console.log(isValid);
```

اگر Password درست باشد:

```text
true
```

و اگر اشتباه باشد:

```text
false
```

---

# 109.16 - چرا `bcrypt.compare()`؟

چون Hash شامل اطلاعات مورد نیاز الگوریتم برای بررسی Password است.

به‌صورت مفهومی:

```text
Stored Hash
   ↓
Salt + Cost + Hash
```

`bcrypt.compare()` از این اطلاعات برای بررسی Password استفاده می‌کند.

بنابراین لازم نیست Salt را جداگانه از Database استخراج و خودمان مدیریت کنیم.

# 109.17 - Register Flow

یک Register امن می‌تواند چنین جریانی داشته باشد:

```text
Client
  ↓
POST /register
  ↓
Validation
  ↓
Check Existing User
  ↓
Hash Password
  ↓
Save User
  ↓
Response
```

مثلاً:

```js
const passwordHash = await bcrypt.hash(password, 12);

const user = await db.user.create({
  data: {
    email,
    passwordHash
  }
});
```

نکته مهم:

```text
password
```

را ذخیره نمی‌کنیم.

فقط:

```text
passwordHash
```

ذخیره می‌شود.

# 109.20 - آیا Hash را Encrypt کنیم؟

معمولاً نه.

این اشتباه مفهومی است:

```text
Password
   ↓
Encryption
   ↓
Hash
```

برای Password Storage، راهکار اصلی استفاده از Password Hashing Algorithm مناسب است.

اگر داده‌ای نیاز دارد که بعداً دوباره به مقدار اصلی تبدیل شود، آن موضوع بیشتر به Encryption مربوط می‌شود.

# 109.21 - Cost Factor چیست؟

Cost Factor مشخص می‌کند الگوریتم Hashing چه مقدار کار محاسباتی انجام دهد.

در bcrypt مثلاً:

```js
bcrypt.hash(password, 12);
```

عدد `12` Cost Factor است.

به‌صورت مفهومی:

```text
Cost پایین
   ↓
Hash سریع‌تر
   ↓
امنیت کمتر در برابر Brute Force

Cost بالاتر
   ↓
Hash کندتر
   ↓
مقاومت بیشتر
```

اما Cost بیش از حد نیز می‌تواند Server را تحت فشار قرار دهد.

---

# 109.22 - Cost Factor را چگونه انتخاب کنیم؟

نباید فقط بگوییم:

```text
12 همیشه بهترین مقدار است.
```

مقدار مناسب به مواردی مانند:

* سخت‌افزار Server
* تعداد Loginها
* نوع Application
* تعداد کاربران
* Latency قابل قبول
* الگوریتم انتخاب‌شده

وابسته است.

روش بهتر:

```text
Benchmark
   ↓
اندازه‌گیری زمان
   ↓
Load Testing
   ↓
انتخاب مقدار مناسب
```

# 109.25 - Password Reset

در Password Reset نباید Password جدید را برای کاربر به‌صورت Plain Text در Database ذخیره کنیم.

بهتر است از یک فرآیند Token-based استفاده کنیم:

```text
Request Reset
     ↓
Reset Token
     ↓
User Receives Link
     ↓
Validate Token
     ↓
New Password
     ↓
Hash Password
     ↓
Save Hash
```

Token مربوط به Reset Password نیز باید:

* زمان انقضا داشته باشد.
* یک‌بار مصرف باشد.
* به شکل امن مدیریت شود.

# 109.26 - Password Policy

Hash کردن Password به این معنی نیست که هر Passwordی را قبول کنیم.

باید سیاست مناسبی برای Password داشته باشیم.

برای مثال:

```text
حداقل طول مناسب
عدم پذیرش Passwordهای بسیار ضعیف
جلوگیری از Passwordهای افشاشده در صورت نیاز
```

اما نباید با قوانین بیش از حد پیچیده تجربه کاربر را خراب کنیم.

مثلاً اجبار همزمان به:

```text
حرف بزرگ
حرف کوچک
عدد
علامت
چند قانون عجیب
```

لزوماً بهترین روش نیست.

طول مناسب Password اهمیت زیادی دارد.

# 109.28 - Timing Attack

در بعضی سناریوهای امنیتی، تفاوت زمان اجرای عملیات می‌تواند اطلاعاتی درباره وضعیت داخلی سیستم در اختیار مهاجم قرار دهد.

برای Password Verification بهتر است از APIهای استاندارد و معتبر Library استفاده کنیم.

مثلاً:

```js
bcrypt.compare(password, hash);
```

بهتر از طراحی دستی الگوریتم مقایسه Password است.

نباید خودمان فرآیندهای حساس Cryptographic را بدون دانش کافی طراحی کنیم.

# 109.33 - مهاجرت Hash قدیمی

فرض کنید یک سیستم قدیمی داریم که از الگوریتم ضعیف‌تری استفاده می‌کند.

لازم نیست همیشه همه کاربران را مجبور کنیم همان لحظه Password خود را تغییر دهند.

یک روش رایج:

```text
User Login
    ↓
Verify Old Hash
    ↓
Authentication Success
    ↓
Hash with New Algorithm
    ↓
Update Database
```

به این ترتیب می‌توان به‌تدریج کاربران را به الگوریتم جدید منتقل کرد.

---

# اشتباهات رایج

## 1. ذخیره Password به‌صورت Plain Text

```js
password: "123456"
```

کاملاً نامناسب است.

---

## 2. استفاده از MD5

```text
MD5(password)
```

برای Password Storage مناسب نیست.

---

## 3. استفاده مستقیم از SHA-256

```text
SHA256(password)
```

هم Password Hashing مناسب محسوب نمی‌شود.

---

## 4. استفاده از یک Salt ثابت برای همه کاربران

مثلاً:

```text
SALT = "123456"
```

برای همه Passwordها مناسب نیست.

Salt باید به‌صورت مناسب و تصادفی برای هر Password تولید شود.

---

## 5. ساخت Salt دستی بدون دلیل

اگر Library معتبر خودش Salt را مدیریت می‌کند، نیازی نیست فرآیند Salt را از صفر بازنویسی کنیم.

---

## 6. مقایسه Hash با `===`

نباید سیستم Password Verification را این‌گونه طراحی کنیم:

```js
hash(password) === storedHash
```

بهتر است از API مقایسه الگوریتم استفاده شود.

---

## 7. Log کردن Password

```js
console.log(password);
```

هرگز.

---

## 8. برگرداندن Password Hash در API

Hash نیز نباید در Responseهای معمول API قرار بگیرد.

---

## 9. Cost بیش از حد بالا

Cost بسیار بالا می‌تواند باعث مصرف زیاد CPU و کند شدن Login شود.

---

## 10. Cost بسیار پایین

Cost بسیار پایین نیز می‌تواند مقاومت Password Hashing را در برابر Brute Force کاهش دهد.

---

# نکات حرفه‌ای

## 1. از الگوریتم مناسب Password Hashing استفاده کنید

گزینه‌های شناخته‌شده:

```text
Argon2id
bcrypt
scrypt
```

---

## 2. Library معتبر استفاده کنید

Cryptography جایی نیست که بخواهیم برای پروژه واقعی الگوریتم شخصی طراحی کنیم.

---

## 3. Password را هیچ‌وقت Decrypt نمی‌کنیم

اگر طراحی سیستم به شکلی است که باید Password کاربر را Decrypt کنیم، احتمالاً برای Password Storage طراحی مناسبی انجام نداده‌ایم.

---

## 4. Hash را همراه User Data مدیریت کنید

مثلاً:

```text
User
├── id
├── email
├── passwordHash
└── createdAt
```

---

## 5. Password Hash را از Response حذف کنید

در DTO یا Serializer بهتر است Password Hash به‌صورت پیش‌فرض Exclude شود.

---

## 6. Login را Rate Limit کنید

Password Hashing به‌تنهایی جلوی Brute Force را نمی‌گیرد.

ترکیب:

```text
Password Hashing
+
Rate Limiting
+
Monitoring
```

امنیت بیشتری ایجاد می‌کند.

---

## 7. MFA را در سیستم‌های حساس در نظر بگیرید

در سیستم‌های حساس می‌توان لایه دیگری مانند Multi-Factor Authentication اضافه کرد.

---

## 8. Password Reset را امن طراحی کنید

Reset Token باید:

```text
Random
Short-lived
Single-use
```

باشد.

---

## 9. Hash Migration را در نظر بگیرید

اگر الگوریتم Password Hashing در آینده تغییر کند، معماری باید امکان Migration را داشته باشد.

---

## 10. Benchmark واقعی انجام دهید

Cost Factor را فقط از روی یک عدد ثابت انتخاب نکنید.

روی سخت‌افزار واقعی Application اندازه‌گیری کنید.

---

# پاسخ تشریحی

## پاسخ تمرین 1

پاسخ:

```text
C) SHA-256
```

SHA-256 یک Hash Function عمومی است و برای Password Hashing طراحی نشده است.

گزینه‌هایی مانند:

```text
bcrypt
Argon2id
scrypt
```

برای Password Hashing مناسب‌تر هستند.

---

## پاسخ تمرین 2

به‌جای ذخیره Password خام:

```js
const passwordHash = await bcrypt.hash(password, 12);

const user = {
  email,
  passwordHash
};
```

در Database فقط Hash ذخیره می‌شود.

---

## پاسخ تمرین 3

```js
import bcrypt from "bcrypt";

const password = "MySecurePassword123!";

const hash = await bcrypt.hash(password, 12);

console.log(hash);
```

نکته: عدد `12` صرفاً نمونه است و در پروژه واقعی باید با Benchmark مناسب انتخاب شود.

---

## پاسخ تمرین 4

```js
const isValid = await bcrypt.compare(
  password,
  storedHash
);

if (isValid) {
  console.log("Password is correct");
} else {
  console.log("Invalid password");
}
```

---

## پاسخ تمرین 5

به دلیل Salt.

اگر:

```text
User A → Password123
User B → Password123
```

یک Salt تصادفی متفاوت برای هر Password استفاده شود:

```text
Password123 + Salt A → Hash A
Password123 + Salt B → Hash B
```

بنابراین Hashها متفاوت خواهند بود.

---

## پاسخ تمرین 6

Cost بالاتر:

**مزیت:**

* Hash کردن پرهزینه‌تر می‌شود.
* Brute Force برای مهاجم سخت‌تر می‌شود.

**عیب:**

* CPU بیشتری مصرف می‌شود.
* Login و Register ممکن است کندتر شوند.
* در Load بالا فشار بیشتری به Server وارد می‌شود.

بنابراین باید تعادل مناسبی پیدا کنیم.

# مرحله 2 - Register

Request:

```json
{
  "email": "user@example.com",
  "password": "MySecurePassword123!"
}
```

جریان:

```text
Request
   ↓
Validation
   ↓
Check Email
   ↓
Hash Password
   ↓
Save passwordHash
   ↓
Create User
```

نمونه:

```js
import bcrypt from "bcrypt";

async function register(email, password) {
  const passwordHash = await bcrypt.hash(password, 12);

  return {
    email,
    passwordHash
  };
}
```

# جمع‌بندی

Password یکی از حساس‌ترین داده‌های هر سیستم است و نباید به‌صورت Plain Text ذخیره شود.

فرآیند صحیح به‌صورت کلی:

```text
Register:

Password
   ↓
Password Hashing
   ↓
Password Hash
   ↓
Database
```

و هنگام Login:

```text
Password
   ↓
Compare
   ↓
Stored Hash
   ↓
Valid / Invalid
```

نکات اصلی این فصل:

```text
Password را Plain Text ذخیره نکن.
برای Password از Hashing مناسب استفاده کن.
از الگوریتم‌های مناسب مانند Argon2id، bcrypt یا scrypt استفاده کن.
Salt را درست مدیریت کن.
SHA-256 و MD5 را به‌عنوان Password Hashing انتخاب نکن.
Password را Log نکن.
Password Hash را در API Response برنگردان.
Cost Factor را با Benchmark انتخاب کن.
Login را Rate Limit کن.
Password Reset را با Token امن پیاده‌سازی کن.
Secretهای مربوط به سیستم را امن نگهداری کن.
```

در فصل بعد با **Encryption** آشنا می‌شویم و تفاوت کاربردی Encryption و Hashing را عمیق‌تر بررسی می‌کنیم.
