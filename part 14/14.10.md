# فصل 117 - NoSQL Injection

## مقدمه

در فصل قبل با **SQL Injection** آشنا شدیم؛ آسیب‌پذیری‌ای که معمولاً در برنامه‌هایی اتفاق می‌افتد که با Databaseهای رابطه‌ای و SQL کار می‌کنند.

اما تمام برنامه‌های Node.js از SQL Database استفاده نمی‌کنند. در این دوره نیز در بخش پایگاه داده، علاوه بر SQL و PostgreSQL، فصل مستقلی برای **MongoDB** و سپس ORM و ODM در نظر گرفته شده است. 

در Databaseهای NoSQL نیز اگر داده‌ای که کاربر ارسال می‌کند بدون کنترل مناسب وارد Query شود، ممکن است مهاجم بتواند **منطق Query را تغییر دهد**.

به این نوع آسیب‌پذیری:

```text
NoSQL Injection
```

گفته می‌شود.

یکی از معروف‌ترین نمونه‌های آن در برنامه‌هایی رخ می‌دهد که از MongoDB استفاده می‌کنند و Objectهایی که از Request دریافت شده‌اند، مستقیماً به Query Database منتقل می‌شوند.

---

# 117.1 - NoSQL چیست؟

NoSQL به خانواده‌ای از Databaseها گفته می‌شود که مدل ذخیره‌سازی آن‌ها الزاماً مانند Databaseهای رابطه‌ای و Table-based نیست.

یکی از معروف‌ترین Databaseهای NoSQL:

```text
MongoDB
```

است.

در MongoDB داده‌ها معمولاً به شکل Document ذخیره می‌شوند.

مثلاً:

```json
{
  "_id": "123",
  "username": "sobhan",
  "email": "sobhan@example.com"
}
```

در Node.js نیز MongoDB کاربرد زیادی دارد و در ساخت Backendها و APIها مورد استفاده قرار می‌گیرد.

---

# 117.2 - NoSQL Injection چیست؟

NoSQL Injection زمانی اتفاق می‌افتد که ورودی کنترل‌نشده کاربر وارد Query یک NoSQL Database شود و کاربر بتواند رفتار یا منطق Query را تغییر دهد.

به‌صورت ساده:

```text
User Input
    ↓
Node.js
    ↓
NoSQL Query
    ↓
Database
```

اگر Application فرض کند تمام داده‌های دریافتی فقط Valueهای معمولی هستند، اما مهاجم بتواند Object یا Operator وارد کند، ممکن است Query رفتاری غیرمنتظره پیدا کند.

---

# 117.3 - تفاوت SQL Injection و NoSQL Injection

در SQL معمولاً با چیزی مانند:

```sql
SELECT *
FROM users
WHERE username = '...'
```

کار می‌کنیم.

مشکل می‌تواند از ترکیب:

```text
SQL Code + User Input
```

ایجاد شود.

در NoSQL، مخصوصاً MongoDB، Query می‌تواند به شکل Object باشد:

```js
{
  username: username
}
```

مشکل زمانی ایجاد می‌شود که به‌جای یک مقدار ساده، ساختار Query یا Operator وارد شود.

بنابراین:

```text
SQL Injection
    ↓
تغییر SQL Query

NoSQL Injection
    ↓
تغییر NoSQL Query / Operator
```

---

# 117.4 - Query در MongoDB

مثلاً یک Query ساده:

```js
const user = await users.findOne({
  username: username
});
```

اگر:

```js
username = "sobhan";
```

باشد، Query منطقی است.

اما اگر Application به‌جای یک String، یک Object کنترل‌نشده را نیز قبول کند، شرایط متفاوت می‌شود.

---

# 117.5 - مشکل Objectهای کنترل‌نشده

فرض کنید API زیر را داریم:

```http
POST /login
```

و Body:

```json
{
  "username": "sobhan",
  "password": "123456"
}
```

کد:

```js
const { username, password } = req.body;

const user = await users.findOne({
  username,
  password
});
```

در نگاه اول ساده به نظر می‌رسد.

اما اگر Application نوع ورودی را کنترل نکند، ممکن است Client به‌جای String، Object ارسال کند.

مثلاً:

```json
{
  "username": {
    "$ne": null
  },
  "password": {
    "$ne": null
  }
}
```

در چنین شرایطی، اگر این Objectها مستقیماً وارد Query شوند، ساختار Query تغییر می‌کند.

---

# 117.6 - MongoDB Operators

MongoDB Operatorهای مختلفی دارد.

برخی از Operatorها:

```text
$eq
$ne
$gt
$gte
$lt
$lte
$in
$nin
$exists
$regex
$or
$and
```

این Operatorها بخشی از زبان Query MongoDB هستند.

بنابراین نباید اجازه دهیم کاربر هر Object دلخواهی را به‌عنوان Query به Database منتقل کند.

---

# 117.7 - Operator Injection

یکی از مفاهیم مهم در NoSQL Injection:

```text
Operator Injection
```

است.

فرض کنید برنامه انتظار دارد:

```json
{
  "username": "sobhan"
}
```

دریافت کند.

اما به‌جای آن:

```json
{
  "username": {
    "$ne": null
  }
}
```

دریافت شود.

در این حالت `$ne` دیگر یک Value معمولی نیست؛ بلکه یک MongoDB Operator است.

---

# 117.8 - چرا این اتفاق خطرناک است؟

چون برنامه تصور کرده:

```text
username = String
```

اما داده واقعی ممکن است:

```text
username = Object
```

باشد.

بنابراین باید همیشه بین:

```text
Expected Type
```

و:

```text
Received Type
```

تفاوت قائل شویم.

---

# 117.9 - Validation

یکی از اولین لایه‌های دفاعی:

```text
Input Validation
```

است.

مثلاً اگر `username` باید String باشد:

```js
if (typeof username !== "string") {
  return res.status(400).json({
    message: "Invalid username"
  });
}
```

همین موضوع برای Password و سایر Fieldها نیز باید رعایت شود.

---

# 117.10 - Schema Validation

بهتر است Validation را به شکل ساختاری انجام دهیم.

مثلاً با یک Validation Library:

```js
const schema = z.object({
  username: z.string(),
  password: z.string()
});
```

سپس:

```js
const result = schema.safeParse(req.body);

if (!result.success) {
  return res.status(400).json({
    message: "Invalid input"
  });
}
```

در این حالت اگر کاربر به‌جای String یک Object ارسال کند، داده از Validation عبور نمی‌کند.

---

# 117.11 - Allowlist کردن فیلدها

نباید هر Fieldای که کاربر ارسال می‌کند را مستقیماً وارد Query کنیم.

فرض کنید فقط این فیلدها مجاز هستند:

```text
username
email
```

بهتر است فقط همین Fieldها را استخراج کنیم:

```js
const {
  username,
  email
} = req.body;
```

و از انتقال مستقیم کل Body جلوگیری کنیم.

---

# 117.12 - مشکل استفاده مستقیم از req.body

یکی از الگوهای خطرناک:

```js
const user = await users.findOne(req.body);
```

است.

چرا؟

چون در این حالت Client عملاً تعیین می‌کند Query چه ساختاری داشته باشد.

Client باید:

```text
Data
```

ارسال کند.

نه:

```text
Database Query
```

---

# 117.13 - الگوی امن‌تر

به‌جای:

```js
const user = await users.findOne(req.body);
```

از Fieldهای مشخص استفاده کنید:

```js
const {
  username
} = req.body;

const user = await users.findOne({
  username
});
```

و قبل از آن:

```js
if (typeof username !== "string") {
  return res.status(400).json({
    message: "Invalid username"
  });
}
```

---

# 117.14 - حذف MongoDB Operatorها از Input

یکی از روش‌های دفاعی دیگر، جلوگیری از ورود Keyهایی است که با `$` یا `.` شروع می‌شوند، در جاهایی که چنین ساختاری از کاربر نباید پذیرفته شود.

اما این روش را نباید تنها لایه امنیتی در نظر گرفت.

روش اصلی همچنان:

```text
Schema Validation
+
Type Validation
+
Controlled Query Construction
```

است.

---

# 117.15 - Prototype Pollution و NoSQL

در JavaScript و Node.js موضوع دیگری نیز وجود دارد:

```text
Prototype Pollution
```

که با NoSQL Injection یکسان نیست.

اما در برخی Applicationها می‌تواند در کنار پردازش Objectهای کنترل‌نشده، ریسک امنیتی ایجاد کند.

بنابراین نباید تمام آسیب‌پذیری‌های Objectهای JavaScript را NoSQL Injection بدانیم.

---

# 117.16 - Query Construction

بهترین رویکرد این است که Query را Application بسازد.

مثلاً:

```js
const filter = {
  username
};
```

نه اینکه:

```js
const filter = req.body;
```

در حالت اول:

```text
Application
    ↓
Query Structure
```

را کنترل می‌کند.

در حالت دوم:

```text
User
    ↓
Query Structure
```

را تا حد زیادی کنترل می‌کند.

---

# 117.17 - Login امن با MongoDB

یک Login ساده:

```js
app.post("/login", async (req, res) => {
  const { username, password } = req.body;

  if (
    typeof username !== "string" ||
    typeof password !== "string"
  ) {
    return res.status(400).json({
      message: "Invalid input"
    });
  }

  const user = await users.findOne({
    username
  });

  if (!user) {
    return res.status(401).json({
      message: "Invalid credentials"
    });
  }

  // Password hash verification

  res.json({
    message: "Login successful"
  });
});
```

در این طراحی، Password مستقیماً داخل Query قرار نگرفته است.

Password باید با Hash ذخیره‌شده مقایسه شود.

---

# 117.18 - چرا Password را داخل Query نکنیم؟

روش نامناسب:

```js
const user = await users.findOne({
  username,
  password
});
```

روش بهتر:

```js
const user = await users.findOne({
  username
});
```

سپس:

```text
Password
   ↓
Hash Verification
   ↓
Stored Password Hash
```

این موضوع با فصل Hash Password مرتبط است.

---

# 117.19 - Mongoose و NoSQL Injection

در پروژه‌های Node.js ممکن است از:

```text
Mongoose
```

استفاده کنیم.

Mongoose یک ODM برای MongoDB است و در فهرست اکوسیستم دوره نیز در کنار Prisma و Drizzle قرار گرفته است. 

استفاده از Mongoose می‌تواند Validation و Schema را ساده‌تر کند، اما:

```text
Mongoose
≠
امنیت کامل
```

اگر Query را به شکل ناامن بسازیم، همچنان باید مراقب باشیم.

---

# 117.20 - Mongoose Schema

مثلاً:

```js
const userSchema = new mongoose.Schema({
  username: {
    type: String,
    required: true
  },

  email: {
    type: String,
    required: true
  },

  passwordHash: {
    type: String,
    required: true
  }
});
```

Schema کمک می‌کند ساختار داده مشخص باشد.

---

# 117.21 - Validation در Mongoose

مثلاً:

```js
const user = new User({
  username,
  email,
  passwordHash
});

await user.save();
```

Mongoose می‌تواند برخی Validationهای تعریف‌شده در Schema را انجام دهد.

اما Validation ورودی HTTP همچنان اهمیت دارد.

---

# 117.22 - مستقیم Query کردن با Body

این الگو مناسب نیست:

```js
User.findOne(req.body);
```

بهتر است:

```js
User.findOne({
  username: req.body.username
});
```

و قبل از آن:

```js
if (typeof req.body.username !== "string") {
  return res.status(400).json({
    message: "Invalid username"
  });
}
```

---

# 117.23 - Filtering

فرض کنید API زیر داریم:

```http
GET /products
```

و کاربر می‌تواند محصولات را Filter کند.

نباید بدون طراحی مناسب اجازه دهیم Client هر Query Objectی را ارسال کند.

بهتر است API مشخص کند:

```text
category
minPrice
maxPrice
page
limit
```

و Server خودش Query را بسازد.

---

# 117.24 - Pagination

مثلاً:

```js
const page = Number(req.query.page);
const limit = Number(req.query.limit);
```

سپس Validation:

```js
if (
  !Number.isInteger(page) ||
  page < 1 ||
  !Number.isInteger(limit) ||
  limit < 1 ||
  limit > 100
) {
  return res.status(400).json({
    message: "Invalid pagination"
  });
}
```

سپس Query با مقادیر کنترل‌شده ساخته می‌شود.

---

# 117.25 - Regex و NoSQL Injection

MongoDB از Regex نیز پشتیبانی می‌کند.

مثلاً:

```js
{
  username: {
    $regex: search
  }
}
```

در اینجا باید علاوه بر Injection، به **Regular Expression Abuse** نیز توجه کنیم.

اگر Regex کاملاً تحت کنترل کاربر باشد، ممکن است مشکلات Performance ایجاد شود.

بنابراین باید:

```text
Input Validation
+
Length Limit
+
Regex Design
+
Performance Testing
```

را در نظر گرفت.

---

# 117.26 - NoSQL Injection و DoS

گاهی یک ورودی مخرب الزاماً باعث خواندن اطلاعات نمی‌شود، اما می‌تواند Query بسیار سنگینی ایجاد کند.

مثلاً Regex پیچیده یا Query بسیار گسترده می‌تواند منابع Server یا Database را مصرف کند.

بنابراین NoSQL Security فقط درباره:

```text
Authentication Bypass
```

نیست.

Performance نیز بخشی از امنیت است.

---

# 117.27 - Rate Limiting

Endpointهای حساس مانند:

```text
/login
/search
/password-reset
```

به Rate Limiting نیاز دارند.

این موضوع با فصل Rate Limit نیز ارتباط مستقیم دارد.

ترکیب:

```text
Validation
+
Query Security
+
Rate Limit
```

امنیت Endpoint را افزایش می‌دهد.

---

# 117.28 - Least Privilege در MongoDB

Application نباید با یک Database User با دسترسی کامل کار کند.

بهتر است:

```text
Application
    ↓
Limited MongoDB User
    ↓
Required Database Permissions
```

داشته باشیم.

این همان اصل:

```text
Least Privilege
```

است.

---

# 117.29 - Error Handling

نباید Error داخلی MongoDB را مستقیماً به Client بدهیم.

اشتباه:

```js
catch (error) {
  res.status(500).json({
    error: error.message
  });
}
```

بهتر:

```js
catch (error) {
  console.error(error);

  res.status(500).json({
    message: "Internal server error"
  });
}
```

---

# 117.30 - Logging

Error باید در Server ثبت شود:

```js
console.error(error);
```

در پروژه‌های حرفه‌ای بهتر است از Logging Library استفاده کنیم.

برای مثال در اکوسیستم Node.js این دوره نیز ابزارهایی مانند Winston و Pino در نظر گرفته شده‌اند.

# 117.31 - تست NoSQL Injection

برای Endpointهای MongoDB باید ورودی‌های مختلف را تست کنیم:

```text
String
Number
Boolean
Null
Array
Object
Nested Object
Unexpected Operator
Very Long Input
```

هدف این است که Application فقط Type و Structure مورد انتظار را قبول کند.

# 117.32 - تست Type

مثلاً اگر:

```text
username
```

باید String باشد، این موارد باید بررسی شوند:

```json
{
  "username": "sobhan"
}
```

و:

```json
{
  "username": 123
}
```

و:

```json
{
  "username": {}
}
```

و:

```json
{
  "username": []
}
```

تنها Type مورد انتظار باید پذیرفته شود.

---

# 117.33 - Security Boundary

یک اصل بسیار مهم:

```text
HTTP Request
```

یک مرز امنیتی است.

هر داده‌ای که از:

```text
req.body
req.query
req.params
req.headers
cookies
```

می‌آید باید **Untrusted Input** در نظر گرفته شود.

---

# 117.34 - Untrusted Input

هیچ‌وقت فرض نکنید:

```text
User Input = Safe
```

بلکه:

```text
User Input = Untrusted
```

تا زمانی که Validation و Processing مناسب روی آن انجام شود.

# 117.35 - معماری دفاعی

برای ساخت یک API امن بهتر است چند لایه داشته باشیم:

```text
HTTP Request
      ↓
Validation
      ↓
Normalization
      ↓
Authorization
      ↓
Controlled Query
      ↓
MongoDB
      ↓
Safe Response
```

امنیت نباید فقط به یک Function یا Package وابسته باشد.

# پاسخ تشریحی

## پاسخ تمرین 1

NoSQL Injection آسیب‌پذیری‌ای است که در آن ورودی کنترل‌نشده کاربر باعث تغییر رفتار یا ساختار Query در یک NoSQL Database می‌شود.

---

## پاسخ تمرین 2

SQL Injection معمولاً با تغییر ساختار SQL Query مرتبط است، در حالی که NoSQL Injection می‌تواند از طریق وارد کردن Objectها یا Operatorهای Database مانند MongoDB، منطق Query را تغییر دهد.

---

## پاسخ تمرین 3

چون کل `req.body` مستقیماً به Query تبدیل شده است.

در این حالت Client می‌تواند بیش از مقدار مورد انتظار روی ساختار Query تأثیر بگذارد.

---

## پاسخ تمرین 4

ابتدا مقدار را استخراج و Validate می‌کنیم:

```js
const { username } = req.body;

if (typeof username !== "string") {
  return res.status(400).json({
    message: "Invalid username"
  });
}

const user = await users.findOne({
  username
});
```

---

## پاسخ تمرین 5

چون JavaScript به‌صورت Dynamic Typed است و داده‌ای که از HTTP دریافت می‌کنیم الزاماً Type مورد انتظار Application را ندارد.

---

## پاسخ تمرین 6

```js
if (typeof username !== "string") {
  return res.status(400).json({
    message: "Username must be a string"
  });
}
```

---

## پاسخ تمرین 7

چون Operatorهایی مانند:

```text
$ne
$gt
$in
$exists
```

بخشی از زبان Query MongoDB هستند و اگر کاربر بتواند آن‌ها را آزادانه وارد Query کند، ممکن است رفتار Query برخلاف انتظار Application شود.

---

## پاسخ تمرین 8

در:

```js
users.findOne({
  username
});
```

Application ساختار Query را کنترل می‌کند.

اما:

```js
users.findOne(req.body);
```

ساختار Query تا حد زیادی از داده‌ای که Client ارسال کرده می‌آید.

---

## پاسخ تمرین 9

چون Developer همچنان می‌تواند Queryهای ناامن بسازد، Raw Query استفاده کند، Input را بدون Validation وارد Query کند یا ساختار Query را به Client واگذار کند.

---

## پاسخ تمرین 10

Regex پیچیده یا بسیار بزرگ می‌تواند باعث مصرف زیاد CPU و زمان پردازش شود و در شرایط خاص به یک مشکل Performance یا حتی DoS تبدیل شود.

# مرحله 4 - Register

```js
app.post("/users", async (req, res) => {
  const result = userSchema.safeParse(req.body);

  if (!result.success) {
    return res.status(400).json({
      message: "Invalid input"
    });
  }

  const {
    username,
    email,
    password
  } = result.data;

  const existingUser = await users.findOne({
    $or: [
      { username },
      { email }
    ]
  });

  if (existingUser) {
    return res.status(409).json({
      message: "User already exists"
    });
  }

  const passwordHash = await bcrypt.hash(
    password,
    12
  );

  const resultInsert = await users.insertOne({
    username,
    email,
    passwordHash,
    createdAt: new Date()
  });

    username,
    email
  });
});
```

# مرحله 7 - Pagination

```js
app.get("/users", async (req, res) => {
  const page = Number(req.query.page ?? 1);
  const limit = Number(req.query.limit ?? 20);

  if (
    !Number.isInteger(page) ||
    page < 1
  ) {
    return res.status(400).json({
      message: "Invalid page"
    });
  }

  if (
    !Number.isInteger(limit) ||
    limit < 1 ||
    limit > 100
  ) {
    return res.status(400).json({
      message: "Invalid limit"
    });
  }

  const usersList = await users
    .find(
      {},
      {
        projection: {
          passwordHash: 0
        }
      }
    )
    .skip((page - 1) * limit)
    .limit(limit)
    .toArray();

  res.json({
    page,
    limit,
    data: usersList
  });
});
```

```js
app.patch("/users/:username", async (req, res) => {
  const username = req.params.username;

  const updateSchema = z.object({
    email: z.string().email()
  });

  const result = updateSchema.safeParse(req.body);

  if (!result.success) {
    return res.status(400).json({
      message: "Invalid input"
    });

  const { email } = result.data;

  const updateResult = await users.updateOne(
    { username },
    {
      $set: {
        email
      }
    }
  );

  if (updateResult.matchedCount === 0) {
    return res.status(404).json({
      message: "User not found"
    });
  }

  res.json({
    message: "User updated"
  });
});
```

# جمع‌بندی

NoSQL Injection یکی از مهم‌ترین آسیب‌پذیری‌هایی است که هنگام ساخت Backend با Databaseهای NoSQL باید بشناسیم.

در MongoDB یکی از سناریوهای مهم زمانی ایجاد می‌شود که Application انتظار یک مقدار ساده مانند:

```json
{
  "username": "sobhan"
}
```

را دارد، اما به‌جای آن یک Object حاوی Operator دریافت می‌کند.

بنابراین یکی از مهم‌ترین اصول این فصل:

```text
Never trust request data as a database query.
```

یعنی:

```text
هیچ‌وقت داده Request را مستقیماً به Query Database تبدیل نکنید.
```

به‌جای آن:

```text
Validation
    ↓
Type Checking
    ↓
Allowlist
    ↓
Controlled Query Construction
    ↓
MongoDB
```

را دنبال کنید.

همچنین باید به خاطر داشته باشیم که امنیت فقط با یک تکنیک حل نمی‌شود:

```text
NoSQL Injection Protection
+
Validation
+
Authentication
+
Authorization
+
Rate Limiting
+
Least Privilege
+
Secure Error Handling
+
Logging
+
Security Testing
```

ترکیب این لایه‌هاست که یک Backend امن‌تر ایجاد می‌کند.
