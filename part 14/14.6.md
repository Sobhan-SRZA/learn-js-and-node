# فصل 113 - CORS

## مقدمه

وقتی یک Frontend و یک Backend داریم، ممکن است این دو برنامه روی Originهای متفاوت اجرا شوند.

برای مثال:

```text
Frontend
http://localhost:5173

Backend
http://localhost:3000
```

اگر Frontend بخواهد از طریق JavaScript به Backend درخواست ارسال کند، مرورگر قوانین امنیتی خاصی را اعمال می‌کند.

یکی از مهم‌ترین این قوانین، **Same-Origin Policy** است.

CORS یا:

> Cross-Origin Resource Sharing

مکانیزمی است که به Server اجازه می‌دهد مشخص کند چه Originهایی می‌توانند به منابع آن از طریق مرورگر دسترسی داشته باشند.

در Node.js، مخصوصاً هنگام ساخت REST API، شناخت CORS بسیار مهم است؛ چون بسیاری از خطاهایی که هنگام اتصال React، Vue، Angular یا سایر Frontendها به Backend مشاهده می‌کنیم، مربوط به تنظیمات CORS هستند.

---

# 113.1 - Origin چیست؟

برای درک CORS ابتدا باید مفهوم Origin را بدانیم.

Origin از سه بخش تشکیل می‌شود:

```text
Scheme + Host + Port
```

مثلاً:

```text
https://example.com:443
```

دارای:

```text
Scheme → https
Host   → example.com
Port   → 443
```

است.

---

# 113.2 - مثال Origin

این دو URL را در نظر بگیرید:

```text
http://localhost:3000
http://localhost:5173
```

Host هر دو یکی است:

```text
localhost
```

اما Port متفاوت است:

```text
3000
5173
```

بنابراین Origin آن‌ها متفاوت است.

---

# 113.3 - چه چیزهایی Origin را متفاوت می‌کنند؟

تغییر هرکدام از موارد زیر می‌تواند Origin را متفاوت کند:

```text
Scheme
Host
Port
```

مثلاً:

```text
http://example.com
https://example.com
```

به دلیل تفاوت Scheme، دو Origin متفاوت هستند.

همچنین:

```text
https://example.com
https://api.example.com
```

به دلیل تفاوت Host متفاوت هستند.

و:

```text
https://example.com:443
https://example.com:8443
```

به دلیل تفاوت Port متفاوت هستند.

---

# 113.4 - Same-Origin Policy چیست؟

مرورگرها برای امنیت کاربران، دسترسی JavaScript به منابع Originهای دیگر را محدود می‌کنند.

به این مکانیزم:

```text
Same-Origin Policy
```

گفته می‌شود.

مثلاً فرض کنید:

```text
Frontend
http://localhost:5173
```

به:

```text
Backend
http://localhost:3000
```

Request ارسال می‌کند.

این دو Origin متفاوت هستند.

در چنین شرایطی Browser باید بررسی کند که Server آیا اجازه Cross-Origin Access را داده است یا خیر.

---

# 113.5 - CORS چیست؟

CORS مکانیزمی مبتنی بر HTTP Headers است که Server با استفاده از آن مشخص می‌کند چه درخواست‌های Cross-Origin از طرف Browser مجاز هستند.

مثلاً Server می‌تواند بگوید:

```http
Access-Control-Allow-Origin: http://localhost:5173
```

یعنی:

```text
Frontend:
http://localhost:5173
```

اجازه دسترسی دارد.

---

# 113.6 - CORS مربوط به Browser است

یک نکته بسیار مهم:

> CORS عمدتاً مکانیزم امنیتی Browser است، نه خود Node.js.

مثلاً اگر یک Frontend در Browser با `fetch()` به API درخواست بفرستد، Browser سیاست CORS را اعمال می‌کند.

اما اگر همان API را با یک برنامه Server-Side، `curl` یا ابزار دیگری صدا بزنیم، رفتار CORS مانند Browser نخواهد بود.

مثلاً:

```bash
curl http://localhost:3000/api/users
```

ممکن است Response را دریافت کند، حتی اگر Browser به دلیل CORS اجازه دسترسی JavaScript به Response را ندهد.

---

# 113.7 - CORS چگونه کار می‌کند؟

فرض کنید:

```text
Frontend
http://localhost:5173
       │
       │ fetch()
       ▼
Backend
http://localhost:3000
```

Browser متوجه می‌شود Request Cross-Origin است.

Server می‌تواند در Response Header اعلام کند:

```http
Access-Control-Allow-Origin: http://localhost:5173
```

Browser این Header را بررسی می‌کند.

اگر Origin مجاز باشد، JavaScript می‌تواند Response را در اختیار داشته باشد.

---

# 113.8 - `Access-Control-Allow-Origin`

مهم‌ترین Header در CORS:

```http
Access-Control-Allow-Origin
```

است.

مثلاً:

```http
Access-Control-Allow-Origin: https://example.com
```

یا:

```http
Access-Control-Allow-Origin: *
```

---

# 113.9 - Wildcard `*`

می‌توان گفت همه Originها مجاز هستند:

```http
Access-Control-Allow-Origin: *
```

اما استفاده از `*` همیشه مناسب نیست.

خصوصاً وقتی Authentication مبتنی بر Cookie داریم.

برای APIهایی که داده حساس دارند بهتر است Originهای مجاز را به‌صورت دقیق مشخص کنیم.

---

# 113.10 - مثال ساده

فرض کنید:

```text
Frontend:
https://app.example.com

Backend:
https://api.example.com
```

Backend می‌تواند Response Header زیر را ارسال کند:

```http
Access-Control-Allow-Origin: https://app.example.com
```

در نتیجه Browser می‌داند که این Origin مجاز است.

---

# 113.11 - Request Origin

Browser در Request Cross-Origin معمولاً Header زیر را ارسال می‌کند:

```http
Origin: https://app.example.com
```

Server می‌تواند این Origin را بررسی کند.

مثلاً:

```text
Origin
   ↓
https://app.example.com
   ↓
Allowed?
   ↓
Yes
```

---

# 113.12 - CORS فقط GET نیست

CORS می‌تواند برای Methodهای مختلف مطرح شود:

```text
GET
POST
PUT
PATCH
DELETE
```

برای مثال:

```http
DELETE /api/users/10
```

نیز می‌تواند Cross-Origin باشد.

---

# 113.13 - Simple Request

بعضی Requestها در شرایط مشخص می‌توانند بدون Preflight ارسال شوند.

به این نوع Requestها معمولاً:

```text
Simple Request
```

گفته می‌شود.

اما Simple بودن Request به چند شرط وابسته است؛ از جمله Method، Headerها و Content-Type.

---

# 113.14 - Preflight چیست؟

برای برخی Requestهای Cross-Origin، Browser قبل از ارسال Request اصلی، یک Request از نوع:

```http
OPTIONS
```

ارسال می‌کند.

به این Request:

```text
Preflight Request
```

گفته می‌شود.

مثلاً:

```text
Browser
   │
   │ OPTIONS
   ▼
Server
   │
   │ Permission
   ▼
Browser
   │
   │ POST
   ▼
Server
```

---

# 113.15 - چرا Preflight انجام می‌شود؟

فرض کنید Frontend قصد دارد چنین Requestی ارسال کند:

```http
PUT /api/users/10
Authorization: Bearer ...
Content-Type: application/json
```

Browser ممکن است ابتدا بررسی کند که Server چنین Requestی را اجازه می‌دهد یا خیر.

بنابراین:

```http
OPTIONS /api/users/10
```

ارسال می‌شود.

---

# 113.16 - `Access-Control-Allow-Methods`

Server می‌تواند Methodهای مجاز را اعلام کند:

```http
Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE
```

مثلاً:

```http
Access-Control-Allow-Methods: GET, POST
```

یعنی فقط Methodهای مشخص‌شده مجاز هستند.

---

# 113.17 - `Access-Control-Allow-Headers`

اگر Client Headerهای خاصی ارسال کند، Server می‌تواند آن‌ها را اعلام کند.

مثلاً:

```http
Access-Control-Allow-Headers: Content-Type, Authorization
```

این مورد در APIهایی که از JWT یا سایر Authorization Headerها استفاده می‌کنند بسیار مهم است.

---

# 113.18 - مثال Preflight

Browser:

```http
OPTIONS /api/users
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Authorization, Content-Type
```

Server:

```http
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: POST
Access-Control-Allow-Headers: Authorization, Content-Type
```

پس Browser می‌تواند Request اصلی را ارسال کند.

---

# 113.19 - `Access-Control-Request-Method`

در Preflight Browser می‌تواند مشخص کند که قصد دارد چه Methodی ارسال کند:

```http
Access-Control-Request-Method: POST
```

Server باید بر اساس Policy خودش تصمیم بگیرد که این Method مجاز است یا خیر.

---

# 113.20 - `Access-Control-Request-Headers`

Browser می‌تواند Headerهای مورد نیاز Request اصلی را نیز اعلام کند:

```http
Access-Control-Request-Headers: Authorization, Content-Type
```

Server باید بررسی کند که آیا این Headerها مجاز هستند یا خیر.

---

# 113.21 - Credentials چیست؟

Credentials می‌تواند شامل اطلاعات احراز هویت مانند:

```text
Cookies
HTTP Authentication
```

باشد.

در Fetch می‌توان Credentialها را فعال کرد:

```js
fetch("https://api.example.com/profile", {
  credentials: "include"
});
```

---

# 113.22 - `Access-Control-Allow-Credentials`

اگر Server اجازه ارسال Credentialهای Cross-Origin را بدهد، می‌تواند Header زیر را ارسال کند:

```http
Access-Control-Allow-Credentials: true
```

اما این موضوع با `Access-Control-Allow-Origin: *` محدودیت مهمی دارد.

---

# 113.23 - مشکل `*` با Credentials

این ترکیب مناسب نیست:

```http
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
```

برای Credentialed CORS باید Origin مشخص و قابل اعتماد استفاده شود.

مثلاً:

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
```

---

# 113.24 - Cookie و CORS

فرض کنید Frontend:

```text
https://app.example.com
```

و Backend:

```text
https://api.example.com
```

است.

اگر Authentication با Cookie انجام شود، تنظیمات Cookie و CORS باید با هم سازگار باشند.

در سمت Client:

```js
fetch("https://api.example.com/profile", {
  credentials: "include"
});
```

و Server باید Policy مناسب Credentials را داشته باشد.

---

# 113.25 - SameSite Cookie

در کنار CORS، Cookieها تنظیمات مهمی مانند:

```text
SameSite
Secure
HttpOnly
```

دارند.

مثلاً:

```js
res.cookie("session", token, {
  httpOnly: true,
  secure: true,
  sameSite: "lax"
});
```

تنظیم دقیق `SameSite` به معماری واقعی Frontend و Backend وابسته است.

---

# 113.26 - CORS و Authentication

CORS جایگزین Authentication نیست.

CORS مشخص می‌کند:

```text
چه Originهایی از Browser
اجازه دسترسی Cross-Origin دارند
```

اما Authentication مشخص می‌کند:

```text
چه Userای هویت معتبر دارد
```

و Authorization مشخص می‌کند:

```text
User چه کاری اجازه دارد انجام دهد
```

این سه مفهوم را نباید با هم اشتباه گرفت.

---

# 113.27 - CORS و Authorization

ممکن است:

```text
Origin → مجاز
User → احراز هویت شده
```

باشد اما User اجازه حذف User دیگری را نداشته باشد.

بنابراین:

```text
CORS
+
Authentication
+
Authorization
```

سه لایه متفاوت هستند.

---

# 113.28 - نصب Package `cors`

در Express یکی از Packageهای رایج برای مدیریت CORS:

```text
cors
```

است.

نصب:

```bash
npm install cors
```

---

# 113.29 - استفاده ساده از `cors`

```js
import express from "express";
import cors from "cors";

const app = express();

app.use(cors());

app.get("/api/users", (req, res) => {
  res.json({
    users: []
  });
});

app.listen(3000);
```

این تنظیمات Policy پیش‌فرض Package را اعمال می‌کند.

برای Production بهتر است Policy را آگاهانه تنظیم کنیم.

---

# 113.30 - اجازه دادن به یک Origin مشخص

مثلاً:

```text
http://localhost:5173
```

```js
import cors from "cors";

app.use(
  cors({
    origin: "http://localhost:5173"
  })
);
```

در این حالت API برای همان Origin تنظیم شده است.

---

# 113.31 - چند Origin مجاز

فرض کنید این Originها مجاز هستند:

```text
https://app.example.com
https://admin.example.com
http://localhost:5173
```

می‌توانیم آن‌ها را در یک Array نگه داریم:

```js
const allowedOrigins = [
  "https://app.example.com",
  "https://admin.example.com",
  "http://localhost:5173"
];
```

---

# 113.32 - بررسی Dynamic Origin

می‌توانیم Origin درخواست را بررسی کنیم:

```js
const allowedOrigins = [
  "https://app.example.com",
  "https://admin.example.com"
];

app.use(
  cors({
    origin(origin, callback) {
      if (!origin || allowedOrigins.includes(origin)) {
        callback(null, true);
      } else {
        callback(new Error("Not allowed by CORS"));
      }
    }
  })
);
```

در اینجا فقط Originهای موجود در Allow List مجاز هستند.

---

# 113.33 - چرا `origin` ممکن است وجود نداشته باشد؟

همه Requestها الزاماً از Browser با Origin معمولی نمی‌آیند.

برای مثال بعضی Requestها ممکن است Header `Origin` نداشته باشند.

بنابراین باید بر اساس نیاز Application تصمیم بگیریم که:

```js
if (!origin)
```

چه رفتاری داشته باشد.

---

# 113.34 - CORS برای کل Application

می‌توان Middleware را روی کل Application قرار داد:

```js
app.use(
  cors({
    origin: "https://app.example.com"
  })
);
```

در این حالت Policy برای Routeهای بعدی اعمال می‌شود.

---

# 113.35 - CORS برای یک Route

می‌توان CORS را فقط برای یک Route فعال کرد:

```js
app.get(
  "/api/public",
  cors({
    origin: "https://app.example.com"
  }),
  (req, res) => {
    res.json({
      message: "Public API"
    });
  }
);
```

---

# 113.36 - `methods`

می‌توان Methodهای مجاز را مشخص کرد:

```js
app.use(
  cors({
    origin: "https://app.example.com",
    methods: ["GET", "POST", "PUT", "PATCH", "DELETE"]
  })
);
```

---

# 113.37 - `allowedHeaders`

مثلاً:

```js
app.use(
  cors({
    origin: "https://app.example.com",
    allowedHeaders: ["Content-Type", "Authorization"]
  })
);
```

این تنظیم برای APIهایی که Authorization Header دارند کاربردی است.

---

# 113.38 - `credentials`

اگر Cookie یا Credentialهای مناسب استفاده می‌کنیم:

```js
app.use(
  cors({
    origin: "https://app.example.com",
    credentials: true
  })
);
```

و سمت Client:

```js
fetch("https://api.example.com/profile", {
  credentials: "include"
});
```

---

# 113.39 - `maxAge`

می‌توان مدت Cache شدن نتیجه Preflight را مشخص کرد:

```js
app.use(
  cors({
    origin: "https://app.example.com",
    maxAge: 86400
  })
);
```

این مقدار بر حسب ثانیه است.

---

# 113.40 - چرا Preflight Cache مهم است؟

اگر Browser برای هر Request پیچیده دوباره Preflight بفرستد:

```text
OPTIONS
POST
OPTIONS
POST
OPTIONS
POST
```

تعداد Requestها افزایش پیدا می‌کند.

با Cache مناسب، Browser می‌تواند برای مدتی نتیجه Preflight را نگه دارد.

---

# 113.41 - `OPTIONS` Route

در برخی تنظیمات ممکن است لازم باشد درخواست‌های `OPTIONS` به‌درستی مدیریت شوند.

Package `cors` در Express می‌تواند بسیاری از این جزئیات را مدیریت کند، اما باید Middlewareها و ترتیب آن‌ها را درست تنظیم کنیم.

---

# 113.42 - ترتیب Middlewareها

ترتیب Middlewareها در Express مهم است.

مثلاً:

```js
app.use(cors());
app.use(express.json());
```

و سپس:

```js
app.use("/api", router);
```

در بسیاری از پروژه‌ها بهتر است CORS قبل از Routeهایی که باید Headerهای CORS دریافت کنند اجرا شود.

---

# 113.43 - CORS Error

یکی از خطاهای رایج در Browser چیزی شبیه این است:

```text
Access to fetch at ...
from origin ...
has been blocked by CORS policy
```

این پیام به این معنی است که Browser Policy CORS را قبول نکرده است.

---

# 113.44 - CORS Error لزوماً خطای Server نیست

ممکن است Backend Response ارسال کرده باشد، اما Browser اجازه ندهد JavaScript آن Response را بخواند.

بنابراین باید در DevTools بررسی کنیم:

```text
Request
Response
Response Headers
OPTIONS
Origin
```

---

# 113.45 - بررسی CORS با DevTools

در Browser:

```text
DevTools
   ↓
Network
   ↓
Request
   ↓
Headers
```

بررسی کنید:

```text
Origin
Access-Control-Allow-Origin
Access-Control-Allow-Methods
Access-Control-Allow-Headers
Access-Control-Allow-Credentials
```

---

# 113.46 - CORS و Postman

Postman مانند Browser همان محدودیت CORS را اعمال نمی‌کند.

بنابراین ممکن است:

```text
Postman → Request موفق
Browser → CORS Error
```

باشد.

این موضوع طبیعی است و باید تست Browser را نیز انجام دهیم.

---

# 113.47 - CORS و cURL

همین مسئله برای `curl` نیز صدق می‌کند.

مثلاً:

```bash
curl -i http://localhost:3000/api/users
```

ممکن است Response را دریافت کند.

اما این به معنی آن نیست که Browser نیز اجازه دسترسی JavaScript به Response را خواهد داد.

---

# 113.48 - اشتباهات رایج

## 1. استفاده بی‌دلیل از `*`

مثلاً:

```js
cors({
  origin: "*"
});
```

برای API حساس ممکن است Policy بیش از حد بازی باشد.

---

## 2. استفاده از `*` همراه با Credentials

ترکیب:

```text
Allow-Origin: *
Allow-Credentials: true
```

مناسب نیست.

---

## 3. تصور اینکه CORS امنیت API است

CORS جایگزین Authentication و Authorization نیست.

---

## 4. Allow کردن همه Originها در Production

مثلاً:

```js
origin: true
```

بدون بررسی نیاز واقعی می‌تواند Policy بیش از حد بازی ایجاد کند.

---

## 5. فراموش کردن `Authorization`

اگر Frontend از:

```http
Authorization: Bearer ...
```

استفاده کند، باید تنظیمات CORS مناسب باشد.

---

## 6. فراموش کردن Preflight

ممکن است Request اصلی صحیح باشد اما:

```http
OPTIONS
```

درست پاسخ داده نشود.

---

## 7. تنظیم CORS بعد از Routeها

اگر Middleware CORS خیلی دیر اجرا شود، ممکن است بعضی Responseها Headerهای مورد نیاز را نداشته باشند.

## 8. تست فقط با Postman

# مرحله 10 - Dynamic Origin

برای چند Origin می‌توان بررسی دقیق‌تری انجام داد:

```js
app.use(
  cors({
    origin(origin, callback) {
      if (!origin || allowedOrigins.includes(origin)) {
        callback(null, true);
        return;
      }

      callback(new Error("Origin not allowed"));
    },
    credentials: true,
    methods: [
      "GET",
      "POST",
      "PUT",
      "PATCH",
      "DELETE"
    ],
    allowedHeaders: [
      "Content-Type",
      "Authorization"
    ]
  })
);
```

# چالش نهایی

یک API طراحی کنید که:

```text
Frontend:
https://app.example.com

Admin:
https://admin.example.com

API:
https://api.example.com
```

و قوانین زیر را داشته باشد:

```text
App → GET /api/products
Admin → GET /api/products

App → POST /api/orders
Admin → POST /api/orders

Only Admin → DELETE /api/users/:id
```

در این پروژه باید توجه کنید که CORS فقط مشخص می‌کند چه Originهایی اجازه دسترسی Browser دارند.

برای اینکه فقط Admin بتواند User را حذف کند، همچنان باید:

```text
Authentication
+
Authorization
```

را پیاده‌سازی کنید.

یعنی صرفاً این موضوع که:

```text
admin.example.com
```

یک Origin مجاز است، به معنی داشتن Permission حذف User نیست.

# جمع‌بندی نهایی فصل

در این فصل یاد گرفتیم که CORS چیست و چرا در APIهای Node.js اهمیت دارد.

مهم‌ترین مفاهیم:

```text
CORS
Same-Origin Policy
Origin
Cross-Origin Request
Preflight
OPTIONS
Access-Control-Allow-Origin
Access-Control-Allow-Methods
Access-Control-Allow-Headers
Access-Control-Allow-Credentials
Access-Control-Request-Method
Access-Control-Request-Headers
Credentials
Cookie
SameSite
Simple Request
cors Package
```

همچنین یاد گرفتیم که:

```text
CORS ≠ Authentication
CORS ≠ Authorization
CORS ≠ DDoS Protection
```

CORS فقط یکی از بخش‌های معماری امنیتی یک API است.

یک معماری مناسب می‌تواند شامل:

```text
HTTPS
   ↓
CORS
   ↓
Rate Limit
   ↓
Authentication
   ↓
Authorization
   ↓
Validation
   ↓
Business Logic
   ↓
Database
```

باشد.

مهم‌ترین نکته این فصل این است که در Production نباید بدون فکر از:

```http
Access-Control-Allow-Origin: *
```

استفاده کنیم.

باید مشخص کنیم:

```text
چه Frontendهایی؟
چه Originهایی؟
چه Methodهایی؟
چه Headerهایی؟
آیا Credential داریم؟
آیا Cookie داریم؟
آیا Preflight داریم؟
```

و سپس CORS Policy را دقیقاً متناسب با معماری Application تنظیم کنیم.
