# فصل 70 - Semantic Version

## مقدمه

در پروژه‌های نرم‌افزاری، مخصوصاً در اکوسیستم Node.js، مدیریت نسخه‌ها اهمیت بسیار زیادی دارد.

وقتی یک Package منتشر می‌کنیم یا از یک کتابخانه استفاده می‌کنیم، باید بدانیم:

* آیا نسخه جدید فقط یک Bug Fix است؟
* آیا یک قابلیت جدید اضافه شده؟
* آیا تغییرات باعث خراب شدن کدهای قبلی می‌شود؟

برای حل این مشکل، استانداردی به نام:

```text
Semantic Versioning
```

یا به اختصار:

```text
SemVer
```

ایجاد شده است.

Semantic Version یک روش استاندارد برای شماره‌گذاری نسخه‌های نرم‌افزار است.

ساختار اصلی:

```text id="7bq2xm"
MAJOR.MINOR.PATCH
```

مثال:

```text id="9k3pfd"
2.5.1
```

---

# 70.1 - Semantic Version چیست؟

Semantic Versioning یک قرارداد برای معنی دادن به شماره نسخه‌ها است.

به جای اینکه نسخه‌ها فقط یک عدد تصادفی باشند:

```text
Version 15
Version 16
Version 17
```

هر بخش مفهوم مشخصی دارد:

```text
2.5.1

│ │ │
│ │ └── Patch
│ └──── Minor
└────── Major
```

---

# 70.2 - ساختار MAJOR.MINOR.PATCH

سه بخش اصلی:

```text
MAJOR.MINOR.PATCH
```

مثال:

```text
4.7.2
```

یعنی:

```text
4 = Major
7 = Minor
2 = Patch
```

---

# 70.3 - Major Version

Major زمانی افزایش پیدا می‌کند که تغییرات بزرگ و Breaking Change ایجاد شود.

مثال:

قبل:

```js
user.getName()
```

بعد:

```js
user.name()
```

کدهای قبلی ممکن است خراب شوند.

نسخه:

```text
1.9.0

↓

2.0.0
```

---

# 70.4 - Breaking Change چیست؟

Breaking Change یعنی تغییری که باعث شود کدهای قبلی دیگر کار نکنند.

مثال:

نسخه قدیمی:

```js
calculate(price)
```

نسخه جدید:

```js
calculate(price, tax)
```

استفاده قبلی ممکن است مشکل ایجاد کند.

---

# 70.5 - Minor Version

Minor زمانی افزایش پیدا می‌کند که قابلیت جدید اضافه شود، اما کدهای قبلی همچنان کار کنند.

مثال:

نسخه:

```text
2.3.0
```

قابلیت جدید:

```js
user.getEmail()
```

اضافه شده است.

نسخه جدید:

```text
2.4.0
```

---

# 70.6 - Patch Version

Patch برای اصلاح Bug استفاده می‌شود.

مثال:

مشکل:

```text
Login Error
```

رفع شده.

نسخه:

```text
2.4.0
```

به:

```text
2.4.1
```

تغییر می‌کند.

---

# 70.7 - قوانین افزایش Version

| نوع تغییر                          | بخش تغییر |
| ---------------------------------- | --------- |
| Bug Fix                            | Patch     |
| Feature جدید بدون خراب کردن قبلی‌ها | Minor     |
| Breaking Change                    | Major     |

---

# 70.8 - مثال واقعی تغییر نسخه

فرض کنیم:

```text
1.2.3
```

---

رفع باگ:

```text
1.2.4
```

---

اضافه کردن Feature:

```text
1.3.0
```

---

تغییر بزرگ:

```text
2.0.0
```

---

# 70.9 - Version صفر (0.x.x)

نسخه‌های:

```text
0.x.x
```

معمولاً برای پروژه‌های در حال توسعه هستند.

مثال:

```text
0.5.1
```

یعنی:

* API هنوز پایدار نیست.
* ممکن است تغییرات بزرگ رخ دهد.

---

# 70.10 - نسخه 1.0.0

رسیدن به:

```text
1.0.0
```

معمولاً یعنی:

* API پایدار شده.
* پروژه آماده استفاده عمومی است.

---

# 70.11 - Pre-release Version

گاهی نسخه آزمایشی منتشر می‌شود.

مثال:

```text
2.0.0-beta.1
```

انواع:

```text
alpha
beta
rc
```

---

## Alpha

نسخه بسیار ابتدایی:

```text
1.0.0-alpha
```

---

## Beta

نسخه نزدیک‌تر به انتشار:

```text
1.0.0-beta
```

---

## RC

Release Candidate:

```text
1.0.0-rc.1
```

تقریباً نسخه نهایی.

---

# 70.12 - Build Metadata

می‌توان اطلاعات اضافی اضافه کرد.

مثال:

```text
1.0.0+build123
```

---

# 70.13 - Version Range در npm

در npm معمولاً نسخه دقیق نوشته نمی‌شود.

مثال:

```json
{
"express":"^5.0.0"
}
```

این یعنی:

نسخه‌های سازگار با:

```text
5.x.x
```

---

# 70.14 - علامت ^ در npm

Caret:

```json
"express":"^5.0.0"
```

اجازه:

```text
5.1.0
5.2.3
```

اما:

```text
6.0.0
```

نصب نمی‌شود.

زیرا Major تغییر کرده.

---

# 70.15 - علامت ~ در npm

Tilde:

```json
"express":"~5.0.0"
```

اجازه:

```text
5.0.1
5.0.5
```

اما:

```text
5.1.0
```

نصب نمی‌شود.

---

# 70.16 - Version دقیق

مثال:

```json
{
"lodash":"4.17.21"
}
```

یعنی فقط همین نسخه.

---

# 70.17 - Wildcard Version

مثال:

```json
{
"package":"*"
}
```

یعنی:

هر نسخه‌ای.

استفاده از آن معمولاً توصیه نمی‌شود.

---

# 70.22 - Semantic Version در پروژه‌های تیمی

در تیم‌ها Version کمک می‌کند:

* تغییرات قابل فهم باشند.
* Releaseها مدیریت شوند.
* Migration راحت‌تر باشد.
* کاربران بدانند چه چیزی تغییر کرده.

---

# 70.23 - Semantic Version در npm Packageها

وقتی Package منتشر می‌کنیم:

نسخه مهم‌ترین اطلاعات آن است.

مثال:

```json
{
"name":"my-library",
"version":"1.4.0"
}
```

کاربران بر اساس Version تصمیم می‌گیرند Update کنند یا نه.

---

# 70.24 - اشتباهات رایج

## 1) افزایش Version اشتباه

مثلاً:

رفع Bug:

```text
1.0.0 → 2.0.0
```

اشتباه است.

باید:

```text
1.0.1
```

باشد.

---

## 2) استفاده نکردن از Version ثابت

مثال:

```json
{
"express":"latest"
}
```

می‌تواند مشکل ایجاد کند.

---

## 3) انتشار Breaking Change با Minor

اشتباه:

```text
1.5.0 → 1.6.0
```

در حالی که API خراب شده است.

---

## 4) استفاده زیاد از 0.x.x

پروژه‌های بالغ نباید همیشه در نسخه صفر بمانند.

---

## 5) تغییر Version بدون تغییر واقعی

Version باید معنی داشته باشد.

---

# 70.25 - نکات حرفه‌ای

* همیشه قبل از انتشار تغییرات Breaking را مشخص کن.
* از Semantic Version واقعی استفاده کن.
* برای Packageهای عمومی Changelog بنویس.
* Major Version را جدی بگیر.
* قبل از Update Major تست کامل انجام بده.
* Version Dependencyهای مهم را کنترل کن.
* از Version Range با دقت استفاده کن.
* Releaseها را Tag کن.
* از Git Tag برای Versionها استفاده کن.

# جمع‌بندی

Semantic Version یکی از پایه‌های مدیریت حرفه‌ای نرم‌افزار است.

در پروژه‌های Node.js و npm، Version فقط یک عدد نیست؛ بلکه یک قرارداد ارتباطی بین توسعه‌دهندگان و کاربران است.

با رعایت Semantic Versioning:

* انتشارها قابل پیش‌بینی می‌شوند.
* کاربران راحت‌تر Update می‌کنند.
* مدیریت Dependencyها امن‌تر می‌شود.
* پروژه حرفه‌ای‌تر توسعه پیدا می‌کند.

سه قانون اصلی را همیشه به یاد داشته باشید:

```text
PATCH  → رفع مشکل

MINOR  → قابلیت جدید

MAJOR  → تغییر بزرگ و ناسازگار
```
