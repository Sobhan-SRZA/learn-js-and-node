# فصل 48 - Abstraction

## مقدمه

**Abstraction** یا **انتزاع** یکی از مهم‌ترین اصول برنامه‌نویسی شی‌گرا (OOP) است.

اگر بخواهیم Encapsulation را در یک جمله خلاصه کنیم، می‌توان گفت:

> **اطلاعات را مخفی کن.**

اما Abstraction یک قدم جلوتر می‌رود و می‌گوید:

> **فقط چیزهایی را نمایش بده که کاربر واقعاً به آن‌ها نیاز دارد و جزئیات پیاده‌سازی را پنهان کن.**

در دنیای واقعی تقریباً همه چیز بر پایه انتزاع ساخته شده است.

وقتی با یک خودرو رانندگی می‌کنید، فقط از فرمان، پدال گاز، ترمز و دنده استفاده می‌کنید. لازم نیست بدانید موتور چگونه سوخت را می‌سوزاند یا گیربکس دقیقاً چگونه کار می‌کند.

در برنامه‌نویسی نیز دقیقاً همین اتفاق رخ می‌دهد.

---

# 48.1 - Abstraction چیست؟

Abstraction یعنی:

* پنهان کردن جزئیات غیرضروری
* نمایش فقط قابلیت‌های مهم
* ساده‌تر کردن استفاده از یک سیستم

به جای اینکه کاربر بداند داخل کلاس چه اتفاقی می‌افتد، فقط متدهایی را می‌بیند که باید از آن‌ها استفاده کند.

مثلاً:

```text
ماشین

✓ start()
✓ stop()
✓ accelerate()

اما...

✗ احتراق موتور
✗ تزریق سوخت
✗ کنترل ECU
✗ محاسبات گیربکس
```

کاربر فقط عملیات مهم را مشاهده می‌کند.

---

# 48.2 - چرا Abstraction مهم است؟

بدون Abstraction، پروژه‌ها خیلی سریع پیچیده می‌شوند.

مزایای آن:

* کاهش پیچیدگی
* خوانایی بیشتر
* نگهداری ساده‌تر
* تغییر راحت‌تر پیاده‌سازی
* جلوگیری از استفاده اشتباه

---

# 48.3 - تفاوت Encapsulation و Abstraction

بسیاری از برنامه‌نویس‌های تازه‌کار این دو مفهوم را اشتباه می‌گیرند.

| Encapsulation             | Abstraction                    |
| ------------------------- | ------------------------------ |
| مخفی کردن داده‌ها          | مخفی کردن جزئیات               |
| امنیت اطلاعات             | ساده کردن استفاده              |
| کنترل دسترسی              | نمایش قابلیت‌های ضروری          |
| بیشتر روی Data تمرکز دارد | بیشتر روی Interface تمرکز دارد |

مثال:

یک دستگاه ATM را تصور کنید.

شما فقط این گزینه‌ها را می‌بینید:

* برداشت پول
* موجودی
* انتقال وجه

اما پشت صحنه:

* اتصال به بانک
* رمزنگاری
* بررسی موجودی
* ثبت تراکنش
* مدیریت خطا

همه مخفی هستند.

این همان Abstraction است.

---

# 48.4 - اولین مثال

بدون Abstraction:

```js
const car = {
  fuelPump() {},
  injectFuel() {},
  startEngine() {},
  igniteSpark() {},
  rotateFlywheel() {}
};
```

کاربر باید بداند کدام متدها را اجرا کند.

این اصلاً خوب نیست.

---

با Abstraction:

```js
class Car {
  start() {
    console.log("Car Started");
  }

  stop() {
    console.log("Car Stopped");
  }
}

const car = new Car();

car.start();
car.stop();
```

کاربر فقط دو متد ساده می‌بیند.

جزئیات پشت صحنه پنهان شده‌اند.

---

# 48.5 - Abstraction در کلاس‌ها

فرض کنید می‌خواهیم سیستم ارسال ایمیل بسازیم.

کاربر فقط می‌خواهد بنویسد:

```js
emailService.send();
```

او نباید بداند:

* SMTP چیست
* TLS چیست
* Authentication چیست
* Socket چگونه کار می‌کند

تمام این موارد داخل کلاس مخفی می‌شوند.

```js
class EmailService {
  send(to, subject, message) {
    console.log(`Sending email to ${to}`);
    console.log(subject);
    console.log(message);
  }
}

const email = new EmailService();

email.send(
  "user@example.com",
  "Welcome",
  "Hello!"
);
```

---

# 48.6 - Abstraction با متدهای خصوصی

در JavaScript جدید می‌توان متدهای خصوصی داشت.

```js
class Database {
  connect() {
    this.#authenticate();
    console.log("Connected");
  }

  #authenticate() {
    console.log("Authentication...");
  }
}

const db = new Database();

db.connect();
```

کاربر فقط متد connect را می‌بیند.

تابع authenticate مخفی است.

---

# 48.7 - Abstraction در Node.js

در Node.js تقریباً همه چیز بر پایه Abstraction ساخته شده است.

مثلاً:

```js
const fs = require("fs");

fs.readFile("data.txt", "utf8", (err, data) => {
  console.log(data);
});
```

ما فقط readFile را صدا می‌زنیم.

اما پشت صحنه:

* باز شدن فایل
* بررسی دسترسی
* مدیریت سیستم‌عامل
* مدیریت Buffer
* آزاد کردن حافظه
* مدیریت خطا

همه مخفی هستند.

---

# 48.8 - مثال دیگر

فرض کنید کلاس ماشین حساب داریم.

```js
class Calculator {
  add(a, b) {
    return a + b;
  }

  multiply(a, b) {
    return a * b;
  }
}

const calc = new Calculator();

console.log(calc.add(5, 10));
```

کاربر فقط متد add را استفاده می‌کند.

نحوه انجام عملیات برای او اهمیتی ندارد.

# 48.9 - Abstraction در API

وقتی از یک API استفاده می‌کنید:

```js
fetch("/users");
```

شما فقط یک تابع را صدا می‌زنید.

اما پشت صحنه:

* DNS Lookup
* TCP
* TLS
* HTTP
* Header
* Socket
* Packet

همه مخفی هستند.

# 48.10 - Abstraction در Express

مثلاً:

```js
app.get("/users", (req, res) => {
    res.send("Users");
});
```

شما فقط یک Route تعریف می‌کنید.

اما Express خودش:

* Parsing Request
* ساخت Response
* مدیریت Header
* مدیریت Status Code

را انجام می‌دهد.

این یعنی Abstraction.

# 48.11 - Abstraction در Database

مثلاً در ORMها:

```js

```

پشت صحنه:

همه مخفی هستند.

# 48.12 - Interface خوب چه ویژگی‌هایی دارد؟

یک Interface خوب باید:

* ساده باشد.
* قابل فهم باشد.
* متدهای کمی داشته باشد.
* نام‌های واضح داشته باشد.
* استفاده از آن راحت باشد.

مثال خوب:

```js
user.login();
user.logout();
user.changePassword();
```

مثال بد:

```js
user.initConnection();
user.loadHash();
user.verifySecurity();
user.openSession();
```

کاربر مجبور می‌شود جزئیات را بداند.

---

# 48.13 - طراحی بر پایه Abstraction

یک طراحی خوب معمولاً این شکل را دارد:

```text
Application

↓

Controller

↓

Service

↓

Repository

↓

Database
```

هر لایه فقط با لایه پایین خودش کار می‌کند.

هیچ‌کس از جزئیات پایین‌تر خبر ندارد.

---

# 48.14 - Abstraction و SOLID

اصل Dependency Inversion در SOLID کاملاً بر پایه Abstraction است.

به جای وابستگی به کلاس‌های واقعی،

به Interface یا قرارداد وابسته می‌شویم.

در JavaScript Interface رسمی وجود ندارد اما می‌توان همین ایده را با کلاس‌ها، قراردادهای کدنویسی و تزریق وابستگی پیاده‌سازی کرد.

---

# 48.15 - اشتباهات رایج

### 1) نمایش جزئیات غیرضروری

```js
db.openSocket();
db.createPacket();
db.sendPacket();
db.waitResponse();
```

بهتر است:

```js
db.query();
```

---

### 2) ساخت کلاس‌های بسیار پیچیده

اگر کاربر برای انجام یک کار ساده مجبور باشد چندین متد را پشت سر هم فراخوانی کند، انتزاع خوبی طراحی نشده است.

---

### 3) نام‌گذاری نامناسب

```js
runA()
```

بهتر است:

```js
startServer()
```

---

### 4) مخلوط کردن چند مسئولیت

یک کلاس نباید هم ایمیل ارسال کند، هم فایل بخواند، هم دیتابیس مدیریت کند.

---

### 5) افشای وضعیت داخلی

اگر کاربر مجبور شود ساختار داخلی کلاس را بشناسد، انتزاع از بین رفته است.

---

# 48.16 - نکات حرفه‌ای

* همیشه APIهای کوچک طراحی کن.
* متدها را بر اساس نیاز کاربر طراحی کن، نه بر اساس پیاده‌سازی داخلی.
* نام متدها باید مفهوم کاری را منتقل کنند.
* جزئیات داخلی را هر زمان ممکن مخفی نگه دار.
* اگر کاربر مجبور است مستندات طولانی بخواند تا یک کلاس را استفاده کند، طراحی نیاز به بازنگری دارد.
* لایه‌های مختلف پروژه Node.js را از هم جدا نگه دار.
* از Abstraction برای کاهش وابستگی بین بخش‌های پروژه استفاده کن.

# 48.18 - پاسخ تشریحی

## پاسخ تمرین 1

```js
class Light {
  on() {
    console.log("Light ON");
  }

  off() {
    console.log("Light OFF");
  }
}

const light = new Light();

light.on();
light.off();
```

در این مثال، نحوه تأمین برق یا کنترل سخت‌افزار از دید کاربر مخفی است.

---

## پاسخ تمرین 2

```js
class MusicPlayer {
  play() {
    console.log("Playing...");
  }

  pause() {
    console.log("Paused");
  }

  stop() {
    console.log("Stopped");
  }
}
```

کاربر فقط عملیات اصلی را می‌بیند و از جزئیات پخش صدا اطلاعی ندارد.

---

## پاسخ تمرین 3

```js
class Logger {
  log(message) {
    this.#save(message);
  }

  #save(message) {
    console.log(`[LOG]: ${message}`);
  }
}

const logger = new Logger();

logger.log("Application Started");
```

متد خصوصی `#save` جزئیات ذخیره‌سازی را پنهان می‌کند.

---

## پاسخ تمرین 4

```js
class PaymentService {
  pay(amount) {
    this.#validate(amount);
    this.#checkBalance();
    this.#saveTransaction();

    console.log(`Paid ${amount}`);
  }

  #validate(amount) {
    if (amount <= 0) {
      throw new Error("Invalid amount");
    }
  }

  #checkBalance() {
    console.log("Balance Checked");
  }

  #saveTransaction() {
    console.log("Transaction Saved");
  }
}

const payment = new PaymentService();

payment.pay(500);
```

تمام مراحل داخلی پرداخت از دید کاربر پنهان هستند و فقط متد `pay` در اختیار او قرار دارد.

# 48.19 - مینی‌پروژه

## ساخت یک File Manager ساده

هدف این پروژه ساخت یک کلاس است که فقط چند قابلیت ساده در اختیار برنامه‌نویس قرار دهد و تمام جزئیات کار با فایل را درون خود مخفی کند.

```js
const fs = require("fs");

class FileManager {
  save(path, data) {
    this.#write(path, data);
  }

  read(path) {
    return this.#read(path);
  }

  #write(path, data) {
    fs.writeFileSync(path, data);
  }

  #read(path) {
    return fs.readFileSync(path, "utf8");
  }
}

const manager = new FileManager();

manager.save("note.txt", "Hello Node.js");

console.log(
  manager.read("note.txt")
);
```

### ایده‌هایی برای توسعه پروژه

* اضافه کردن حذف فایل
* اضافه کردن تغییر نام فایل
* مدیریت خطاها
* ثبت لاگ عملیات
* پشتیبانی از Promise و Async/Await
* رمزنگاری فایل‌ها قبل از ذخیره‌سازی
* تعیین سطح دسترسی کاربران برای خواندن و نوشتن فایل‌ها

---

# جمع‌بندی

Abstraction یکی از مهم‌ترین اصول طراحی نرم‌افزار است. این اصل به ما کمک می‌کند تا سیستم‌های پیچیده را با ارائه رابط‌های ساده و قابل‌فهم مدیریت کنیم. در پروژه‌های واقعی Node.js، از ماژول‌های داخلی مانند `fs` گرفته تا فریم‌ورک‌هایی مانند Express و ORMها، همگی نمونه‌هایی از استفاده صحیح از انتزاع هستند. با طراحی APIهای کوچک، واضح و مستقل از جزئیات پیاده‌سازی، کدهایی خواهیم نوشت که توسعه، تست و نگهداری آن‌ها بسیار ساده‌تر خواهد بود.
