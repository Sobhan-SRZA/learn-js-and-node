# فصل 104 - Integration Test

## مقدمه

در فصل قبل با **Unit Test** آشنا شدیم. در Unit Test معمولاً یک Function، Class، Service یا Module را به صورت مستقل بررسی می‌کردیم و Dependencyهای آن را در صورت نیاز Mock می‌کردیم.

اما در پروژه‌های واقعی، بخش‌های مختلف Application باید با یکدیگر همکاری کنند.

برای مثال:

```text
Client
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

ممکن است هر کدام از این بخش‌ها به صورت جداگانه Unit Test شده باشند، اما هنوز احتمال دارد ارتباط بین آنها مشکل داشته باشد.

مثلاً:

```text
Controller
   ↓
Service
```

ممکن است Controller یک Argument اشتباه به Service ارسال کند.

یا:

```text
Service
   ↓
Repository
```

ممکن است Service متدی را با نام یا پارامتر اشتباه فراخوانی کند.

یا:

```text
Repository
   ↓
Database
```

ممکن است Query واقعی با ساختار Database هماهنگ نباشد.

اینجاست که **Integration Test** اهمیت پیدا می‌کند.

Integration Test برای بررسی همکاری واقعی چند بخش از Application استفاده می‌شود.

در این فصل یاد می‌گیریم:

* Integration Test چیست؟
* چه تفاوتی با Unit Test دارد؟
* چه بخش‌هایی را باید با Integration Test بررسی کنیم؟
* چگونه APIهای Node.js را تست کنیم؟
* چگونه Database واقعی را در Test استفاده کنیم؟
* Test Database چیست؟
* چگونه داده‌های Test را مدیریت کنیم؟
* چگونه Authentication و Authorization را تست کنیم؟
* چگونه Errorهای واقعی Application را بررسی کنیم؟
* چگونه Integration Testهای قابل اعتماد و مستقل بنویسیم؟

---

# بخش 1 - Integration Test چیست؟

## 104.1 - مفهوم Integration Test

Integration Test نوعی Test است که تعامل بین چند بخش واقعی Application را بررسی می‌کند.

در Unit Test:

```text
Service
   ↓
Mock Repository
```

اما در Integration Test ممکن است:

```text
Service
   ↓
Real Repository
   ↓
Test Database
```

استفاده شود.

هدف این است که مطمئن شویم اجزای مختلف سیستم در کنار یکدیگر درست کار می‌کنند.

---

## 104.2 - چرا Integration Test لازم است؟

فرض کنید این بخش‌ها Unit Test شده‌اند:

```text
UserController      ✅
UserService         ✅
UserRepository      ✅
```

اما ممکن است در Application واقعی:

```text
Controller
   ↓
Service
   ↓
Repository
```

در نحوه ارتباط مشکل وجود داشته باشد.

Unit Test به تنهایی نمی‌تواند تمام این مشکلات را پیدا کند.

Integration Test برای بررسی همین Integrationها استفاده می‌شود.

---

## 104.3 - هدف Integration Test

هدف اصلی:

> بررسی تعامل صحیح چند Component واقعی با یکدیگر.

مثلاً:

```text
HTTP Request
   ↓
Router
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
   ↓
HTTP Response
```

اگر این مسیر به درستی کار کند، Integration Test موفق است.

---

# بخش 2 - تفاوت Unit Test و Integration Test

## 104.4 - Unit Test

در Unit Test معمولاً:

```text
یک Unit
+
Dependencyهای Mock شده
```

داریم.

مثلاً:

```text
UserService
   ↓
Mock Repository
```

---

## 104.5 - Integration Test

در Integration Test:

```text
چند Component واقعی
+
Dependencyهای واقعی یا Test-specific
```

با یکدیگر اجرا می‌شوند.

مثلاً:

```text
UserService
   ↓
UserRepository
   ↓
Test Database
```

---

## 104.6 - مقایسه

| ویژگی      | Unit Test    | Integration Test     |
| ---------- | ------------ | -------------------- |
| Scope      | کوچک         | بزرگ‌تر               |
| Dependency | معمولاً Mock  | بیشتر واقعی          |
| Database   | معمولاً Mock  | معمولاً Test DB       |
| سرعت       | بسیار سریع   | کندتر                |
| هدف        | منطق یک Unit | ارتباط چند Component |
| Isolation  | زیاد         | کمتر                 |
| پیچیدگی    | کمتر         | بیشتر                |

---

# بخش 3 - چه چیزهایی را Integration Test کنیم؟

## 104.7 - Integration بین Service و Repository

مثلاً:

```text
UserService
   ↓
UserRepository
   ↓
Database
```

بررسی می‌کنیم که عملیات‌هایی مانند:

```text
Create
Read
Update
Delete
```

واقعاً درست انجام شوند.

---

## 104.8 - Integration بین Controller و Service

مثلاً:

```text
HTTP Request
   ↓
Controller
   ↓
Service
```

بررسی می‌کنیم که:

* Request درست Parse شود.
* Validation درست اجرا شود.
* Service درست فراخوانی شود.
* Response مناسب برگردد.

---

## 104.9 - Integration بین Application و Database

این یکی از مهم‌ترین کاربردهای Integration Test است.

مثلاً:

```text
Application
   ↓
Repository
   ↓
PostgreSQL
```

یا:

```text
Application
   ↓
Mongoose
   ↓
MongoDB
```

در اینجا Query و Mapping واقعی بررسی می‌شوند.

---


# بخش 9 - Isolation در Integration Test

## 104.25 - استقلال Testها

Testها نباید به ترتیب اجرای یکدیگر وابسته باشند.

بد:

```text
Test A
↓
Creates User

Test B
↓
Uses User from Test A
```

بهتر:

```text
Test A
↓
Own Data

Test B
↓
Own Data
```

---

## 104.26 - چرا Isolation مهم است؟

اگر Testها به یکدیگر وابسته باشند:

```text
Test A → PASS
Test B → PASS
```

ممکن است با تغییر ترتیب:

```text
Test B → FAIL
```

شود.

این نوع Testها قابل اعتماد نیستند.

---

# بخش 10 - Transaction در Integration Test

## 104.27 - استفاده از Transaction

در Databaseهای رابطه‌ای می‌توان برای بعضی Testها از Transaction استفاده کرد.

ساختار:

```text
BEGIN
↓
Test
↓
ROLLBACK
```

در نتیجه تغییرات Test باقی نمی‌مانند.

---

## 104.28 - مزیت Transaction

Transaction می‌تواند Cleanup را ساده‌تر کند.

اما باید توجه کرد که تمام رفتارهای Application همیشه داخل همان Transaction قابل کنترل نیستند.

بنابراین Transaction جایگزین همه روش‌های Cleanup نیست.

# بخش 21 - Test کردن API با Supertest

## 104.44 - مفهوم Supertest

```text

↓
HTTP Request
↓
Application
↓
HTTP Response
↓

```

# نکات حرفه‌ای

## 1. Test Database جدا داشته باشید

Database Test باید کاملاً از Development و Production جدا باشد.

---

## 2. Testها را Deterministic کنید

اجرای دوباره Test با شرایط یکسان باید نتیجه یکسان بدهد.

---

## 3. Test Data را کنترل کنید

از داده‌هایی استفاده کنید که هدف Test را واضح نشان دهند.

---

## 4. Cleanup مطمئن داشته باشید

حتی در صورت Failure نیز تا حد امکان Environment Test باید قابل پاک‌سازی باشد.

---

## 5. Test Pyramid را رعایت کنید

معمولاً تعداد Testها باید به شکل تقریبی:

```text
        E2E
       /   \
 Integration
    /       \
     Unit
```

باشد.

یعنی Unit Testها بیشتر و سریع‌تر، Integration Testها کمتر و سنگین‌تر و E2E Testها محدودتر باشند.

---

## 6. Mock را هوشمندانه استفاده کنید

Database داخلی پروژه معمولاً بخش مهمی از Integration Test است، اما سرویس خارجی ممکن است Mock شود.

---

## 7. Test را از Production Configuration جدا کنید

Secretها، Database URLها و API Keyهای Production نباید وارد Test شوند.

---

## 8. Failureها را قابل Debug کنید

نام Test، داده‌ها و Assertionها باید به اندازه‌ای واضح باشند که علت Failure سریع مشخص شود.

---

## 9. Integration Test را در CI اجرا کنید

Integration Test یکی از مراحل مهم CI است.

مثلاً:

```text
Push
↓
Install
↓
Lint
↓
Unit Tests
↓
Integration Tests
↓
Build
```

---

## 10. Testهای Slow را شناسایی کنید

اگر یک Integration Test چندین ثانیه زمان می‌برد، علت آن را بررسی کنید.

معمولاً مشکلاتی مثل:

```text
Database Setup
Network
Unnecessary Seed
Slow Cleanup
```

عامل اصلی هستند.

همچنین یاد گرفتیم Integration Test در Backend می‌تواند موارد زیر را بررسی کند:

```text
HTTP Request
Routing
Middleware
Controller
Service
Repository
Database
Authentication
Authorization
Validation
CRUD
Error Handling
Transaction
Pagination
Filtering
Sorting
```

یکی از مهم‌ترین اصول این فصل این است:

> Integration Test باید تعامل واقعی بخش‌هایی را بررسی کند که قرار است در محیط واقعی Application با یکدیگر کار کنند.

همچنین باید همیشه به این موارد توجه کنیم:

```text
Test Database
Test Environment
Test Isolation
Cleanup
Deterministic Tests
Controlled Dependencies
```

در نتیجه Testing در یک پروژه حرفه‌ای معمولاً فقط به Unit Test محدود نمی‌شود:

```text
Unit Test
    ↓
Integration Test
    ↓
E2E Test
```

Unit Test منطق کوچک Application را بررسی می‌کند، Integration Test ارتباط Componentها را بررسی می‌کند و در مراحل بعدی با **End-to-End Test** می‌توانیم رفتار Application را از دید یک کاربر و در یک Flow کامل بررسی کنیم.
