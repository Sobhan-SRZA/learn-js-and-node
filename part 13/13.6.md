# فصل 107 - Coverage

## مقدمه

در فصل‌های قبل با Testing، Unit Test، Integration Test، Jest و Mock آشنا شدیم. در این فصل می‌خواهیم به یک سؤال مهم پاسخ دهیم:

**از کجا بفهمیم Testهایی که نوشته‌ایم چه مقدار از Code برنامه را پوشش داده‌اند؟**

اینجاست که مفهوم **Code Coverage** مطرح می‌شود.

Coverage به ما کمک می‌کند بفهمیم Testهای ما چه بخش‌هایی از برنامه را اجرا کرده‌اند و چه قسمت‌هایی هنوز بدون Test باقی مانده‌اند.

برای مثال فرض کنید Function زیر را داریم:

```javascript
function getDiscount(price, isVip) {
  if (isVip) {
    return price * 0.8;
  }

  return price;
}
```

اگر فقط این حالت را Test کنیم:

```javascript
getDiscount(100, true);
```

یک مسیر از برنامه را تست کرده‌ایم، اما مسیر:

```javascript
getDiscount(100, false);
```

هنوز تست نشده است.

Coverage می‌تواند به ما نشان دهد که بخشی از Code هنوز توسط Testها اجرا نشده است.

در Jest می‌توانیم Coverage را با اجرای:

```bash
npm test -- --coverage
```

دریافت کنیم.

Coverage فقط یک عدد نیست؛ بلکه ابزاری برای پیدا کردن قسمت‌های تست‌نشده و افزایش اطمینان نسبت به کیفیت Testهاست.

در این فصل یاد می‌گیریم:

* Coverage چیست؟
* چرا Coverage مهم است؟
* Statement Coverage
* Branch Coverage
* Function Coverage
* Line Coverage
* خواندن گزارش Coverage
* اجرای Coverage در Jest
* Coverage Threshold
* فایل‌ها و پوشه‌های Exclude شده
* HTML Coverage Report
* Coverage در پروژه‌های Node.js
* Coverage در CI/CD
* تفاوت Coverage بالا و Test باکیفیت
* اشتباهات رایج در استفاده از Coverage

# بخش 1 - Coverage چیست؟

## 107.1 - مفهوم Code Coverage

Code Coverage یعنی اندازه‌گیری اینکه چه مقدار از Code برنامه هنگام اجرای Testها اجرا شده است.

فرض کنید برنامه ما 100 بخش قابل اندازه‌گیری داشته باشد و Testها 80 بخش را اجرا کنند.

به صورت ساده می‌توان گفت:

```text
Coverage = 80%
```

اما Coverage می‌تواند از جنبه‌های مختلف اندازه‌گیری شود.

مهم‌ترین انواع Coverage عبارت‌اند از:

```text
Line Coverage
Statement Coverage
Function Coverage
Branch Coverage
```

---

## 107.2 - چرا Coverage مهم است؟

Coverage می‌تواند به ما کمک کند قسمت‌هایی از برنامه را که Test ندارند پیدا کنیم.

مثلاً:

```text
src/
├── user.js
├── auth.js
├── payment.js
└── email.js
```

ممکن است:

```text
user.js      → 95%
auth.js      → 90%
payment.js   → 45%
email.js     → 20%
```

در این حالت مشخص است که `payment.js` و `email.js` نیاز به بررسی بیشتری دارند.

Coverage می‌تواند یک ابزار مناسب برای پیدا کردن نقاط کم‌تست‌شده باشد.

# بخش 2 - Coverage در Jest

## 107.3 - اجرای Coverage

اگر Jest در پروژه نصب شده باشد، می‌توان Coverage را با این دستور اجرا کرد:

```bash
npm test -- --coverage
```

یا اگر Script پروژه به شکل مناسب تنظیم شده باشد:

```bash
npm run test:coverage
```

برای مثال:

```json
{
  "scripts": {
    "test": "jest",
    "test:coverage": "jest --coverage"
  }
}
```

سپس:

```bash
npm run test:coverage
```

---

## 107.4 - خروجی Coverage

Jest معمولاً گزارشی مشابه این ارائه می‌دهد:

```text
----------------|---------|----------|---------|---------
| File             | % Stmts   | % Branch   | % Funcs   | % Lines   |
| ---------------- | --------- | ---------- | --------- | --------- |
| All files        | 85.71     | 75.00      | 90.00     | 85.71     |
| ---------------- | --------- | ---------- | --------- | --------- |
```

این جدول به ما می‌گوید چه مقدار از Code توسط Testها پوشش داده شده است.

# بخش 3 - انواع Coverage

## 107.5 - Statement Coverage

Statement Coverage بررسی می‌کند چه تعداد از Statementهای برنامه اجرا شده‌اند.

مثلاً:

```javascript
function add(a, b) {
  const result = a + b;

  return result;
}
```

اگر Test این Function را اجرا کند:

```javascript
add(2, 3);
```

Statementهای موجود اجرا شده‌اند.

---

## 107.6 - Branch Coverage

Branch Coverage بررسی می‌کند شاخه‌های مختلف تصمیم‌گیری اجرا شده‌اند یا خیر.

مثلاً:

```javascript
function getPrice(price, isVip) {
  if (isVip) {
    return price * 0.8;
  }

  return price;
}
```

دو Branch داریم:

```text
isVip = true
isVip = false
```

اگر فقط:

```javascript
getPrice(100, true);
```

را Test کنیم، یک Branch تست شده است.

برای پوشش هر دو Branch باید هر دو حالت را بررسی کنیم:

```javascript
getPrice(100, true);
getPrice(100, false);
```

---

## 107.7 - Function Coverage

Function Coverage بررسی می‌کند چه تعداد از Functionهای برنامه هنگام Test اجرا شده‌اند.

مثلاً:

```javascript
function add(a, b) {
  return a + b;
}

function subtract(a, b) {
  return a - b;
}
```

اگر فقط:

```javascript
add(2, 3);
```

را اجرا کنیم، Function `add` اجرا شده اما `subtract` اجرا نشده است.

---

## 107.8 - Line Coverage

Line Coverage بررسی می‌کند چه تعداد از Lineهای قابل اجرای Code هنگام Test اجرا شده‌اند.

مثلاً:

```javascript
function greet(name) {
  const message = `Hello ${name}`;
  console.log(message);
}
```

اگر:

```javascript
greet("Ali");
```

اجرا شود، Lineهای قابل اجرای این Function پوشش داده می‌شوند.

---

# بخش 4 - تفاوت انواع Coverage

چهار معیار اصلی را می‌توان این‌گونه خلاصه کرد:

| نوع       | چه چیزی را بررسی می‌کند؟ |
| --------- | ----------------------- |
| Statement | اجرای Statementها       |
| Branch    | اجرای شاخه‌های تصمیم‌گیری |
| Function  | اجرای Functionها        |
| Line      | اجرای Lineهای قابل اجرا |

ممکن است Coverage یک پروژه در یک معیار بالا و در معیار دیگری پایین باشد.

مثلاً:

```text
Statements → 95%
Functions  → 100%
Lines      → 95%
Branches   → 70%
```

این یعنی Functionها تقریباً همگی تست شده‌اند، اما برخی مسیرهای شرطی هنوز تست نشده‌اند.

---

# بخش 5 - مثال ساده Coverage

## 107.9 - Function دارای شرط

```javascript
function calculateDiscount(price, isVip) {
  if (isVip) {
    return price * 0.8;
  }

  return price;
}
```

Test اول:

```javascript
test("calculates VIP discount", () => {
  expect(
    calculateDiscount(100, true)
  ).toBe(80);
});
```

در این حالت Branch مربوط به:

```text
isVip = true
```

اجرا شده است.

اما Branch مربوط به:

```text
isVip = false
```

هنوز تست نشده است.

Test دوم:

```javascript
test("returns original price for non VIP", () => {
  expect(
    calculateDiscount(100, false)
  ).toBe(100);
});
```

حالا هر دو مسیر بررسی شده‌اند.

داشته باشیم.

# بخش 7 - Coverage و Edge Case

Coverage فقط به مسیرهای معمول محدود نمی‌شود.

باید حالت‌های مرزی را نیز در نظر بگیریم.

مثلاً:

```javascript
function isAdult(age) {
  return age >= 18;
}
```

Testهای مهم:

```text
17
18
19
```

چرا؟

چون `18` یک Boundary مهم است.

Jest می‌تواند گزارش HTML نیز تولید کند.

```text

```

قرار می‌گیرد.


است.

## 107.14 - بررسی Lineهای تست‌نشده

گزارش HTML می‌تواند مشخص کند کدام Lineها توسط Test اجرا نشده‌اند.

مثلاً:

```text

    return 100;
  }

  return 200;

```

اگر یکی از مسیرها Test نشده باشد، گزارش می‌تواند آن قسمت را به عنوان پوشش‌داده‌نشده مشخص کند.

این قابلیت برای پیدا کردن قسمت‌های جاافتاده بسیار مفید است.

# بخش 9 - Coverage Threshold

## 107.15 - Threshold چیست؟

می‌توان برای Coverage حداقل تعیین کرد.

مثلاً:

```text
Statements ≥ 80%
Branches   ≥ 75%
Functions  ≥ 80%
Lines      ≥ 80%
```

اگر Coverage از این مقدار پایین‌تر باشد، اجرای Test می‌تواند Fail شود.

این کار از کاهش تدریجی کیفیت Testها جلوگیری می‌کند.

## 107.16 - تنظیم Coverage Threshold

```javascript
  coverageThreshold: {

      statements: 80
    }
  }
};
```

حالا اگر Coverage کلی کمتر از مقدار مشخص‌شده باشد، Test Command موفق نخواهد بود.

# بخش 10 - Coverage برای فایل‌های مشخص

گاهی می‌خواهیم Coverage فقط روی بخش خاصی از پروژه اجرا شود.

مثلاً:

```text
src/services/
```

یا:

```text
src/controllers/
```

در این شرایط می‌توان تنظیمات Coverage را متناسب با ساختار پروژه انجام داد.

هدف این است که Coverage معنی‌دار باشد و فایل‌های غیرضروری وارد محاسبه نشوند.

# بخش 11 - Exclude کردن فایل‌ها

همه فایل‌های پروژه الزاماً نیاز به Coverage ندارند.

برای مثال:

```text
Generated Code
Configuration
Type Definitions
Migration
Test Files
```

ممکن است نیاز به Coverage مستقیم نداشته باشند.

Jest امکان Exclude کردن فایل‌ها از Coverage را فراهم می‌کند.

مثلاً:

```javascript
module.exports = {
  coveragePathIgnorePatterns: [
    "/node_modules/",
    "/dist/"
  ]
};
```

# بخش 13 - Coverage برای Service

فرض کنید:

```javascript
class UserService {
  constructor(repository) {
    this.repository = repository;
  }

  async getUser(id) {
    if (!id) {
      throw new Error("Invalid ID");
    }

    return this.repository.findById(id);
  }
}
```

برای Coverage مناسب حداقل باید دو مسیر را بررسی کنیم:

```text
id معتبر
id نامعتبر
```

Test اول:

```javascript
await service.getUser(1);
```

Test دوم:

```javascript
await expect(
  service.getUser()
).rejects.toThrow("Invalid ID");
```

# بخش 14 - Coverage و Error Handling

Error Pathها بخش بسیار مهمی از Coverage هستند.

مثلاً:

```javascript
async function createUser(data) {
  try {
    return await repository.create(data);
  } catch (error) {
    throw new Error("Create user failed");
  }
}
```

اگر فقط حالت موفق را Test کنیم:

```text
Success → Covered
Error   → Not Covered
```

برای Coverage بهتر باید Error Path نیز تست شود.

# بخش 15 - Coverage و Async Code

در Node.js بسیاری از Functionها Async هستند.

مثلاً:

```javascript
async function getUser(id) {
  return await repository.findById(id);
}
```

Test باید Promise را واقعاً Await کند:

```javascript
test("gets user", async () => {
  const user = await getUser(1);

  expect(user.id).toBe(1);
});
```

اگر Test به درستی منتظر Promise نماند، ممکن است نتیجه Test و Coverage قابل اعتماد نباشد.

# بخش 16 - Coverage و Mock

Mock و Coverage مکمل یکدیگر هستند.

در فصل قبل یاد گرفتیم Dependencyها را Mock کنیم.

مثلاً:

```javascript
repository.findById.mockResolvedValue({
  id: 1
});
```

حالا می‌توانیم Branchهای مختلف Service را با Mock کنترل کنیم.

مثلاً:

```text
Repository Success
Repository Not Found
Repository Error
```

و Coverage مربوط به مسیرهای مختلف را افزایش دهیم.

# بخش 17 - Coverage و Unit Test

Unit Test معمولاً برای Coverage بسیار مناسب است، چون:

* Testها مستقل‌تر هستند.

مثلاً:

```text
Service
├── Success
├── Not Found
├── Validation Error
```

می‌توان هر مسیر را به صورت مستقل تست کرد.

# بخش 19 - آیا Coverage صد درصد لازم است؟

**خیر.**

Coverage برابر 100% لزوماً به معنای Test Suite عالی نیست.

مثلاً ممکن است یک Function را اجرا کنیم اما نتیجه آن را به درستی بررسی نکنیم.

در این حالت:

```text
Coverage = 100%
Test Quality = پایین
```

بنابراین Coverage یک Metric است، نه معیار کامل کیفیت نرم‌افزار.

# بخش 21 - Coverage و Mutation Testing

یکی از روش‌های پیشرفته‌تر بررسی کیفیت Testها:

**Mutation Testing**

است.

در Mutation Testing بخش‌هایی از Code به صورت عمدی تغییر داده می‌شوند.

مثلاً:

```javascript
if (age >= 18)
```

به:

```javascript
if (age > 18)
```

تغییر می‌کند.

اگر Testها بتوانند این تغییر اشتباه را تشخیص دهند، نشان می‌دهد Test Suite کیفیت خوبی دارد.

بنابراین:

```text
Coverage
```

به ما می‌گوید چه مقدار Code اجرا شده است.

اما:

```text
Mutation Testing
```

می‌تواند اطلاعات بیشتری درباره قدرت Testها بدهد.

# اشتباهات رایج

## 1. تصور اینکه 100% Coverage یعنی برنامه بدون Bug است

Coverage فقط نشان می‌دهد Code تا چه اندازه اجرا شده است.

---

## 2. تست نکردن نتیجه

فقط اجرای Function کافی نیست.

باید نتیجه را نیز بررسی کنیم:

```javascript
expect(result).toBe(expected);
```

---

## 3. دنبال کردن درصد به هر قیمت

هدف Test باید افزایش اطمینان باشد، نه صرفاً بالا بردن عدد Coverage.

---

## 4. نادیده گرفتن Branch Coverage

ممکن است Line Coverage بالا باشد اما برخی مسیرهای شرطی تست نشده باشند.

---

## 5. تست نکردن Error Path

Errorها نیز بخشی از رفتار Application هستند.

---

## 6. نوشتن Testهای بی‌معنی برای افزایش Coverage

مثلاً:

```javascript
test("runs code", () => {
  someFunction();
});
```

بدون بررسی نتیجه.

---

## 7. Mock کردن بیش از حد

اگر همه چیز Mock شود، ممکن است بخش مهمی از Integration واقعی تست نشود.

---

## 8. Exclude کردن بیش از حد فایل‌ها

اگر فایل‌های زیادی را از Coverage خارج کنیم، درصد Coverage ممکن است تصویری غیرواقعی ارائه دهد.

---

## 9. استفاده از Coverage به عنوان تنها معیار کیفیت

کیفیت Test فقط Coverage نیست.

---

## 10. فراموش کردن Testهای Edge Case

مثلاً فقط:

```text
age = 20
```

را تست کنیم و:

```text
age = 18
age = 17
```

را فراموش کنیم.

# نکات حرفه‌ای

## 1. Coverage را ابزار تشخیص بدانید

Coverage به شما کمک می‌کند قسمت‌های بدون Test را پیدا کنید.

---

## 2. Branch Coverage را جدی بگیرید

در Backend، مسیرهای مختلف Business Logic اهمیت زیادی دارند.

## 4. Coverage Threshold منطقی تعیین کنید

مثلاً:

```text
80%
```

ممکن است برای یک پروژه نقطه شروع خوبی باشد، اما مقدار مناسب به پروژه بستگی دارد.

Threshold نباید بدون دلیل 100% تعیین شود.

## 5. Coverage را در CI اجرا کنید

Coverage باید بخشی از فرآیند توسعه باشد، نه کاری که فقط گاهی روی سیستم Developer اجرا می‌شود.

## 6. فایل‌های مهم را اولویت‌بندی کنید

---

## 7. Coverage پایین را بررسی کنید، نه اینکه کورکورانه پر کنید

اگر یک فایل Coverage پایینی دارد، اول دلیل آن را پیدا کنید.

---

## 8. Test Quality مهم‌تر از Coverage است

این:

```text
80% Coverage + Testهای باکیفیت
```

ممکن است بهتر از:

```text
100% Coverage + Testهای ضعیف
```

باشد.

---

## 9. از HTML Report استفاده کنید

گزارش HTML برای پیدا کردن Lineها و Branchهای تست‌نشده بسیار کاربردی است.

---

## 10. Coverage را در کنار Code Review استفاده کنید

Coverage جای Code Review را نمی‌گیرد.

هر دو باید در کنار یکدیگر استفاده شوند.

## مرحله 2 - User Service

```javascript
class UserService {
  constructor(repository) {
    this.repository = repository;
  }

  async getUser(id) {
    if (!id) {
      throw new Error("Invalid ID");
    }

    const user =
      await this.repository.findById(id);

    if (!user) {
      throw new Error("User not found");
    }

    return user;
  }

  async createUser(data) {
    if (!data.email) {
      throw new Error("Email is required");
    }

    if (data.email.includes("@") === false) {
      throw new Error("Invalid email");
    }

    return this.repository.create(data);
  }
}

module.exports = UserService;
```

# جمع‌بندی فصل

در این فصل با **Code Coverage** آشنا شدیم.

Coverage به ما کمک می‌کند بفهمیم Testهای ما چه مقدار از Code برنامه را اجرا کرده‌اند.

چهار معیار اصلی:

```text
Line Coverage
Statement Coverage
Function Coverage
Branch Coverage
```

را بررسی کردیم.

همچنین یاد گرفتیم در Jest Coverage را با:

```bash
npm test -- --coverage
```

اجرا کنیم و گزارش Coverage را بررسی کنیم.

با Coverage Threshold نیز آشنا شدیم:

```javascript
coverageThreshold: {
  global: {
    branches: 80,
    functions: 80,
    lines: 80,
    statements: 80
  }
}
```

همچنین دیدیم که Coverage بالا الزاماً به معنی Test باکیفیت نیست.

یک Test Suite خوب باید:

```text
رفتار درست
Errorها
Edge Caseها
Branchهای مختلف
Business Logic
```

را بررسی کند.

در نهایت:

```text
Coverage
```

باید به عنوان یک **ابزار اندازه‌گیری و پیدا کردن نقاط تست‌نشده** استفاده شود، نه هدف نهایی پروژه.

در ساختار تست پروژه:

```text
Testing
│
├── Unit Test
│   ├── Mock
│   └── Coverage
│
├── Integration Test
│   └── Integration Coverage
│
└── E2E Test
    └── Complete Flow
```

Coverage به ما کمک می‌کند بفهمیم کدام قسمت‌های این Test Suite هنوز نیاز به توجه بیشتری دارند.

طبق ساختار مستند، فصل 107 پایان بخش **تست** است و بعد از آن وارد **بخش امنیت Node.js** و فصل 108 می‌شویم.
