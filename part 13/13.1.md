# فصل 102 - Testing چیست؟

## مقدمه

تا اینجا یاد گرفتیم چگونه با Node.js برنامه‌های مختلفی بسازیم؛ از کار با HTTP و API گرفته تا Database، Authentication و منطق‌های پیچیده Backend.

اما یک سؤال مهم وجود دارد:

> از کجا مطمئن شویم کدی که نوشته‌ایم درست کار می‌کند؟

فرض کنید یک تابع برای محاسبه قیمت نهایی سفارش نوشته‌ایم:

```javascript
function calculateTotal(price, quantity) {
  return price * quantity;
}
```

ممکن است برای ورودی‌های ساده درست کار کند:

```javascript
calculateTotal(100, 2);
// 200
```

اما اگر ورودی‌های دیگری داشته باشیم چه؟

```javascript
calculateTotal(100, 0);
calculateTotal(100, -1);
calculateTotal("100", 2);
calculateTotal(undefined, 2);
```

آیا برنامه باید این ورودی‌ها را قبول کند؟

اینجاست که مفهوم **Testing** اهمیت پیدا می‌کند.

Testing یعنی بررسی رفتار برنامه با استفاده از روش‌های مشخص، تا بتوانیم با اطمینان بیشتری متوجه شویم که کد مطابق انتظار ما کار می‌کند.

در پروژه‌های واقعی Node.js، Testing فقط برای پیدا کردن Bug نیست؛ بلکه به ما کمک می‌کند:

* از خراب شدن قابلیت‌های قبلی جلوگیری کنیم.
* هنگام Refactor کردن با اطمینان بیشتری کد را تغییر دهیم.
* رفتار مورد انتظار Application را مستند کنیم.
* خطاهای منطقی را زودتر پیدا کنیم.
* کیفیت کد را افزایش دهیم.
* توسعه تیمی را ساده‌تر کنیم.
* قبل از Deploy مشکلات مهم را شناسایی کنیم.

در این فصل ابتدا با مفهوم Testing آشنا می‌شویم و سپس در فصل‌های بعدی به سراغ ابزارها و تکنیک‌های عملی Testing در Node.js خواهیم رفت.

---

# بخش 1 - Testing چیست؟

## 102.1 - مفهوم Testing

Testing یعنی بررسی برنامه برای اطمینان از اینکه رفتار آن مطابق چیزی است که انتظار داریم.

مثلاً اگر تابع زیر را داشته باشیم:

```javascript
function add(a, b) {
  return a + b;
}
```

می‌توانیم یک Test بنویسیم که بررسی کند:

```javascript
add(2, 3)
```

برابر با:

```text
5
```

است.

به زبان ساده:

```text
Input
  ↓
Application
  ↓
Output
  ↓
Compare with Expected Result
```

اگر نتیجه واقعی با نتیجه مورد انتظار برابر باشد:

```text
PASS
```

و اگر نباشد:

```text
FAIL
```

---

## 102.2 - چرا Testing مهم است؟

بدون Test ممکن است یک تغییر کوچک باعث خراب شدن بخش دیگری از Application شود.

مثلاً:

```text
روز اول
Login ✅

روز دوم
Feature جدید اضافه شد

روز سوم
Login ❌
```

اگر Test داشته باشیم، می‌توانیم بعد از تغییر کد دوباره Testها را اجرا کنیم:

```text
Login Test      ✅
Register Test   ✅
Order Test      ✅
Payment Test    ❌
```

بنابراین سریع‌تر متوجه مشکل می‌شویم.

---

## 102.3 - Testing و Bug

Bug یعنی رفتاری در برنامه که با رفتار مورد انتظار ما مطابقت ندارد.

مثلاً انتظار داریم:

```javascript
add(2, 3)
```

برابر باشد با:

```text
5
```

اما برنامه:

```text
6
```

برگرداند.

Test می‌تواند چنین مشکلی را شناسایی کند.

---

## 102.4 - Testing و Debugging

Testing و Debugging یکی نیستند.

### Testing

برای بررسی درست بودن رفتار برنامه استفاده می‌شود.

### Debugging

برای پیدا کردن علت یک مشکل و اصلاح آن استفاده می‌شود.

مثلاً:

```text
Test
 ↓
FAIL
 ↓
Bug identified
 ↓
Debugging
 ↓
Fix
 ↓
Run Test again
 ↓
PASS
```

# بخش 2 - Test Case چیست؟

## 102.5 - Test Case

Test Case یک سناریوی مشخص برای بررسی رفتار Application است.

مثلاً برای تابع:

```javascript
function multiply(a, b) {
  return a * b;
}
```

می‌توان Test Caseهای زیر را تعریف کرد:

```text
Input: 2, 3
Expected: 6
```

```text
Input: 5, 0
Expected: 0
```

```text
Input: -2, 3
Expected: -6
```

هرکدام یک Test Case هستند.

---

## 102.6 - Expected و Actual

در Testing معمولاً دو مفهوم مهم داریم:

### Expected

نتیجه‌ای که انتظار داریم.

### Actual

نتیجه‌ای که Application واقعاً تولید کرده است.

مثلاً:

```text
Expected: 10
Actual:   10
```

Test:

```text
PASS
```

اما:

```text
Expected: 10
Actual:   8
```

Test:

```text
FAIL
```

# بخش 3 - Test Suite

## 102.7 - Test Suite چیست؟

Test Suite مجموعه‌ای از Testهای مرتبط است.

مثلاً برای User:

```text
User Test Suite
├── Create User
├── Find User
├── Update User
├── Delete User
└── Login User
```

و برای Product:

```text
Product Test Suite
├── Create Product
├── Get Product
├── Update Product
└── Delete Product
```

---

## 102.8 - Test Runner چیست؟

Test Runner ابزاری است که Testها را اجرا می‌کند و نتیجه آنها را نمایش می‌دهد.

به طور کلی:

```text
Test Files
   ↓
Test Runner
   ↓
Execute Tests
   ↓
PASS / FAIL
```

در Node.js ابزارهایی مانند:

* Node.js Test Runner
* Jest
* Vitest
* Mocha

برای اجرای Testها استفاده می‌شوند.

در ادامه مسیر یادگیری Node.js، هرکدام را در جای مناسب بررسی خواهیم کرد.

# بخش 4 - انواع Testing

## 102.9 - Unit Testing

Unit Test کوچک‌ترین بخش مستقل برنامه را بررسی می‌کند.

معمولاً یک:

* Function
* Method
* Class
* Module

را بررسی می‌کنیم.

مثلاً:

```javascript
function add(a, b) {
  return a + b;
}
```

Test:

```text
add(2, 3) → 5
```

---

## 102.10 - Integration Testing

در Integration Testing چند بخش Application را در کنار یکدیگر بررسی می‌کنیم.

مثلاً:

```text
Service
   ↓
Repository
   ↓
Database
```

هدف این است که بررسی کنیم اجزای مختلف به درستی با یکدیگر کار می‌کنند.

---

## 102.11 - End-to-End Testing

در End-to-End یا E2E Testing، رفتار Application را از دید جریان واقعی کاربر بررسی می‌کنیم.

مثلاً در یک فروشگاه:

```text
Register
   ↓
Login
   ↓
Add Product
   ↓
Create Order
   ↓
Payment
   ↓
Order Completed
```

---

## 102.12 - تفاوت Unit، Integration و E2E

به صورت ساده:

```text
Unit
↓
یک بخش کوچک

Integration
↓
چند بخش متصل

E2E
↓
جریان کامل Application
```

هرچه از Unit به سمت E2E حرکت کنیم، معمولاً Scope تست بزرگ‌تر و اجرای آن پیچیده‌تر می‌شود.

# بخش 5 - Manual Testing و Automated Testing

## 102.13 - Manual Testing

در Manual Testing انسان به صورت دستی Application را بررسی می‌کند.

مثلاً:

```text
Open Browser
↓
Open Login Page
↓
Enter Email
↓
Enter Password
↓
Click Login
↓
Check Result
```

---

## 102.14 - Automated Testing

در Automated Testing این بررسی‌ها توسط کد انجام می‌شوند.

مثلاً:

```javascript
const result = add(2, 3);

if (result !== 5) {
  throw new Error("Test failed");
}
```

مزیت اصلی Automated Testing این است که می‌توان Testها را بارها و با سرعت بالا اجرا کرد.

---

## 102.15 - آیا Manual Testing بی‌ارزش است؟

خیر.

Manual Testing همچنان در موارد مختلف مفید است؛ مخصوصاً برای:

* بررسی تجربه کاربری
* Exploratory Testing
* بررسی رفتارهایی که خودکارسازی آنها دشوار است
* بررسی اولیه Featureهای جدید

هدف این نیست که تمام Manual Testing را حذف کنیم.

# بخش 6 - Assertion

## 102.16 - Assertion چیست؟

Assertion یعنی بررسی اینکه یک شرط یا نتیجه مطابق انتظار است.

مثلاً:

```javascript
const result = 2 + 3;

if (result !== 5) {
  throw new Error("Expected 5");
}
```

در Test Frameworkها معمولاً Assertion به شکل خواناتر نوشته می‌شود.

مثلاً مفهوم:

```javascript
expect(result).toBe(5);
```

یعنی:

> انتظار داریم result برابر 5 باشد.

---

## 102.17 - انواع Assertion

بسته به ابزار Testing می‌توان Assertionهای مختلفی داشت.

مثلاً بررسی:

```text
Equality
Inequality
Truthy
Falsy
Null
Undefined
Array
Object
String
Error
```

در فصل‌های بعدی نحوه استفاده عملی از آنها را بررسی می‌کنیم.

# بخش 7 - Arrange، Act، Assert

## 102.18 - الگوی AAA

یکی از الگوهای معروف در Testing، **Arrange-Act-Assert** است.

### Arrange

شرایط اولیه را آماده می‌کنیم.

### Act

عملیاتی که می‌خواهیم Test کنیم را اجرا می‌کنیم.

### Assert

نتیجه را بررسی می‌کنیم.

مثلاً:

```javascript
// Arrange
const a = 2;
const b = 3;

// Act
const result = add(a, b);

// Assert
expect(result).toBe(5);
```

ساختار:

```text
Arrange
   ↓
Act
   ↓
Assert
```

باعث خواناتر شدن Testها می‌شود.

# بخش 10 - Test کردن Async Code

## 102.24 - چرا Async Testing مهم است؟

در Node.js بخش زیادی از کدها Async هستند.

مثلاً:

```javascript
async function getUser(id) {
  return await database.findUser(id);
}
```

Test باید بتواند Promise را مدیریت کند.

---

## 102.25 - Testing Promise

مفهوم کلی:

```javascript
const user = await getUser(1);

expect(user.id).toBe(1);
```

یا در برخی Frameworkها:

```javascript
await expect(getUser(1))
  .resolves
  .toEqual(expectedUser);
```

---

## 102.26 - Testing Async Error

همچنین باید خطاهای Async را بررسی کنیم:

```javascript
await expect(getUser(999))
  .rejects
  .toThrow();
```

# بخش 13 - Test Isolation

## 102.31 - Test Isolation چیست؟

هر Test بهتر است تا حد امکان مستقل از Testهای دیگر باشد.

بد:

```text
Test A
↓
Creates User

Test B
↓
Assumes User from Test A exists
```

اگر Test A اجرا نشود، Test B نیز خراب می‌شود.

بهتر:

```text
Test A
↓
Own Setup

Test B
↓
Own Setup
```

---

## 102.32 - چرا Isolation مهم است؟

اگر Testها به یکدیگر وابسته باشند:

```text
Test A → PASS
Test B → PASS
Test C → FAIL
```

ممکن است مشخص نباشد مشکل واقعاً از کدام Test یا کدام وضعیت قبلی ایجاد شده است.

Test مستقل:

```text
Test A → مستقل
Test B → مستقل
Test C → مستقل
```

عیب‌یابی را بسیار ساده‌تر می‌کند.

# بخش 15 - Mock، Stub و Spy

## 102.36 - Mock چیست؟

Mock یک جایگزین کنترل‌شده برای یک Dependency است.

مثلاً Application ما به یک سرویس Email وابسته است:

```text
Application
   ↓
Email Service
   ↓
SMTP Server
```

در Test ممکن است نخواهیم واقعاً Email ارسال شود.

پس می‌توانیم Email Service را Mock کنیم.

---

## 102.37 - چرا Mock استفاده می‌کنیم؟

برای اینکه:

* Test سریع‌تر شود.
* وابستگی خارجی حذف شود.
* Test قابل پیش‌بینی‌تر باشد.
* بتوانیم شرایط خاص را شبیه‌سازی کنیم.

---

## 102.38 - Stub چیست؟

Stub معمولاً یک رفتار از پیش تعیین‌شده ارائه می‌دهد.

مثلاً:

```javascript
getUser()
```

به جای رفتن به Database، مقدار مشخصی برگرداند:

```javascript
{
  id: 1,
  name: "Ali"
}
```

---

## 102.39 - Spy چیست؟

Spy برای مشاهده نحوه استفاده از یک Function یا Method استفاده می‌شود.

مثلاً بررسی کنیم:

```text
sendEmail()
```

چند بار فراخوانی شده است و با چه Argumentهایی.

---

# بخش 16 - Dependency Injection و Testing

## 102.40 - Dependency Injection

Dependency Injection می‌تواند Test کردن Application را ساده‌تر کند.

مثلاً به جای اینکه Service مستقیماً Database را ایجاد کند:

```javascript
class UserService {
  constructor(database) {
    this.database = database;
  }
}
```

در Test می‌توانیم یک Database جعلی یا Mock به آن بدهیم.

```javascript
const fakeDatabase = {
  findUser: async () => ({
    id: 1,
    name: "Ali"
  })
};
```

این کار وابستگی‌ها را قابل کنترل‌تر می‌کند.

# بخش 17 - Test Pyramid

## 102.41 - Test Pyramid چیست؟

یکی از مدل‌های معروف برای توزیع Testها، Test Pyramid است.

به صورت ساده:

```text
        E2E
       /   \
   Integration
  /           \
      Unit
```

معمولاً:

```text
Unit Tests
↓
زیاد

Integration Tests
↓
متوسط

E2E Tests
↓
کمتر
```

دلیل این است که Unit Testها معمولاً سریع‌تر و ارزان‌تر هستند، در حالی که E2E Testها پیچیده‌تر و کندتر هستند.

# بخش 20 - Test-Driven Development

## 102.45 - TDD چیست؟

TDD مخفف:

**Test-Driven Development**

است.

در TDD ابتدا Test نوشته می‌شود و سپس Implementation انجام می‌شود.

چرخه معروف:

```text
RED
 ↓
GREEN
 ↓
REFACTOR
```

---

## 102.46 - RED

ابتدا Testی می‌نویسیم که شکست می‌خورد.

```text
Test
↓
FAIL
```

---

## 102.47 - GREEN

سپس حداقل کدی را می‌نویسیم که Test را Pass کند.

```text
Test
↓
PASS
```

---

## 102.48 - REFACTOR

بعد کد را بدون تغییر رفتار آن بهبود می‌دهیم.

```text
PASS
↓
Refactor
↓
PASS
```

---

# اشتباهات رایج

## 1. فقط Happy Path را Test کردن

بد:

```text
Valid Input → PASS
```

اما هیچ Testی برای:

```text
Invalid Input
Empty Input
Null
Error
```

وجود ندارد.

---

## 2. نوشتن Testهای وابسته به یکدیگر

هر Test باید تا حد امکان مستقل باشد.

---

## 3. Test کردن Implementation به جای Behavior

هدف Test باید بررسی رفتار قابل انتظار Application باشد، نه وابستگی شدید به جزئیات داخلی Implementation.

---

## 4. استفاده بیش از حد از Mock

Mock کردن همه چیز ممکن است Testها را از رفتار واقعی Application دور کند.

---

## 5. استفاده نکردن از Test برای Bugهای مهم

اگر Bug مهمی پیدا شد، بهتر است برای جلوگیری از بازگشت آن یک Regression Test اضافه شود.

---

## 6. نوشتن Testهای بسیار بزرگ

یک Test که ده‌ها رفتار مختلف را بررسی می‌کند، در صورت Fail شدن سخت‌تر Debug می‌شود.

---

## 7. نادیده گرفتن Error Case

Test فقط برای Success نیست.

باید Failure و Exception را نیز بررسی کنیم.

---

## 8. وابستگی Testها به محیط واقعی

Test نباید بدون دلیل به:

* سرویس خارجی
* Database توسعه‌دهنده
* فایل‌های محلی خاص
* وضعیت فعلی سیستم

وابسته باشد.

---

## 9. هدف قرار دادن صرفاً Coverage بالا

Coverage بالا به تنهایی کیفیت Testها را تضمین نمی‌کند.

---

## 10. Testهای شکننده

Testی که با کوچک‌ترین تغییر غیرضروری در Implementation خراب می‌شود، معمولاً Test مناسبی نیست.

---

# نکات حرفه‌ای

## 1. Testها را خوانا بنویسید

کسی که Test را می‌خواند باید سریع متوجه شود:

```text
چه چیزی؟
با چه شرایطی؟
چه نتیجه‌ای؟
```

---

## 2. هر Test یک هدف مشخص داشته باشد

مثلاً:

```text
should create user with valid data
```

بهتر از Testی است که چند رفتار نامرتبط را همزمان بررسی کند.

---

## 3. نام Test مهم است

نام مناسب:

```text
should reject login with invalid password
```

نام ضعیف:

```text
test1
```

---

## 4. Testها را Deterministic کنید

یک Test باید در شرایط یکسان، نتیجه یکسانی داشته باشد.

وابستگی بی‌دلیل به:

```text
Random Data
Current Time
Network
External API
```

می‌تواند Test را ناپایدار کند.

---

## 5. Testهای سریع را زیاد داشته باشید

Unit Testهای سریع باعث می‌شوند Developer بتواند مرتب Testها را اجرا کند.

---

## 6. Test را جایگزین طراحی خوب ندانید

اگر Testing یک بخش بسیار سخت است، ممکن است خود Design مشکل داشته باشد.

گاهی سخت بودن Test کردن یک کلاس یا Service نشانه وابستگی بیش از حد آن است.

---

## 7. Bug Fix باید Test داشته باشد

وقتی یک Bug مهم پیدا می‌شود:

```text
Bug
↓
Fix
↓
Regression Test
```

اضافه کنید تا دوباره ایجاد نشود.

---

## 8. Testهای Integration را حذف نکنید

Unit Test به تنهایی نمی‌تواند تضمین کند که تمام اجزای واقعی Application به درستی با هم کار می‌کنند.

---

## 9. E2E را برای جریان‌های مهم استفاده کنید

برای تمام حالت‌های ممکن E2E Test ننویسید.

جریان‌های حیاتی مثل:

```text
Login
Checkout
Payment
Registration
```

کاندیدای خوبی برای E2E هستند.

---

## 10. Test Database مستقل داشته باشید

Testهای Database را به Database توسعه یا Production متصل نکنید.

---

# پاسخ تشریحی

## پاسخ تمرین 1

Testing فرآیند بررسی رفتار Application برای اطمینان از درست بودن آن نسبت به رفتار مورد انتظار است.

Testing می‌تواند به صورت Manual یا Automated انجام شود.

---

## پاسخ تمرین 2

Testing برای بررسی رفتار برنامه استفاده می‌شود.

Debugging برای پیدا کردن علت خطا و اصلاح آن انجام می‌شود.

به صورت ساده:

```text
Testing → پیدا کردن مشکل
Debugging → پیدا کردن علت و رفع مشکل
```

---

## پاسخ تمرین 3

برای:

```javascript
function divide(a, b) {
  return a / b;
}
```

می‌توان Test Caseهای زیر را داشت:

```text
divide(10, 2) → 5
divide(9, 3) → 3
divide(0, 5) → 0
divide(-10, 2) → -5
divide(10, 0) → بررسی رفتار مورد انتظار
```

مورد آخر اهمیت زیادی دارد؛ زیرا باید مشخص کنیم Application در برابر تقسیم بر صفر چه رفتاری باید داشته باشد.

### E2E

## پاسخ تمرین 7

در نتیجه:

```text

```

```text

```

در حالی که مشکل اصلی فقط Test A بوده است.

## پاسخ تمرین 9

Mock یک Dependency جایگزین‌شده است که رفتار کنترل‌شده‌ای ارائه می‌دهد.

مثلاً به جای ارسال واقعی Email:

```text

↓
```

این کار باعث می‌شود Test سریع‌تر و قابل پیش‌بینی‌تر شود.

---

## پاسخ تمرین 10

به صورت ساده:

```text
Stub
→ رفتار مشخص ارائه می‌دهد.

Mock
→ Dependency را جایگزین می‌کند و معمولاً تعامل مورد انتظار را نیز کنترل می‌کند.

Spy
→ تعاملات یک Function یا Method را مشاهده می‌کند.
```

مرز دقیق این اصطلاحات ممکن است در Frameworkهای مختلف متفاوت باشد.

## پاسخ تمرین 11

# جمع‌بندی فصل

Testing یکی از مهم‌ترین بخش‌های توسعه حرفه‌ای Software است.

در این فصل با مفاهیم پایه Testing آشنا شدیم:

```text
Testing
Test Case
Test Suite
Test Runner
Assertion
Unit Test
Integration Test
E2E Test
Manual Testing
Automated Testing
Mock
Stub
Spy
Test Isolation
Setup
Teardown
Code Coverage
Regression Testing
TDD
```

همچنین یاد گرفتیم که Test خوب فقط بررسی نمی‌کند:

```text
"آیا برنامه در حالت عادی کار می‌کند؟"
```

بلکه سؤال‌های دیگری نیز می‌پرسد:

```text
اگر ورودی اشتباه باشد چه؟

اگر Database خطا بدهد چه؟

اگر User وجود نداشته باشد چه؟

اگر دو Request همزمان برسند چه؟

اگر یک Dependency در دسترس نباشد چه؟

اگر Feature جدیدی اضافه کنیم، قابلیت‌های قبلی همچنان کار می‌کنند؟
```

در یک پروژه حرفه‌ای Node.js معمولاً از ترکیبی از Testها استفاده می‌کنیم:

```text
             E2E
              ↑
        Integration
              ↑
            Unit
```

Unit Testها برای بررسی منطق‌های کوچک، Integration Testها برای بررسی ارتباط اجزای Application و E2E Testها برای بررسی جریان‌های مهم و واقعی سیستم استفاده می‌شوند.

مهم‌ترین نکته این فصل:

> Testing فقط پیدا کردن Bug نیست؛ Testing ابزاری برای افزایش اطمینان ما نسبت به رفتار Application و امکان تغییر دادن کد با ریسک کمتر است.

در فصل‌های بعدی وارد Testing عملی در Node.js می‌شویم و با ابزارهای واقعی، نوشتن Unit Test، Integration Test، API Test، Mocking، Test Database و اجرای Testها در پروژه‌های واقعی کار خواهیم کرد.
