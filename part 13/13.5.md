# فصل 106 - Mock

## مقدمه

در فصل‌های قبل با Testing، Unit Test، Integration Test و Jest آشنا شدیم. در این فصل به یکی از مهم‌ترین مفاهیم در Testing می‌رسیم:

**Mock**

در یک برنامه واقعی Node.js، معمولاً یک Function یا Service به بخش‌های دیگری از برنامه وابسته است.

برای مثال:

```text
UserService
    ↓
UserRepository
    ↓
Database
```

اگر بخواهیم `UserService` را به صورت Unit Test تست کنیم، معمولاً نمی‌خواهیم هر بار واقعاً به Database متصل شویم.

در این حالت می‌توانیم به جای Repository واقعی، یک نسخه ساختگی از آن ایجاد کنیم:

```text
UserService
    ↓
Mock UserRepository
```

Mock به ما اجازه می‌دهد Dependencyهای یک بخش از برنامه را کنترل کنیم و رفتارهای مختلفی برای آنها تعریف کنیم.

با Mock می‌توانیم:

* Functionهای ساختگی ایجاد کنیم.
* مقدار بازگشتی Function را تعیین کنیم.
* تعداد دفعات فراخوانی Function را بررسی کنیم.
* Arguments ارسال‌شده را بررسی کنیم.
* Promise موفق را شبیه‌سازی کنیم.
* Promise شکست‌خورده را شبیه‌سازی کنیم.
* Moduleها را Mock کنیم.
* Methodها را Spy کنیم.
* خطاهای Dependencyها را شبیه‌سازی کنیم.
* ارتباط بین بخش‌های مختلف برنامه را بدون اجرای Dependency واقعی تست کنیم.

در Jest ابزارهای مختلفی برای این کار وجود دارد؛ از جمله:

```text
jest.fn()
jest.mock()
jest.spyOn()
```

در این فصل Mock را از ساده‌ترین حالت شروع می‌کنیم و در نهایت به Mock کردن Repository، Database، API و Service در یک پروژه واقعی Node.js می‌رسیم.

---

# بخش 1 - Mock چیست؟

## 106.1 - مفهوم Mock

Mock یک نسخه ساختگی از یک Dependency است که برای کنترل رفتار آن در Test استفاده می‌شود.

فرض کنید:

```javascript
class UserService {
  constructor(repository) {
    this.repository = repository;
  }

  async getUser(id) {
    return this.repository.findById(id);
  }
}
```

در حالت واقعی:

```text
UserService
    ↓
UserRepository
    ↓
Database
```

اما در Unit Test:

```text
UserService
    ↓
Mock Repository
```

در این حالت Database واقعی اجرا نمی‌شود.

---

## 106.2 - چرا به Mock نیاز داریم؟

فرض کنید UserService برای دریافت User به Database متصل می‌شود.

اگر برای هر Test به Database واقعی متصل شویم:

* Testها کندتر می‌شوند.
* Testها به Database وابسته می‌شوند.
* مدیریت داده‌های Test سخت‌تر می‌شود.
* خطاهای Database ممکن است Test را خراب کنند.
* Testها ممکن است مستقل نباشند.
* اجرای Test در CI/CD پیچیده‌تر می‌شود.

Mock کردن این Dependencyها می‌تواند Test را ساده‌تر و قابل‌کنترل‌تر کند.

# بخش 2 - Dependency چیست؟

## 106.3 - مفهوم Dependency

Dependency یعنی بخشی از برنامه که یک بخش دیگر برای انجام کار خود به آن نیاز دارد.

مثلاً:

```javascript
class UserService {
  constructor(repository) {
    this.repository = repository;
  }
}
```

در این مثال:

```text
UserService
    ↓
repository
```

`repository` یک Dependency است.

Dependency می‌تواند شامل موارد مختلفی باشد:

* Database
* Repository
* API Client
* Email Service
* File System
* Cache
* Logger
* Payment Service
* Queue
* دیگر Serviceها

---

## 106.4 - چرا Dependency در Mock مهم است؟

هدف Unit Test این است که یک واحد مشخص را مستقل از Dependencyهای خارجی بررسی کنیم.

مثلاً:

```text
UserService
```

را تست کنیم بدون اینکه:

```text
Database
Email
Redis
External API
```

واقعاً اجرا شوند.

# بخش 3 - Mock Function

## 106.5 - jest.fn()

ساده‌ترین روش ساخت Mock Function در Jest استفاده از `jest.fn()` است:

```javascript
const mockFn = jest.fn();
```

حالا:

```javascript
mockFn();
```

یک Function ساختگی را اجرا می‌کند.

---

## 106.6 - بررسی اینکه Function اجرا شده است

```javascript
const mockFn = jest.fn();

mockFn();

expect(mockFn).toHaveBeenCalled();
```

---

## 106.7 - بررسی تعداد فراخوانی

```javascript
const mockFn = jest.fn();

mockFn();
mockFn();

expect(mockFn).toHaveBeenCalledTimes(2);
```

---

## 106.8 - بررسی Arguments

```javascript
const mockFn = jest.fn();

mockFn("Ali", 20);

expect(mockFn).toHaveBeenCalledWith("Ali", 20);
```

---

## 106.9 - بررسی اولین Call

می‌توان اطلاعات Callها را از Mock Function دریافت کرد:

```javascript
const mockFn = jest.fn();

mockFn("Ali");

expect(mockFn.mock.calls[0][0])
  .toBe("Ali");
```

البته در بیشتر Testها استفاده از Matcherهای Jest خواناتر است:

```javascript
expect(mockFn)
  .toHaveBeenCalledWith("Ali");
```

# بخش 4 - Mock Return Value

## 106.10 - mockReturnValue

می‌توانیم مشخص کنیم Mock چه مقداری برگرداند:

```javascript
const mockFn = jest.fn();

mockFn.mockReturnValue(100);

expect(mockFn()).toBe(100);
```

---

## 106.11 - Mock کردن Object

```javascript
const getUser = jest.fn();

getUser.mockReturnValue({
  id: 1,
  name: "Ali"
});
```

حالا:

```javascript
const user = getUser();

expect(user).toEqual({
  id: 1,
  name: "Ali"
});
```

---

## 106.12 - mockReturnValueOnce

گاهی می‌خواهیم Mock در هر Call مقدار متفاوتی برگرداند:

```javascript
const mockFn = jest.fn();

mockFn
  .mockReturnValueOnce(10)
  .mockReturnValueOnce(20)
  .mockReturnValueOnce(30);
```

نتیجه:

```javascript
mockFn(); // 10
mockFn(); // 20
mockFn(); // 30
```

# بخش 5 - Mock کردن Promise

## 106.13 - mockResolvedValue

برای Functionهای Async:

```javascript
const getUser = jest.fn();

getUser.mockResolvedValue({
  id: 1,
  name: "Ali"
});
```

حالا:

```javascript
const user = await getUser();
```

نتیجه:

```javascript
{
  id: 1,
  name: "Ali"
}
```

---

## 106.14 - mockResolvedValueOnce

```javascript
const getUser = jest.fn();

getUser
  .mockResolvedValueOnce({
    id: 1
  })
  .mockResolvedValueOnce({
    id: 2
  });
```

---

## 106.15 - mockRejectedValue

برای شبیه‌سازی خطای Promise:

```javascript
const getUser = jest.fn();

getUser.mockRejectedValue(
  new Error("Database Error")
);
```

حالا:

```javascript
await getUser();
```

با Error مواجه می‌شود.

---

## 106.16 - mockRejectedValueOnce

```javascript
const getUser = jest.fn();

getUser
  .mockRejectedValueOnce(
    new Error("Database Error")
  )
  .mockResolvedValueOnce({
    id: 1
  });
```

در اولین Call خطا و در Call دوم نتیجه موفق دریافت می‌شود.

# بخش 6 - Mock Implementation

## 106.17 - mockImplementation

گاهی فقط تعیین مقدار Return کافی نیست و می‌خواهیم رفتار Function را مشخص کنیم:

```javascript
const add = jest.fn();

add.mockImplementation((a, b) => {
  return a + b;
});
```

حالا:

```javascript
expect(add(2, 3)).toBe(5);
```

---

## 106.18 - mockImplementationOnce

می‌توان Implementation را فقط برای یک Call مشخص کرد:

```javascript
const fn = jest.fn();

fn
  .mockImplementationOnce(() => 10)
  .mockImplementationOnce(() => 20);
```

# بخش 7 - Mock و Spy

## 106.19 - Spy چیست؟

Spy به ما اجازه می‌دهد یک Function یا Method را زیر نظر بگیریم و بررسی کنیم:

* آیا اجرا شده؟
* چند بار اجرا شده؟
* با چه Argumentsهایی اجرا شده؟
* چه مقداری برگردانده؟

---

## 106.20 - jest.spyOn()

مثلاً:

```javascript
const math = {
  add(a, b) {
    return a + b;
  }
};

const spy = jest.spyOn(math, "add");

math.add(2, 3);

expect(spy)
  .toHaveBeenCalledWith(2, 3);
```

---

## 106.21 - تفاوت Spy و Mock

به صورت ساده:

**Mock Function:**

```javascript
jest.fn()
```

یک Function ساختگی ایجاد می‌کند.

**Spy:**

```javascript
jest.spyOn(object, "method")
```

روی یک Method موجود نظارت می‌کند و در صورت نیاز می‌توان رفتار آن را نیز تغییر داد.

---

## 106.22 - تغییر رفتار Spy

```javascript
const spy = jest.spyOn(math, "add");

spy.mockImplementation(() => {
  return 100;
});
```

حالا:

```javascript
expect(math.add(2, 3))
  .toBe(100);
```

---

## 106.23 - Restore کردن Spy

بعد از Test بهتر است Spy را به حالت اصلی برگردانیم:

```javascript
spy.mockRestore();
```

```javascript
expect(repository.findById)
  .toHaveBeenCalledWith(1);
```


این یکی از مهم‌ترین مزیت‌های Mock است.

# بخش 20 - Mock و Dependency Injection

Dependency Injection یکی از بهترین روش‌ها برای ساده کردن Mocking است.

بد:

```javascript
class UserService {
  async getUser(id) {
    return database.users.findById(id);
  }
}
```

در این حالت Mock کردن Dependency می‌تواند سخت‌تر شود.

ساختار بهتر:

```javascript
class UserService {
  constructor(repository) {
    this.repository = repository;
  }

  async getUser(id) {
    return this.repository.findById(id);
  }
}
```

حالا در Test:

```javascript
const repository = {
  findById: jest.fn()
};

const service = new UserService(repository);
```

این ساختار Testability بیشتری دارد.

# بخش 23 - تفاوت Mock، Stub و Spy

این سه مفهوم به یکدیگر نزدیک هستند اما دقیقاً یکسان نیستند.

## Mock

معمولاً برای جایگزین کردن یک Dependency و بررسی تعامل با آن استفاده می‌شود.

---

## Stub

معمولاً برای ارائه یک پاسخ مشخص به یک Call استفاده می‌شود.

مثلاً:

```javascript
repository.findById
  .mockResolvedValue({
    id: 1
  });
```

---

## Spy

برای مشاهده رفتار یک Function یا Method واقعی استفاده می‌شود.

مثلاً:

```javascript
jest.spyOn(logger, "error");
```

در پروژه‌های واقعی این اصطلاحات گاهی با هم استفاده می‌شوند، اما دانستن تفاوت مفهومی آنها مهم است.

---

## 106.29 - mockRestore

برای Mockهای قابل Restore، مانند Spyها، رفتار اصلی را برمی‌گرداند.


# بخش 25 - پاک‌سازی Mockها

می‌توان از Lifecycle Hookهای Jest استفاده کرد:

```javascript
beforeEach(() => {
  jest.clearAllMocks();
});
```

یا:

```javascript
afterEach(() => {
  jest.restoreAllMocks();
});
```

باید دقت کنیم که هر کدام از این روش‌ها دقیقاً چه چیزی را پاک یا Restore می‌کنند.

# بخش 26 - Mock کردن Moduleهای Node.js

گاهی لازم است Moduleهای داخلی Node.js را نیز Mock کنیم.

# بخش 35 - Mock و Test Isolation

یکی از مهم‌ترین اهداف Mock:

**Isolation**

است.

هر Test باید تا حد امکان مستقل از Testهای دیگر باشد.

مثلاً:

```javascript
test("test 1", () => {
  // ...
});

test("test 2", () => {
  // ...
});
```

نباید Test دوم به تغییراتی که Test اول روی Mock ایجاد کرده وابسته باشد.

برای همین Cleanup بسیار مهم است.

---

# اشتباهات رایج

## 1. Mock کردن همه چیز

اگر همه Dependencyها را Mock کنیم، ممکن است Test دیگر رفتار واقعی Application را بررسی نکند.

---

## 2. Mock نکردن Dependency خارجی

اگر Unit Test مستقیماً به:

```text
Database
External API
Payment Gateway
Email Server
```

متصل شود، Test دیگر کاملاً مستقل نیست.

---

## 3. فراموش کردن Cleanup

Mock باقی‌مانده می‌تواند روی Test بعدی اثر بگذارد.

---

## 4. استفاده اشتباه از mockClear

`mockClear` رفتار Mock را لزوماً به حالت اولیه برنمی‌گرداند؛ بیشتر اطلاعات Callها را پاک می‌کند.

---

## 5. استفاده اشتباه از mockReset

`mockReset` می‌تواند Implementation و Return Valueهای Mock را نیز پاک کند.

---

## 6. Restore نکردن Spy

اگر روی Method واقعی Spy ایجاد کرده‌اید، باید در صورت نیاز آن را Restore کنید.

---

## 7. تست کردن Mock به جای Application

نباید Test را طوری بنویسیم که فقط ثابت کند Mock درست کار می‌کند.

هدف باید بررسی رفتار Application باشد.

---

## 8. Mock کردن Implementation Detail

اگر Test بیش از حد به ساختار داخلی Code وابسته شود، تغییرات ساده در Implementation باعث شکستن Testها می‌شوند.

---

## 9. استفاده بیش از حد از `jest.mock`

Mock کردن کامل Module همیشه بهترین راه‌حل نیست.

گاهی Dependency Injection و `jest.fn()` خواناتر و قابل‌کنترل‌تر هستند.

---

## 10. Mock نکردن Error Scenario

فقط Success را تست نکنید.

حتماً حالت‌هایی مانند:

```text
Not Found
Database Error
API Error
Validation Error
Timeout
Unauthorized
```

را نیز بررسی کنید.

---

## 11. Mock کردن Database در Integration Test بدون دلیل

اگر هدف Test بررسی ارتباط با Database است، Mock کردن Database باعث می‌شود چیزی که می‌خواستیم تست کنیم دیگر تست نشود.

---

## 12. Mockهای بسیار پیچیده

اگر Mock از خود Code اصلی پیچیده‌تر شود، احتمالاً طراحی Test یا معماری Code نیاز به بازبینی دارد.

---

# نکات حرفه‌ای

## 1. فقط Dependencyهای لازم را Mock کنید

هر Dependency را صرفاً به دلیل اینکه امکان Mock کردن آن وجود دارد Mock نکنید.

---

## 2. از Dependency Injection استفاده کنید

ساختار:

```javascript
constructor(repository)
```

Mock کردن را بسیار ساده‌تر می‌کند.

---

## 3. رفتار را تست کنید

به جای تمرکز روی اینکه Application دقیقاً چگونه کار می‌کند، نتیجه و رفتار قابل مشاهده را بررسی کنید.

---

## 4. Error Scenarioها را جدی بگیرید

Mock یکی از بهترین ابزارها برای شبیه‌سازی Errorهای سخت‌تکرار است.

---

## 5. Mock را ساده نگه دارید

Mock باید فقط رفتار مورد نیاز Test را شبیه‌سازی کند.

---

## 6. از `mockResolvedValue` برای Promiseهای موفق استفاده کنید

```javascript
mockFn.mockResolvedValue(data);
```

خواناتر از ساخت دستی Promise است.

---

## 7. از `mockRejectedValue` برای خطاهای Async استفاده کنید

```javascript
mockFn.mockRejectedValue(error);
```

---

## 8. از Spy برای مشاهده رفتار واقعی استفاده کنید

اگر نمی‌خواهید Implementation را کاملاً جایگزین کنید، Spy می‌تواند انتخاب مناسبی باشد.

---

## 9. Cleanup را جدی بگیرید

در پروژه‌های بزرگ:

```javascript
afterEach(() => {
  jest.clearAllMocks();
});
```

یا در موارد مناسب:

```javascript
afterEach(() => {
  jest.restoreAllMocks();
});
```

می‌تواند از آلودگی بین Testها جلوگیری کند.

---

## 10. Mock نباید از Code اصلی پیچیده‌تر شود

اگر برای یک Test نیاز به Mock بسیار پیچیده دارید، معماری Code را بررسی کنید.

---

## 11. Unit و Integration Test را با هم اشتباه نگیرید

```text
Unit Test
→ Isolation
→ Mock Dependency

Integration Test
→ Integration
→ Real Components / Test Infrastructure
```

هدف هر دو متفاوت است.

---

## 12. Mock را با واقعیت اشتباه نگیرید

ممکن است Test با Mock کاملاً موفق باشد اما Integration واقعی مشکل داشته باشد.

به همین دلیل Mock جای Integration Test را نمی‌گیرد.

```javascript
class UserService {
  constructor(repository, emailService) {
    this.repository = repository;
    this.emailService = emailService;
  }

  async getUser(id) {
    if (!id) {
      throw new Error("Invalid ID");
    }

    return this.repository.findById(id);

    if (!data.email) {
      throw new Error("Email is required");
    }

    const user =
      await this.repository.create(data);

    await this.emailService
      .sendWelcomeEmail(user.email);

    return user;
  }
}

module.exports = UserService;
```

# جمع‌بندی فصل

در این فصل با یکی از مهم‌ترین مفاهیم Testing یعنی **Mock** آشنا شدیم.

یاد گرفتیم که Mock برای جایگزین کردن یا کنترل کردن Dependencyها در Test استفاده می‌شود.

مهم‌ترین ابزارهای Jest که در این فصل یاد گرفتیم:

```text
jest.fn()
jest.mock()
jest.spyOn()
```

همچنین با روش‌های مختلف تعیین رفتار Mock آشنا شدیم:

```text
mockReturnValue
mockReturnValueOnce

mockResolvedValue
mockResolvedValueOnce

mockRejectedValue
mockRejectedValueOnce

mockImplementation
mockImplementationOnce
```

و یاد گرفتیم چگونه Dependencyهای واقعی مانند:

```text
Repository
Database
External API
Email Service
Payment Service
Queue
Logger
File System
```

را در Unit Test شبیه‌سازی کنیم.

همچنین تفاوت مفهومی:

```text
Mock
Stub
Spy
```

را بررسی کردیم و با:

```text
mockClear
mockReset
mockRestore
```

برای مدیریت Mockها آشنا شدیم.

مهم‌ترین نکته این فصل این است:

> Mock جای Test کردن سیستم واقعی را نمی‌گیرد؛ Mock ابزاری برای کنترل Dependencyها در Testهای ایزوله، مخصوصاً Unit Testها است.

در ساختار کلی پروژه:

```text
Testing
│
├── Unit Test
│   └── Mock Dependencies
│
├── Integration Test
│   └── Test Real Integration
│
└── E2E Test
    └── Test Complete Flow
```

Mock بیشتر در بخش Unit Test به کار می‌رود و در فصل بعد، در **Coverage** بررسی می‌کنیم چگونه میزان پوشش Testهای نوشته‌شده را اندازه‌گیری کنیم.
