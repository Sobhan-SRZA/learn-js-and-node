# فصل 103 - Unit Test

## مقدمه

در فصل قبل با مفهوم کلی Testing آشنا شدیم و دیدیم که یکی از مهم‌ترین انواع تست، **Unit Test** است.

در پروژه‌های Node.js، بخش زیادی از منطق برنامه در قالب Function، Class، Module و Service نوشته می‌شود. Unit Test به ما کمک می‌کند این بخش‌های کوچک را به صورت مستقل بررسی کنیم.

هدف اصلی Unit Test این است که یک **Unit کوچک از کد** را جدا کنیم و بررسی کنیم که آیا در شرایط مختلف، رفتار مورد انتظار را دارد یا خیر.

برای مثال:

```javascript
function add(a, b) {
  return a + b;
}
```

می‌توانیم بدون اجرای کل Application بررسی کنیم:

```text
add(2, 3)
↓
5
```

اگر نتیجه 5 باشد:

```text
PASS
```

و اگر نتیجه چیز دیگری باشد:

```text
FAIL
```

در این فصل یاد می‌گیریم چگونه Unit Test بنویسیم، چه چیزهایی را Test کنیم، چگونه Testها را سازمان‌دهی کنیم، چگونه با Functionهای Sync و Async کار کنیم و چگونه Dependencyهای یک Unit را Mock کنیم.

---

# بخش 1 - Unit چیست؟

## 103.1 - مفهوم Unit

Unit کوچک‌ترین بخش منطقی و قابل تست برنامه است.

بسته به طراحی Application، Unit می‌تواند یک:

* Function
* Method
* Class
* Module
* Service

باشد.

مثلاً:

```javascript
function calculatePrice(price, quantity) {
  return price * quantity;
}
```

در اینجا می‌توانیم خود Function را به عنوان یک Unit در نظر بگیریم.

---

## 103.2 - هدف Unit Test

هدف Unit Test این است که یک بخش کوچک از Application را تا حد امکان مستقل از سایر بخش‌ها بررسی کنیم.

مثلاً:

```text
Application
│
├── User Service
├── Product Service
├── Order Service
└── Payment Service
```

می‌توانیم هر Service را جداگانه Test کنیم.

```text
User Service
↓
Unit Tests
```

```text
Order Service
↓
Unit Tests
```

---

# بخش 2 - اولین Unit Test

## 103.3 - Function ساده

فرض کنید Function زیر را داریم:

```javascript
function add(a, b) {
  return a + b;
}

module.exports = add;
```

هدف ما این است که رفتار آن را بررسی کنیم.

Test باید مشخص کند:

```text
2 + 3 = 5
```

---

## 103.4 - ساختار کلی Unit Test

یک Unit Test معمولاً شامل سه مرحله است:

```text
Arrange
↓
Act
↓
Assert
```

مثال:

```javascript
const result = add(2, 3);

expect(result).toBe(5);
```

در این مثال:

```text
Arrange → آماده کردن ورودی
Act     → اجرای Function
Assert  → بررسی نتیجه
```

---

# بخش 3 - Assertion در Unit Test

## 103.5 - Assertion

Assertion قلب Unit Test است.

ما باید مشخص کنیم که چه نتیجه‌ای انتظار داریم.

مثلاً:

```javascript
expect(add(2, 3)).toBe(5);
```

یعنی:

> انتظار داریم خروجی Function برابر 5 باشد.

---

## 103.6 - Equality

برای مقایسه مقادیر:

```javascript
expect(result).toBe(10);
```

---

## 103.7 - Object Equality

برای Objectها بسته به Test Runner ممکن است نیاز به مقایسه عمیق داشته باشیم.

مثلاً:

```javascript
expect(user).toEqual({
  id: 1,
  name: "Ali"
});
```

---

## 103.8 - Truthy و Falsy

می‌توانیم بررسی کنیم مقدار Truthy یا Falsy است.

مثلاً:

```javascript
expect(isValid).toBeTruthy();
```

یا:

```javascript
expect(isValid).toBeFalsy();
```

---

## 103.9 - Null و Undefined

می‌توان وضعیت مقدار را نیز بررسی کرد:

```javascript
expect(result).toBeNull();
```

یا:

```javascript
expect(result).toBeUndefined();
```

---

## 103.10 - بررسی Error

اگر Function باید خطا ایجاد کند، باید این رفتار نیز Test شود.

مثلاً:

```javascript
expect(() => divide(10, 0)).toThrow();
```


# بخش 5 - Test کردن Edge Case

```text

```

چون دقیقاً مرز است.

بسته به Function ممکن است موارد زیر مهم باشند:

```text

-1
1
Maximum Value
Minimum Value
Empty String
Whitespace
Empty Array
Null
Undefined
NaN
```

# بخش 6 - Test کردن Invalid Input

## 103.16 - ورودی نامعتبر

فرض کنید:

```javascript
function calculateDiscount(price, percent) {
  if (price < 0 || percent < 0 || percent > 100) {
    throw new Error("Invalid input");
  }

  return price * (1 - percent / 100);
}
```

باید Test کنیم:

```text
Valid Price
Valid Percent
Negative Price
Negative Percent
Percent > 100
```

---

## 103.17 - چرا Invalid Input مهم است؟

چون بسیاری از Bugها در شرایط غیرعادی رخ می‌دهند.

یک Unit Test خوب فقط این را بررسی نمی‌کند:

```text
Valid Input → PASS
```

بلکه موارد زیر را نیز بررسی می‌کند:

```text
Invalid Input → Correct Error
```

## 103.21 - بررسی Property


این موضوع به هدف Test بستگی دارد.

# بخش 9 - Unit Test برای Class

## 103.22 - Test کردن Class

مثلاً:

```javascript
class Counter {
  constructor() {
    this.value = 0;
  }

  increment() {
    this.value++;
  }

  decrement() {
    this.value--;
  }
```

می‌توان Test کرد:

```text

Increment → 1
Decrement → 0
```

---

## 103.23 - Test کردن State

برای Classهایی که State دارند باید بررسی کنیم عملیات مختلف State را درست تغییر می‌دهند.

مثلاً:

```text
Initial
↓
increment()
↓
Updated State
```

# بخش 10 - Unit Test برای Module

## 103.24 - Module چیست؟

در Node.js کد معمولاً به Moduleهای مختلف تقسیم می‌شود.

```text
│   ├── math.js
│   └── string.js
├── services/
│   └── user.service.js

    └── user.controller.js
```

هر Module می‌تواند Unit Testهای خودش را داشته باشد.

## 103.25 - جداسازی Testها

```text
src/
└── utils/
    └── math.js

tests/
└── utils/
    └── math.test.js
```

یا:

```text
src/
└── utils/
    └── math.test.js
```

هر دو رویکرد در پروژه‌های مختلف دیده می‌شوند.

# بخش 11 - Unit Test برای Async Function

## 103.26 - Async Function

در Node.js بسیاری از Functionها Async هستند.

مثلاً:

```javascript
async function getUser(id) {
  return await repository.findById(id);
}
```

چون Function یک Promise برمی‌گرداند، Test نیز باید Promise را مدیریت کند.

---

## 103.27 - Await کردن نتیجه

مثلاً:

```javascript
const user = await getUser(1);

expect(user.id).toBe(1);
```

---

## 103.28 - Test کردن Promise Rejection

اگر Function باید Error ایجاد کند:

```javascript
await expect(getUser(999))

  .toThrow();
```

# بخش 12 - Dependency در Unit Test

## 103.29 - Dependency چیست؟

Dependency چیزی است که یک بخش از برنامه برای انجام کار خود به آن نیاز دارد.

مثلاً:

```text
UserService
   ↓
UserRepository
```

یا:

```text
OrderService
   ↓
PaymentService
```

یا:

```text
NotificationService
   ↓
EmailProvider
```

---

## 103.30 - مشکل Dependency

اگر بخواهیم UserService را Test کنیم و UserService مستقیماً به Database متصل باشد، دیگر Test ما کاملاً مستقل نیست.

```text
Unit Test
   ↓
UserService
   ↓
Database
   ↓
Network
```

این باعث می‌شود Test:

* کندتر شود.
* پیچیده‌تر شود.
* وابسته به محیط باشد.
* احتمالاً ناپایدار شود.

---

# بخش 13 - Mock کردن Dependency

## 103.31 - Mock

برای Unit Test می‌توانیم Dependency را Mock کنیم.

مثلاً:

```text
Unit Test
   ↓
UserService
   ↓
Mock Repository
```

در نتیجه Database واقعی اجرا نمی‌شود.

---

## 103.32 - مثال Mock Repository

فرض کنید:

```javascript
class UserService {
  constructor(repository) {
    this.repository = repository;
  }

  async getUser(id) {
    return this.repository.findById(id);
  }
}
```

در Test:

```javascript
const repository = {
  findById: async () => ({
    id: 1,
    name: "Ali"
  })
};

const service = new UserService(repository);
```

اکنون UserService بدون Database واقعی قابل تست است.

---

# بخش 14 - Dependency Injection

## 103.33 - Dependency Injection چیست؟

Dependency Injection یعنی Dependency را از بیرون به Component بدهیم.

بد:

```javascript
class UserService {
  constructor() {
    this.repository = new UserRepository();
  }
}
```

در این حالت Mock کردن Repository دشوارتر می‌شود.

بهتر:

```javascript
class UserService {
  constructor(repository) {
    this.repository = repository;
  }
}
```

حالا می‌توانیم در Production:

```javascript
const service = new UserService(realRepository);
```

و در Test:

```javascript
const service = new UserService(mockRepository);
```

استفاده کنیم.

Stub یک پاسخ از پیش تعیین‌شده ارائه می‌دهد.

مثلاً:

```javascript
repository.findById = async () => ({
  id: 1,

```

## 103.35 - Mock

Mock می‌تواند Dependency را جایگزین کند و رفتار یا تعامل مورد انتظار را کنترل کند.

---

## 103.36 - Spy

Spy برای بررسی نحوه استفاده از Function استفاده می‌شود.

مثلاً:

```text
↓

با چه Argumentی؟
```

# بخش 16 - Test کردن Side Effect

## 103.37 - Side Effect چیست؟

Side Effect تغییری است که خارج از محاسبه مستقیم Function رخ می‌دهد.

مثلاً:

```text
Database Write
File Write
Send Email
Send HTTP Request
Console Output
```

---

## 103.38 - Unit Test برای Side Effect

مثلاً اگر Service باید Email ارسال کند، در Unit Test معمولاً Email واقعی ارسال نمی‌کنیم.

به جای آن:

```text
Email Service
↓
Mock
```

و بررسی می‌کنیم که Function مربوطه با Argument مناسب فراخوانی شده است.

# بخش 19 - Table-Driven Testing

## 103.43 - Table-Driven Test

مثلاً:

این روش از تکرار کد جلوگیری می‌کند.

# اشتباهات رایج

## 1. Test کردن چند Unit در یک Test

یک Test بسیار بزرگ که چند رفتار مختلف را بررسی می‌کند، معمولاً خوانایی و Debugging را سخت می‌کند.

---

## 2. وابستگی به Database واقعی

Unit Test نباید بدون دلیل به Database واقعی وابسته باشد.

---

## 3. وابستگی به API خارجی

اگر هدف Test کردن یک Service داخلی است، معمولاً نباید هر Test یک API خارجی واقعی را فراخوانی کند.

---

## 4. Mock کردن همه چیز

اگر تمام Dependencyها Mock شوند، ممکن است Test دیگر رفتار واقعی سیستم را به خوبی بررسی نکند.

---

## 5. نادیده گرفتن Error

فقط Success Case را Test نکنید.

---

## 6. نادیده گرفتن Edge Case

مواردی مثل:

```text
0
null
undefined
empty
negative
maximum
```

بسته به Domain باید بررسی شوند.

---

## 7. Testهای وابسته به ترتیب اجرا

نباید فرض کنیم:

```text
Test A
```

حتماً قبل از:

```text
Test B
```

اجرا می‌شود.

---

## 8. استفاده از داده مشترک Mutable

اگر چند Test یک Object مشترک را تغییر دهند، ممکن است نتیجه Testها به یکدیگر وابسته شود.

---

## 9. Test کردن Implementation جزئی

اگر Test بیش از حد به جزئیات داخلی وابسته باشد، هر Refactor ساده می‌تواند Test را خراب کند.

---

## 10. Assertion کم

Testی که فقط Function را اجرا کند ولی نتیجه را بررسی نکند، ارزش محدودی دارد.

بد:

```javascript
calculateTotal(100, 2);
```

بهتر:

```javascript
expect(calculateTotal(100, 2)).toBe(200);
```

# نکات حرفه‌ای

## 1. Unit را کوچک نگه دارید

هرچه Unit ساده‌تر و مستقل‌تر باشد، Test کردن آن راحت‌تر است.

---

## 2. رفتار را Test کنید

تا حد امکان Test را بر اساس رفتار مورد انتظار بنویسید، نه Implementation داخلی.

---

## 3. Testها را خوانا بنویسید

Test Code هم بخشی از Codebase است و باید کیفیت مناسبی داشته باشد.

---

## 4. Testهای سریع ایجاد کنید

Unit Test باید تا حد امکان سریع اجرا شود تا Developer بتواند مرتب آن را اجرا کند.

---

## 5. Dependency Injection را جدی بگیرید

طراحی مناسب Dependencyها باعث می‌شود Unit Test ساده‌تر شود.

---

## 6. Testهای Deterministic بنویسید

Test نباید به شکل تصادفی یک بار PASS و بار دیگر FAIL شود.

---

## 7. زمان را کنترل کنید

اگر Function به زمان فعلی وابسته است، بهتر است زمان را قابل کنترل کنید.

بد:

```javascript
new Date();
```

در هر Test ممکن است نتیجه متفاوت شود.

بهتر است Time Dependency قابل تزریق یا Mock باشد.

---

## 8. Randomness را کنترل کنید

اگر Application از Random Number استفاده می‌کند، در Test بهتر است نتیجه قابل پیش‌بینی باشد.

---

## 9. Testهای Bug را نگه دارید

هر Bug مهم می‌تواند به یک Regression Test تبدیل شود.

---

## 10. Unit Test جای Integration Test را نمی‌گیرد

Unit Test بسیار مهم است، اما به تنهایی کافی نیست.

برای بررسی تعامل واقعی اجزای Application به Integration Test نیز نیاز داریم.

# جمع‌بندی فصل

Unit Test یکی از مهم‌ترین ابزارهای توسعه حرفه‌ای Node.js است.

در این فصل یاد گرفتیم:

```text
Unit چیست؟
Unit Test چیست؟
Assertion چیست؟
Arrange / Act / Assert
Test کردن Function
Test کردن Class
Test کردن Module
Test کردن Array
Test کردن Object
Test کردن Async Code
Test کردن Error
Edge Case
Branch Testing
Mock
Stub
Spy
Dependency Injection
Test Isolation
Code Coverage
Refactoring
```

مهم‌ترین اصل Unit Test این است:

> یک بخش کوچک از برنامه را تا حد امکان مستقل، سریع و قابل پیش‌بینی Test کنیم.

یک Unit Test خوب باید:

```text
سریع
خوانا
مستقل
قابل تکرار
قابل اعتماد
```

باشد.

در پروژه‌های واقعی Node.js، Unit Testها معمولاً بخش بزرگی از مجموعه Testهای پروژه را تشکیل می‌دهند و به Developer اجازه می‌دهند منطق برنامه را با سرعت بالا بررسی و Refactor کند.

اما Unit Test به تنهایی کافی نیست. حتی اگر تمام Serviceها و Functionهای برنامه را جداگانه Test کنیم، هنوز ممکن است ارتباط واقعی بین آنها مشکل داشته باشد.

به همین دلیل در ادامه مسیر Testing باید به سراغ **Integration Test** برویم؛ جایی که چند بخش واقعی Application را در کنار یکدیگر بررسی می‌کنیم.
