# فصل 134 - CI/CD

## مقدمه

تا اینجا یاد گرفتیم چگونه یک پروژه Node.js را توسعه دهیم، تست کنیم، با Docker بسته‌بندی کنیم و با Docker Compose چند سرویس را در کنار یکدیگر اجرا کنیم.

اما در یک پروژه واقعی، یک سؤال مهم مطرح می‌شود:

> وقتی کد جدید را به Git Push می‌کنیم، چه کسی باید تست‌ها را اجرا کند؟ Docker Image را بسازد؟ خطاها را بررسی کند؟ و در نهایت برنامه را Deploy کند؟

اگر تمام این کارها را دستی انجام دهیم، احتمال خطای انسانی زیاد می‌شود و با بزرگ‌تر شدن پروژه، زمان زیادی نیز صرف کارهای تکراری خواهد شد.

اینجاست که مفهوم **CI/CD** وارد می‌شود.

CI/CD مجموعه‌ای از روش‌ها و فرآیندها برای خودکارسازی بخش‌هایی از چرخه توسعه نرم‌افزار است.

یک Pipeline ساده می‌تواند چنین شکلی داشته باشد:

```text
Developer
   │
   ▼
git push
   │
   ▼
CI Pipeline
   │
   ├── Install Dependencies
   ├── Lint
   ├── Test
   ├── Build
   └── Security Checks
          │
          ▼
      Docker Image
          │
          ▼
       Deploy
```

هدف این فصل این نیست که فقط چند فایل CI را حفظ کنیم؛ بلکه باید بفهمیم **CI/CD چیست، چرا استفاده می‌شود، Pipeline چگونه کار می‌کند و چگونه یک پروژه Node.js واقعی را وارد این فرآیند کنیم.**

---

# 1. CI/CD چیست؟

CI/CD معمولاً به دو مفهوم اصلی اشاره دارد:

```text
CI = Continuous Integration
CD = Continuous Delivery / Continuous Deployment
```

### Continuous Integration

یعنی تغییرات کوچک و مکرر توسعه‌دهندگان به صورت خودکار وارد فرآیند Build و Test شوند.

### Continuous Delivery

یعنی نرم‌افزار همیشه در شرایطی باشد که بتوان آن را با فرآیندی قابل‌اعتماد Deploy کرد.

### Continuous Deployment

یعنی تغییرات تأییدشده بتوانند به صورت خودکار تا محیط Production نیز Deploy شوند.

---

# 2. Continuous Integration چیست؟

در CI، هر بار که تغییری به Repository ارسال می‌کنیم، Pipeline می‌تواند کارهایی مانند:

* نصب Dependencyها
* اجرای Linter
* اجرای Test
* بررسی Build
* بررسی Security
* تولید Artifact

را انجام دهد.

مثلاً:

```text
git push
   ↓
Install
   ↓
Lint
   ↓
Test
   ↓
Build
```

اگر Test شکست بخورد:

```text
Pipeline ❌
```

و معمولاً اجازه ادامه فرآیند را نمی‌دهیم.

---

# 3. چرا CI مهم است؟

فرض کنید یک پروژه Node.js داریم و چند توسعه‌دهنده روی آن کار می‌کنند.

اگر هر شخص فقط بگوید:

> روی سیستم من درست کار می‌کند.

این روش قابل اعتماد نیست.

CI باعث می‌شود یک محیط استاندارد داشته باشیم که تغییرات را بررسی کند.

مثلاً:

```text
Developer A → Push
Developer B → Push
Developer C → Pull Request

             ↓

          CI Server

             ↓

       Tests + Build
```

در نتیجه قبل از Merge شدن کد می‌توانیم مشکلات زیادی را پیدا کنیم.

---

# 4. Continuous Delivery چیست؟

در Continuous Delivery هدف این است که Application بعد از عبور از Pipeline در وضعیتی قرار داشته باشد که بتوان آن را Deploy کرد.

مثلاً:

```text
Code
 ↓
Test
 ↓
Build
 ↓
Package
 ↓
Ready to Deploy
```

اما Deployment ممکن است هنوز به تأیید انسان نیاز داشته باشد.

مثلاً:

```text
CI
 ↓
Build
 ↓
Test
 ↓
Production Ready
 ↓
Manual Approval
 ↓
Deploy
```

---

# 5. Continuous Deployment چیست؟

در Continuous Deployment مرحله Deploy نیز به صورت خودکار انجام می‌شود.

مثلاً:

```text
git push
   ↓
Test
   ↓
Build
   ↓
Docker Image
   ↓
Deploy
   ↓
Production
```

در این مدل اگر تغییرات تمام مراحل موردنظر را با موفقیت پشت سر بگذارند، سیستم به صورت خودکار Deploy می‌شود.

---

# 6. تفاوت Delivery و Deployment

تفاوت اصلی:

```text
Continuous Delivery
        ↓
Deploy آماده است
        ↓
ممکن است تأیید دستی نیاز باشد
```

اما:

```text
Continuous Deployment
        ↓
Deploy به صورت خودکار انجام می‌شود
```

این تفاوت در طراحی Pipelineهای Production اهمیت زیادی دارد.

---

# 7. Pipeline چیست؟

Pipeline مجموعه‌ای از مراحل خودکار است که روی Code اجرا می‌شوند.

مثلاً:

```text
Pipeline
│
├── Checkout
├── Install
├── Lint
├── Test
├── Build
├── Security Scan
└── Deploy
```

هر مرحله می‌تواند یک یا چند Command اجرا کند.

---

# 8. Stage چیست؟

Pipeline معمولاً به چند Stage تقسیم می‌شود.

مثلاً:

```text
Stage 1 → Test
Stage 2 → Build
Stage 3 → Deploy
```

برای یک پروژه Node.js:

```text
Test
│
├── npm ci
├── npm run lint
└── npm test

Build
│
└── docker build

Deploy
│
└── deploy application
```

---

# 9. Job چیست؟

در بسیاری از سیستم‌های CI/CD، Pipeline از Jobها تشکیل می‌شود.

مثلاً:

```text
Pipeline
│
├── lint
├── test
├── build
└── deploy
```

هر Job می‌تواند روی یک محیط اجرایی جداگانه اجرا شود.

---

# 10. Runner چیست؟

Runner محیطی است که Jobهای CI را اجرا می‌کند.

مثلاً:

```text
Git Repository
      │
      ▼
CI System
      │
      ▼
Runner
      │
      ├── Node.js
      ├── npm
      ├── Docker
      └── Test
```

Runner می‌تواند:

* Hosted
* Self-hosted

باشد.

---

# 11. Hosted Runner

در Hosted Runner، Provider محیط اجرای CI را در اختیار ما قرار می‌دهد.

مزایا:

* Setup ساده‌تر
* Maintenance کمتر
* شروع سریع

معایب:

* محدودیت‌های Provider
* هزینه در بعضی شرایط
* کنترل کمتر نسبت به Self-hosted

---

# 12. Self-hosted Runner

در Self-hosted Runner، خودمان سیستم اجرای Pipeline را مدیریت می‌کنیم.

مزایا:

* کنترل بیشتر
* امکان تنظیم Environment اختصاصی
* دسترسی به منابع داخلی

معایب:

* Maintenance
* Security
* Updates
* Monitoring

مسئولیت بیشتری ایجاد می‌کند.

---

# 13. Git و CI/CD

CI/CD معمولاً به Git Repository متصل است.

مثلاً:

```text
git push
    ↓
Repository
    ↓
Webhook / Event
    ↓
CI Pipeline
```

در نتیجه Git نقش مهمی در Trigger کردن Pipeline دارد.

---

# 14. Trigger چیست؟

Trigger مشخص می‌کند Pipeline چه زمانی اجرا شود.

مثلاً:

* Push
* Pull Request
* Merge
* Tag
* Schedule
* Manual Trigger

مثلاً:

```text
Push → Run CI
```

یا:

```text
Pull Request → Run Tests
```

---

# 15. CI روی Pull Request

یکی از مهم‌ترین کاربردهای CI اجرای آن روی Pull Request است.

مثلاً:

```text
Feature Branch
      │
      ▼
Pull Request
      │
      ▼
CI
      │
      ├── Lint
      ├── Test
      └── Build
```

اگر CI موفق باشد:

```text
✅ Ready to Review
```

و اگر شکست بخورد:

```text
❌ Fix Required
```

---

# 16. Branch Protection

در Repositoryهای حرفه‌ای می‌توان قوانینی تعریف کرد که مثلاً:

> بدون موفق شدن CI اجازه Merge داده نشود.

مثلاً:

```text
Pull Request
      │
      ▼
CI ❌
      │
      ▼
Merge Blocked
```

یا:

```text
Pull Request
      │
      ▼
CI ✅
      │
      ▼
Merge Allowed
```

---

# 17. اولین CI برای پروژه Node.js

فرض کنیم `package.json` ما شامل این Scriptها است:

```json
{
  "scripts": {
    "test": "node --test",
    "lint": "eslint ."
  }
}
```

یک Pipeline ساده باید حداقل بتواند:

```bash
npm ci
npm run lint
npm test
```

را اجرا کند.

---

# 18. چرا npm ci؟

در CI معمولاً بهتر است از:

```bash
npm ci
```

استفاده کنیم.

این دستور بر اساس Lockfile نصب Dependencyها را انجام می‌دهد.

در پروژه‌ای که:

```text
package-lock.json
```

دارد، این روش برای محیط‌های CI مناسب است.

در نتیجه بهتر است در CI معمولاً:

```bash
npm ci
```

را به:

```bash
npm install
```

ترجیح دهیم.

---

# 19. اهمیت Lockfile

فایل:

```text
package-lock.json
```

باعث می‌شود نسخه Dependencyهای نصب‌شده قابل پیش‌بینی‌تر باشند.

مثلاً:

```text
Developer
   ↓
package-lock.json
   ↓
CI
   ↓
همان Dependency Tree
```

این موضوع برای Reproducible Build اهمیت زیادی دارد.

---

# 20. CI باید چه چیزهایی را بررسی کند؟

برای یک پروژه Node.js می‌توانیم Pipeline را با این مراحل شروع کنیم:

```text

   ↓
Node.js Setup
   ↓
npm ci
   ↓
Lint
   ↓
Test
   ↓
Build
```

و در پروژه‌های جدی‌تر:

```text

Dependency Audit
Container Scan
Integration Tests
E2E Tests
```

را نیز اضافه کنیم.

---

# 21. Artifact چیست؟

Artifact خروجی تولیدشده توسط Pipeline است.

مثلاً:

```text
dist/
coverage/
build/
test-results/
Docker Image
```

در پروژه Node.js ممکن است Artifact شامل:

```text
dist/
```

باشد.

---

# 22. Artifact و Cache

Artifact و Cache یکی نیستند.

### Artifact

خروجی Pipeline است که می‌تواند برای مراحل بعدی یا دریافت توسط کاربر ذخیره شود.

### Cache

برای سریع‌تر کردن فرآیندهایی مانند نصب Dependencyها استفاده می‌شود.

به شکل ساده:

```text
Artifact
→ Output

Cache
→ Speed
```

---

# 23. Cache در CI

فرض کنیم npm Dependencyهای زیادی دارد.

هر Pipeline مجبور نیست همه چیز را از صفر دانلود کند.

می‌توان Cache ایجاد کرد:

```text
Pipeline 1
   ↓
Download Dependencies
   ↓
Cache

Pipeline 2
   ↓
Reuse Cache
   ↓
Faster
```

اما Cache نباید جایگزین `package-lock.json` و نصب قابل‌تکرار شود.

# 29. CI و Docker

Docker می‌تواند در Pipeline نقش مهمی داشته باشد.

مثلاً:

```text

 ↓

 ↓
Tests
 ↓

 ↓
```

# 30. Docker Image در CI

فرض کنیم Dockerfile داریم:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

CMD ["node", "src/server.js"]
```

Pipeline می‌تواند:

```bash
docker build -t my-node-app .
```

را اجرا کند.

---

# 31. Tag کردن Docker Image

بهتر است Imageها Tag مشخص داشته باشند.

مثلاً:

```text
my-node-app:1.0.0
```

یا:

```text
my-node-app:abc123
```

که `abc123` می‌تواند Commit SHA باشد.

---

# 32. چرا استفاده از Commit SHA مفید است؟

فرض کنید:

```text

```

داریم.

می‌توانیم بفهمیم هر Image از کدام Commit ساخته شده است.

این موضوع برای:

* Debugging
* Rollback
* Traceability

بسیار مهم است.

# 34. Deploy چیست؟

Deploy یعنی انتشار نسخه جدید Application در یک Environment.

مثلاً:

```text
Docker Image
     ↓
Server
     ↓
Container
     ↓
```

# 35. Deployment Strategy

روش‌های مختلفی برای Deployment وجود دارد.

از جمله:

* Rolling Deployment
* Blue-Green Deployment
* Canary Deployment
* Recreate Deployment

در پروژه‌های مختلف با توجه به Architecture انتخاب می‌شوند.

---

# 36. Rolling Deployment

در Rolling Deployment نسخه جدید به تدریج جایگزین نسخه قبلی می‌شود.

مثلاً:

```text
v1 v1 v1 v1

   ↓

v2 v1 v1 v1

   ↓

v2 v2 v1 v1

   ↓

v2 v2 v2 v2
```

هدف کاهش Downtime و ریسک Deployment است.

---

# 37. Blue-Green Deployment

دو محیط داریم:

```text
Blue → Current
Green → New
```

نسخه جدید در Green اجرا می‌شود.

پس از بررسی:

```text
Traffic
   ↓
Green
```

منتقل می‌شود.

اگر مشکلی ایجاد شد، می‌توان Traffic را به Blue برگرداند.

---

# 38. Canary Deployment

در Canary Deployment ابتدا درصد کوچکی از Traffic به نسخه جدید می‌رود.

مثلاً:

```text
95% → v1
5%  → v2
```

اگر وضعیت مناسب بود:

```text
80% → v1
20% → v2
```

و سپس به تدریج نسخه جدید جایگزین می‌شود.

---

# 39. Rollback

اگر Deployment جدید مشکل داشته باشد باید بتوانیم به نسخه قبلی برگردیم.

مثلاً:

```text
v1 → Stable

Deploy v2

v2 → ❌

Rollback

v1 → Stable
```

به همین دلیل Versioning و Immutable Artifactها بسیار مهم هستند.

---

# 40. CI/CD و تست

Pipeline نباید فقط Build کند.

باید تا جای ممکن کیفیت Code را نیز بررسی کند.

مثلاً:

```text
Lint
 ↓
Unit Test
 ↓
Integration Test
 ↓
E2E Test
 ↓
Build
```

هر مرحله می‌تواند از ادامه Pipeline در صورت شکست جلوگیری کند.

---

# 41. Unit Test در CI

Unit Testها معمولاً سریع هستند.

مثلاً:

```bash
npm test
```

و می‌توانند در هر Pull Request اجرا شوند.

---

# 42. Integration Test در CI

Integration Test برای بررسی ارتباط چند Component استفاده می‌شود.

مثلاً:

```text
Node.js
   ↓
PostgreSQL
```

در این حالت Docker Compose می‌تواند برای ایجاد محیط تست بسیار مفید باشد.

---

# 43. E2E Test در CI

E2E کل جریان Application را بررسی می‌کند.

مثلاً:

```text
Client
 ↓
HTTP Request
 ↓
Node.js
 ↓
Database
 ↓
Response
```

این تست‌ها معمولاً از Unit Testها سنگین‌تر هستند.

---

# 44. Quality Gate

Quality Gate مجموعه‌ای از شرط‌هاست که باید قبل از ادامه Pipeline برقرار باشند.

مثلاً:

```text
Lint       ✅
Unit Test  ✅
Coverage   ✅
Security   ✅
Build      ✅
```

اگر یکی از آن‌ها شکست بخورد:

```text
Pipeline ❌
```

---

# 45. Coverage در CI

می‌توان Coverage تست‌ها را نیز بررسی کرد.

مثلاً:

```text
Statements: 92%
Branches:   84%
Functions:  90%
Lines:      93%
```

می‌توان حداقل Coverage تعریف کرد.

مثلاً:

```text
Coverage >= 80%
```

# 46. Security در CI

Security باید بخشی از Pipeline باشد.

برای پروژه Node.js می‌توان بررسی‌هایی مانند:

```bash
npm audit
```

را در نظر گرفت.

همچنین در پروژه‌های Docker می‌توان Container Image را نیز Scan کرد.

# 47. Dependency Security

Dependencyهای پروژه ممکن است Vulnerability داشته باشند.

Pipeline می‌تواند به صورت خودکار آن‌ها را بررسی کند.

مثلاً:

```text
npm dependencies
       ↓
Security Scan
       ↓
Vulnerability
       ↓
Pipeline Result
```

# 48. CI/CD و Monorepo

در پروژه‌های Monorepo ممکن است چند Application و Package داشته باشیم:

```text
apps/
├── api/
├── worker/
└── frontend/

packages/
├── shared/
└── config/
```

# 51. GitHub Actions

# 52. اولین GitHub Actions Workflow

فایل:

```text
.github/workflows/ci.yml
```

مثلاً:

```yaml
name: CI

on:
  push:
    branches:
      - main

  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test
```

این Workflow روی Push به `main` و Pull Request اجرا می‌شود.

# 71. Flaky Test

Flaky Test تستی است که بدون تغییر Code گاهی Pass و گاهی Fail می‌شود.

مثلاً:

```text
Run 1 → PASS
Run 2 → FAIL
Run 3 → PASS
```

Flaky Test در CI بسیار خطرناک است، زیرا اعتماد تیم به Pipeline را کاهش می‌دهد.

---

# 72. Idempotency

یکی از مفاهیم مهم در Automation این است که اجرای دوباره یک عملیات نباید باعث وضعیت خراب یا غیرقابل‌پیش‌بینی شود.

مثلاً Deployment باید تا حد امکان قابل تکرار باشد.

```text
Deploy
Deploy
Deploy
```

نباید هر بار نتیجه غیرقابل پیش‌بینی ایجاد کند.

# 73. Reproducible Build

```text
Same Dependencies

=
Predictable Result
```

برای این موضوع:

* Lockfile
* Version Pinning
* Docker
* CI Environment

بسیار مهم هستند.

# 76. اشتباهات رایج

## اشتباه ۱ - اجرای فقط Build

در پروژه‌هایی که Lockfile دارند، `npm ci` معمولاً انتخاب مناسب‌تری برای نصب قابل‌تکرار است.

---

## اشتباه ۴ - استفاده از Node.js Version متفاوت

اگر Local روی Node.js 24 باشد ولی CI روی نسخه دیگری اجرا شود، ممکن است رفتار متفاوت باشد.

## اشتباه ۵ - Deploy بدون Test

این الگو خطرناک است:

```text

 ↓
```

```text

 ↓

 ↓
Build
 ↓
```

داشته باشیم.

## اشتباه ۶ - نداشتن Rollback

اگر نسخه جدید خراب شود و هیچ راه برگشتی نداشته باشیم، Recovery دشوار می‌شود.

---

## اشتباه ۷ - اعتماد به یک Pipeline سبز بدون بررسی کیفیت آن

سبز بودن CI لزوماً به معنی بدون Bug بودن Application نیست.

Test Coverage، Integration Test، Security و Monitoring نیز اهمیت دارند.

---

## اشتباه ۸ - اجرای Testهای وابسته به Database بدون آماده‌سازی Database

اگر Test به PostgreSQL نیاز دارد، باید قبل از Test محیط مناسب را ایجاد کنیم.

---

## اشتباه ۹ - استفاده از Secretهای یکسان در همه Environmentها

Development، Staging و Production باید Credentialهای مناسب خودشان را داشته باشند.

---

## اشتباه ۱۰ - Pipeline بیش از حد طولانی

Pipeline بسیار کند باعث می‌شود توسعه‌دهندگان کمتر منتظر نتیجه CI بمانند.

باید مراحل را بهینه کنیم.

---

## اشتباه ۱۱ - نداشتن Cache مناسب

در پروژه‌های بزرگ، نصب Dependencyها در هر اجرا می‌تواند زمان Pipeline را افزایش دهد.

---

## اشتباه ۱۲ - استفاده از `latest` برای Production Image

Tagهای متحرک باعث کاهش Traceability می‌شوند.

Version یا Commit SHA معمولاً انتخاب بهتری است.

---

## اشتباه ۱۳ - نداشتن Health Check بعد از Deploy

ممکن است Deployment ظاهراً موفق باشد ولی Application واقعاً سالم نباشد.

---

## اشتباه ۱۴ - نادیده گرفتن Flaky Testها

تست‌های ناپایدار به مرور اعتماد تیم به CI را از بین می‌برند.

---

## اشتباه ۱۵ - Deploy مستقیم از سیستم شخصی

Deploy دستی از لپ‌تاپ توسعه‌دهنده باعث می‌شود فرآیند قابل تکرار و قابل ردیابی نباشد.

# 77. نکات حرفه‌ای

# 83. مرحله دوم - Application

یک HTTP Server ساده ایجاد کنید:

```javascript
const http = require("node:http");

const PORT = process.env.PORT || 3000;

const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "application/json");

  if (req.url === "/health") {
    res.writeHead(200);

    return res.end(
      JSON.stringify({
        status: "ok",
      }),
    );
  }

  res.writeHead(200);

  return res.end(
    JSON.stringify({
      message: "CI/CD Project",
    }),
  );
});

server.listen(PORT, "0.0.0.0");
```

# 87. مرحله ششم - GitHub Actions


```yaml
name: CI

on:
  push:
    branches:
      - main

  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 24
          cache: npm

      - name: Run tests
```

# 93. جمع‌بندی

CI/CD یکی از مهم‌ترین بخش‌های توسعه نرم‌افزار حرفه‌ای است.

در یک پروژه ساده ممکن است Deployment دستی قابل‌قبول باشد، اما با رشد پروژه، تعداد توسعه‌دهندگان و تعداد Releaseها، Automation اهمیت بسیار بیشتری پیدا می‌کند.

در این فصل مفاهیم زیر را یاد گرفتیم:

```text
CI
CD
Continuous Integration
Continuous Delivery
Continuous Deployment
Pipeline
Stage
Job
Runner
Trigger
Artifact
Cache
Secret
Environment
Quality Gate
Health Check
Smoke Test
Rollback
Staging
Production
Docker Build
Container Registry
GitHub Actions
```

یک Pipeline ساده Node.js می‌تواند:

```text
git push
   ↓
CI
   ↓
npm ci
   ↓
Lint
   ↓
Test
   ↓
Build
   ↓
Docker Image
   ↓
Deploy
   ↓
Health Check
```

باشد.

و یک Pipeline حرفه‌ای‌تر می‌تواند به شکل زیر تکامل پیدا کند:

```text
Pull Request
      ↓
Lint
      ↓
Unit Test
      ↓
Integration Test
      ↓
Security Scan
      ↓
Build
      ↓
Docker Image
      ↓
Registry
      ↓
Staging
      ↓
Smoke Test
      ↓
Approval
      ↓
Production
      ↓
Monitoring
      ↓

```

مهم‌ترین نکته این فصل این است که **CI/CD فقط یک ابزار نیست**؛ بلکه یک روش برای ساخت فرآیند قابل‌اعتماد، قابل‌تکرار و خودکار برای تحویل نرم‌افزار است.
