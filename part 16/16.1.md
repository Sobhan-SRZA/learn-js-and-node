# فصل 126 - Git

## مقدمه

وقتی وارد دنیای برنامه‌نویسی می‌شویم، فقط نوشتن کد مهم نیست؛ بلکه باید بتوانیم **تغییرات کد را مدیریت کنیم، نسخه‌های مختلف پروژه را نگه داریم، اشتباهات را برگردانیم و با دیگر برنامه‌نویسان همکاری کنیم**.

در پروژه‌های کوچک ممکن است بتوانیم فایل‌ها را به‌صورت دستی کپی کنیم و نسخه‌های مختلف را نگه داریم، اما در پروژه‌های واقعی این روش خیلی سریع به مشکل می‌خورد.

برای مثال ممکن است پوشه‌هایی مانند این داشته باشیم:

```text
project/
project-final/
project-final-2/
project-final-new/
project-final-new-real/
project-final-new-real-last/
```

این روش نه‌تنها حرفه‌ای نیست، بلکه در پروژه‌های بزرگ تقریباً غیرقابل استفاده است.

اینجاست که **Git** وارد می‌شود.

Git یک **Version Control System** یا سیستم کنترل نسخه است که به ما اجازه می‌دهد تاریخچه تغییرات پروژه را مدیریت کنیم.

در این فصل Git را از پایه یاد می‌گیریم و هم‌زمان آن را در پروژه‌های Node.js استفاده می‌کنیم.

هدف این فصل این است که در پایان بتوانید:

* Git را نصب کنید.
* یک Repository بسازید.
* فایل‌های پروژه را مدیریت کنید.
* تغییرات را مشاهده کنید.
* Commit ایجاد کنید.
* تغییرات را برگردانید.
* Branch بسازید.
* Branchها را ادغام کنید.
* Conflict را حل کنید.
* پروژه را به Git مجهز کنید.
* فایل‌های غیرضروری را با `.gitignore` نادیده بگیرید.
* تاریخچه پروژه را بررسی کنید.
* با Git در پروژه‌های Node.js کار کنید.
* یک Workflow حرفه‌ای برای مدیریت کد داشته باشید.

---

# 126.1 - Git چیست؟

Git یک سیستم کنترل نسخه توزیع‌شده یا **Distributed Version Control System (DVCS)** است.

Git به ما کمک می‌کند تغییرات فایل‌های پروژه را در طول زمان ثبت کنیم.

به‌جای اینکه فقط آخرین نسخه پروژه را داشته باشیم، Git تاریخچه‌ای از تغییرات پروژه نگه می‌دارد.

برای مثال:

```text
Project Started
      ↓
Create package.json
      ↓
Create server.js
      ↓
Add HTTP Server
      ↓
Add Routing
      ↓
Fix Authentication
      ↓
Add Database
```

هر مرحله می‌تواند در Git ثبت شود.

---

# 126.2 - چرا Git مهم است؟

فرض کنید در حال ساخت یک API با Node.js هستیم.

امروز کد زیر را داریم:

```js
const http = require("node:http");

const server = http.createServer((req, res) => {
  res.end("Hello");
});

server.listen(3000);
```

فردا آن را تغییر می‌دهیم و قابلیت جدیدی اضافه می‌کنیم.

اگر تغییر جدید باعث خراب شدن پروژه شود، ممکن است بخواهیم به نسخه قبلی برگردیم.

بدون Git انجام این کار می‌تواند سخت باشد.

اما با Git می‌توانیم تاریخچه تغییرات را داشته باشیم.

---

# 126.3 - Git چه مشکلاتی را حل می‌کند؟

Git مشکلات زیادی را حل می‌کند.

مهم‌ترین آن‌ها:

* نگهداری تاریخچه پروژه
* بازگشت به نسخه قبلی
* بررسی تغییرات
* همکاری چند برنامه‌نویس
* ایجاد Branch
* آزمایش قابلیت‌های جدید بدون خراب کردن نسخه اصلی
* ادغام تغییرات
* بررسی اینکه چه کسی چه تغییری ایجاد کرده است
* مدیریت نسخه‌های مختلف پروژه

---

# 126.4 - Git و GitHub چه تفاوتی دارند؟

این دو مفهوم بسیار مهم هستند.

**Git** یک ابزار کنترل نسخه است.

**GitHub** یک سرویس آنلاین برای میزبانی Repositoryهای Git و همکاری روی پروژه‌ها است.

به زبان ساده:

```text
Git
│
├── Version Control
├── Commit
├── Branch
├── Merge
└── History
```

در مقابل:

```text
GitHub
│
├── Remote Repository
├── Pull Request
├── Issues
├── Code Review
└── Collaboration
```

بنابراین Git و GitHub یکی نیستند.

می‌توانیم بدون GitHub از Git استفاده کنیم.


# 126.7 - Repository چیست؟

Repository یا به اختصار **Repo** محل نگهداری پروژه‌ای است که Git آن را مدیریت می‌کند.

برای مثال:

```text
my-node-app/
```

می‌تواند یک Repository باشد.

برای تبدیل یک پروژه به Git Repository:

```bash
git init
```

بعد از اجرای این دستور، Git یک پوشه مخفی به نام `.git` ایجاد می‌کند.

ساختار پروژه:

```text
my-node-app/
├── .git/
├── package.json
├── package-lock.json
└── server.js
```

پوشه `.git` اطلاعات مربوط به Repository را نگهداری می‌کند.

**نباید این پوشه را به‌صورت دستی تغییر دهیم.**

# 126.11 - Staging Area

Git یک مرحله میانی به نام **Staging Area** دارد.

فرآیند کلی به شکل زیر است:

```text
Working Directory
        ↓
   git add
        ↓
Staging Area
        ↓
  git commit
        ↓
Repository
```

این مفهوم یکی از مهم‌ترین مفاهیم Git است.

---

# 126.12 - اضافه کردن فایل به Staging

برای اضافه کردن یک فایل:

```bash
git add server.js
```

برای اضافه کردن چند فایل:

```bash
git add server.js package.json
```

برای اضافه کردن تمام فایل‌های تغییرکرده:

```bash
git add .
```

بعد:

```bash
git status
```

فایل‌ها در قسمت Staged Changes نمایش داده می‌شوند.

# 126.13 - Commit چیست؟

Commit یک Snapshot از وضعیت پروژه در یک لحظه مشخص است.

به زبان ساده:

> Commit یعنی ثبت یک مرحله مشخص از تاریخچه پروژه.

برای ایجاد Commit:

```bash
git commit -m "Create Node.js server"
```

پیام Commit باید توضیح دهد چه تغییری ایجاد شده است.

مثلاً:

```bash
git commit -m "Add user authentication"
```

یا:

```bash
git commit -m "Fix login validation"
```

---

# 126.14 - Commit خوب چه ویژگی‌هایی دارد؟

پیام Commit باید:

* واضح باشد.
* کوتاه باشد.
* دقیق باشد.
* تغییر انجام‌شده را توضیح دهد.

بد:

```bash
git commit -m "update"
```

بهتر:

```bash
git commit -m "Add user registration endpoint"
```

یا:

```bash
git commit -m "Fix password validation"
```

# 126.19 - Untracked File چیست؟

اگر فایلی ایجاد کنیم:

```bash
test.js
```

و هنوز آن را به Git اضافه نکرده باشیم، Git آن را به‌عنوان:

```text
Untracked
```

نمایش می‌دهد.

برای اضافه کردن:

```bash

```

---

# 126.20 - حذف فایل از Staging

فرض کنید این دستور را اجرا کرده‌ایم:

```bash
git add .
```

اما نمی‌خواهیم `test.js` در Commit قرار بگیرد.

می‌توانیم آن را از Staging خارج کنیم:

```bash
git restore --staged test.js
```

این دستور فایل را حذف نمی‌کند؛ فقط آن را از Staging خارج می‌کند.

---

# 126.21 - اصلاح آخرین Commit

اگر Commit ایجاد کرده‌ایم اما می‌خواهیم تغییر جدیدی به همان Commit اضافه کنیم:

```bash
git add .
```

سپس:

```bash
git commit --amend
```

برای تغییر پیام Commit نیز می‌توانیم استفاده کنیم:

```bash
git commit --amend -m "Better commit message"
```

باید در استفاده از `--amend` مخصوصاً روی Commitهایی که قبلاً به Repository مشترک Push شده‌اند، احتیاط کنیم.

---

# 126.22 - حذف تغییرات فایل

اگر تغییراتی ایجاد کرده‌ایم و هنوز Commit نکرده‌ایم، برای برگرداندن تغییرات یک فایل می‌توانیم از:

```bash
git restore server.js
```

استفاده کنیم.

**هشدار:**

این کار تغییرات محلی آن فایل را از بین می‌برد.

پس قبل از استفاده باید مطمئن باشیم که تغییرات را نیاز نداریم.

# 126.23 - Branch چیست؟

Branch یکی از مهم‌ترین قابلیت‌های Git است.

Branch به ما اجازه می‌دهد روی یک مسیر مستقل از پروژه کار کنیم.

مثلاً:

```text
main
 │
 ├── login
 │
 ├── payment
 │
 └── profile
```

می‌توانیم قابلیت Login را در Branch جداگانه توسعه دهیم.

---

برای مشاهده Branchهای موجود:

```bash
git branch
```

Branch فعلی با `*` مشخص می‌شود.

مثلاً:

```text
* main
```

# 126.25 - ساخت Branch

برای ساخت Branch:

```bash
git branch feature/login
```

اما این دستور فقط Branch را ایجاد می‌کند و وارد آن نمی‌شود.

برای جابه‌جایی:

```bash
git switch feature/login
```

یا:

```bash
git checkout feature/login
```

روش جدیدتر:

```bash
git switch
```

است.

# 126.26 - ساخت و ورود هم‌زمان به Branch

می‌توانیم با یک دستور Branch را بسازیم و وارد آن شویم:

```bash
git switch -c feature/login
```

مثلاً:

```bash
git switch -c feature/user-auth
```

# 126.27 - Naming Convention برای Branch

نام‌گذاری مناسب Branchها باعث نظم بیشتر پروژه می‌شود.

مثلاً:

# 126.28 - Merge چیست؟

فرض کنید در Branch زیر کار کرده‌ایم:

```text
feature/login
```

و قابلیت Login کامل شده است.

اکنون می‌خواهیم تغییرات آن را وارد `main` کنیم.

ابتدا:

```bash
git switch main
```

سپس:

```bash
git merge feature/login
```

Git تغییرات Branch را با `main` ادغام می‌کند.

---

# 126.29 - Merge Conflict چیست؟

گاهی Git نمی‌تواند تغییرات دو Branch را به‌صورت خودکار ادغام کند.

مثلاً در Branch اول:

```js
const message = "Hello";
```

و در Branch دیگر:

```js
const message = "Welcome";
```

اگر هر دو تغییر مربوط به یک قسمت باشند، ممکن است Conflict ایجاد شود.

Git ممکن است چیزی شبیه این ایجاد کند:

```text
<<<<<<< HEAD
const message = "Hello";
=======
const message = "Welcome";
>>>>>>> feature/message
```

برنامه‌نویس باید تصمیم بگیرد کدام نسخه باقی بماند.

---

# 126.30 - حل Merge Conflict

برای حل Conflict:

### مرحله 1

فایل Conflict شده را باز کنید.

### مرحله 2

مشخص کنید کدام تغییر باید باقی بماند.

مثلاً:

```js
const message = "Welcome";
```

### مرحله 3

علامت‌های Conflict را حذف کنید.

### مرحله 4

فایل را Stage کنید:

```bash
git add .
```

### مرحله 5

Merge را Commit کنید:

```bash
git commit
```

# 126.31 - .gitignore چیست؟

بعضی فایل‌ها نباید وارد Git شوند.

در پروژه‌های Node.js یکی از مهم‌ترین آن‌ها:

```text
node_modules
```

است.

برای مشخص کردن فایل‌هایی که Git نباید Track کند، از `.gitignore` استفاده می‌کنیم.

مثلاً:

```gitignore
node_modules/
.env
*.log
coverage/
dist/
```

# 126.32 - چرا node_modules را Commit نمی‌کنیم؟

پوشه `node_modules` می‌تواند بسیار بزرگ باشد.

در پروژه Node.js معمولاً به جای Commit کردن آن، فایل:

```text
package.json
```

و:

```text
package-lock.json
```

را Commit می‌کنیم.

سپس شخص دیگری می‌تواند وابستگی‌ها را نصب کند:

```bash
npm install
```

# 126.33 - فایل .env

فایل `.env` معمولاً می‌تواند شامل اطلاعات حساسی مانند:

```text
DATABASE_URL=...
JWT_SECRET=...
API_KEY=...
```

باشد.

به همین دلیل معمولاً باید در `.gitignore` قرار بگیرد:

```gitignore
.env
```

در عوض می‌توانیم فایلی مانند:

```text
.env.example
```

قرار دهیم:

```env
DATABASE_URL=
JWT_SECRET=
API_KEY=
```

تا مشخص شود پروژه به چه متغیرهایی نیاز دارد، بدون اینکه مقدار واقعی Secretها منتشر شود.

# 126.34 - Tag چیست؟

Tag برای علامت‌گذاری یک نقطه مشخص در تاریخچه پروژه استفاده می‌شود.

برای مثال نسخه:

```text
v1.0.0
```

را می‌توانیم Tag کنیم:

```bash
git tag v1.0.0
```

برای مشاهده Tagها:

```bash

```

---

# 126.35 - Git Reset

`git reset` برای جابه‌جایی HEAD و در برخی حالت‌ها تغییر وضعیت Staging یا تاریخچه استفاده می‌شود.

مثلاً:

```bash
git reset HEAD~1
```

می‌تواند آخرین Commit را از تاریخچه محلی خارج کند و تغییرات را نگه دارد.

استفاده از `reset` نیازمند دقت است، مخصوصاً زمانی که Commitها قبلاً با دیگران به اشتراک گذاشته شده‌اند.

---

# 126.36 - Git Revert

`git revert` برای ایجاد یک Commit جدید است که اثر یک Commit قبلی را خنثی می‌کند.

مثلاً:

```bash
git revert abc123
```

مزیت مهم آن این است که تاریخچه را به‌صورت مخرب بازنویسی نمی‌کند.

در پروژه‌های تیمی، این ویژگی اهمیت زیادی دارد.

---

# 126.37 - تفاوت Reset و Revert

به‌صورت ساده:

```text
reset
    ↓
تغییر تاریخچه

revert
    ↓
ایجاد Commit جدید برای خنثی کردن تغییر قبلی
```

برای Branchهای مشترک معمولاً باید در استفاده از دستورات بازنویسی تاریخچه بسیار محتاط باشیم.

# 126.38 - Git Stash

گاهی در حال کار روی یک قابلیت هستیم اما ناگهان باید روی تغییر دیگری کار کنیم.

می‌توانیم تغییرات فعلی را موقتاً کنار بگذاریم:

```bash

```

برای مشاهده Stashها:

```bash
git stash list
```

برای برگرداندن آخرین Stash:

```bash
git stash pop
```

# 126.43 - Atomic Commit

Atomic Commit یعنی یک Commit یک تغییر منطقی مشخص را انجام دهد.

مثلاً:

```text
Add authentication middleware
```

نباید هم‌زمان شامل موارد نامرتبط زیر باشد:

```text

Change CSS
Rename unrelated files
Update documentation
Fix another feature
```

هر تغییر منطقی بهتر است Commit مستقل داشته باشد.

# جمع‌بندی فصل

در این فصل با Git آشنا شدیم و مفاهیم اصلی کنترل نسخه را یاد گرفتیم.

```text
Git
Repository
Working Directory
Staging Area
Commit
Status
Diff
Branch
Merge
Merge Conflict
.gitignore
Tag
Reset
Revert
Stash
```

همچنین یاد گرفتیم چگونه Git را در یک پروژه Node.js استفاده کنیم.

فرآیند اصلی کار با Git را می‌توان این‌گونه خلاصه کرد:

```bash
git init
```

```bash

```

```bash
git switch main

```

Git فقط یک ابزار برای نگهداری نسخه‌های مختلف پروژه نیست؛ بلکه یکی از ابزارهای اصلی **Workflow توسعه نرم‌افزار حرفه‌ای** است.

در فصل بعد، سراغ **GitHub** می‌رویم و یاد می‌گیریم چگونه Repository خود را روی Remote قرار دهیم، پروژه را Push کنیم، Pull Request ایجاد کنیم و با دیگر برنامه‌نویسان روی یک پروژه Node.js همکاری کنیم.
