# فصل 133 - Docker Compose

## مقدمه

در فصل قبل یاد گرفتیم چگونه یک پروژه Node.js را با Docker داخل یک Container اجرا کنیم.

اما پروژه‌های واقعی Backend معمولاً فقط از یک برنامه تشکیل نشده‌اند.

برای مثال، ممکن است یک پروژه Node.js به سرویس‌های زیر نیاز داشته باشد:

```text
Node.js API
PostgreSQL
Redis
Worker
Nginx
```

اگر بخواهیم هرکدام را با دستورات جداگانه Docker اجرا کنیم، خیلی زود مدیریت پروژه پیچیده می‌شود.

مثلاً باید چندین دستور مانند:

```bash
docker run ...
docker run ...
docker run ...
```

را اجرا کنیم و برای هر سرویس:

* Container
* Port
* Environment Variable
* Volume
* Network
* Dependency

را جداگانه مدیریت کنیم.

**Docker Compose** برای حل همین مشکل ساخته شده است.

Docker Compose به ما اجازه می‌دهد چند Container را به عنوان یک Application تعریف و مدیریت کنیم.

به جای اینکه همه تنظیمات را با دستورات طولانی بنویسیم، آن‌ها را در یک فایل YAML قرار می‌دهیم.

مثلاً:

```text
docker-compose.yml
```

و سپس می‌توانیم با یک دستور کل محیط پروژه را اجرا کنیم:

```bash
docker compose up
```

---

# 1. Docker Compose چیست؟

Docker Compose ابزاری برای تعریف و اجرای برنامه‌هایی است که از چند Container تشکیل شده‌اند.

برای مثال یک پروژه Node.js می‌تواند چنین معماری داشته باشد:

```text
                    ┌──────────────┐
                    │   Node.js    │
                    │     API      │
                    └──────┬───────┘
                           │
              ┌────────────┴────────────┐
              │                         │
              ▼                         ▼
       ┌─────────────┐          ┌─────────────┐
       │ PostgreSQL  │          │    Redis    │
       └─────────────┘          └─────────────┘
```

با Docker Compose می‌توانیم تمام این سرویس‌ها را در یک فایل تعریف کنیم.

---

# 2. چرا Docker Compose لازم است؟

فرض کنید یک Backend Node.js داریم که به PostgreSQL و Redis نیاز دارد.

بدون Compose ممکن است چیزی شبیه این داشته باشیم:

```bash
docker run ...
docker run ...
docker run ...
```

و باید موارد مختلفی را خودمان تنظیم کنیم.

اما با Compose:

```bash
docker compose up
```

تمام سرویس‌های تعریف‌شده اجرا می‌شوند.

به همین دلیل Docker Compose مخصوصاً برای:

* Development
* Testing
* محیط‌های چندسرویسی
* Microservices
* Backendهای وابسته به Database
* Redis
* Message Queue

بسیار کاربردی است.

---

# 3. Docker Compose و Docker

Docker و Docker Compose جایگزین یکدیگر نیستند.

Docker مسئول اجرای Containerها است.

Docker Compose برای مدیریت چند سرویس و Container در کنار یکدیگر استفاده می‌شود.

می‌توانیم رابطه را این‌گونه تصور کنیم:

```text
Docker
│
├── Image
├── Container
├── Volume
└── Network

Docker Compose
│
├── Service 1
├── Service 2
├── Service 3
├── Network
└── Volume
```

# 4. docker compose در نسخه‌های جدید

در نسخه‌های جدید Docker معمولاً از دستور:

```bash

```

استفاده می‌کنیم.

مثلاً:

```bash

```

در برخی آموزش‌های قدیمی ممکن است با:

```bash
docker-compose
```

مواجه شوید.

این تفاوت به نسخه و نحوه نصب Docker Compose مربوط است.

در این مستند از شکل مدرن:

```bash
docker compose
```

استفاده می‌کنیم.

# 5. فایل Compose

برای تعریف Application معمولاً یک فایل با نام:

```text
compose.yaml
```

یا:

```text
docker-compose.yml
```

ایجاد می‌کنیم.

در پروژه‌های جدید `compose.yaml` یک نام رایج و مناسب است.

مثلاً:

```text

```

# 6. اولین Compose File

یک نمونه بسیار ساده:

```yaml
services:
  app:
    image: node:24
```

در اینجا یک Service به نام:

```text
app
```

داریم که از Image مربوط به Node.js استفاده می‌کند.

---

# 7. Service چیست؟

در Docker Compose هر Application Component را معمولاً به عنوان یک **Service** تعریف می‌کنیم.

مثلاً:

```yaml
services:
  app:
    ...
  
  database:
    ...
  
  redis:
    ...
```

در این مثال سه Service داریم:

```text
app
database
redis
```

هر Service معمولاً به یک Container یا مجموعه‌ای از Containerهای مرتبط منتهی می‌شود.

---

# 8. اولین پروژه Node.js با Compose

فرض کنیم پروژه ما:

```text
my-node-app/
│
├── compose.yaml
├── Dockerfile
├── package.json
├── package-lock.json
└── server.js
```

باشد.

Dockerfile:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 3000

CMD ["node", "server.js"]
```

---

# 9. compose.yaml

اکنون:

```yaml
services:
  app:
    build: .
    ports:
      - "3000:3000"
```

در اینجا به Compose گفته‌ایم:

* یک Service به نام `app` بساز.
* Image را از Dockerfile پروژه Build کن.
* Port 3000 را Publish کن.

---

# 10. اجرای Compose

در پوشه پروژه:

```bash
docker compose up
```

Compose:

1. فایل Compose را می‌خواند.
2. Image موردنیاز را Build می‌کند.
3. Container را ایجاد می‌کند.
4. Network لازم را ایجاد می‌کند.
5. سرویس را اجرا می‌کند.

# 14. توقف Compose

برای توقف سرویس‌ها:

```bash
docker compose stop
```

این دستور Containerها را متوقف می‌کند ولی آن‌ها را حذف نمی‌کند.

---

# 15. خاموش کردن Application

برای متوقف کردن و حذف منابع ایجادشده توسط Compose:

```bash
docker compose down
```

این دستور معمولاً Containerها و Networkهای مربوط به Compose را حذف می‌کند.

---

# 16. تفاوت stop و down

این دو دستور بسیار مهم هستند.

### stop

```bash
docker compose stop
```

Containerها را متوقف می‌کند.

### down

```bash
docker compose down
```

Application را پایین می‌آورد و منابع مربوط به آن را حذف می‌کند.

بنابراین:

```text
stop
↓
Container باقی می‌ماند

down
↓
Container حذف می‌شود
```

# 21. اتصال Node.js به PostgreSQL

یکی از مهم‌ترین ویژگی‌های Compose این است که Serviceها می‌توانند از طریق Network داخلی Docker با یکدیگر ارتباط برقرار کنند.

مثلاً:

```text
Node.js
   │
   │ PostgreSQL
   ▼
database
```

در Compose می‌توانیم به جای IP، از نام Service استفاده کنیم.

مثلاً:

```text
database
```

---

# 22. Service Name به عنوان Host

اگر Service ما:

```yaml
services:
  database:
    image: postgres:17
```

باشد، برنامه Node.js می‌تواند Database Host را:

```text
database
```

قرار دهد.

مثلاً:

```text
postgresql://app:password@database:5432/myapp
```

نکته مهم:

در داخل Docker Compose معمولاً نباید برای اتصال Container به Container از:

```text
localhost
```

استفاده کنیم.

---

# 23. localhost در Docker Compose

این اشتباه رایج است:

```text
localhost:5432
```

از داخل Container مربوط به Node.js.

چرا؟

چون `localhost` داخل Container به خود همان Container اشاره می‌کند.

پس:

```text
Node.js Container
localhost
   ↓
Node.js Container
```

نه PostgreSQL.

برای اتصال به PostgreSQL باید از نام Service استفاده کنیم:

```text
database:5432
```

---

# 24. Portهای داخلی و خارجی

فرض کنیم:

```yaml
ports:
  - "3000:3000"
```

Port اول:

```text
3000
```

Port روی Host است.

Port دوم:

```text
3000
```

Port داخل Container است.

اما وقتی Node.js از داخل Compose به PostgreSQL وصل می‌شود، لزوماً نیازی نداریم Port Database را روی Host Publish کنیم.

مثلاً:

```yaml
services:
  database:
    image: postgres:17
```

Node.js می‌تواند از طریق:

```text
database:5432
```

به آن متصل شود.

---

# 25. چرا همه Portها را Publish نکنیم؟

اگر PostgreSQL فقط باید از داخل Docker Network قابل دسترسی باشد، انتشار Port آن روی Host ممکن است غیرضروری باشد.

این:

```yaml
database:
  image: postgres:17
```

می‌تواند کافی باشد.

در حالی که:

```yaml
database:
  ports:
    - "5432:5432"
```

Database را از Host نیز قابل دسترسی می‌کند.

در Production باید فقط Portهای موردنیاز را Publish کنیم.

---

# 26. Volume در Compose

برای Database بسیار مهم است که داده‌ها را Persistent کنیم.

مثلاً:

```yaml
services:
  database:
    image: postgres:17
    volumes:
      - postgres-data:/var/lib/postgresql/data

volumes:
  postgres-data:
```

در اینجا:

```text
postgres-data
```

یک Named Volume است.

---

# 27. چرا Database به Volume نیاز دارد؟

اگر PostgreSQL داخل Container داده‌هایش را نگهداری کند و Container حذف شود، بدون Storage مناسب ممکن است داده‌ها از بین بروند.

با Volume:

```text
PostgreSQL Container
        │
        ▼
postgres-data
        │
        ▼
Persistent Storage
```

داده‌ها مستقل‌تر از Lifecycle Container مدیریت می‌شوند.

# 30. چند Network

مثلاً:

```text
frontend-network
backend-network
```

و یک Service می‌تواند عضو چند Network باشد.

این موضوع برای جداسازی سرویس‌ها کاربرد دارد.

---

# 31. depends_on

اگر `app` به Database وابسته باشد، می‌توانیم Dependency را مشخص کنیم:

```yaml
services:
  app:
    build: .
    depends_on:
      - database

  database:
    image: postgres:17
```

این تنظیم رابطه بین Serviceها را مشخص می‌کند.

اما یک نکته بسیار مهم وجود دارد:

`depends_on` به‌تنهایی تضمین نمی‌کند که Database واقعاً آماده دریافت Connection است.

ممکن است Container PostgreSQL شروع شده باشد اما خود Database هنوز در حال Initialization باشد.

---

# 32. Healthcheck

برای بررسی آماده بودن Service می‌توانیم از Health Check استفاده کنیم.

مثلاً برای PostgreSQL:

```yaml
services:
  database:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: password
      POSTGRES_DB: myapp
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d myapp"]
      interval: 5s
      timeout: 5s
      retries: 5
```

اکنون می‌توانیم وضعیت سلامت Service را بهتر بررسی کنیم.

---

# 33. depends_on همراه Healthcheck

در Composeهای جدید می‌توانیم Dependency را بر اساس Health نیز تعریف کنیم:

```yaml
services:
  app:
    build: .
    depends_on:
      database:
        condition: service_healthy

  database:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: password
      POSTGRES_DB: myapp
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d myapp"]
      interval: 5s
      timeout: 5s
      retries: 5
```

این الگو از حالت ساده `depends_on` قابل‌اعتمادتر است، اما Application همچنان باید Connection Failure و Retry را به شکل مناسب مدیریت کند.

---

# 34. Restart Policy

می‌توانیم مشخص کنیم Container در شرایط خاص دوباره اجرا شود.

مثلاً:

```yaml
services:
  app:
    build: .
    restart: unless-stopped
```

گزینه‌های متداول شامل:

```text
no
always
on-failure
unless-stopped
```

هستند.

---

# 35. Command

می‌توانیم Command پیش‌فرض Container را Override کنیم.

مثلاً:

```yaml
services:
  app:
    build: .
    command: npm run dev
```

در این حالت Command تعریف‌شده در Compose اجرا می‌شود.

---

# 36. Working Directory

می‌توانیم Working Directory را نیز مشخص کنیم:

```yaml
services:
  app:
    build: .
    working_dir: /app
```

البته اگر در Dockerfile `WORKDIR` مشخص کرده باشیم، معمولاً نیازی به تکرار آن نیست مگر اینکه عمداً بخواهیم Override کنیم.

---

# 37. Bind Mount در Development

برای Development می‌توانیم Source Code را Mount کنیم:

```yaml
services:
  app:
    build: .
    volumes:
      - .:/app
```

در این حالت تغییرات فایل‌های Host داخل Container نیز قابل مشاهده هستند.

---

# 38. مشکل node_modules در Bind Mount

اگر این کار را انجام دهیم:

```yaml
volumes:
  - .:/app
```

ممکن است `node_modules` داخل Container تحت تأثیر Mount شدن پوشه Host قرار بگیرد.

یک الگوی رایج Development این است:

```yaml
volumes:
  - .:/app
  - /app/node_modules
```

در این حالت `node_modules` داخل Container جدا نگه داشته می‌شود.

---

# 39. Docker Compose و Nodemon

برای Development می‌توانیم:

```yaml
services:
  app:
    build: .
    command: npm run dev
    volumes:
      - .:/app
      - /app/node_modules
    ports:
      - "3000:3000"
```

و در `package.json`:

```json
{
  "scripts": {
    "dev": "nodemon server.js"
  }
}
```

قرار دهیم.

# 44. Compose و Environment File

می‌توانیم از `.env` برای بعضی تنظیمات Compose استفاده کنیم.

مثلاً:

```text
POSTGRES_USER=app
POSTGRES_PASSWORD=secret
POSTGRES_DB=myapp
```

سپس:

```yaml
services:
  database:
    image: postgres:17
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
```

# 45. تفاوت Environment داخل Container و Compose Interpolation

این دو مفهوم را باید از هم جدا کنیم.

مثلاً:

```yaml
environment:
  PORT: ${PORT}
```

اینجا `${PORT}` توسط Compose از Environment یا `.env` مقداردهی می‌شود.

اما:

```yaml
environment:
  PORT: 3000
```

مقدار مستقیماً داخل Environment Container قرار می‌گیرد.

# 60. حذف Volumeها

# 65. نمونه کامل Node.js + PostgreSQL + Redis

```yaml
services:
  app:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: development
      PORT: 3000
      DATABASE_URL: postgresql://app:password@database:5432/myapp
      REDIS_HOST: redis
    depends_on:
      database:
        condition: service_healthy
      redis:
        condition: service_started
    volumes:
      - .:/app
      - /app/node_modules

  database:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: password
      POSTGRES_DB: myapp
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d myapp"]
      interval: 5s
      timeout: 5s
      retries: 5

  redis:
    image: redis:8

volumes:
  postgres-data:
```

این نمونه یک محیط Development چندسرویسی را نشان می‌دهد.

# 67. اشتباهات رایج

## اشتباه ۱ - استفاده از localhost برای ارتباط Serviceها

اشتباه:

```text
DATABASE_HOST=localhost
```

در Node.js Container.

در Compose باید معمولاً از نام Service استفاده شود:

```text
DATABASE_HOST=database
```

---

## اشتباه ۲ - تصور اینکه depends_on آماده بودن Database را تضمین می‌کند

`depends_on` ساده صرفاً ترتیب/Dependency را مدیریت می‌کند و به‌تنهایی آماده بودن Application-level Database را تضمین نمی‌کند.

برای شرایط مناسب می‌توان از Health Check و همچنین Retry در خود Application استفاده کرد.

---

## اشتباه ۳ - حذف Volume Database

دستور:

```bash
docker compose down -v
```

می‌تواند Volumeها را حذف کند.

قبل از اجرای آن باید بدانیم چه داده‌ای در Volume وجود دارد.

---

## اشتباه ۴ - Publish کردن همه Portها

اگر PostgreSQL فقط برای Node.js لازم است، ممکن است نیازی به:

```yaml
ports:
  - "5432:5432"
```

نداشته باشیم.

---

## اشتباه ۵ - قرار دادن Secret واقعی در Compose

قرار دادن Password واقعی در فایل Compose و Commit کردن آن به Git می‌تواند خطرناک باشد.

---

## اشتباه ۶ - استفاده اشتباه از Bind Mount

در Development:

```yaml
volumes:
  - .:/app
```

مفید است، اما باید تأثیر آن روی `node_modules` و Permissionها را در نظر گرفت.

---

## اشتباه ۷ - اجرای Production با تنظیمات Development

استفاده از:

```text
nodemon
source mount
debug
```

در Production معمولاً انتخاب مناسبی نیست.

---

## اشتباه ۸ - نادیده گرفتن Healthcheck

در سیستم‌های چندسرویسی، صرفاً Running بودن Container به معنی آماده بودن Service نیست.

---

## اشتباه ۹ - استفاده از Imageهای بدون Version مشخص

مثلاً:

```yaml
image: postgres:latest
```

می‌تواند باعث تغییر ناخواسته نسخه شود.

---

## اشتباه ۱۰ - استفاده بی‌دلیل از چند Compose File پیچیده

Compose Fileهای متعدد اگر بدون طراحی مناسب استفاده شوند، درک Configuration را دشوار می‌کنند.

---

## اشتباه ۱۱ - حذف Volumeها در زمان Debug

استفاده مکرر از:

```bash
docker compose down -v
```

ممکن است باعث از دست رفتن داده‌های Development شود.

---

## اشتباه ۱۲ - فرض اینکه Restart Policy جایگزین Error Handling است

Application باید خودش نیز:

* Connection Retry
* Error Handling
* Graceful Shutdown

را درست پیاده‌سازی کند.

# 68. نکات حرفه‌ای

## نکته ۴ - Application را برای Retry آماده کنید

حتی با Healthcheck، Application باید بتواند Connection Failureهای موقت را مدیریت کند.

## نکته ۵ - Volume Database را جدی بگیرید

Database بدون Storage مناسب در برابر حذف Container آسیب‌پذیر است.

## نکته ۶ - Development و Production را جدا کنید

است.

در سیستم‌های بزرگ‌تر باید CPU و Memory مصرفی Serviceها را نیز در نظر گرفت.

# 74. مرحله سوم - ایجاد Server

فایل:

```text
src/server.js
```

را ایجاد کنید:

```javascript
const http = require("node:http");
const { Pool } = require("pg");
const { createClient } = require("redis");

const PORT = process.env.PORT || 3000;

const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
});

const redis = createClient({
  url: `redis://${process.env.REDIS_HOST || "redis"}:6379`,
});

redis.on("error", (error) => {
  console.error("Redis Error:", error);
});

async function start() {
  await redis.connect();

  const server = http.createServer(async (req, res) => {
    res.setHeader("Content-Type", "application/json");

    if (req.method === "GET" && req.url === "/") {
      res.writeHead(200);

      return res.end(
        JSON.stringify({
          message: "Node.js + Docker Compose",
        }),
      );
    }

    if (req.method === "GET" && req.url === "/health") {
      try {
        await pool.query("SELECT 1");

        res.writeHead(200);

        return res.end(
          JSON.stringify({
            status: "ok",
            database: "connected",
            redis: redis.isReady,
          }),
        );
      } catch {
        res.writeHead(503);

        return res.end(
          JSON.stringify({
            status: "error",
          }),
        );
      }
    }

    res.writeHead(404);

    return res.end(
      JSON.stringify({
        message: "Route not found",
      }),
    );
  });

  server.listen(PORT, "0.0.0.0", () => {
    console.log(`Server running on port ${PORT}`);
  });
}

start().catch((error) => {
  console.error(error);
  process.exit(1);
});
```

# 78. مرحله هفتم - Compose

  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      PORT: 3000
      DATABASE_URL: postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@database:5432/${POSTGRES_DB}
      REDIS_HOST: redis
    depends_on:
      database:
        condition: service_healthy
      redis:
        condition: service_started

    image: postgres:17
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test:
        [
          "CMD-SHELL",
          "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}",
        ]
      interval: 5s
      timeout: 5s
      retries: 5

  redis:
    image: redis:8

volumes:
  postgres-data:

# 90. جمع‌بندی

در این فصل یاد گرفتیم که Docker Compose چگونه مدیریت پروژه‌های چندسرویسی را ساده می‌کند.

مهم‌ترین مفاهیم این فصل:

```text
Docker Compose
compose.yaml
Service
Network
Volume
Environment
depends_on
Healthcheck
Restart Policy
Bind Mount
docker compose up
docker compose down
docker compose ps
docker compose logs
docker compose exec
docker compose run
docker compose build
docker compose config
```

مهم‌ترین مفهوم عملی فصل این است:

```text
Node.js
   +
PostgreSQL
   +
Redis
   ↓
Docker Compose
   ↓
یک محیط یکپارچه
```

از اینجا به بعد، Docker Compose یکی از ابزارهای مهم ما برای ساخت محیط‌های واقعی Node.js خواهد بود.

در فصل بعد وارد **CI/CD** می‌شویم و یاد می‌گیریم چگونه فرآیندهایی مانند:

```text
Git Push
   ↓
Test
   ↓
Build
   ↓
Docker Image
   ↓
Deploy
```

را تا حد زیادی خودکار کنیم.
