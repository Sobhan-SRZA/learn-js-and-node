# فصل 130 - Husky

## مقدمه

در فصل‌های قبل با ابزارهایی مانند **Git، GitHub، ESLint و Prettier** آشنا شدیم.

اکنون یک سؤال مهم مطرح می‌شود:

> چگونه مطمئن شویم قبل از اینکه یک Commit یا Push انجام شود، کد پروژه بررسی و آماده باشد؟

فرض کنید یک Developer کدی نوشته است که:

* Formatting آن درست نیست.
* ESLint روی آن خطا می‌دهد.
* تست‌ها Fail می‌شوند.
* فایل‌های موقتی به Git اضافه شده‌اند.
* یک Commit با Message نامناسب ایجاد شده است.

اگر همه این موارد را بعد از Commit یا حتی بعد از Push متوجه شویم، Workflow تیمی ضعیف‌تر می‌شود.

اینجاست که **Husky** وارد می‌شود.

Husky ابزاری برای مدیریت و اجرای **Git Hooks** در پروژه است.

به کمک Husky می‌توانیم کاری کنیم که قبل یا بعد از رویدادهایی مانند:

```text
git commit
git push
```

دستورهای مشخصی به‌صورت خودکار اجرا شوند.

مثلاً:

```text
Developer
    ↓
git commit
    ↓
Husky
    ↓
ESLint
    ↓
Prettier
    ↓
Tests
    ↓
Commit
```

اگر بررسی‌ها موفق نباشند، می‌توانیم Commit را متوقف کنیم.

در این فصل یاد می‌گیریم:

* Git Hook چیست؟
* Husky چیست؟
* چرا از Husky استفاده می‌کنیم؟
* نصب Husky
* ساخت Hook
* `pre-commit`
* `commit-msg`
* `pre-push`
* اجرای ESLint و Prettier
* اجرای Test
* استفاده از lint-staged
* تفاوت Husky و CI
* ساخت Workflow حرفه‌ای
* اشتباهات رایج
* نکات حرفه‌ای
* تمرین
* پاسخ تشریحی
* مینی‌پروژه

---

# 130.1 - Git Hook چیست؟

قبل از یادگیری Husky باید مفهوم **Git Hook** را بشناسیم.

Git Hook یک Script است که Git در زمان رخ دادن یک Event مشخص اجرا می‌کند.

مثلاً:

```text
git commit
```

می‌تواند باعث اجرای:

```text
pre-commit
```

شود.

یا:

```text
git push
```

می‌تواند باعث اجرای:

```text
pre-push
```

شود.

به‌صورت کلی:

```text
Git Event
    ↓
Git Hook
    ↓
Script
    ↓
Action
```

---

# 130.2 - چرا Git Hook مفید است؟

فرض کنید یک تیم ۵ نفره داریم:

```text
Developer A
Developer B
Developer C
Developer D
Developer E
```

ممکن است یکی از آن‌ها قبل از Commit:

```bash
npm run lint
```

را اجرا کند، اما دیگری فراموش کند.

Git Hook کمک می‌کند این فرآیند به‌صورت خودکار انجام شود.

یعنی:

```text
Developer
    ↓
git commit
    ↓
Automatic Checks
```

---

# 130.3 - Husky چیست؟

**Husky** ابزاری است که تنظیم و مدیریت Git Hooks را در پروژه ساده‌تر می‌کند.

به‌جای اینکه هر Developer به‌صورت دستی Git Hookهای سیستم خود را تنظیم کند، Configuration مربوط به Hookها را داخل پروژه قرار می‌دهیم.

مثلاً:

```text
project/
│
├── .husky/
│   ├── pre-commit
│   └── pre-push
│
├── package.json
└── src/
```

با این روش، Hookهای پروژه قابل Version Control هستند.

---

# 130.4 - Husky چه مشکلی را حل می‌کند؟

بدون Husky ممکن است Workflow به این شکل باشد:

```text
Write Code
   ↓
git add
   ↓
git commit
   ↓
git push
   ↓
CI
   ↓
Error
```

یعنی Developer تازه بعد از Push متوجه مشکل شود.

با Husky می‌توان بخشی از مشکلات را زودتر پیدا کرد:

```text
Write Code
   ↓
git commit
   ↓
Husky
   ↓
Lint
   ↓
Test
   ↓
Commit
```

این کار باعث می‌شود Feedback سریع‌تر باشد.

# 130.5 - Git Hooks مهم

Git Hookهای زیادی وجود دارند، اما برای توسعه پروژه‌های Node.js چند مورد مهم‌تر هستند.

مهم‌ترین آن‌ها:

```text
pre-commit
commit-msg
pre-push
```

---

# 130.6 - `pre-commit`

Hook:

```text
pre-commit
```

قبل از ایجاد Commit اجرا می‌شود.

مثلاً:

```bash
git commit -m "Add authentication"
```

ابتدا:

```text
pre-commit
```

اجرا می‌شود.

اگر Hook موفق باشد:

```text
Commit
```

انجام می‌شود.

---

# 130.7 - کاربرد `pre-commit`

یکی از رایج‌ترین کاربردهای `pre-commit`:

```text
ESLint
Prettier
Tests
```

است.

مثلاً:

```text
git commit
    ↓
pre-commit
    ↓
ESLint
    ↓
Prettier Check
    ↓
Tests
    ↓
Commit
```

---

# 130.8 - `commit-msg`

Hook دیگری به نام:

```text
commit-msg
```

وجود دارد.

این Hook بعد از وارد شدن Commit Message و قبل از ثبت نهایی Commit می‌تواند Message را بررسی کند.

مثلاً می‌توانیم الزام کنیم Commit Message به شکل مشخصی باشد:

```text
feat: add authentication
fix: resolve login bug
docs: update README
```

و Commitهایی مانند:

```text
hello
test
asdf
```

را رد کنیم.

---

# 130.9 - `pre-push`

Hook:

```text
pre-push
```

قبل از Push شدن تغییرات اجرا می‌شود.

مثلاً:

```bash
git push
```

می‌تواند باعث اجرای:

```text
pre-push
   ↓
npm test
```

شود.

اگر تست‌ها Fail شوند:

```text
Push
   ↓
Blocked
```

می‌شود.

---

# 130.10 - تفاوت Hookها

| Hook         | زمان اجرا                  | کاربرد            |
| ------------ | -------------------------- | ----------------- |
| `pre-commit` | قبل از Commit              | Lint و Formatting |
| `commit-msg` | هنگام بررسی Commit Message | استاندارد Message |
| `pre-push`   | قبل از Push                | تست‌های کامل‌تر   |

یک Workflow معمول:

```text
pre-commit
    ↓
Fast Checks

pre-push
    ↓
More Expensive Checks

CI
    ↓
Complete Verification
```

# 130.14 - اولین `pre-commit`

فرض کنید می‌خواهیم قبل از هر Commit دستور زیر اجرا شود:

```bash

```

```text
.husky/pre-commit
```

می‌تواند شامل:

```sh

```

باشد.

```bash

```

# 130.15 - اگر Lint Fail شود چه اتفاقی می‌افتد؟

فرض کنید ESLint خطا پیدا کند:

```text

```

در این حالت دستور Hook با وضعیت ناموفق تمام می‌شود.

در نتیجه:

```text
pre-commit
    ↓
FAIL
    ↓
Commit
    ↓
STOP
```

Commit ایجاد نمی‌شود.

# 130.16 - چرا این موضوع مهم است؟

چون مشکل قبل از ورود به تاریخچه Git پیدا می‌شود.

به‌جای:

```text

 ↓
Push
 ↓
CI
 ↓
Failure
```

داریم:

```text
Commit
 ↓
Husky
 ↓
Failure
```

Feedback بسیار سریع‌تر است.

مثلاً:

اگر Formatting اشتباه باشد، Commit متوقف می‌شود.

# 130.18 - اجرای Test با Husky

می‌توانیم Test را نیز اجرا کنیم:


# 130.20 - Husky و lint-staged

یکی از ابزارهای بسیار مفید در کنار Husky:

```text
lint-staged
```

است.

ایده اصلی آن این است که ابزارهای Lint و Formatting را فقط روی فایل‌هایی اجرا کنیم که در Git Stage شده‌اند.

بدون lint-staged:

```text
Change 2 files
    ↓
ESLint
    ↓
Check entire project
```

با lint-staged:

```text
Change 2 files
    ↓
git add
    ↓
lint-staged
    ↓
Check only staged files
```

# 130.21 - نصب lint-staged

```bash
npm install --save-dev lint-staged
```

---

# 130.22 - تنظیم lint-staged

در `package.json` می‌توانیم چیزی مانند این تعریف کنیم:

```json
{
  "lint-staged": {
    "*.{js,mjs,cjs}": "eslint --fix",
    "*.{js,mjs,cjs,json,md}": "prettier --write"
  }
}
```

هدف این Configuration این است که ابزارها روی فایل‌های Stage شده اجرا شوند.

# 130.25 - تغییرات توسط Prettier

# 130.28 - چرا Commit Message مهم است؟

Commit Message خوب باعث می‌شود تاریخچه پروژه قابل فهم‌تر باشد.

بهتر:

# 130.29 - Husky و CI/CD

Husky جایگزین CI/CD نیست.

این نکته بسیار مهم است.

Husky روی سیستم Developer اجرا می‌شود:

```text
Developer Machine
       ↓
Husky
```

اما CI روی محیط CI اجرا می‌شود:

```text
GitHub
   ↓
CI Server
   ↓
Tests
Lint
Build
```

بنابراین:

```text
Husky ≠ CI
```

---

# 130.30 - چرا فقط به Husky اعتماد نکنیم؟

Git Hookهای Local می‌توانند توسط Developer غیرفعال یا دور زده شوند.

همچنین CI باید مستقل از محیط Developer صحت Repository را بررسی کند.

بنابراین:

```text
Local Protection
        +
Remote Verification
```

بهتر از استفاده از یکی از آن‌ها به‌تنهایی است.

---

# 130.31 - Husky و `--no-verify`

Git امکان دور زدن Hookها را فراهم می‌کند.

مثلاً:

```bash
git commit --no-verify
```

در چنین حالتی Hookهای مربوط به Commit اجرا نمی‌شوند.

بنابراین Husky یک **لایه کنترل محلی** است، نه یک سیستم امنیتی مطلق.

---

# 130.32 - آیا باید `--no-verify` را ممنوع کنیم؟

در حالت عادی بهتر است استفاده از آن استثنایی باشد.

اگر Developer دائماً از:

```bash
--no-verify
```

استفاده کند، عملاً هدف Hookها از بین می‌رود.

اگر Hook خیلی کند یا آزاردهنده است، بهتر است Workflow را اصلاح کنیم.

مثلاً:

```text
Heavy Tests
```

را از `pre-commit` به `pre-push` یا CI منتقل کنیم.

می‌توانند از قوانین یکسان استفاده کنند.

مثلاً:

# 130.34 - Husky و Git Clone

وقتی یک Developer پروژه را Clone می‌کند، Dependencyها را نصب می‌کند:

```bash

```

و Husky طبق Configuration پروژه آماده می‌شود.

# 130.35 - Husky و npm scripts

بهتر است دستورات پیچیده را مستقیماً داخل Hook ننویسیم.

مثلاً به‌جای:

```sh
eslint . && prettier . --check && node --test
```

می‌توانیم Scriptهای مشخص در `package.json` داشته باشیم:

```json
{
  "scripts": {
    "lint": "eslint .",
    "format:check": "prettier . --check",
    "test": "node --test"
  }
}
```

و Hook:

```sh
npm run lint
npm run format:check
npm test
```

باشد.

این کار خوانایی و نگهداری Configuration را بهتر می‌کند.

# 130.44 - Hook و Exit Code

یکی از مفاهیم مهم در Hookها:

```text
Exit Code
```

است.

اگر Command موفق باشد:

و اگر شکست بخورد:

```text
Exit Code ≠ 0
```

Git می‌تواند بر اساس این وضعیت تصمیم بگیرد که فرآیند ادامه پیدا کند یا متوقف شود.

مثلاً:

```sh
npm test
```

اگر Test Fail شود، معمولاً Process با Exit Code ناموفق تمام می‌شود.

در نتیجه Push متوقف می‌شود.

# جمع‌بندی فصل

در این فصل با **Husky** آشنا شدیم.

Husky کمک می‌کند Git Hookهای پروژه را مدیریت کنیم و قبل یا هنگام رویدادهای Git، عملیات مشخصی را به‌صورت خودکار اجرا کنیم.

مهم‌ترین Hookها:

```text
pre-commit
commit-msg
pre-push
```

یک Workflow ساده:

```text
git commit
    ↓
pre-commit
    ↓
ESLint / Prettier
    ↓
Commit
```

یک Workflow حرفه‌ای‌تر:

```text
git commit
    ↓
Husky
    ↓
lint-staged
    ↓
ESLint + Prettier
    ↓
Commit
    ↓
git push
    ↓
pre-push
    ↓
Tests
    ↓
Push
    ↓
CI
    ↓
Full Verification
```

مهم‌ترین نکته این فصل:

> **Husky جایگزین CI نیست؛ Husky یک لایه سریع و محلی برای جلوگیری از ورود اشتباهات به Workflow توسعه است.**

همچنین نباید Hookها را بیش از حد سنگین کنیم. هدف Hookهای محلی، ارائه **Feedback سریع** است؛ در حالی که بررسی‌های کامل‌تر بهتر است در CI انجام شوند.

با ترکیب:

```text
Git
+
Husky
+
lint-staged
+
ESLint
+
Prettier
+
Tests
+
CI/CD
```

می‌توانیم یک Workflow حرفه‌ای و قابل اعتماد برای پروژه‌های Node.js ایجاد کنیم.
