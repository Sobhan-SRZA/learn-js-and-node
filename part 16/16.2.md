# فصل 127 - GitHub

## مقدمه

در فصل قبل با **Git** آشنا شدیم و یاد گرفتیم چگونه تاریخچه پروژه را مدیریت کنیم، Commit ایجاد کنیم، Branch بسازیم و تغییرات مختلف را کنترل کنیم.

اما Git به‌تنهایی یک ابزار محلی است. یعنی Repository می‌تواند فقط روی کامپیوتر خودمان قرار داشته باشد.

در پروژه‌های واقعی معمولاً لازم است کد پروژه را:

* روی اینترنت ذخیره کنیم.
* از چند کامپیوتر به آن دسترسی داشته باشیم.
* با دیگر برنامه‌نویسان همکاری کنیم.
* کد را برای دیگران قابل مشاهده کنیم.
* تغییرات را با اعضای تیم به اشتراک بگذاریم.
* Pull Request ایجاد کنیم.
* Code Review انجام دهیم.
* Issue ثبت کنیم.
* پروژه‌های Open Source بسازیم.
* نسخه پشتیبان از Repository داشته باشیم.

یکی از معروف‌ترین سرویس‌ها برای این کار **GitHub** است.

GitHub در کنار Git، یکی از مهم‌ترین ابزارهایی است که یک برنامه‌نویس Node.js باید بتواند با آن کار کند.

در این فصل یاد می‌گیریم چگونه یک پروژه Node.js را از کامپیوتر خودمان به GitHub منتقل کنیم و سپس Workflow توسعه یک پروژه واقعی را با Git و GitHub تمرین کنیم.

---

# 127.1 - GitHub چیست؟

GitHub یک پلتفرم برای میزبانی Repositoryهای Git و همکاری روی پروژه‌های نرم‌افزاری است.

به زبان ساده:

```text
Git
│
├── مدیریت نسخه
├── Commit
├── Branch
├── Merge
└── History
```

و:

```text
GitHub
│
├── Remote Repository
├── Pull Request
├── Issues
├── Code Review
├── Collaboration
└── Project Hosting
```

Git و GitHub یک چیز نیستند.

Git ابزار Version Control است.

GitHub یک سرویس آنلاین است که امکانات مختلفی برای استفاده از Git و همکاری تیمی فراهم می‌کند.

---

# 127.2 - Git و GitHub چه تفاوتی دارند؟

فرض کنید پروژه‌ای روی کامپیوتر خودمان داریم:

```text
my-node-app/
```

با Git می‌توانیم تاریخچه پروژه را مدیریت کنیم:

```text
Commit 1
   ↓
Commit 2
   ↓
Commit 3
   ↓
Commit 4
```

اما اگر بخواهیم همین Repository را روی اینترنت قرار دهیم، می‌توانیم از GitHub استفاده کنیم:

```text
Local Repository
       │
       │ push
       ↓
GitHub Repository
```

و تغییرات دیگران را دریافت کنیم:

```text
GitHub Repository
       │
       │ pull
       ↓
Local Repository
```

---

# 127.3 - Repository چیست؟

Repository یا Repo محلی پروژه در Git، محل نگهداری فایل‌ها و تاریخچه پروژه است.

در GitHub نیز می‌توانیم یک Repository آنلاین داشته باشیم.

مثلاً:

```text
Local Repository
      ↓
my-node-app
```

و:

```text
Remote Repository
      ↓
GitHub
      ↓
my-node-app
```

این دو می‌توانند به یکدیگر متصل باشند.

---

# 127.4 - Local و Remote Repository

در کار با GitHub باید دو مفهوم را به‌خوبی بشناسیم:

### Local Repository

Repository روی کامپیوتر ما.

### Remote Repository

Repository روی یک سرویس آنلاین مانند GitHub.

ساختار کلی:

```text
┌──────────────────────┐
│   Local Repository   │
│      Computer        │
└──────────┬───────────┘
           │
       push / pull
           │
           ↓
┌──────────────────────┐
│  Remote Repository   │
│       GitHub         │
└──────────────────────┘
```

برای استفاده از GitHub ابتدا باید یک حساب کاربری ایجاد کنیم.

بعد از ورود به حساب، معمولاً مواردی مانند این را خواهیم داشت:

```text
Profile
Repositories
Issues
Pull Requests
Settings
```

نام کاربری GitHub اهمیت زیادی دارد؛ زیرا معمولاً در URL پروژه‌ها و Portfolio برنامه‌نویس استفاده می‌شود.

---

# 127.6 - ساخت Repository در GitHub

فرض کنید پروژه‌ای به نام:

```text
task-manager
```

داریم.

در GitHub می‌توانیم Repository جدیدی با همین نام ایجاد کنیم.

مثلاً:

```text
task-manager
```

Repository می‌تواند Public یا Private باشد.

### Public

دیگران می‌توانند Repository را مشاهده کنند.

### Private

فقط افراد مجاز می‌توانند به Repository دسترسی داشته باشند.

برای پروژه‌های آموزشی و Open Source معمولاً Public بودن مناسب است.

برای پروژه‌های خصوصی یا تجاری معمولاً Private استفاده می‌شود.

---

# 127.7 - Public و Private Repository

انتخاب Public یا Private اهمیت دارد.

مثلاً اگر پروژه‌ای شامل اطلاعات حساس باشد، نباید صرفاً برای نمایش Portfolio آن را Public کنیم.

مواردی که نباید در Repository عمومی قرار بگیرند:

```text
Database Password
API Key
JWT Secret
Private Key
Access Token
Credentials
```

---

# 127.8 - اتصال Repository محلی به GitHub

فرض کنید Repository محلی داریم:

```bash
git init
```

و Commit ایجاد کرده‌ایم:

```bash
git add .
git commit -m "Initial commit"
```

حالا باید Repository محلی را به Repository موجود در GitHub متصل کنیم.

برای این کار یک Remote اضافه می‌کنیم:

```bash
git remote add origin <repository-url>
```

برای مثال:

```bash
git remote add origin https://github.com/USERNAME/task-manager.git
```

---

# 127.9 - Remote چیست؟

Remote یک نام برای یک Repository خارجی است.

معمولاً Remote اصلی پروژه با نام:

```text
origin
```

شناخته می‌شود.

برای مشاهده Remoteها:

```bash
git remote -v
```

ممکن است خروجی شبیه این باشد:

```text
origin  https://github.com/USERNAME/task-manager.git (fetch)
origin  https://github.com/USERNAME/task-manager.git (push)
```

---

# 127.10 - چرا اسم origin؟

`origin` یک قرارداد رایج است.

Git مجبور نیست Remote را `origin` نام‌گذاری کند.

مثلاً می‌توانیم Remoteهای دیگری داشته باشیم:

```text
origin
upstream
company
```

اما در پروژه‌های معمولی، Remote اصلی معمولاً:

```text
origin
```

است.

---

# 127.11 - مشاهده Remote

برای مشاهده Remote:

```bash
git remote -v
```

برای مشاهده جزئیات بیشتر:

```bash
git remote show origin
```

---

# 127.12 - Push چیست؟

Push یعنی ارسال Commitهای Local به Remote Repository.

مثلاً:

```bash
git push origin main
```

یعنی:

```text
Local main
     ↓
   push
     ↓
origin/main
```

پس تغییرات Commit شده از کامپیوتر ما به GitHub ارسال می‌شوند.

---

# 127.13 - اولین Push

بعد از اتصال Repository:

```bash
git remote add origin <repository-url>
```

می‌توانیم Branch اصلی را Push کنیم:

```bash
git push -u origin main
```

گزینه:

```text
-u
```

باعث می‌شود Upstream مربوط به Branch تنظیم شود.

پس از آن معمولاً می‌توانیم ساده‌تر بنویسیم:

```bash
git push
```

---

# 127.14 - Fetch چیست؟

`git fetch` تغییرات جدید Remote را دریافت می‌کند، اما آن‌ها را به‌صورت خودکار وارد Branch فعلی نمی‌کند.

مثلاً:

```bash
git fetch origin
```

به زبان ساده:

```text
GitHub
   ↓
fetch
   ↓
Local Git
```

اما فایل‌های Working Directory لزوماً تغییر نمی‌کنند.

---

# 127.15 - Pull چیست؟

`git pull` معمولاً ترکیبی از دریافت تغییرات Remote و ادغام آن‌ها با Branch فعلی است.

مثلاً:

```bash
git pull origin main
```

به‌صورت مفهومی:

```text
fetch
  +
merge
```

است.

---

# 127.16 - تفاوت Fetch و Pull

به‌صورت ساده:

```text
git fetch
```

یعنی:

> تغییرات Remote را دریافت کن، اما هنوز آن‌ها را با Branch فعلی ادغام نکن.

در مقابل:

```text
git pull
```

یعنی:

> تغییرات Remote را دریافت کن و آن‌ها را با Branch فعلی ادغام کن.

در پروژه‌های حرفه‌ای، شناخت این تفاوت بسیار مهم است.

---

# 127.17 - Clone چیست؟

اگر پروژه‌ای روی GitHub وجود داشته باشد و بخواهیم آن را روی کامپیوتر خودمان دریافت کنیم، از `git clone` استفاده می‌کنیم.

مثلاً:

```bash
git clone https://github.com/USERNAME/task-manager.git
```

Git Repository را دانلود می‌کند.

پس از آن:

```text
task-manager/
├── .git/
├── package.json
├── package-lock.json
└── app.js
```

خواهیم داشت.

---

# 127.18 - Clone با GitHub چیست؟

فرض کنید یک برنامه‌نویس دیگر پروژه را روی GitHub قرار داده است.

ما می‌توانیم:

```text
GitHub Repository
        ↓
      clone
        ↓
Computer
```

و پروژه را روی سیستم خود داشته باشیم.

بعد:

```bash
cd task-manager
npm install
```

و پروژه را اجرا کنیم.

---

# 127.19 - HTTPS و SSH

برای اتصال Git به GitHub معمولاً با دو روش رایج مواجه می‌شویم:

```text
HTTPS
SSH
```

مثال HTTPS:

```text
https://github.com/USERNAME/project.git
```

مثال SSH:

```text
git@github.com:USERNAME/project.git
```

هر دو روش برای کار با Repository استفاده می‌شوند.

---

# 127.20 - Authentication چیست؟

GitHub باید مطمئن شود شخصی که قصد Push کردن دارد، اجازه دسترسی به Repository را دارد.

برای همین Authentication اهمیت دارد.

در محیط‌های امروزی، برای کارهای GitHub معمولاً از روش‌هایی مانند:

* SSH
* HTTPS همراه با روش‌های احراز هویت مناسب
* GitHub CLI

استفاده می‌شود.

نباید اطلاعات حساس مانند Password یا Token را داخل فایل‌های پروژه قرار دهیم.

---

# 127.21 - SSH چیست؟

SSH یک روش امن برای برقراری ارتباط با سرویس‌های مختلف است.

در GitHub می‌توانیم SSH Key ایجاد کنیم و Public Key را در حساب GitHub خود ثبت کنیم.

ساختار کلی:

```text
Computer
   │
   ├── Private Key
   │
   └── Public Key
          ↓
       GitHub
```

Private Key باید روی سیستم ما باقی بماند و نباید منتشر شود.

---

# 127.22 - ایجاد SSH Key

در سیستم‌هایی که OpenSSH در دسترس است، می‌توانیم یک SSH Key ایجاد کنیم.

مثلاً:

```bash
ssh-keygen -t ed25519 -C "you@example.com"
```

پس از ساخت، معمولاً دو فایل اصلی خواهیم داشت:

```text
Private Key
Public Key
```

Public Key معمولاً با پسوندی مانند:

```text
.pub
```

شناخته می‌شود.

---

# 127.23 - Private Key و Public Key

این دو را با هم اشتباه نگیریم.

### Public Key

می‌تواند در GitHub ثبت شود.

### Private Key

باید محرمانه باقی بماند.

به هیچ عنوان Private Key را:

```text
GitHub Repository
Discord
Telegram
GitHub Issue
README
```

منتشر نکنید.

# 127.24 - تست اتصال SSH

پس از تنظیم SSH می‌توانیم اتصال را آزمایش کنیم:

```bash
ssh -T git@github.com
```

در صورت تنظیم صحیح، GitHub اتصال را شناسایی می‌کند.

آن را Clone می‌کنیم:

# 127.27 - Branch در GitHub

Branch فقط در Repository محلی نیست.

Remote Repository نیز Branch دارد.

مثلاً:

```text
main
feature/auth
feature/products
fix/login
```

ممکن است روی GitHub قابل مشاهده باشند.

---

# 127.28 - Push کردن Branch

فرض کنید Branch زیر را ساخته‌ایم:

```bash
git switch -c feature/auth
```

بعد از Commit:

```bash
git push -u origin feature/auth
```

حالا Branch روی GitHub نیز وجود خواهد داشت.

---

# 127.29 - Pull Request چیست؟

Pull Request یا **PR** یکی از مهم‌ترین قابلیت‌های GitHub است.

Pull Request یعنی:

> درخواست برای وارد کردن تغییرات یک Branch به Branch دیگر.

مثلاً:

```text
feature/auth
      ↓
Pull Request
      ↓
main
```

برنامه‌نویس می‌تواند تغییرات خود را برای بررسی دیگر اعضای تیم ارسال کند.

---

# 127.30 - چرا Pull Request مهم است؟

Pull Request امکان مواردی مانند:

* Code Review
* بررسی تغییرات
* بحث درباره کد
* اجرای تست‌ها
* بررسی CI/CD
* ثبت توضیحات
* پیشنهاد تغییرات

را فراهم می‌کند.

در پروژه‌های تیمی، PR بخش مهمی از Workflow توسعه است.

---

# 127.31 - Code Review

در Code Review اعضای تیم کد نوشته‌شده را بررسی می‌کنند.

مثلاً:

```text
Developer A
     ↓
Feature Branch
     ↓
Pull Request
     ↓
Developer B
     ↓
Code Review
     ↓
Merge
```

Reviewer ممکن است درباره:

* کیفیت کد
* امنیت
* Performance
* نام‌گذاری
* معماری
* تست‌ها
* خطاهای احتمالی

نظر بدهد.

---

# 127.32 - Approve و Request Changes

در Pull Request معمولاً Reviewer می‌تواند:

```text
Approve
```

یا:

```text
Request Changes
```

انجام دهد.

### Approve

یعنی تغییرات مورد قبول است.

### Request Changes

یعنی قبل از Merge نیاز به اصلاحاتی وجود دارد.

---

# 127.33 - Merge Pull Request

پس از تأیید PR می‌توان تغییرات را Merge کرد.

به‌صورت مفهومی:

```text
feature/auth
     │
     │ Pull Request
     ↓
main
     │
     ↓
Merge
```

GitHub روش‌های مختلفی برای Merge ارائه می‌دهد.

---

# 127.34 - Merge Commit

در روش Merge Commit، یک Commit برای ادغام Branch ایجاد می‌شود.

ساختار تاریخچه ممکن است شبیه این باشد:

```text
A---B---C---M
     \     /
      D---E
```

که `M` مربوط به Merge است.

---

# 127.35 - Squash and Merge

در Squash and Merge چند Commit مربوط به یک Feature می‌توانند به یک Commit تبدیل شوند.

مثلاً:

```text
Add login
Fix login
Fix validation
Fix typo
```

می‌تواند تبدیل شود به:

```text
Add authentication feature
```

این روش می‌تواند تاریخچه `main` را تمیزتر نگه دارد.

---

# 127.36 - Rebase and Merge

روش دیگری برای ادغام تغییرات:

```text
Rebase and Merge
```

است.

Rebase تاریخچه Commitها را روی Base جدید قرار می‌دهد.

این موضوع پیشرفته‌تر است و هنگام استفاده باید تفاوت Rebase با Merge و اثر آن بر تاریخچه را به‌خوبی بدانیم.

# 127.37 - Issue چیست؟

GitHub Issue برای ثبت و مدیریت موضوعات پروژه استفاده می‌شود.

مثلاً:

```text
Bug: Login fails with invalid token
```

یا:

```text
Feature: Add password reset
```

Issue می‌تواند شامل:

* عنوان
* توضیحات
* Label
* Assignee
* Comment
* Reference

باشد.

---

# 127.38 - Bug Report

یک Bug Report خوب باید توضیح دهد:

```text
What happened?
What was expected?
How can we reproduce it?
What environment was used?
```

مثلاً:

```text
Title:
Login returns 500 for invalid password
```

و در توضیحات:

```text
Steps to reproduce:
1. Open login endpoint
2. Send invalid password
3. Observe response

Expected:
401 Unauthorized

Actual:
500 Internal Server Error
```

Review

License مشخص می‌کند دیگران تحت چه شرایطی می‌توانند از کد پروژه استفاده کنند.

در پروژه‌های Open Source انتخاب License اهمیت زیادی دارد.

نباید فرض کنیم:

> چون Repository عمومی است، پس همه می‌توانند هر کاری با کد انجام دهند.

Public بودن Repository به‌تنهایی به معنی مجوز نامحدود استفاده از کد نیست.

# 127.50 - مینی‌پروژه: انتشار یک REST API روی GitHub

در این مینی‌پروژه یک پروژه ساده Node.js ایجاد می‌کنیم و آن را با Workflow شبیه پروژه‌های واقعی روی GitHub مدیریت می‌کنیم.

هدف:

```text
Node.js
   ↓
Git
   ↓
GitHub
   ↓
Branch
   ↓
Pull Request
   ↓
Code Review
   ↓
Merge
```

---

## مرحله 1 - ساخت پروژه

```bash
mkdir github-task-api
cd github-task-api
npm init -y
```

---

## مرحله 2 - ایجاد برنامه

فایل `app.js`:

```js
const http = require("node:http");

const tasks = [
  {
    id: 1,
    title: "Learn Node.js",
    completed: false
  },
  {
    id: 2,
    title: "Learn GitHub",
    completed: false
  }
];

const server = http.createServer((req, res) => {
  if (req.url === "/tasks" && req.method === "GET") {
    res.setHeader("Content-Type", "application/json");
    res.end(JSON.stringify(tasks));
    return;
  }

  res.statusCode = 404;
  res.end("Not Found");
});

server.listen(3000, () => {
  console.log("Server running on port 3000");
});
```

# جمع‌بندی فصل

در این فصل یاد گرفتیم که GitHub چگونه در کنار Git قرار می‌گیرد.

مفاهیم اصلی این فصل:

```text
GitHub
Repository
Remote
origin
push
pull
fetch
clone
HTTPS
SSH
Pull Request
Code Review
Issue
Label
README
LICENSE
Public Repository
Private Repository
```

مهم‌ترین دستورات:

```bash
git clone <url>

git remote -v

git remote add origin <url>

git push -u origin main

git push

git pull

git fetch

git switch -c feature/name

git push -u origin feature/name
```

Workflow ساده یک پروژه تیمی نیز به این شکل است:

```text
Issue
 ↓
Branch
 ↓
Code
 ↓
Commit
 ↓
Push
 ↓
Pull Request
 ↓
Code Review
 ↓
Merge
```

برای یک برنامه‌نویس Node.js، یادگیری Git و GitHub تقریباً به اندازه یادگیری خود Node.js در فرآیند توسعه پروژه اهمیت دارد؛ زیرا در پروژه‌های واقعی معمولاً کد به‌صورت تیمی توسعه داده می‌شود و مدیریت صحیح نسخه، Review و همکاری بخش جدایی‌ناپذیر کار است.

در فصل بعد، سراغ **ESLint** می‌رویم و یاد می‌گیریم چگونه خطاها و مشکلات رایج کد JavaScript/Node.js را به‌صورت خودکار شناسایی کنیم و کیفیت کد پروژه را بالاتر ببریم.
