# فصل 132 - Docker

## مقدمه

وقتی یک پروژه Node.js روی کامپیوتر خودمان به‌درستی اجرا می‌شود، لزوماً به این معنی نیست که روی کامپیوتر شخص دیگری، سرور یا محیط Production نیز بدون مشکل اجرا خواهد شد.

ممکن است نسخه Node.js متفاوت باشد، نسخه Packageها متفاوت باشد، بعضی Dependencyها نصب نباشند، تنظیمات سیستم‌عامل فرق داشته باشد یا حتی بعضی ابزارهای موردنیاز پروژه روی سیستم مقصد وجود نداشته باشند.

اینجاست که **Docker** وارد می‌شود.

Docker به ما اجازه می‌دهد برنامه را به همراه محیط موردنیاز آن در یک واحد قابل‌انتقال به نام **Container** اجرا کنیم.

در یک پروژه Node.js می‌توانیم مواردی مانند:

* نسخه Node.js
* Dependencyهای پروژه
* فایل‌های پروژه
* تنظیمات اجرای برنامه
* Port مورد استفاده
* بعضی تنظیمات محیط اجرا

را در قالب یک Image قرار دهیم و سپس همان Image را در محیط‌های مختلف اجرا کنیم.

به زبان ساده:

> Docker کمک می‌کند برنامه ما در محیط‌های مختلف، تا حد امکان با یک روش یکسان اجرا شود.

---

# 1. Docker چیست؟

Docker یک پلتفرم برای ساخت، بسته‌بندی و اجرای نرم‌افزارها در محیط‌های جداشده به نام **Container** است.

برای مثال فرض کنید یک پروژه Node.js داریم که با Node.js نسخه 24 اجرا می‌شود.

بدون Docker ممکن است برای اجرای پروژه روی یک سیستم جدید مجبور باشیم:

1. Node.js را نصب کنیم.
2. نسخه مناسب Node.js را پیدا کنیم.
3. npm را آماده کنیم.
4. پروژه را Clone کنیم.
5. Dependencyها را نصب کنیم.
6. Environment Variableها را تنظیم کنیم.
7. پروژه را اجرا کنیم.

اما با Docker می‌توانیم محیط اجرای پروژه را در یک Image تعریف کنیم و سپس Container را بر اساس آن اجرا کنیم.

---

# 2. Docker چه مشکلی را حل می‌کند؟

یکی از مشکلات معروف در توسعه نرم‌افزار این جمله است:

> روی سیستم من کار می‌کند!

فرض کنید سه برنامه‌نویس روی یک پروژه کار می‌کنند:

```text
Developer A
Node.js 24
npm 11

Developer B
Node.js 22
npm 10

Developer C
Node.js 20
npm 10
```

ممکن است پروژه روی سیستم A درست اجرا شود اما روی سیستم B یا C با مشکل مواجه شود.

Docker کمک می‌کند محیط اجرای برنامه را استاندارد کنیم.

مثلاً:

```text
Node.js 24
+
Project Files
+
Dependencies
+
Configuration
=
Docker Image
```

سپس:

```text
Docker Image
      ↓
Container
      ↓
Running Application
```

---

# 3. Container چیست؟

Container یک محیط اجرای ایزوله برای اجرای یک برنامه است.

برای مثال:

```text
Host Machine
│
├── Container 1
│   └── Node.js API
│
├── Container 2
│   └── PostgreSQL
│
└── Container 3
    └── Redis
```

هر Container محیط اجرای مخصوص خود را دارد.

اما Container یک Virtual Machine کامل نیست.

---

# 4. تفاوت Container و Virtual Machine

در Virtual Machine معمولاً یک سیستم‌عامل کامل مجازی اجرا می‌شود.

مثلاً:

```text
Physical Machine
│
├── Host OS
│
├── VM
│   ├── Guest OS
│   └── Application
│
└── VM
    ├── Guest OS
    └── Application
```

اما در Docker:

```text
Physical Machine
│
├── Host OS
│
├── Docker Engine
│
├── Container
│   └── Application
│
└── Container
    └── Application
```

Containerها معمولاً سبک‌تر و سریع‌تر از Virtual Machineها هستند.

---

# 5. Image چیست؟

**Docker Image** یک Template برای ساخت Container است.

Image شامل موارد موردنیاز برای اجرای برنامه است.

مثلاً:

```text
Node.js Image
+
Application Code
+
Dependencies
+
Configuration
=
Application Image
```

سپس از روی Image می‌توان Container ساخت.

---

# 6. رابطه Image و Container

یک مثال ساده:

```text
Image
  │
  ├── Container 1
  ├── Container 2
  └── Container 3
```

Image مانند یک الگو است.

Container نمونه در حال اجرای آن Image است.

بنابراین:

```text
Image = Template

Container = Running Instance
```

---

# 7. Docker Engine

Docker Engine بخش اصلی Docker است که Containerها را اجرا و مدیریت می‌کند.

معمولاً معماری کلی را می‌توان این‌گونه تصور کرد:

```text
Docker CLI
    ↓
Docker Engine
    ↓
Containers
Images
Networks
Volumes
```

ما معمولاً از Terminal و دستور `docker` با Docker Engine کار می‌کنیم.

# 9. اولین Container

برای آزمایش Docker می‌توانیم از Image معروف `hello-world` استفاده کنیم:

```bash

```

Docker در صورت نیاز Image را دریافت کرده و Container را اجرا می‌کند.

فرآیند تقریباً چنین است:

```text
docker run hello-world
        ↓
Check Image
        ↓
Download Image if needed
        ↓
Create Container
        ↓
Run Container
```


```bash

```

# 14. Dockerfile چیست؟

برای ساخت Image اختصاصی پروژه، معمولاً از فایلی به نام:

```text
Dockerfile
```

استفاده می‌کنیم.

Dockerfile مجموعه‌ای از دستورها برای ساخت Image است.

مثلاً:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

CMD ["node", "server.js"]
```

---

# 15. FROM

اولین دستور مهم Dockerfile معمولاً `FROM` است.

مثلاً:

```dockerfile
FROM node:24
```

یعنی Image ما از Image مربوط به Node.js نسخه 24 ساخته شود.

---

# 16. WORKDIR

دستور `WORKDIR` مسیر کاری داخل Container را مشخص می‌کند.

مثلاً:

```dockerfile
WORKDIR /app
```

بعد از آن دستورهای بعدی در این مسیر اجرا می‌شوند.

---

# 17. COPY

برای انتقال فایل‌ها از پروژه به Image از `COPY` استفاده می‌کنیم.

مثلاً:

```dockerfile
COPY package*.json ./
```

و:

```dockerfile
COPY . .
```

دستور دوم فایل‌های Context پروژه را به مسیر کاری Container منتقل می‌کند؛ مگر اینکه توسط `.dockerignore` حذف شده باشند.

---

# 18. RUN

دستور `RUN` هنگام Build شدن Image اجرا می‌شود.

مثلاً:

```dockerfile
RUN npm ci
```

در اینجا Dependencyهای پروژه هنگام ساخت Image نصب می‌شوند.

---

# 19. CMD

دستور `CMD` مشخص می‌کند Container به صورت پیش‌فرض چه کاری انجام دهد.

مثلاً:

```dockerfile
CMD ["node", "server.js"]
```

بهتر است فرم JSON را برای اجرای برنامه استفاده کنیم.

---

# 20. EXPOSE

می‌توانیم Port مورد استفاده برنامه را در Dockerfile مستند کنیم:

```dockerfile
EXPOSE 3000
```

نکته مهم:

`EXPOSE` به‌تنهایی Port را روی سیستم Host منتشر نمی‌کند.

برای Publish کردن Port باید هنگام اجرای Container از `-p` استفاده کنیم.

---

# 21. ساخت Dockerfile برای پروژه Node.js

فرض کنیم پروژه چنین ساختاری دارد:

```text
my-app/
│
├── package.json
├── package-lock.json
├── server.js
└── Dockerfile
```

Dockerfile:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 3000

CMD ["node", "server.js"]
```

# 25. Port Mapping

فرض کنیم Node.js روی Port `3000` اجرا می‌شود.

برای دسترسی از سیستم Host:

```bash

```

```text

```

یعنی:

```text
3000:3000
```

---

# 26. چرا Port Mapping لازم است؟

Container محیط جداگانه‌ای دارد.

اگر برنامه داخل Container روی:

```text
3000
```

گوش دهد، الزاماً به این معنی نیست که سیستم Host بتواند مستقیماً به آن دسترسی داشته باشد.

با:

```bash
-p 3000:3000
```

ارتباط را برقرار می‌کنیم:

```text
Browser
   ↓
localhost:3000
   ↓
Host Port 3000
   ↓
Container Port 3000
   ↓
Node.js
```

# 38. چرا node_modules را Copy نکنیم؟

بهتر است `node_modules` سیستم Host را وارد Container نکنیم.

چرا؟

چون ممکن است:

* سیستم‌عامل متفاوت باشد.
* Architecture متفاوت باشد.
* Native Dependencyها متفاوت باشند.
* حجم آن زیاد باشد.
* Dependencyها با محیط Container سازگار نباشند.

بهتر است Dependencyها داخل Container نصب شوند.

به همین دلیل معمولاً:

```text
COPY package*.json ./
RUN npm ci
COPY . .
```

را می‌بینیم.

# 39. npm install یا npm ci؟

```bash

```

`npm ci` برای نصب قابل‌تکرار Dependencyها طراحی شده است.

مثلاً:

```dockerfile

```

# 40. Docker Layer

Dockerfile به صورت Layerهای مختلف ساخته می‌شود.

مثلاً:

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

CMD ["node", "server.js"]
```

هر بخش می‌تواند در Cache شدن Build نقش داشته باشد.

---

# 41. چرا ترتیب COPY مهم است؟

اگر این کار را انجام دهیم:

```dockerfile
COPY . .

RUN npm ci
```

با هر تغییر کوچک در Source Code ممکن است Cache مربوط به Dependencyها نیز بی‌استفاده شود.

اما:

```dockerfile
COPY package*.json ./
RUN npm ci
COPY . .
```

باعث می‌شود تا زمانی که فایل‌های Dependency تغییر نکرده‌اند، Docker بتواند Layer مربوط به نصب Packageها را Cache کند.

# 42. Environment Variable در Docker

برنامه Node.js معمولاً از Environment Variable استفاده می‌کند.

مثلاً:

```javascript
const port = process.env.PORT || 3000;
```

می‌توانیم هنگام اجرای Container مقدار تعیین کنیم:

```bash
docker run -e PORT=3000 my-node-app
```

یا چند مقدار:

```bash
docker run \
  -e PORT=3000 \
  -e NODE_ENV=production \
  my-node-app
```

# 43. استفاده از فایل .env

برای پروژه‌های واقعی ممکن است Environment Variableها زیاد باشند.

مثلاً:

```text

NODE_ENV=production
DATABASE_URL=...
```

می‌توانیم در Docker از فایل Environment استفاده کنیم:

```bash

```

اما فایل‌های حساس مانند `.env` نباید بدون بررسی وارد Git Repository شوند.

# 44. Volume چیست؟

Containerها معمولاً برای داده‌های موقت مناسب هستند.

اگر Container حذف شود، داده‌هایی که داخل Layer قابل‌نوشتن آن ذخیره شده‌اند ممکن است از بین بروند.

برای نگهداری داده‌ها می‌توانیم از **Volume** استفاده کنیم.

```text
Container
   │
   │
   ↓
Volume
   │
   ↓
Persistent Data
```

# 50. Multi-Stage Build

برای پروژه‌های بزرگ‌تر می‌توانیم از **Multi-Stage Build** استفاده کنیم.

مثلاً:

```dockerfile
FROM node:24 AS builder

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build


FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY --from=builder /app/dist ./dist

CMD ["node", "dist/server.js"]
```

ایده اصلی:

```text
Builder Stage
      ↓
Build Application
      ↓
Production Stage
```

# 59. اشتباهات رایج

## اشتباه ۱ - استفاده از `latest` بدون دلیل

مثلاً:

```dockerfile
FROM node:latest
```

این کار می‌تواند باعث شود در زمان‌های مختلف نسخه‌های متفاوتی دریافت کنیم.

بهتر است نسخه مناسب پروژه را مشخص کنیم:

```dockerfile
FROM node:24
```

---

## اشتباه ۲ - Copy کردن node_modules

بد:

```dockerfile
COPY . .
```

در حالی که `node_modules` داخل پروژه وجود دارد.

راه بهتر استفاده از `.dockerignore` است:

```text
node_modules
```

---

## اشتباه ۳ - قرار دادن Secret داخل Dockerfile

بد:

```dockerfile
ENV DATABASE_PASSWORD=my-secret-password
```

اطلاعات حساس نباید به این شکل داخل Image قرار بگیرند.

---

## اشتباه ۴ - تصور اینکه EXPOSE Port را Publish می‌کند

این:

```dockerfile
EXPOSE 3000
```

به‌تنهایی کافی نیست.

برای Publish:

```bash
docker run -p 3000:3000 my-node-app
```

---

## اشتباه ۵ - اجرای npm install به جای npm ci در Buildهای قابل‌تکرار

اگر `package-lock.json` داریم، در بسیاری از Buildهای CI/Production بهتر است:

```dockerfile
RUN npm ci
```

استفاده شود.

---

## اشتباه ۶ - نصب Packageهای غیرضروری داخل Image

قرار دادن ابزارهای Development در Production Image می‌تواند Image را بزرگ‌تر و محیط را پیچیده‌تر کند.

---

## اشتباه ۷ - اجرای برنامه با User ریشه بدون نیاز

در Container بهتر است در صورت امکان برنامه با User غیرRoot اجرا شود.

برای مثال:

```dockerfile
USER node
```

البته باید Permissionهای پروژه نیز با این User سازگار باشند.

---

## اشتباه ۸ - نادیده گرفتن `.dockerignore`

اگر `.dockerignore` مناسب نداشته باشیم ممکن است فایل‌های غیرضروری وارد Build Context شوند.

---

## اشتباه ۹ - ذخیره داده مهم فقط داخل Container

Container نباید تنها محل نگهداری داده‌های مهم و Persistent باشد.

برای داده‌های ماندگار باید راهکار مناسب مانند Volume یا سرویس خارجی در نظر گرفته شود.

---

## اشتباه ۱۰ - استفاده از Docker بدون درک Lifecycle

باید تفاوت این دستورات را بدانیم:

```bash
docker create
docker start
docker stop
docker rm
docker run
```

`docker run` عملاً ایجاد و اجرای یک Container جدید را انجام می‌دهد.

## پاسخ تمرین ۱۲

```dockerfile
FROM node:24

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY --from=builder /app/dist ./dist

CMD ["node", "dist/server.js"]
```

در این روش Stage اول وظیفه Build را انجام می‌دهد و Stage دوم فقط موارد لازم برای اجرای Production را دریافت می‌کند.

# مینی‌پروژه - Dockerize کردن یک REST API ساده Node.js

## هدف پروژه

در این پروژه قرار است یک REST API ساده Node.js بسازیم و آن را کاملاً داخل Docker اجرا کنیم.

ساختار نهایی:

```text

│
├── package.json
├── package-lock.json
├── server.js
├── Dockerfile
└── .dockerignore
```

---

## مرحله ۱ - ایجاد پروژه

```bash
mkdir docker-rest-api

cd docker-rest-api

npm init -y
```

---

## مرحله ۲ - ایجاد Server

فایل:

```text
server.js
```

را ایجاد کنید.

```javascript
const http = require("node:http");

const PORT = process.env.PORT || 3000;

const users = [
  {
    id: 1,
    name: "Ali",
  },
  {
    id: 2,
    name: "Sara",
  },
];

const server = http.createServer((req, res) => {
  res.setHeader("Content-Type", "application/json");

  if (req.method === "GET" && req.url === "/") {
    res.writeHead(200);

    return res.end(
      JSON.stringify({
        message: "Docker REST API",
      }),
    );
  }

  if (req.method === "GET" && req.url === "/users") {
    res.writeHead(200);

    return res.end(JSON.stringify(users));
  }

  res.writeHead(404);

  return res.end(
    JSON.stringify({
      message: "Route not found",
    }),
  );
});

server.listen(PORT, "0.0.0.0", () => {
  console.log(`Server running on port ${PORT}`);
});
```

# نکته پایانی

در این فصل Docker را از پایه یاد گرفتیم و یک پروژه واقعی Node.js را Containerize کردیم.

اما در پروژه‌های واقعی معمولاً تنها یک Container نداریم.

برای مثال ممکن است یک Backend Node.js به موارد زیر نیاز داشته باشد:

```text
Node.js
PostgreSQL
Redis
Nginx
Worker
```

مدیریت جداگانه این Containerها می‌تواند دشوار شود.

در فصل بعد، با **Docker Compose** یاد می‌گیریم چگونه چند سرویس را در قالب یک پروژه تعریف کنیم و با یک دستور، کل محیط Backend را بالا بیاوریم.
