# فصل 98 - MongoDB

## مقدمه

تا اینجا با Databaseهای رابطه‌ای و SQL آشنا شدیم و PostgreSQL را به عنوان یکی از قدرتمندترین Databaseهای رابطه‌ای بررسی کردیم.

اما همه پروژه‌ها نیاز به ساختار رابطه‌ای و Tableهای ثابت ندارند.

**MongoDB** یکی از محبوب‌ترین Databaseهای NoSQL و Document-Oriented است که داده‌ها را به صورت Documentهای شبیه JSON ذخیره می‌کند.

در MongoDB به جای:

```text
Database
    ↓
Table
    ↓
Row
    ↓
Column
```

با ساختاری مانند زیر کار می‌کنیم:

```text
Database
    ↓
Collection
    ↓
Document
    ↓
Field
```

یک Document می‌تواند مثلاً چنین شکلی داشته باشد:

```javascript
{
  name: "Ali",
  email: "ali@example.com",
  age: 25,
  skills: ["Node.js", "JavaScript"]
}
```

MongoDB برای پروژه‌هایی که داده‌های انعطاف‌پذیر، ساختارهای تو در تو، Documentهای پیچیده و تغییرات سریع Schema دارند، می‌تواند انتخاب مناسبی باشد.

در این فصل ابتدا با مفهوم NoSQL و MongoDB آشنا می‌شویم، سپس نصب و راه‌اندازی، Database، Collection، Document، CRUD، Query، Update، Delete، Index، Aggregation، رابطه بین Documentها، Transaction، امنیت، Backup و در نهایت اتصال MongoDB به Node.js را یاد می‌گیریم.

هدف این فصل این است که بتوانیم MongoDB را در پروژه‌های واقعی Node.js استفاده کنیم.

---

# بخش 1 - آشنایی با MongoDB

## 98.1 - MongoDB چیست؟

MongoDB یک Database از نوع **NoSQL** و **Document-Oriented** است.

در Databaseهای رابطه‌ای معمولاً داده‌ها داخل Table ذخیره می‌شوند؛ اما MongoDB داده‌ها را در Collection و Document ذخیره می‌کند.

ساختار کلی:

```text
MongoDB
│
└── Database
    │
    ├── Collection
    │   ├── Document
    │   ├── Document
    │   └── Document
    │
    └── Collection
        ├── Document
        └── Document
```

---

## 98.2 - NoSQL چیست؟

NoSQL معمولاً به خانواده‌ای از Databaseها گفته می‌شود که برای مدل‌های داده‌ای غیررابطه‌ای طراحی شده‌اند.

انواع رایج Databaseهای NoSQL:

* Document Database
* Key-Value Database
* Wide-Column Database
* Graph Database

MongoDB در دسته **Document Database** قرار می‌گیرد.

---

## 98.3 - تفاوت SQL و MongoDB

در SQL:

```text
Database
    ↓
Table
    ↓
Row
    ↓
Column
```

در MongoDB:

```text
Database
    ↓
Collection
    ↓
Document
    ↓
Field
```

مثلاً در PostgreSQL:

```text
users

id | name | email
1  | Ali  | ali@example.com
```

در MongoDB:

```javascript
{
  _id: ObjectId("..."),
  name: "Ali",
  email: "ali@example.com"
}
```

---

## 98.4 - MongoDB چه زمانی مناسب است؟

MongoDB می‌تواند برای پروژه‌هایی مانند:

* REST API
* سیستم‌های Content Management
* Catalogهای محصولات
* سیستم‌های Event
* اپلیکیشن‌های Real-Time
* سیستم‌های دارای داده‌های JSON
* Prototypeها
* پروژه‌هایی با Schema انعطاف‌پذیر

مناسب باشد.

البته انتخاب Database باید بر اساس نیاز واقعی پروژه انجام شود، نه صرفاً محبوبیت یک ابزار.

را پشتیبانی می‌کند.

این روش برای داده‌هایی که ارتباط نزدیک و وابستگی زیادی به Document اصلی دارند می‌تواند مناسب باشد.

و سپس با Query یا `$lookup` اطلاعات مرتبط را دریافت می‌کنیم.

---

## 98.74 - انتخاب Embed یا Reference

هنگام طراحی MongoDB باید مواردی مانند:

* تعداد داده

* تعداد دفعات دسترسی

را بررسی کنیم.

نباید صرفاً به دلیل NoSQL بودن MongoDB، تمام اطلاعات را داخل یک Document قرار دهیم.

# بخش 18 - Schema Design

## 98.75 - Schema-less به چه معناست؟

MongoDB نسبت به Databaseهای رابطه‌ای انعطاف بیشتری در ساختار Documentها دارد.

اما این به معنی:

```text
بدون ساختار
```

نیست.

در پروژه واقعی باید مشخص کنیم:

* چه Fieldهایی داریم.
* Type آنها چیست.
* کدام Fieldها Required هستند.
* کدام Fieldها Unique هستند.
* چه Indexهایی نیاز داریم.
* رابطه بین داده‌ها چگونه است.

---

## 98.76 - Schema Validation

MongoDB می‌تواند Validation برای Documentها تعریف کند.

مثلاً می‌توان تعیین کرد که:

```text
name
email
age
```

Typeهای مشخصی داشته باشند.

Schema Validation باعث می‌شود انعطاف MongoDB به بی‌نظمی تبدیل نشود.

## 98.78 - مفهوم Session

Transactionهای MongoDB با Session کار می‌کنند.

در Node.js می‌توان از Session برای مدیریت Transaction استفاده کرد.

---

## 98.79 - مثال Transaction در Node.js

```javascript
const session = client.startSession();

try {
  session.startTransaction();

  await usersCollection.updateOne(
    { _id: userId },
    {
      $inc: {
        balance: -100
      }
    },
    { session }
  );

  await accountsCollection.updateOne(
    { _id: targetId },
    {
      $inc: {
        balance: 100
      }
    },
    { session }
  );

  await session.commitTransaction();
} catch (error) {
  await session.abortTransaction();
  throw error;
} finally {
  await session.endSession();
}
```

در پروژه واقعی باید شرایط خطا و محدودیت‌های Transaction را نیز در نظر گرفت.

# اشتباهات رایج

## 1. تصور اینکه MongoDB هیچ Schemaای ندارد

MongoDB انعطاف‌پذیر است، اما طراحی داده همچنان ضروری است.

---

## 2. ذخیره همه چیز در یک Document

Nested Document مفید است، اما Document بیش از حد بزرگ و پیچیده می‌تواند مشکلات Performance و Maintainability ایجاد کند.

---

## 3. استفاده نکردن از Index

Queryهای پرتکرار بدون Index می‌توانند در حجم بالای داده بسیار کند شوند.

---

## 4. ایجاد Index بیش از حد

Index رایگان نیست.

Indexها:

* Storage مصرف می‌کنند.
* Writeها را تحت تأثیر قرار می‌دهند.
* Maintenance دارند.

---

## 5. استفاده اشتباه از `skip`

برای Pagination روی داده‌های بسیار بزرگ، `skip` و `limit` همیشه بهترین انتخاب نیستند.

---

## 6. قرار دادن Password در Database به صورت Plain Text

Password نباید به صورت Plain Text ذخیره شود.

---

## 7. استفاده نادرست از `ObjectId`

ورودی کاربر باید قبل از تبدیل به ObjectId اعتبارسنجی شود.

---

## 8. ساخت MongoClient برای هر Request

این کار می‌تواند باعث ایجاد Connectionهای غیرضروری و مشکلات Performance شود.

---

## 9. استفاده از `$lookup` برای همه روابط

اگر مدل داده به گونه‌ای طراحی شود که دائماً نیاز به Join داشته باشد، ممکن است طراحی Documentها مناسب نباشد.

---

## 10. استفاده بی‌دلیل از Transaction

Transaction مفید است، اما پیچیدگی و هزینه دارد و نباید برای هر عملیات ساده استفاده شود.

---

## 11. اعتماد کامل به Mongoose Validation

Validation لایه Application است و نباید جایگزین کامل طراحی صحیح Database و کنترل ورودی شود.

---

## 12. حذف Collection بدون توجه به Environment

دستورهایی مانند:

```javascript
db.users.deleteMany({})
```

یا:

```javascript
db.users.drop()
```

در Production می‌توانند بسیار خطرناک باشند.

# نکات حرفه‌ای

## 1. Queryهای واقعی را مبنای Index قرار دهید

Index را بر اساس Query Pattern طراحی کنید، نه صرفاً بر اساس نام Fieldها.

---

## 2. از `explain()` استفاده کنید

برای بررسی Performance:

```javascript
db.users.find({
  email: "ali@example.com"
}).explain("executionStats")
```

---

## 3. Documentهای کوچک و کاربردی طراحی کنید

ساختار Document باید بر اساس نحوه خواندن و تغییر داده طراحی شود.

---

## 4. Embed و Reference را آگاهانه انتخاب کنید

برای داده‌های وابسته و کوچک، Embed می‌تواند مناسب باشد.

برای داده‌هایی که مستقل هستند یا تعداد آنها زیاد است، Reference ممکن است انتخاب بهتری باشد.

---

## 5. Unique Index را جدی بگیرید

اگر Email باید Unique باشد، فقط در Application بررسی نکنید.

Database باید نیز این قانون را enforce کند:

```javascript
db.users.createIndex(
  { email: 1 },
  { unique: true }
)
```

---

## 6. Projection استفاده کنید

اگر فقط چند Field نیاز دارید، تمام Document را دریافت نکنید.

---

## 7. Queryهای قابل پیش‌بینی طراحی کنید

قبل از طراحی Schema بپرسید:

```text
چه داده‌ای بیشتر خوانده می‌شود؟
چه داده‌ای بیشتر تغییر می‌کند؟
چه Queryهایی بیشتر اجرا می‌شوند؟
```

---

## 8. از MongoDB برای چیزی که مناسب آن نیست استفاده نکنید

MongoDB ابزار قدرتمندی است، اما همیشه بهترین انتخاب نیست.

اگر سیستم به روابط پیچیده، Integrity رابطه‌ای شدید و Queryهای رابطه‌ای پیچیده نیاز دارد، Databaseهای SQL ممکن است انتخاب مناسب‌تری باشند.

---

## 9. Backup را تست کنید

داشتن Backup کافی نیست.

باید فرآیند Restore نیز تست شده باشد.

---

## 10. Monitoring داشته باشید

در Production باید مواردی مانند:

* Query Performance
* CPU
* Memory
* Disk
* Connections
* Slow Queries

مانیتور شوند.

در این مینی‌پروژه یک Backend ساده فروشگاه با Node.js و MongoDB ایجاد می‌کنیم.

## هدف پروژه

سیستم باید بتواند:

* User ایجاد کند.
* User را پیدا کند.
* Product ایجاد کند.
* Product را ویرایش کند.
* Product را حذف کند.
* Order ایجاد کند.
* Orderهای User را نمایش دهد.
* موجودی Product را مدیریت کند.
* Queryهای مناسب داشته باشد.
* Index داشته باشد.
* Validation داشته باشد.
* از Environment Variable استفاده کند.

# مرحله 3 - اتصال Database

```javascript
import { MongoClient } from "mongodb";

const client = new MongoClient(
  process.env.MONGODB_URI
);

await client.connect();

export const db = client.db(
  process.env.MONGODB_DB_NAME
);
```

# مرحله 9 - جستجوی Product

```javascript
const products = await db
  .collection("products")
  .find({
    category: "electronics",
    price: {
      $lte: 2000
    }
  })
  .sort({
    price: 1
  })
  .limit(20)
  .toArray();
```

# مرحله 10 - ایجاد Order

ساختار Order:

```javascript
{
  userId: ObjectId("..."),
  items: [
    {
      productId: ObjectId("..."),
      quantity: 2,
      price: 1200
    }
  ],
  total: 2400,
  status: "pending",
  createdAt: new Date()
}
```

ذخیره قیمت محصول در Order باعث می‌شود قیمت تاریخی سفارش حفظ شود.

مثلاً اگر قیمت Product در آینده از:

```text
1200
```

به:

```text
1500
```

تغییر کند، Order قبلی همچنان قیمت خرید واقعی خود را خواهد داشت.

# مرحله 13 - کاهش موجودی

```javascript
await db
  .collection("products")
  .updateOne(
    {
      _id: productId,
      stock: {
        $gte: quantity
      }
    },
    {
      $inc: {
        stock: -quantity
      }
    }
  );
```

در پروژه واقعی باید نتیجه Update بررسی شود تا مشخص شود موجودی کافی بوده است یا خیر.

# مرحله 14 - Transaction

ثبت Order و کاهش موجودی چند Product بهتر است در سناریوهای لازم به صورت Transaction طراحی شود تا در صورت شکست بخشی از عملیات، وضعیت ناسازگار ایجاد نشود.

الگوی کلی:

```javascript
const session = client.startSession();

try {
  session.startTransaction();

  // ایجاد Order

  // کاهش موجودی Productها

  await session.commitTransaction();
} catch (error) {
  await session.abortTransaction();
  throw error;
} finally {
  await session.endSession();
}
```
