# فصل 101 - Transaction

## مقدمه

در پروژه‌های واقعی Backend، معمولاً یک عملیات فقط شامل یک Query ساده نیست.

فرض کنید در یک فروشگاه کاربر می‌خواهد محصولی را خریداری کند.

برای ثبت این خرید ممکن است لازم باشد:

```text
1. ایجاد Order
2. ایجاد OrderItem
3. کاهش موجودی Product
4. ثبت مبلغ سفارش
5. ثبت Payment
```

حالا تصور کنید مراحل 1 تا 3 با موفقیت انجام شوند، اما مرحله 4 با خطا مواجه شود.

اگر Database را بدون Transaction مدیریت کنیم، ممکن است اطلاعاتی ناقص ایجاد شود:

```text
Order        ✅
OrderItem    ✅
Stock        ✅
Payment      ❌
```

در این حالت Database در وضعیت ناسازگار قرار می‌گیرد.

Transaction برای حل چنین مشکلاتی استفاده می‌شود.

Transaction مجموعه‌ای از عملیات Database است که باید به عنوان **یک واحد منطقی** اجرا شود؛ یعنی یا تمام عملیات مورد نیاز با موفقیت انجام شوند، یا در صورت شکست، تغییرات انجام‌شده به شکل مناسب برگشت داده شوند.

# بخش 1 - مفهوم Transaction

## 101.1 - Transaction چیست؟

Transaction مجموعه‌ای از عملیات Database است که باید به عنوان یک عملیات منطقی واحد در نظر گرفته شود.

مثلاً انتقال 100 واحد پول از حساب A به حساب B:

```text
Account A
-100

Account B
+100
```

این عملیات شامل حداقل دو تغییر است.

نباید حالتی ایجاد شود که:

```text
Account A
-100

Account B
+0
```

Transaction کمک می‌کند این عملیات به صورت یک واحد انجام شود.

---

## 101.2 - چرا به Transaction نیاز داریم؟

بدون Transaction ممکن است یک عملیات چندمرحله‌ای در میانه راه شکست بخورد.

مثلاً:

```text
Create Order       ✅
Create OrderItem   ✅
Decrease Stock     ✅
Create Payment     ❌
```

در این حالت اطلاعات ناقص داریم.

با Transaction:

```text
BEGIN
 ↓
Create Order
 ↓
Create OrderItem
 ↓
Decrease Stock
 ↓
Create Payment
 ↓
COMMIT
```

و اگر خطایی رخ دهد:

```text
BEGIN
 ↓
Create Order
 ↓
Create OrderItem
 ↓
ERROR
 ↓
ROLLBACK
```

---

# بخش 2 - ACID

## 101.3 - ACID چیست؟

Transactionهای Database معمولاً با چهار ویژگی اصلی ACID شناخته می‌شوند:

```text
A → Atomicity
C → Consistency
I → Isolation
D → Durability
```

این چهار مفهوم پایه اصلی درک Transaction هستند.

---

## 101.4 - Atomicity

Atomicity یعنی عملیات Transaction باید به صورت یک واحد منطقی اجرا شود.

به زبان ساده:

> همه عملیات موفق شوند یا تغییرات Transaction به شکل مناسب اعمال نشوند.

مثلاً:

```text
Transfer Money

A -100
B +100
```

نباید فقط یکی از این دو عملیات انجام شود.

---

## 101.5 - Consistency

Consistency یعنی Transaction نباید Database را به وضعیتی ببرد که Constraintها و قوانین تعریف‌شده نقض شوند.

مثلاً اگر:

```text
balance >= 0
```

یک قانون سیستم باشد، عملیات نباید باعث ایجاد وضعیت نامعتبر شود.

---

## 101.6 - Isolation

Isolation مشخص می‌کند Transactionهای همزمان چگونه روی یکدیگر تأثیر بگذارند.

فرض کنید دو کاربر همزمان روی یک محصول کار می‌کنند:

```text
User A
Buy Product

User B
Buy Product
```

اگر موجودی محصول فقط `1` باشد، باید Database بتواند از ایجاد وضعیت اشتباه جلوگیری کند.

---

## 101.7 - Durability

Durability یعنی پس از Commit شدن Transaction، تغییرات باید به شکل پایدار در Database باقی بمانند؛ حتی اگر Application بعداً Restart شود.

```text
COMMIT
 ↓
Application Crash
 ↓
Database
 ↓
Data remains
```

# بخش 3 - دستورات پایه Transaction

## 101.8 - BEGIN

برای شروع Transaction در SQL معمولاً از:

```sql
BEGIN;
```

استفاده می‌شود.

مثلاً:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;
```

---

## 101.9 - COMMIT

اگر تمام عملیات موفق باشند:

```sql
COMMIT;
```

تغییرات Transaction نهایی می‌شوند.

---

## 101.10 - ROLLBACK

اگر مشکلی رخ دهد:

```sql
ROLLBACK;
```

برای برگشت دادن تغییرات Transaction استفاده می‌شود.

---

## 101.11 - یک Transaction ساده

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

اگر یکی از عملیات شکست بخورد، می‌توان Transaction را Rollback کرد.

# بخش 4 - Transaction در Node.js

## 101.12 - Transaction در Backend

در Node.js معمولاً Transaction در لایه‌ای از Application اجرا می‌شود که چند عملیات Database را مدیریت می‌کند.

ساختار ساده:

```text
Request
   ↓
Service
   ↓
BEGIN
   ↓
Query 1
   ↓
Query 2
   ↓
Query 3
   ↓
COMMIT
```

در صورت خطا:

```text
Query 1
   ↓
Query 2
   ↓
ERROR
   ↓
ROLLBACK
```

---

## 101.13 - Transaction با PostgreSQL و `pg`

یک نمونه ساده:

```javascript
const client = await pool.connect();

try {
  await client.query("BEGIN");

  await client.query(
    "UPDATE accounts SET balance = balance - $1 WHERE id = $2",
    [100, 1]
  );

  await client.query(
    "UPDATE accounts SET balance = balance + $1 WHERE id = $2",
    [100, 2]
  );

  await client.query("COMMIT");
} catch (error) {
  await client.query("ROLLBACK");
  throw error;
} finally {
  client.release();
}
```

ساختار مهم این کد:

```text
connect
   ↓
BEGIN
   ↓
queries
   ↓
COMMIT
   ↓
release
```

و در صورت خطا:

```text
queries
   ↓
error
   ↓
ROLLBACK
   ↓
release
```

# بخش 5 - Transaction و Connection

## 101.14 - چرا Connection مهم است؟

در PostgreSQL، Transaction به یک Connection مشخص وابسته است.

بنابراین نباید چنین کاری انجام دهیم:

```text
BEGIN → Connection A

Query 1 → Connection B

Query 2 → Connection C

COMMIT → Connection D
```

Transaction باید روی همان Connection اجرا شود:

```text
BEGIN
 ↓
Connection A

Query 1
 ↓
Connection A

Query 2
 ↓
Connection A

COMMIT
 ↓
Connection A
```

---

## 101.15 - Transaction و Connection Pool

وقتی از Connection Pool استفاده می‌کنیم، باید برای Transaction یک Connection دریافت کنیم.

مثلاً:

```javascript
const client = await pool.connect();
```

سپس تمام Queryهای Transaction با:

```javascript
client.query(...)
```

اجرا شوند.

در پایان:

```javascript
client.release();
```

---

## 101.16 - چرا `release` مهم است؟

اگر Connection را Release نکنیم، ممکن است Connectionهای Pool مصرف شوند و درخواست‌های بعدی نتوانند Connection دریافت کنند.

بنابراین ساختار مناسب:

```javascript
try {
  // transaction
} finally {
  client.release();
}
```

است.

# بخش 6 - Transaction و Error Handling

## 101.17 - خطا در Transaction

فرض کنید:

```text
Query 1 ✅
Query 2 ✅
Query 3 ❌
```

نباید Transaction را Commit کنیم.

ساختار مناسب:

```javascript
try {
  await client.query("BEGIN");

  await query1();
  await query2();
  await query3();

  await client.query("COMMIT");
} catch (error) {
  await client.query("ROLLBACK");
  throw error;
}
```

---

## 101.18 - چرا Error را دوباره Throw می‌کنیم؟

اگر خطا را فقط Catch کنیم:

```javascript
catch (error) {
  await client.query("ROLLBACK");
}
```

ممکن است لایه بالاتر Application متوجه خطا نشود.

در بسیاری از معماری‌ها بهتر است:

```javascript
throw error;
```

انجام شود تا Error Handler اصلی Application آن را مدیریت کند.

# بخش 7 - Transaction در Prisma

## 101.19 - `$transaction`

Prisma برای اجرای Transaction API مخصوص خود را دارد.

مثلاً:

```javascript
await prisma.$transaction([
  prisma.user.create({
    data: {
      name: "Ali"
    }
  }),

  prisma.profile.create({
    data: {
      bio: "Developer"
    }
  })
]);
```

---

## 101.20 - Interactive Transaction

در بعضی سناریوها لازم است بین Queryها تصمیم‌گیری کنیم.

در این حالت می‌توان از Interactive Transaction استفاده کرد:

```javascript
await prisma.$transaction(async (tx) => {
  const user = await tx.user.create({
    data: {
      name: "Ali"
    }
  });

  if (!user) {
    throw new Error("User creation failed");
  }

  await tx.profile.create({
    data: {
      userId: user.id,
      bio: "Developer"
    }
  });
});
```

در این حالت:

```text
Transaction
   ↓
Query
   ↓
Business Decision
   ↓
Query
   ↓
Commit
```

و در صورت Exception، Transaction به شکل مناسب پایان داده می‌شود.

---

# بخش 8 - Transaction در Drizzle

## 101.21 - Transaction در Drizzle

Drizzle نیز API برای اجرای Transaction دارد.

ساختار کلی:

```javascript
await db.transaction(async (tx) => {
  await tx.insert(users).values({
    name: "Ali"
  });

  await tx.insert(profiles).values({
    bio: "Developer"
  });
});
```

تمام عملیات داخل Callback متعلق به همان Transaction هستند.

---

## 101.22 - Rollback در Drizzle

در صورت ایجاد Exception:

```javascript
await db.transaction(async (tx) => {
  await tx.insert(users).values({
    name: "Ali"
  });

  throw new Error("Something went wrong");
});
```

Transaction به صورت مناسب Rollback می‌شود.

# بخش 10 - Isolation Level

## 101.26 - Isolation Level چیست؟

Isolation Level مشخص می‌کند Transactionها در زمان اجرای همزمان چگونه داده‌ها را مشاهده و مدیریت کنند.

Isolation Levelهای رایج:

```text
Read Uncommitted
Read Committed
Repeatable Read
Serializable
```

---

## 101.27 - Read Uncommitted

در این سطح محدودیت Isolation کم است.

در بعضی Databaseها رفتار آن ممکن است با Read Committed تفاوت زیادی داشته باشد یا حتی عملاً به شکل متفاوتی پیاده‌سازی شود.

---

## 101.28 - Read Committed

در این سطح Transaction معمولاً داده‌های Commit نشده Transactionهای دیگر را نمی‌بیند.

این سطح در PostgreSQL سطح پیش‌فرض است.

---

## 101.29 - Repeatable Read

هدف این سطح این است که داده‌ای که Transaction در طول اجرای خود مشاهده کرده، در خواندن‌های بعدی همان Transaction به شکل سازگار باقی بماند.

---

## 101.30 - Serializable

Serializable بالاترین سطح Isolation استاندارد در این دسته است.

هدف آن این است که نتیجه اجرای Transactionهای همزمان با یک ترتیب سری قابل قبول باشد.

اما افزایش Isolation می‌تواند هزینه Performance و احتمال Conflict را افزایش دهد.

---

# بخش 11 - مشکلات Concurrency

## 101.31 - Dirty Read

Dirty Read زمانی رخ می‌دهد که یک Transaction داده‌ای را ببیند که Transaction دیگر هنوز Commit نکرده است.

```text
Transaction A
UPDATE
   ↓
Not Commit

Transaction B
   ↓
Reads changed data
```

---

## 101.32 - Non-Repeatable Read

فرض کنید Transaction A یک Row را بخواند.

سپس Transaction B همان Row را تغییر دهد و Commit کند.

اگر Transaction A دوباره آن Row را بخواند، ممکن است مقدار متفاوتی مشاهده کند.

---

## 101.33 - Phantom Read

در Phantom Read، یک Query تکراری ممکن است به دلیل تغییرات Transactionهای دیگر، مجموعه متفاوتی از Rowها را برگرداند.

مثلاً:

```text
Query 1
→ 10 rows

Query 2
→ 12 rows
```

---

## 101.34 - Lost Update

دو درخواست همزمان یک مقدار را می‌خوانند و سپس هر دو آن را تغییر می‌دهند.

مثلاً:

```text
Stock = 10

Request A → reads 10
Request B → reads 10

A → writes 9
B → writes 9
```

در حالی که اگر هر دو خرید معتبر باشند، موجودی باید:

```text
8
```

باشد.

---

# بخش 12 - Lock

## 101.35 - Lock چیست؟

Lock برای کنترل دسترسی همزمان به داده‌ها استفاده می‌شود.

هدف:

```text
Transaction A
      ↓
Lock Row
      ↓
Modify
      ↓
Commit
      ↓
Unlock
```

---

## 101.36 - Row-Level Lock

در بعضی سناریوها می‌توان Row مورد نظر را Lock کرد.

در PostgreSQL:

```sql
SELECT *
FROM products
WHERE id = 1
FOR UPDATE;
```

این Query برای گرفتن Lock مناسب روی Row در سناریوهای خاص استفاده می‌شود.

---

## 101.37 - استفاده از `FOR UPDATE`

مثلاً برای کاهش موجودی:

```text
BEGIN
   ↓
SELECT product FOR UPDATE
   ↓
Check stock
   ↓
Decrease stock
   ↓
COMMIT
```

این الگو می‌تواند برای جلوگیری از Race Condition در سناریوهای خاص مفید باشد.

---

# بخش 13 - Transaction و موجودی کالا

## 101.38 - مشکل موجودی

فرض کنید:

```text
stock = 1
```

دو Request همزمان می‌آیند:

```text
Request A
Request B
```

هر دو موجودی را `1` می‌بینند.

اگر بدون کنترل Concurrency عملیات را انجام دهیم، ممکن است هر دو خرید موفق شوند.

---

## 101.39 - راهکار Transaction + Lock

ساختار:

```text
BEGIN
   ↓
SELECT stock FOR UPDATE
   ↓
Check stock
   ↓
Decrease stock
   ↓
COMMIT
```

Request دوم تا زمانی که شرایط Lock اجازه دهد، نمی‌تواند همان Row را به همان شکل همزمان تغییر دهد.

# بخش 14 - Deadlock

## 101.40 - Deadlock چیست؟

Deadlock زمانی رخ می‌دهد که دو یا چند Transaction منتظر منابعی باشند که در اختیار یکدیگر است.

مثلاً:

```text
Transaction A
Lock Row 1
   ↓
Wait for Row 2

Transaction B
Lock Row 2
   ↓
Wait for Row 1
```

در نتیجه:

```text
A → waits for B
B → waits for A
```

---

## 101.41 - جلوگیری از Deadlock

یکی از روش‌های مهم:

> ترتیب دسترسی به منابع را در Transactionهای مختلف تا حد امکان ثابت نگه دارید.

مثلاً همیشه:

```text
Row 1
↓
Row 2
```

را قبل از:

```text
Row 2
↓
Row 1
```

دسترسی دهید.

# بخش 16 - Transaction و Validation

## 101.45 - Validation قبل از Transaction

Validationهایی که نیازی به Database ندارند بهتر است قبل از شروع Transaction انجام شوند.

مثلاً:

```text
Validate Request
   ↓
BEGIN
   ↓
Database Operations
   ↓
COMMIT
```

به جای:

```text
BEGIN
   ↓
Validate Input
   ↓
Database
   ↓
COMMIT
```

---

## 101.46 - Validation وابسته به Database

بعضی Validationها باید داخل Transaction انجام شوند.

مثلاً:

```text
Check Stock
```

اگر مقدار Stock در Database ممکن است همزمان توسط Request دیگری تغییر کند، صرفاً Validation قبل از Transaction کافی نیست.

# بخش 17 - Savepoint

## 101.47 - Savepoint چیست؟

Savepoint یک نقطه مشخص داخل Transaction است که می‌توان به آن Rollback کرد.

مثلاً:

```sql
BEGIN;

INSERT INTO users (...);

SAVEPOINT user_created;

INSERT INTO profile (...);

ROLLBACK TO SAVEPOINT user_created;

COMMIT;
```

Savepoint برای سناریوهای خاص و پیچیده کاربرد دارد.

# بخش 18 - Nested Transaction

## 101.48 - Transaction تو در تو

در Application ممکن است چنین ساختاری داشته باشیم:

```text
Service A
  ↓
Transaction
  ↓
Service B
  ↓
Transaction
```

اما بسیاری از Databaseها Transaction واقعی را به این شکل ساده پشتیبانی نمی‌کنند.

بنابراین باید معماری Transaction را به صورت آگاهانه طراحی کنیم.

---

## 101.49 - Transaction Context

یک راه مناسب این است که Serviceها بتوانند از Transaction موجود استفاده کنند.

مثلاً مفهوم:

```text
transaction client
```

را به Serviceهای پایین‌تر منتقل کنیم.

در نتیجه:

```text
Controller
   ↓
Service
   ↓
Transaction
   ↓
Service A
   ↓
Service B
```

همه عملیات مورد نیاز از همان Transaction استفاده می‌کنند.

---

# بخش 19 - Retry

## 101.50 - چرا Transaction را Retry کنیم؟

بعضی خطاهای Concurrency ممکن است موقتی باشند.

مثلاً:

```text
Transaction
   ↓
Conflict
   ↓
Rollback
```

در برخی سناریوها می‌توان Transaction را دوباره اجرا کرد.

---

## 101.51 - Retry با احتیاط

Retry باید محدود باشد:

```text
Attempt 1
 ↓
Failed

Attempt 2
 ↓
Failed

Attempt 3
 ↓
Failed

Stop
```

همچنین باید مطمئن شویم عملیات قابل Retry است و باعث اجرای ناخواسته Side Effect نمی‌شود.

---

# اشتباهات رایج

## 1. استفاده نکردن از Transaction برای عملیات Atomic

مثلاً انتقال وجه بدون Transaction.

---

## 2. فراموش کردن ROLLBACK

اگر خطایی رخ دهد ولی Rollback انجام نشود، ممکن است Connection در وضعیت نامناسب باقی بماند.

---

## 3. فراموش کردن `release`

در PostgreSQL با Connection Pool:

```javascript
client.release();
```

نباید فراموش شود.

---

## 4. استفاده از چند Connection برای یک Transaction

تمام Queryهای Transaction باید روی همان Connection مناسب اجرا شوند.

---

## 5. باز نگه داشتن Transaction برای مدت طولانی

Transaction طولانی باعث مصرف منابع و افزایش Lock می‌شود.

---

## 6. قرار دادن HTTP Request داخل Transaction

Call کردن API خارجی در حالی که Transaction باز است معمولاً طراحی مناسبی نیست.

---

## 7. استفاده بی‌دلیل از Serializable

Serializable همیشه بهترین انتخاب نیست.

باید بر اساس نیاز Concurrency و Business Logic انتخاب شود.

---

## 8. تصور اینکه Transaction جلوی تمام Race Conditionها را می‌گیرد

Transaction به تنهایی کافی نیست.

در برخی سناریوها به:

* Isolation مناسب
* Lock
* Constraint
* Query صحیح

نیاز داریم.

---

## 9. خواندن مقدار و سپس نوشتن بدون توجه به Concurrency

الگوی:

```text
SELECT
 ↓
Calculate
 ↓
UPDATE
```

ممکن است در شرایط همزمانی مشکل ایجاد کند.

---

## 10. اجرای Business Logic طولانی داخل Transaction

هرچه Transaction طولانی‌تر باشد، احتمال مشکلات Concurrency و Performance بیشتر می‌شود.

# نکات حرفه‌ای

## 1. Transaction را کوتاه نگه دارید

فقط عملیات واقعاً لازم را داخل Transaction قرار دهید.

---

## 2. Connection را همیشه آزاد کنید

ساختار مناسب:

```javascript
try {
  // transaction
} catch (error) {
  // rollback
} finally {
  // release
}
```

---

## 3. Isolation Level را آگاهانه انتخاب کنید

نه همیشه پایین‌ترین سطح مناسب است و نه همیشه بالاترین سطح.

---

## 4. Lock را فقط زمانی استفاده کنید که لازم است

Lock بیش از حد می‌تواند باعث کاهش Concurrency شود.

---

## 5. Constraintهای Database را فراموش نکنید

Transaction جایگزین Constraint نیست.

مثلاً:

```text
UNIQUE
FOREIGN KEY
CHECK
NOT NULL
```

همچنان اهمیت دارند.

---

## 6. Atomic Operation را تا حد امکان در Database طراحی کنید

گاهی به جای:

```text
SELECT stock
↓
stock - 1
↓
UPDATE
```

می‌توان از Query اتمیک استفاده کرد:

```sql
UPDATE products
SET stock = stock - 1
WHERE id = $1
  AND stock > 0;
```

سپس تعداد Rowهای تغییرکرده بررسی شود.

---

## 7. Transaction را با Logging قابل مشاهده کنید

برای مشکلات Production بهتر است بتوانیم بدانیم:

```text
Transaction started
Transaction committed
Transaction rolled back
Transaction failed
```

---

## 8. Deadlock را جدی بگیرید

Deadlock همیشه صرفاً یک Bug ساده نیست و باید ترتیب Lockها و طراحی Transaction بررسی شود.

---

## 9. Transaction را بخشی از Business Logic بدانید

Transaction صرفاً یک ویژگی Database نیست.

باید مشخص کنیم:

> کدام عملیات از دید Business باید یک واحد Atomic باشند؟

---

## 10. Transaction و Eventها را اشتباه نگیرید

Transaction Database تضمین می‌کند عملیات Database در محدوده خودش مدیریت شوند.

اما اگر بعد از Commit یک Event یا پیام به سیستم دیگری ارسال کنیم، تضمین Transaction Database به صورت خودکار به آن سیستم خارجی منتقل نمی‌شود.

در چنین سناریوهایی ممکن است الگوهایی مانند **Transactional Outbox** لازم شوند.

# پاسخ تشریحی

## پاسخ تمرین 1

Transaction مجموعه‌ای از عملیات Database است که باید به عنوان یک واحد منطقی مدیریت شود.

هدف این است که Database در برابر شکست بخشی از عملیات، وضعیت ناسازگار پیدا نکند.

---

## پاسخ تمرین 2

### Atomicity

همه عملیات Transaction باید به عنوان یک واحد منطقی اجرا شوند.

### Consistency

Transaction نباید Database را به وضعیت نامعتبر ببرد.

### Isolation

Transactionهای همزمان باید طبق قواعد Isolation از یکدیگر جدا شوند.

### Durability

پس از Commit، تغییرات باید به شکل پایدار باقی بمانند.

---

## پاسخ تمرین 3

`COMMIT` تغییرات Transaction را نهایی می‌کند.

```text
Transaction
↓
COMMIT
↓
Changes persisted
```

`ROLLBACK` تغییرات Transaction را برمی‌گرداند.

```text
Transaction
↓
ROLLBACK
↓
Changes undone
```

---

## پاسخ تمرین 4

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 500
WHERE id = 1;

UPDATE accounts
SET balance = balance + 500
WHERE id = 2;

COMMIT;
```

در یک سیستم واقعی باید موجودی حساب، وجود Accountها، Constraintها و شرایط Concurrency نیز بررسی شوند.

---

## پاسخ تمرین 5

Transaction در PostgreSQL روی یک Session/Connection مشخص اجرا می‌شود.

اگر:

```text
BEGIN → Connection A
UPDATE → Connection B
COMMIT → Connection C
```

انجام شود، این عملیات یک Transaction واحد تشکیل نمی‌دهند.

بنابراین باید از یک Connection استفاده کنیم.

---

## پاسخ تمرین 6

مشکل اصلی این است که:

```javascript
pool.query(...)
```

ممکن است Queryهای مختلف را روی Connectionهای متفاوت Pool اجرا کند.

باید ابتدا یک Client بگیریم:

```javascript
const client = await pool.connect();
```

و تمام عملیات را با همان Client انجام دهیم.

---

## پاسخ تمرین 7

```javascript
const client = await pool.connect();

try {
  await client.query("BEGIN");

  await client.query(
    "UPDATE accounts SET balance = balance - $1 WHERE id = $2",
    [100, 1]
  );

  await client.query(
    "UPDATE accounts SET balance = balance + $1 WHERE id = $2",
    [100, 2]
  );

  await client.query("COMMIT");
} catch (error) {
  await client.query("ROLLBACK");
  throw error;
} finally {
  client.release();
}
```

---

## پاسخ تمرین 8

به صورت ساده:

```text
Read Committed
↓
محدودیت متوسط و سطح پیش‌فرض PostgreSQL

Repeatable Read
↓
مشاهده سازگارتر داده‌ها در طول Transaction

Serializable
↓
قوی‌ترین Isolation در این مجموعه
```

افزایش Isolation می‌تواند هزینه Concurrency بیشتری داشته باشد.

---

## پاسخ تمرین 9

Dirty Read یعنی Transaction یک مقدار Commit نشده Transaction دیگری را بخواند.

---

## پاسخ تمرین 10

Non-Repeatable Read زمانی است که Transaction یک Row را دو بار بخواند و بین این دو خواندن، Transaction دیگری مقدار آن Row را تغییر داده و Commit کند.

---

## پاسخ تمرین 11

Phantom Read زمانی رخ می‌دهد که Query یک مجموعه Row را بخواند و در اجرای مجدد همان Query، به دلیل تغییرات Transactionهای دیگر، Rowهای جدیدی در نتیجه ظاهر یا از نتیجه حذف شوند.

---

## پاسخ تمرین 12

Lost Update زمانی رخ می‌دهد که دو عملیات همزمان روی یک مقدار کار کنند و تغییر یکی از آنها توسط دیگری overwrite شود.

مثلاً:

```text
Stock = 10

A reads 10
B reads 10

A writes 9
B writes 9
```

در حالی که نتیجه مورد انتظار ممکن است `8` باشد.

---

## پاسخ تمرین 13

```sql
UPDATE products
SET stock = stock - 1
WHERE id = $1
  AND stock > 0;
```

سپس باید بررسی کنیم آیا واقعاً یک Row تغییر کرده است یا خیر.

اگر:

```text
affected rows = 1
```

باشد، عملیات کاهش موجودی موفق بوده است.

اگر:

```text
affected rows = 0
```

باشد، محصول ممکن است موجودی کافی نداشته باشد یا ID نامعتبر باشد.

---

## پاسخ تمرین 14

`FOR UPDATE` برای گرفتن Lock مناسب روی Rowهای انتخاب‌شده در یک Transaction استفاده می‌شود.

مثلاً:

```sql
BEGIN;

SELECT *
FROM products
WHERE id = 1
FOR UPDATE;
```

سپس می‌توان موجودی را بررسی و تغییر داد.

---

## پاسخ تمرین 15

مثلاً:

```text
Transaction A
Lock User 1
↓
Wait for User 2

Transaction B
Lock User 2
↓
Wait for User 1
```

هر دو منتظر دیگری هستند.

این وضعیت Deadlock است.

---

## پاسخ تمرین 16

چون Transaction در این مدت منابع Database را درگیر نگه می‌دارد.

اگر API خارجی کند باشد:

```text
BEGIN
↓
HTTP Request
↓
Wait
↓
Wait
↓
COMMIT
```

Connection و Lockهای احتمالی مدت بیشتری نگه داشته می‌شوند.

---

## پاسخ تمرین 17

```javascript
await prisma.$transaction(async (tx) => {
  const user = await tx.user.create({
    data: {
      name: "Ali"
    }
  });

  await tx.profile.create({
    data: {
      userId: user.id,
      bio: "Developer"
    }
  });
});
```

اگر Exception رخ دهد، Transaction به شکل مناسب مدیریت می‌شود.

---

## پاسخ تمرین 18

```javascript
await db.transaction(async (tx) => {
  await tx.insert(users).values({
    name: "Ali"
  });

  await tx.insert(profiles).values({
    bio: "Developer"
  });
});
```

هر دو عملیات داخل یک Transaction قرار گرفته‌اند.

---

## پاسخ تمرین 19

Savepoint نقطه‌ای داخل Transaction است که می‌توان Rollback را تا آن نقطه انجام داد، بدون اینکه الزاماً کل Transaction را Rollback کنیم.

---

## پاسخ تمرین 20

بسیاری از Databaseها Nested Transaction واقعی را به معنای ایجاد Transaction مستقل داخل Transaction دیگر ارائه نمی‌کنند.

در بسیاری از موارد چیزی که Application به عنوان Nested Transaction می‌بیند، با Savepoint یا اشتراک Transaction Context پیاده‌سازی می‌شود.

---

## پاسخ تمرین 21

سناریوی فروش آخرین محصول:

```text
stock = 1
```

دو کاربر همزمان درخواست خرید می‌دهند.

راهکار می‌تواند شامل:

```text

↓
SELECT product FOR UPDATE
↓
Check stock
↓
Create Order
↓
Decrease Stock
↓
COMMIT
```

باشد.

در اینجا:

* Transaction برای Atomicity
* Lock برای کنترل دسترسی همزمان
* Isolation برای مدیریت نحوه مشاهده تغییرات

اهمیت پیدا می‌کنند.

# چالش نهایی فصل

سیستم فروشگاه را طوری طراحی کنید که دو کاربر نتوانند همزمان آخرین موجودی یک محصول را خریداری کنند.

شرایط:

```text

```

```text

```

```text

```

و نه:

```text
Request A → Success

Stock → -1
```

برای حل این مسئله از ترکیبی از موارد زیر استفاده کنید:

```text
Transaction
+
Atomic Update / Lock
+
Constraint
+
Proper Error Handling
```

# جمع‌بندی فصل

Transaction یکی از مهم‌ترین مفاهیم Database در Backend است.

در یک پروژه واقعی، بسیاری از عملیات به یک Query محدود نمی‌شوند و لازم است چند تغییر به صورت یک واحد منطقی مدیریت شوند.

مفاهیم اصلی این فصل:

```text
BEGIN
 ↓
Database Operations
 ↓
COMMIT
```

و در صورت خطا:

```text
BEGIN
 ↓
Database Operations
 ↓
ERROR
 ↓
ROLLBACK
```

همچنین با ACID آشنا شدیم:

```text
Atomicity
Consistency
Isolation
Durability
```

و بررسی کردیم که Transaction چگونه با موارد زیر ارتباط دارد:

```text
Node.js
PostgreSQL
Prisma
Drizzle
Connection Pool
Isolation Level
Lock
Concurrency
Deadlock
Savepoint
Retry
```

مهم‌ترین نکته این فصل این است:

> Transaction فقط برای اجرای چند Query پشت سر هم نیست؛ بلکه ابزاری برای حفظ صحت داده‌ها در شرایط خطا و اجرای همزمان عملیات است.

در پروژه‌های واقعی، باید همیشه این سؤال را بپرسیم:

> «کدام عملیات از دید Business باید با هم موفق یا با هم شکست بخورند؟»

پاسخ این سؤال مشخص می‌کند کجا به Transaction نیاز داریم.
