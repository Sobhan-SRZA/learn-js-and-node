# فصل 99 - ORM و ODM

## مقدمه

در فصل‌های قبل با SQL، PostgreSQL و MongoDB آشنا شدیم و یاد گرفتیم چگونه مستقیماً با Databaseها کار کنیم.

در پروژه‌های واقعی Node.js معمولاً نمی‌خواهیم تمام Queryها، Mapping داده‌ها، Validationها و ارتباط بین Entityها را از ابتدا و به صورت دستی مدیریت کنیم.

اینجاست که ابزارهایی مانند **ORM** و **ODM** وارد می‌شوند.

ORM مخفف:

```text
Object-Relational Mapping
```

و برای کار با Databaseهای رابطه‌ای مانند PostgreSQL و MySQL استفاده می‌شود.

ODM مخفف:

```text
Object-Document Mapping
```

و معمولاً برای Databaseهای Document-Oriented مانند MongoDB استفاده می‌شود.

در این فصل با سه ابزار مهم در اکوسیستم Node.js آشنا می‌شویم:

* Prisma
* Drizzle
* Mongoose

هدف این فصل فقط یادگیری Syntax این ابزارها نیست؛ بلکه باید متوجه شویم:

* ORM چیست؟
* ODM چیست؟
* چرا از آنها استفاده می‌کنیم؟
* چه مشکلی را حل می‌کنند؟
* چه تفاوتی با Database Driver دارند؟
* Prisma چه زمانی مناسب است؟
* Drizzle چه زمانی مناسب است؟
* Mongoose چه زمانی مناسب است؟
* چگونه آنها را در Node.js استفاده کنیم؟
* Migration چیست؟
* Schema چیست؟
* Relation چیست؟
* Transaction چگونه انجام می‌شود؟
* چگونه Queryهای امن و بهینه بنویسیم؟
* چه زمانی اصلاً نباید از ORM یا ODM استفاده کنیم؟

# بخش 1 - آشنایی با ORM و ODM

## 99.1 - ORM چیست؟

ORM ابزاری است که بین Application و Database رابطه‌ای قرار می‌گیرد و امکان کار کردن با داده‌های Database را با استفاده از Objectها و APIهای برنامه‌نویسی فراهم می‌کند.

به جای اینکه همیشه مستقیماً SQL بنویسیم:

```sql
SELECT *
FROM users
WHERE age >= 18;
```

ممکن است با یک ORM چیزی شبیه این بنویسیم:

```javascript
const users = await db.user.findMany({
  where: {
    age: {
      gte: 18
    }
  }
});
```

ORM بین این کد Application و Database ارتباط برقرار می‌کند.

---

## 99.2 - ODM چیست؟

ODM مشابه ORM است، اما برای Databaseهای Document-Oriented استفاده می‌شود.

مثلاً در MongoDB به جای کار مستقیم با Collection و Document می‌توانیم از Model و Schema استفاده کنیم.

مثلاً با Mongoose:

```javascript
const users = await User.find({
  age: {
    $gte: 18
  }
});
```

---

## 99.3 - ORM و ODM چه مشکلی را حل می‌کنند؟

بدون ORM یا ODM ممکن است مجبور باشیم:

* Connectionها را مدیریت کنیم.
* Queryهای زیادی بنویسیم.
* داده Database را به Objectهای Application تبدیل کنیم.
* Validation انجام دهیم.
* Relationها را مدیریت کنیم.
* Transactionها را مدیریت کنیم.
* Migrationها را مدیریت کنیم.
* Typeها را کنترل کنیم.
* Queryهای تکراری زیادی بنویسیم.

ORM و ODM بخشی از این مسئولیت‌ها را ساده‌تر می‌کنند.

---

## 99.4 - ORM جای Database را نمی‌گیرد

یک اشتباه مهم این است که فکر کنیم:

```text
Prisma = PostgreSQL
Mongoose = MongoDB
```

این تصور اشتباه است.

Database همچنان Database است.

مثلاً:

```text
Node.js
   ↓
Prisma
   ↓
PostgreSQL
```

یا:

```text
Node.js
   ↓
Mongoose
   ↓
MongoDB
```

ORM و ODM یک لایه برای کار کردن راحت‌تر با Database هستند.

# بخش 2 - Driver، ORM و ODM

## 99.5 - Database Driver چیست؟

Driver ابزار رسمی یا سطح پایین‌تری است که Application را به Database متصل می‌کند.

مثلاً برای MongoDB:

```bash
npm install mongodb
```

و:

```javascript
import { MongoClient } from "mongodb";
```

---

## 99.6 - ORM در مقایسه با Driver

در Database رابطه‌ای ممکن است مستقیماً از Driver استفاده کنیم:

```javascript
const result = await client.query(
  "SELECT * FROM users WHERE id = $1",
  [userId]
);
```

یا از ORM استفاده کنیم:

```javascript
const user = await prisma.user.findUnique({
  where: {
    id: userId
  }
});
```

ORM معمولاً Abstraction بیشتری ارائه می‌دهد.

---

## 99.7 - ODM در مقایسه با Driver

با Driver:

```javascript
const user = await db
  .collection("users")
  .findOne({
    email
  });
```

با Mongoose:

```javascript
const user = await User.findOne({
  email
});
```

هر دو می‌توانند به MongoDB متصل شوند، اما سطح Abstraction آنها متفاوت است.

# بخش 3 - مزایا و معایب ORM و ODM

## 99.8 - مزایای ORM

ORM می‌تواند باعث شود:

* Queryها خواناتر شوند.
* Type Safety بهتر شود.
* Code تکراری کاهش پیدا کند.
* Relationها راحت‌تر مدیریت شوند.
* Migrationها ساختاریافته شوند.
* Validation و Mapping ساده‌تر شود.
* توسعه پروژه سریع‌تر شود.

---

## 99.9 - معایب ORM

ORM همیشه بهترین انتخاب نیست.

ممکن است:

* Query پیچیده سخت‌تر شود.
* Debug کردن Query دشوارتر شود.
* Performance در بعضی سناریوها تحت تأثیر قرار گیرد.
* یادگیری خود ORM زمان‌بر باشد.
* Developer از SQL فاصله بگیرد.
* Abstraction باعث شود رفتار واقعی Database فراموش شود.

به همین دلیل یادگیری SQL همچنان مهم است.

---

## 99.10 - مزایای ODM

ODMهایی مانند Mongoose می‌توانند:

* Schema تعریف کنند.
* Validation انجام دهند.
* Model ایجاد کنند.
* Middleware ارائه دهند.
* Relationهای منطقی ایجاد کنند.
* Query API ارائه دهند.
* کار با MongoDB را ساده‌تر کنند.

---

## 99.11 - معایب ODM

استفاده از ODM ممکن است:

* Abstraction اضافی ایجاد کند.
* بعضی قابلیت‌های MongoDB را پیچیده‌تر کند.
* باعث وابستگی بیشتر Application به ODM شود.
* در Queryهای خاص نیاز به استفاده مستقیم از MongoDB Driver ایجاد کند.

# بخش 6 - Relation در Prisma

## 99.26 - One-to-Many

مثلاً یک User چند Post دارد:

```prisma
model User {
  id    Int    @id @default(autoincrement())
  name  String
  posts Post[]
}

model Post {
  id       Int  @id @default(autoincrement())
  title    String
  authorId Int
  author   User @relation(fields: [authorId], references: [id])
}
```

---

# بخش 8 - Transaction در Prisma

## 99.33 - Transaction ساده

```javascript
const result = await prisma.$transaction([
  prisma.user.update({
    where: {
      id: 1
    },
    data: {
      name: "Ali Reza"
    }
  }),

  prisma.post.create({
    data: {
      title: "Hello"
    }
  })
]);
```

---

## 99.34 - Interactive Transaction

برای Logic پیچیده‌تر می‌توان از Callback استفاده کرد:

```javascript
await prisma.$transaction(async (tx) => {
  const user = await tx.user.update({
    where: {
      id: 1
    },
    data: {
      name: "Ali"
    }
  });

  await tx.post.create({
    data: {
      title: "New Post",
      authorId: user.id
    }
  });
});
```

# بخش 9 - Drizzle

## 99.35 - Drizzle چیست؟

Drizzle یک ORM سبک برای TypeScript و JavaScript است که به‌خصوص در پروژه‌های TypeScript و SQL محور مورد توجه قرار گرفته است.

یکی از ایده‌های اصلی Drizzle این است که Abstraction آن به SQL نزدیک باقی بماند.

---

## 99.36 - نصب Drizzle

بسته به Database مورد استفاده، Packageهای مورد نیاز متفاوت هستند.

مثلاً برای PostgreSQL:

```bash
npm install drizzle-orm
```

و Driver مربوط به PostgreSQL نیز باید نصب شود.

---

## 99.37 - تعریف Schema

مثلاً:

```javascript
import {
  pgTable,
  serial,
  text
} from "drizzle-orm/pg-core";

export const users = pgTable("users", {
  id: serial("id").primaryKey(),
  name: text("name").notNull(),
  email: text("email").notNull()
});
```

---

## 99.38 - اتصال Database

نمونه کلی:

```javascript
import { drizzle } from "drizzle-orm/node-postgres";

const db = drizzle(client);
```

نوع Driver باید متناسب با Database و محیط پروژه انتخاب شود.

---

* می‌خواهیم مقدار زیادی از کارهای Database را به ORM بسپاریم.

# بخش 18 - چه زمانی از Drizzle استفاده کنیم؟

Drizzle می‌تواند مناسب باشد وقتی:

* ORM سبک‌تر می‌خواهیم.

# بخش 19 - چه زمانی از Mongoose استفاده کنیم؟

Mongoose زمانی مناسب است که:

* Schema و Model می‌خواهیم.

* Population نیاز داریم.

# بخش 20 - آیا همیشه باید ORM یا ODM استفاده کنیم؟

خیر.

گاهی استفاده مستقیم از Driver انتخاب بهتری است.

مثلاً:

```text
Node.js
   ↓
Database Driver
   ↓
Database
```

به جای:

```text
Node.js
   ↓
ORM / ODM
   ↓
Database Driver
   ↓
Database
```

در پروژه‌های کوچک، Queryهای خاص، سیستم‌های Performance-sensitive یا زمانی که کنترل کامل روی Query نیاز داریم، استفاده مستقیم از Driver می‌تواند منطقی باشد.

# اشتباهات رایج

## 1. یادگیری ORM بدون یادگیری Database

اگر SQL، Relation، Index و Transaction را ندانیم، استفاده از ORM می‌تواند باعث ایجاد Codeی شود که ظاهراً ساده است اما از نظر Database ضعیف است.

---

## 2. تصور اینکه ORM Queryهای بد را خوب می‌کند

مثلاً اگر Query اشتباه باشد:

```javascript
await prisma.user.findMany({
  include: {
    posts: true
  }
});
```

ممکن است حجم زیادی داده دریافت کنیم.

ORM جای طراحی Query صحیح را نمی‌گیرد.

---

## 3. استفاده از ORM برای همه چیز

هر Query را نباید صرفاً به دلیل وجود ORM با ORM پیاده‌سازی کرد.

گاهی Raw SQL مناسب‌تر است.

---

## 4. نادیده گرفتن Query واقعی Database

Developer باید بداند ORM در نهایت چه Query یا عملیاتی را روی Database اجرا می‌کند.

---

## 5. ایجاد Relationهای بیش از حد

Relation زیاد همیشه نشانه طراحی خوب نیست.

مدل داده باید بر اساس نیاز واقعی Application طراحی شود.

---

## 6. استفاده اشتباه از `populate`

در Mongoose استفاده بیش از حد از:

```javascript
.populate()
```

می‌تواند باعث Queryهای سنگین و دریافت داده‌های غیرضروری شود.

---

## 7. استفاده نکردن از Index

ORM یا ODM به تنهایی Performance را تضمین نمی‌کند.

Index باید بر اساس Queryهای واقعی طراحی شود.

---

## 8. قرار دادن Business Logic در Model

Model نباید تبدیل به محل تمام Logicهای پروژه شود.

Business Logic بهتر است ساختار مشخص و قابل تست داشته باشد.

---

## 9. استفاده نادرست از Middleware

قرار دادن Logic پیچیده داخل Mongoose Middleware می‌تواند Debug و Test کردن Application را دشوار کند.

---

## 10. حذف مستقیم داده بدون توجه به Relation

در Databaseهای رابطه‌ای باید Foreign Key و Cascadeها را در نظر گرفت.

در MongoDB نیز Referenceهای مرتبط باید مدیریت شوند.

---

## 11. اشتباه گرفتن Validation ORM با Validation API

Validation در ORM یا ODM نباید تنها لایه Validation ورودی HTTP باشد.

ورودی API باید قبل از رسیدن به Database نیز بررسی شود.

---

## 12. نادیده گرفتن Migration

تغییر Schema بدون مدیریت Migration می‌تواند باعث ناسازگاری بین محیط‌های مختلف شود.

---

# نکات حرفه‌ای

## 1. قبل از ORM، Database را یاد بگیرید

ترتیب مناسب:

```text
Database
   ↓
Query
   ↓
Index
   ↓
Transaction
   ↓
ORM / ODM
```

---

## 2. SQL را حتی با Prisma یا Drizzle یاد بگیرید

اگر بدانیم SQL چگونه کار می‌کند، استفاده از ORM بسیار حرفه‌ای‌تر خواهد بود.

---

## 3. Queryهای تولیدشده را بررسی کنید

در صورت مشکل Performance باید بفهمیم ORM چه Queryای اجرا می‌کند.

---

## 4. Index را بر اساس Query طراحی کنید

مثلاً اگر مرتباً داریم:

```text
find users by email
```

باید روی Email Index مناسب داشته باشیم.

---

## 5. Transaction را فقط در جای لازم استفاده کنید

Transaction باید زمانی استفاده شود که چند عملیات باید به صورت یک واحد اتمیک اجرا شوند.

---

## 6. N+1 Query را بشناسید

یکی از مشکلات مهم ORMها و ODMها N+1 Query است.

مثلاً:

```text
1 Query برای Users
+
100 Query برای Posts
=
101 Query
```

باید Queryها و Relationها را طوری طراحی کنیم که از چنین مشکلاتی جلوگیری شود.

---

## 7. فقط داده مورد نیاز را دریافت کنید

اگر فقط:

```text
id
name
```

لازم داریم، دریافت 30 Field دیگر منطقی نیست.

---

## 8. ORM را جایگزین معماری نکنید

Prisma، Drizzle و Mongoose ابزار هستند.

آنها جایگزین:

* Service Layer
* Validation
* Error Handling
* Authorization
* Business Logic
* Testing

نیستند.

---

## 9. Repository Pattern را بشناسید

در پروژه‌های بزرگ می‌توان Database Access را پشت یک Repository قرار داد:

```text
Controller
    ↓
Service
    ↓
Repository
    ↓
ORM / ODM
    ↓
Database
```

این ساختار باعث می‌شود Business Logic کمتر به ابزار Database وابسته باشد.

---

## 10. انتخاب ابزار را بر اساس پروژه انجام دهید

نباید بگوییم:

```text
Prisma همیشه بهتر است.
```

یا:

```text
Drizzle همیشه بهتر است.
```

یا:

```text
Mongoose همیشه بهترین ODM است.
```

انتخاب باید بر اساس:

* نوع Database
* اندازه پروژه
* تیم
* نیازهای TypeScript
* Query Complexity
* Performance
* Migration
* Maintainability

انجام شود.

```text
    └── Update Product Stock
          │
          ├── موفق → COMMIT
          │
          └── خطا → ROLLBACK
```

# جمع‌بندی فصل

در این فصل با مفهوم ORM و ODM آشنا شدیم.

یاد گرفتیم که:

```text
ORM
↓
Object
↓
Relational Database
```

و:

```text
ODM
↓
Object
↓
Document Database
```

همچنین با سه ابزار مهم آشنا شدیم:

```text
Prisma
Drizzle
Mongoose
```

**Prisma** بیشتر برای کار با Databaseهای رابطه‌ای و ایجاد یک API سطح بالا و Type-Safe کاربرد دارد.

**Drizzle** رویکردی سبک‌تر و نزدیک‌تر به SQL ارائه می‌دهد و برای کسانی که می‌خواهند همچنان کنترل خوبی روی SQL و ساختار Database داشته باشند، گزینه مناسبی است.

**Mongoose** یک ODM برای MongoDB است که امکاناتی مانند Schema، Model، Validation، Middleware و Population را فراهم می‌کند.

اما نکته مهم این فصل این است:

```text
ORM / ODM
≠
Database
```

و همچنین:

```text
ORM / ODM
≠
جایگزین یادگیری SQL یا MongoDB
```

یک Node.js Developer حرفه‌ای باید بتواند هم با Abstractionهای ORM/ODM کار کند و هم در صورت نیاز Database را در سطح Query، Index، Relation و Transaction درک کند.

در نهایت انتخاب ابزار باید بر اساس پروژه انجام شود:

```text
PostgreSQL / MySQL / SQL
        ↓
   Prisma / Drizzle

MongoDB
   ↓
 Mongoose
```

و در شرایط خاص:

```text
Node.js
   ↓
Database Driver
```

نیز می‌تواند انتخاب مناسبی باشد.
