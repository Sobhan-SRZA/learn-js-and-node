# فصل 100 - Migration

## مقدمه

در پروژه‌های واقعی Backend، ساختار Database در طول زمان ثابت نمی‌ماند.

ممکن است ابتدا جدول `users` فقط شامل این ستون‌ها باشد:

```text
id
name
```

اما بعداً نیاز داشته باشیم:

```text
email
password
createdAt
updatedAt
```

یا یک Table جدید به پروژه اضافه کنیم:

```text
users
posts
comments
```

اگر این تغییرات را به صورت دستی روی Database انجام دهیم، خیلی زود با مشکلاتی مواجه می‌شویم:

* مشخص نبودن تغییرات انجام‌شده
* تفاوت Database محیط توسعه و Production
* سخت شدن همکاری اعضای تیم
* دشوار شدن بازگردانی تغییرات
* از دست رفتن تاریخچه تغییرات Database
* ایجاد ناسازگاری بین نسخه‌های مختلف Application

**Migration** راهکاری برای مدیریت تغییرات ساختار Database به صورت قابل ردیابی، تکرارپذیر و کنترل‌شده است.

در این فصل یاد می‌گیریم:

* Migration چیست؟
* چرا به Migration نیاز داریم؟
* Migration چگونه کار می‌کند؟
* Schema چیست؟
* Migration و Schema چه تفاوتی دارند؟
* Migration اولیه چیست؟
* Migration جدید چگونه ایجاد می‌شود؟
* Up Migration چیست؟
* Down Migration چیست؟
* Rollback چیست؟
* Migration در محیط Development چگونه انجام می‌شود؟
* Migration در Production چگونه انجام می‌شود؟
* Migration با Prisma
* Migration با Drizzle
* Migration در پروژه‌های SQL
* تغییر Column
* حذف Column
* تغییر Table
* ایجاد Index
* ایجاد Foreign Key
* تغییر ساختار Database بدون از دست رفتن داده
* مشکل Migrationهای ناسازگار
* Zero-Downtime Migration
* Migrationهای خطرناک
* اشتباهات رایج
* نکات حرفه‌ای

# بخش 1 - مفهوم Migration

## 100.1 - Migration چیست؟

Migration مجموعه‌ای از تغییرات ثبت‌شده برای تغییر ساختار Database است.

فرض کنید Database اولیه:

```text
users
├── id
└── name
```

داریم.

بعداً می‌خواهیم Email اضافه کنیم:

```text
users
├── id
├── name
└── email
```

این تغییر می‌تواند به صورت یک Migration ثبت شود.

مثلاً:

```text
001_create_users
002_add_email_to_users
```

در نتیجه تاریخچه تغییرات Database مشخص خواهد بود.

---

## 100.2 - چرا Migration لازم است؟

فرض کنید سه Developer روی یک پروژه کار می‌کنند:

```text
Developer A
Developer B
Developer C
```

Developer A یک Column اضافه می‌کند.

Developer B یک Table جدید ایجاد می‌کند.

Developer C یک Index اضافه می‌کند.

اگر همه این تغییرات فقط به صورت دستی روی Database انجام شوند، مشخص نیست:

* چه کسی چه تغییری انجام داده؟
* چه زمانی انجام شده؟
* روی کدام محیط انجام شده؟
* چگونه می‌توان همان تغییر را روی Database دیگری اعمال کرد؟
* اگر مشکلی ایجاد شد چگونه تغییر را برگردانیم؟

Migration این تغییرات را به صورت فایل‌ها و تاریخچه مشخص مدیریت می‌کند.

---

# بخش 2 - Database Schema

## 100.3 - Schema چیست؟

Schema ساختار Database را توصیف می‌کند.

برای مثال:

```text
users
├── id
├── name
├── email
└── created_at
```

Schema مشخص می‌کند:

* چه Tableهایی داریم؟
* چه Columnهایی داریم؟
* Data Type آنها چیست؟
* Primary Key کدام است؟
* Foreign Keyها کدام‌اند؟
* چه Constraintهایی داریم؟
* چه Indexهایی داریم؟

---

## 100.4 - تفاوت Schema و Migration

Schema بیان می‌کند:

> Database الان باید چه شکلی باشد؟

Migration بیان می‌کند:

> چگونه Database را از وضعیت قبلی به وضعیت جدید برسانیم؟

مثلاً:

```text
Schema v1

users
├── id
└── name
```

و:

```text
Schema v2

users
├── id
├── name
└── email
```

Migration تغییر بین این دو وضعیت را مشخص می‌کند:

```text
Schema v1
   ↓
Migration
   ↓
Schema v2
```

# بخش 3 - Migration History

## 100.5 - تاریخچه Migration

Migrationها معمولاً به ترتیب زمانی ثبت می‌شوند.

مثلاً:

```text
migrations/
├── 001_create_users
├── 002_create_posts
├── 003_add_email_to_users
└── 004_add_index_to_users
```

این ساختار نشان می‌دهد Database چگونه به وضعیت فعلی رسیده است.

---

## 100.6 - ترتیب اجرای Migrationها

Migrationها معمولاً باید به ترتیب اجرا شوند:

```text
001
 ↓
002
 ↓
003
 ↓
004
```

اگر Migration شماره 003 قبل از Migration شماره 002 اجرا شود، ممکن است Database در وضعیت نامعتبر قرار بگیرد.

---

## 100.7 - Migration State

ابزار Migration باید بداند کدام Migrationها قبلاً اجرا شده‌اند.

معمولاً یک جدول داخلی در Database یا مکانیزم مشابه برای ثبت وضعیت Migrationها وجود دارد.

مثلاً:

```text
Migration
001 → Applied
002 → Applied
003 → Applied
004 → Pending
```

# بخش 4 - Up و Down Migration

## 100.8 - Up Migration

Up Migration تغییر مورد نظر را اعمال می‌کند.

مثلاً:

```sql
ALTER TABLE users
ADD COLUMN email VARCHAR(255);
```

یعنی:

```text
users
↓
اضافه شدن email
```

---

## 100.9 - Down Migration

Down Migration تغییر را برمی‌گرداند.

مثلاً:

```sql
ALTER TABLE users
DROP COLUMN email;
```

بنابراین:

```text
UP
↓
Add email

DOWN
↓
Remove email
```

---

## 100.10 - Rollback چیست؟

Rollback یعنی بازگرداندن Database به وضعیت قبلی.

مثلاً:

```text
Migration 001
Migration 002
Migration 003
```

اگر Migration سوم مشکل داشته باشد:

```text
003
↓
Rollback
↓
Database → وضعیت Migration 002
```

---

## 100.11 - آیا Rollback همیشه امن است؟

خیر.

مثلاً Migration زیر را در نظر بگیرید:

```sql
ALTER TABLE users
DROP COLUMN phone;
```

اگر اطلاعات مهمی داخل `phone` وجود داشته باشد، اجرای Rollback به تنهایی لزوماً داده‌های حذف‌شده را برنمی‌گرداند.

بنابراین:

```text
Rollback Migration
≠
Restore Data
```

این تفاوت بسیار مهم است.

# بخش 8 - Migration در Prisma

## 100.23 - Prisma Migration

Prisma برای مدیریت Migration از Prisma Migrate استفاده می‌کند.

فرض کنید Schema زیر را داریم:

```prisma
model User {
  id   Int    @id @default(autoincrement())
  name String
}
```

بعد Email اضافه می‌کنیم:

```prisma
model User {
  id    Int    @id @default(autoincrement())
  name  String
  email String
}
```

سپس Migration ایجاد می‌کنیم:

```bash
npx prisma migrate dev --name add-user-email
```

---

## 100.24 - Migration Directory در Prisma

Migrationها معمولاً در ساختاری شبیه این قرار می‌گیرند:

```text
prisma/
└── migrations/
    ├── 202608090001_initial/
    │   └── migration.sql
    │
    └── 202608090002_add_user_email/
        └── migration.sql
```

---

## 100.25 - مشاهده Migration

می‌توان فایل Migration را بررسی کرد.

مثلاً:

```sql
ALTER TABLE "User"
ADD COLUMN "email" TEXT;
```

این نکته مهم است:

**ORM نباید باعث شود از SQL و تغییر واقعی Database بی‌خبر شویم.**

---

## 100.26 - Prisma Migration در Development

در محیط توسعه:

```bash
npx prisma migrate dev
```

این دستور برای Development طراحی شده و فرآیند توسعه Schema را مدیریت می‌کند.

---

## 100.27 - Prisma Migration در Production

در محیط Production معمولاً از:

استفاده می‌شود.

هدف این است که Migrationهای موجود و Commit شده روی Database Production اعمال شوند.

## 100.28 - Prisma Migration و Generate

بعد از تغییر Schema ممکن است نیاز به Generate کردن Prisma Client داشته باشیم:

# بخش 9 - Migration در Drizzle

## 100.29 - Drizzle Migration

Drizzle نیز ابزارهایی برای مدیریت Migration دارد.

Schema را تعریف می‌کنیم:

```javascript
export const users = pgTable("users", {
  id: serial("id").primaryKey(),
  name: text("name").notNull()
});
```

سپس Schema را تغییر می‌دهیم:

```javascript
export const users = pgTable("users", {
  id: serial("id").primaryKey(),
  name: text("name").notNull(),
  email: text("email").notNull()
});
```

بعد Migration ایجاد می‌کنیم.

---

## 100.30 - Generate Migration

در پروژه‌ای که Drizzle Kit تنظیم شده است:

```bash
npx drizzle-kit generate
```

---

## 100.31 - اجرای Migration

پس از ایجاد Migration می‌توان آن را روی Database اعمال کرد.

دستور دقیق به Configuration و نسخه ابزار بستگی دارد، اما مفهوم کلی:

```text
Schema
 ↓
Generate Migration
 ↓
Migration Files
 ↓
Apply Migration
 ↓
Database
```

است.

اگر هر دو Migration ساختار ناسازگاری ایجاد کنند، ممکن است نیاز به حل Conflict یا بازطراحی Migrationها باشد.

# بخش 12 - Backward Compatible Migration

## 100.38 - مشکل تغییر مستقیم

فرض کنید Application فعلی از:

```text
name
```

استفاده می‌کند.

ما می‌خواهیم آن را به:

```text
fullName
```

تغییر دهیم.

اگر فوراً `name` را حذف کنیم:

```text
Application
   ↓
name
   ↓
ERROR
```

ممکن است Application قدیمی از کار بیفتد.

---

## 100.39 - روش Expand and Contract

یکی از روش‌های حرفه‌ای:

```text
مرحله 1
Add new field

مرحله 2
Application starts using both

مرحله 3
Migrate old data

مرحله 4
Application uses new field

مرحله 5
Remove old field
```

مثلاً:

```text
name
fullName
```

ابتدا هر دو وجود دارند.

بعد داده‌ها منتقل می‌شوند.

در نهایت:

```text
name
```

حذف می‌شود.

# بخش 13 - Zero-Downtime Migration

## 100.40 - Zero-Downtime Migration چیست؟

هدف Zero-Downtime Migration این است که تغییر Database بدون متوقف کردن سرویس انجام شود.

مثلاً:

```text
Users
   ↓
Application
   ↓
Database
```

در زمان Migration همچنان Application فعال باقی می‌ماند.

---

## 100.41 - چرا مهم است؟

در سیستم‌های Production بزرگ ممکن است:

```text
24/7
```

سرویس فعال باشد.

بنابراین نمی‌توانیم هر بار Database را برای چند دقیقه متوقف کنیم.

# بخش 18 - Migration و Seed

## 100.51 - Seed چیست؟

مثلاً:

```text

```

---

## 100.52 - تفاوت Migration و Seed

Migration:

```text
ساختار Database
```

را تغییر می‌دهد.

Seed:

```text
داده اولیه
```

را وارد می‌کند.

بنابراین:

```text
Migration ≠ Seed
```


اما روی Production نباید بدون درک کامل از پیامدها انجام شود.

# اشتباهات رایج

## 1. تغییر مستقیم Production

یکی از بدترین عادت‌ها این است که Developer مستقیماً روی Production Query بزند:

```sql
ALTER TABLE ...
```

بدون اینکه تغییر را در Migration ثبت کند.

---

## 2. Commit نکردن Migration

تغییر Database بدون Commit کردن Migration باعث می‌شود سایر Developerها نتوانند ساختار جدید را دریافت کنند.

---

## 3. حذف داده داخل Migration بدون Backup

Migrationهای Data Destructive باید با احتیاط بسیار زیاد طراحی شوند.

---

## 4. یکی دانستن Migration و Backup

Migration برای تغییر ساختار و داده طراحی شده است.

Backup برای Recovery است.

این دو جایگزین یکدیگر نیستند.

---

## 5. Rollback بدون توجه به Data Loss

Rollback لزوماً داده‌های حذف‌شده را برنمی‌گرداند.

---

## 6. اجرای Migration آزمایش‌نشده در Production

Migration باید قبل از Production روی محیط مشابه تست شود.

---

## 7. تغییر چندباره یک Migration قبلی

بعد از اینکه Migration روی محیط‌های مختلف اجرا و Commit شد، معمولاً نباید محتوای آن را به صورت دلخواه تغییر دهیم.

به جای آن Migration جدید ایجاد می‌کنیم.

---

## 8. استفاده از Migration برای Business Logic پیچیده

Migration محل مناسبی برای اجرای Business Logic پیچیده Application نیست.

---

## 9. اضافه کردن NOT NULL بدون بررسی داده‌های قبلی

اگر داده‌های موجود مقدار لازم را نداشته باشند، Migration شکست می‌خورد.

---

## 10. ایجاد Index بدون بررسی Performance

هر Index هزینه Storage و Write دارد.

نباید صرفاً برای هر Column یک Index ایجاد کنیم.

---

# نکات حرفه‌ای

## 1. Migration را Immutable در نظر بگیرید

Migrationی که در محیط‌های مختلف اجرا شده است را تا حد امکان تغییر ندهید.

برای تغییر جدید:

```text
New Requirement
      ↓
New Migration
```

ایجاد کنید.

---

## 2. Migration را کوچک نگه دارید

به جای یک Migration بسیار بزرگ:

```text
001_everything
```

تغییرات منطقی را جدا کنید:

```text
001_create_users
002_create_products
003_add_user_email
004_add_product_index
```

---

## 3. Migration را قبل از Production تست کنید

حداقل روی یک Database مشابه Production اجرا شود.

---

## 4. حجم داده را در نظر بگیرید

Queryای که روی:

```text
1,000 rows
```

در چند میلی‌ثانیه اجرا می‌شود، ممکن است روی:

```text
100,000,000 rows
```

مشکل جدی ایجاد کند.

---

## 5. Data Migration را از Schema Migration تفکیک کنید

در تغییرات بزرگ بهتر است:

```text
Schema Change
      ↓
Data Backfill
      ↓
Application Update
      ↓
Cleanup
```

را جداگانه مدیریت کنیم.

---

## 6. Migration باید قابل مشاهده باشد

قبل از اجرای Production باید بدانیم دقیقاً چه SQL یا عملیاتی قرار است اجرا شود.

---

## 7. Backup و Recovery را جدی بگیرید

داشتن Backup بدون تست Restore کافی نیست.

باید بدانیم:

```text
Backup
   ↓
Restore
   ↓
Working Database
```

واقعاً امکان‌پذیر است.

---

## 8. Migration را در CI/CD مدیریت کنید

Migration نباید وابسته به سیستم شخصی Developer باشد.

---

## 9. Migration را Idempotent تلقی نکنید

بسیاری از Migrationها قرار نیست چند بار اجرا شوند.

ابزار Migration باید وضعیت اجرای آنها را مدیریت کند.

---

## 10. قبل از حذف، Deprecate کنید

برای تغییرات حساس:

```text
Old Field
   ↓
Deprecated
   ↓
New Field
   ↓
Data Migration
   ↓
Remove Old Field
```

رویکرد امن‌تری است.

# پاسخ تشریحی

## پاسخ تمرین 1

Migration روشی برای ثبت و اجرای تغییرات Database است.

به کمک Migration می‌توان Database را به صورت مرحله‌ای از یک Schema به Schema جدید منتقل کرد.

---

## پاسخ تمرین 2

Schema وضعیت و ساختار Database را توصیف می‌کند.

Migration تغییرات لازم برای رسیدن از یک وضعیت Schema به وضعیت دیگر را ثبت می‌کند.

به صورت ساده:

```text
Schema
= وضعیت

Migration
= تغییر وضعیت
```

---

## پاسخ تمرین 3

Migration برای تغییر ساختار یا داده‌های Database استفاده می‌شود.

Seed معمولاً برای وارد کردن داده‌های اولیه، نمونه یا داده‌های مورد نیاز محیط خاص استفاده می‌شود.

---

## پاسخ تمرین 4

```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  email VARCHAR(255) NOT NULL
);
```

---

## پاسخ تمرین 5

```sql
ALTER TABLE users
ADD COLUMN phone VARCHAR(50);
```

---

## پاسخ تمرین 6

```sql
ALTER TABLE users
DROP COLUMN phone;
```

در Production قبل از چنین عملیاتی باید Data Loss را بررسی کنیم.

---

## پاسخ تمرین 7

```sql
CREATE INDEX idx_users_email
ON users(email);
```

اگر Email برای جستجو زیاد استفاده شود، چنین Indexای می‌تواند مفید باشد.

---

## پاسخ تمرین 8

فرض کنید 100 هزار User داریم و Column جدید:

```text
email NOT NULL
```

باشد.

اما هیچ‌کدام از رکوردهای قدیمی Email ندارند.

در این صورت Database نمی‌تواند Constraint `NOT NULL` را برای داده‌های موجود برقرار کند.

راهکار:

```text
Add nullable column
        ↓
Fill old data
        ↓
Validate
        ↓
Set NOT NULL
```

---

## پاسخ تمرین 9

به جای حذف مستقیم `name`:

```text
مرحله 1

مرحله 2
Application supports both

مرحله 3
Copy name → fullName

مرحله 4
Application uses fullName

مرحله 5
Remove name
```

این روش ریسک ناسازگاری بین نسخه‌های مختلف Application را کاهش می‌دهد.

## پاسخ تمرین 11

Rollback معمولاً Schema یا عملیات Migration را به وضعیت قبلی برمی‌گرداند.

اما اگر اطلاعاتی حذف شده باشد، Rollback لزوماً آن اطلاعات را بازسازی نمی‌کند.

مثلاً:

```sql
DROP COLUMN email;
```

داده‌های Email حذف می‌شوند.

اجرای Migration معکوس ممکن است فقط Column را دوباره ایجاد کند:

```sql
ADD COLUMN email VARCHAR(255);
```

اما مقادیر قبلی را برنمی‌گرداند.

# جمع‌بندی فصل

Migration یکی از مهم‌ترین بخش‌های مدیریت Database در پروژه‌های واقعی Backend است.

در این فصل یاد گرفتیم:

```text
Schema
↓
وضعیت Database
```

و:

```text
Migration
↓
تغییر وضعیت Database
```

همچنین با مفاهیم:

* Initial Migration
* Migration History
* Up Migration
* Down Migration
* Rollback
* Schema Migration
* Data Migration
* Migration در Prisma
* Migration در Drizzle
* Migration در Production
* Migration در Git
* Backward Compatibility
* Expand and Contract
* Zero-Downtime Migration
* Migrationهای خطرناک
* Index Migration
* Foreign Key Migration
* Constraint Migration

آشنا شدیم.

مهم‌ترین نکته این است که Migration فقط چند دستور SQL نیست.

در یک پروژه واقعی، Migration بخشی از **Lifecycle نرم‌افزار** است:

```text
Code
  ↓
Schema Change
  ↓
Migration
  ↓
Test
  ↓
Deploy
  ↓
Production
  ↓
Monitor
```

و هرچه پروژه بزرگ‌تر و داده‌ها مهم‌تر شوند، طراحی Migration اهمیت بیشتری پیدا می‌کند.

یک Backend Developer حرفه‌ای باید بتواند Database را نه‌تنها ایجاد کند، بلکه **در طول عمر پروژه به صورت امن و قابل کنترل تکامل دهد.**
